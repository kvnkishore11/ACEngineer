Cloudflare's S-tier factory

yt-48 · "I Ranked Cloudflare's Software Factory and Wow… S TIER TOKENOMICS" · 41:54

Cloudflare's CI-native AI code-review factory — 130,000 reviews a month across 5,000 repos at $1 per merge request — earns S-tier tokenomics by combining seven specialized reviewer agents, a coordinator, a tiered model stack, and agents-plus-code resilience.

Reviews complete in ~3 minutes; 8,000 critical issues found in a month. "Are your eyes open?" — Dan's answer to anyone claiming agents don't raise productivity.

"Don't send in the dream team to review a typo fix." Team size and model tier scale with diff size and risk — never Opus-for-everything.
  • Tokenomics is a skill: use tokens → generate value → arbitrage/capture it. Cloudflare gets S-tier because the whole system is designed around cost from day one.
  • They attack the review constraint (of the two constraints, planning and reviewing) — median first-review wait used to be hours.
  • The journey: out-of-the-box AI tools "didn't offer enough flexibility" → naive diff-in-prompt vibe coding produced noise → a CI-native orchestration system around opencode (open source, contributable, SDK with programmatic sessions). "Any agentic coding tool that does not have programmatic access isn't a legitimate agentic coding tool."
  • 7 specialized reviewers (security, performance, code quality, docs, release mgmt, compliance) + a coordinator that dedupes, filters, and posts one structured comment. "Many specialized agents always beat one generalist. This is just a fact."
  • Prompt engineering gem: tell agents what to ignore, not just what to find — no syntax nitpicks; structured XML findings with severity classifications.
  • JSONL over JSON/YAML: always valid mid-stream, immediately readable, streamable — step-finish events drive cost tracking, error detection, and length-cutoff retries.
  • Three-tier model stack: state-of-the-art / standard workhorse / lightweight (Kimi K2.5). "You cannot use Opus for everything... you'll destroy the tokenomics of your business." Top-tier models are only ~46% of token usage; huge cache-read ratios.
  • Risk tiers: <10 lines → coordinator + one generalist; <100 lines → light tier; >100 lines or 50 files → the full 7-specialist pipeline. Spend compute by risk level.
  • Context engineering: diffs saved to patch files; each sub-reviewer reads only its domain's patch plus one shared context file — duplicating full context would multiply cost 7x.
  • Bias toward approval, plus a human "break glass" escape hatch — agent-forward, never hard-blocking engineers.
  • Resilience S-tier: per-task timeouts, retry budgets, model fallback chains, error classification (model's fault vs not), provider hot-swap via CI job, and incremental re-reviews that carry prior review context.
  • Developers can reply "wontfix / acknowledge / disagree" — the coordinator argues back or resolves. Model diversity matters because different models disagree.
  • Weak spots in the ranking: one mega custom tool (spawn_reviewers does everything — C tier); agents.md rot policed by yelling at humans (self-improving: F); not always-on; humans still in the loop.
  • ZTE is the North Star — "phase three... I haven't seen anyone doing zero-touch work yet." Vibe coding is not looking; ZTE is having built systems so good you don't have to look.

Rebuilding the plan skill

yt-50 · "PLANS For Fable 5: Rebuilding My /Plan Skill for Mythos Class Models" · 1:02:49

Great planning is great engineering — never outsource your planning to the built-in /plan black box. Hand-build a planning meta-skill that templates your engineering, because Mythos-class models will repay every token you spend on HTML+image-rich, living, self-validating plans.

Handing planning to the model "assumes the model knows what you're looking for" — part of "the mass deprecation of raw engineering talent." You should not outsource your thinking.

The future is created by those who plan it, not those who vibe code it.

— yt-50
RULEThe more a skill will be reused, the more upfront investment it deserves — and the plan prompt is the most important tool you and your agents have.
  • The plan skill is a meta skill — a prompt that creates other prompts.
  • Method: start by hand. Open raw.md and just type — purpose, priorities, properties. "Property-based engineering": list the properties the output must have before building anything.
  • Declare priorities explicitly: performance > speed >= cost. "We're spending to win here."
  • The audience trifecta: every plan is consumed by (1) you, (2) your engineering team, (3) AI agents — and must serve all three. Most engineers over-index on just one.
  • Plans become living artifacts: updatable header metadata (created, modified-list, commits, agent names, session IDs), append-only back and forward references, and an Amendments section recording post-build changes.
  • The format: HTML-first, hero image, purpose/problem/solution, existing-vs-new files, phased implementation with per-phase tasks and testing strategy, embedded live checklists with four task states (idle / WIP / done / failed), and validation commands that gate completion — "the plan is not complete until every box is checked and every command passes."
  • One skill, five workflows routed by a table: create plan, update plan, update references, build plan, image generation. Self-contained — no cross-skill dependencies.
  • Build workflow: a fresh-context agent ("one agent, one prompt, one purpose") reads all images + back refs depth 1, executes phases top to bottom, announces each phase, loops until validation passes, updates metadata.
  • Image discipline (GPT Image 2): professional, 1–2 ideas per image, under 10 words of text, visual identity synced with the HTML theme. "An image is worth a thousand words. Let's put that into action."
  • Templating doesn't constrain the model if you add a free-run Notes section: "Let the agent say what it needs to say" — it self-added a feature parity matrix there.
  • Watch your restrictions: changing "2–4 sentences" to "2–8" is a real design decision on the model.
  • "We stopped coding a long time ago... A lot of us are becoming skill atrophied. That's natural. But you do not want to outsource your thinking."
  • "It is your specific domain knowledge and expertise that differentiates you — encode it into your work." Templating your engineering is what gets you out of the normal distribution of results.
  • HTML gives agents more useful tokens (the Anthropic "unreasonable effectiveness of HTML" idea); next up: SVG diagrams, then audio and video in multimodal specs.

Open-weights models are finally real competition for Opus — so stop picking a model and build a model stack: GLM 5.2 is the better model, MiniMax M3 is the better deal.

The only guiding question: do you need maximum capability, or can you optimize for price? And never evaluate a model in isolation — set a max control (Opus 4.8) and a min control (Qwen 3.6 local), then place the experimental models between them.

"The cost curve looks really rough for Opus." Each tier down cuts price ~5x for only ~5–10 benchmark points.
  • The three tiers: state-of-the-art (hardest work), workhorse (daily drivers, high-volume product agents), lightweight (local, private, on-device).
  • GLM 5.2 caveat: it thinks a LOT — most of its speed goes to reasoning tokens, so wall-clock response time (what users feel) is worse than tokens/sec suggests.
  • "Workhorse models call tools like Opus, but they don't ship like Opus" — long-horizon agentic work is still Anthropic's moat. De-hype: GLM cannot replace Opus.
  • The trade-off triangle: performance / speed / cost — "you get to pick two, never all three." Place every model on it.
  • Engineering agents are <1% of the agents that will exist; product agents are everything else — and there, "routing to the cheapest model that clears the bar is what makes or breaks your business."
  • "With great prompt, context, and harness engineering, you can easily make a B-tier model an A-tier" — specialize your workhorses (agent experts) and the price drops further.
  • Substitutability is the whole strategy in 2026: the Fable ban proved a lab or a government can switch your model off. Open weights + 10–20 hosting providers = resilience. "We cannot fully depend on the most important technology being available to us."

Forget loop engineering

yt-53 · "FORGET Loop Engineering. Agentic Engineering is about THIS" · 34:18

"Loop engineering" is a terrible, hype-filled rebrand of the software development life cycle — the real game is designing AI developer workflows (ADWs) inside your software factory, composing the three actors of value creation: engineers, agents, and code.

"Forget about loop engineering... Your prompts go into your software factory, a specific workflow runs — a combination of code plus agents — and your results come out. That's the whole game."

"Code is the unsung hero." It's fast, always runs the same way, and costs nothing — "there are no token costs associated with code."
  • The reductio: "If we have loop engineering, we need condition engineering, function engineering, and exception engineering... It's the software development life cycle with AI bolted on, nothing more."
  • The scale-up ladder: engineer↔agent → add deterministic code (linter, formatter, typechecker, tests) with pass/fail routing back into the build agent → collapse validation into a dedicated test agent → add scout + plan agents → kanban queue → full factory with a factory router agent picking the right ADW at the right price/performance/speed.
  • "You and I always show up at the ends" — planning at the beginning, reviewing at the end, the two constraints; the system handles everything in between. "Add compute to add confidence."
  • "Work trees are a great place to start, not a great place to end." Upgrade: agent sandboxes — give every single agent its own computer. "Agent sandboxes are going to be the majority of computers in the world."
  • The production-down ADW: support ticket → Slack → scout routes to a specialized, surgical hotfix agent ("not doing things the right way, not the fancy way — getting the fix out ASAP") → human approve/reject → parallel sandbox race to the first passing fix → engineer validates → ship. Design this before the crisis.
  • Advanced teams skip translating tickets into prompts: the factory kicks off the moment the kanban ticket lands.
  • "The best engineering teams never touch the product themselves." Effort goes into the agentic layer, not the app layer — building the system that builds the system, the central TAC thesis.
  • "Vibe coding is not knowing how your system works. Agentic engineering is knowing your system works so well you don't have to look."
  • Three rules for ADWs: (1) KISS — start with a build agent + a linter, wired through an agent SDK, failures fed back into the same session, and separate code from skills ("otherwise you just have an agent calling code"; skills-only is fine until production); (2) do the workflow yourself first — step through every node, then diagram it (mermaid.live); (3) use agents AND code — "agents plus code beats either alone"; code runs at light speed, zero hallucination, zero tokens.
  • Specialization is the endgame: "Your expertise is the most valuable thing you have now. Template that into your AI developer workflows" — repeatable, consistent results tens, hundreds, thousands of times.
  • Classic engineering patterns matter MORE now: isolatable, decoupled, single-interface nodes — because every workflow you get right is multiplied a thousandfold.
