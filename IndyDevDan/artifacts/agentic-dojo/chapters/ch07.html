The Idea

Tactic #6: One Agent, One Prompt, One Purpose. "Use specialized agents with focused prompts to achieve a single purpose. No agent runs more than a single prompt."

The enemy is context pollution — context overloading, toxic context. "Massive context windows often lead to a distracted, confused agent." The antidote is the minimum context principle: "You want to context engineer as little as possible — the minimum context in your prompt required to solve the problem."

Four advantages follow: you free up the context window; you let your agent focus; every prompt is committed — reproducible and improvable; and you "effectively create evals for the agentic layer of your codebase."

Why focus wins. "Every piece of context you add increases the number of variables your agent has to reason about" — specialized agents each get one prompt and one purpose.
The SDLC as questions and answers. "Testing answers does it work, but review answers is what we built what we asked for." Conditional documentation closes "a complete software developer lifecycle feedback loop" from documenting back into planning.

The Nuggets

"One agent, one prompt, one purpose."

— quote of the lesson

"Isn't more context better for your agent? This is not true."

"Big tech is chasing the all-in-one god model, the super agent that can do it all. That's not what we're doing here. Real engineering requires real developer workflows, not some pie-in-the-sky god model." Every step of engineering requires "a different set of information, a different approach, a different perspective, a different set of tools and context."

01

Focus is throughput

"A focused engineer working on a single task is a productive engineer. Agents are the same." And: "When your agent's performance drops, your performance drops."

02

Compaction is a band-aid

"If your agent is running compact, it is losing information." Every added piece of context increases the variables your agent must reason about.

03

Proof over promises

"You want your agents communicating proof — a hard asset that proves what was built is what you asked for. Screenshots, reports, ideally video."

04

Fast yes/no

"Even when your agent is wrong, when it presents you with proof that it thinks it's right, you can quickly say yes or no."

05

Embed your own review

"Whatever you would do to review that the thing is what you asked for — that's what you embed into your review step."

06

Blame the system

"I'm not blaming the model for this. I'm blaming my skills. I'm blaming the ADWs."

On the prompt level

  • "Everything comes down to the prompt level. All the ADW surrounding deterministic code is just support for the agents doing the real work."
  • "While other companies run big context windows blown away at the end, you'll run single focused prompts you can pinpoint and improve."
  • "The value in your ADWs isn't in a single workflow — it's the power of combining workflows: isolated, reviewable, improvable."
  • "It's a good practice to encode the agent names as constants right at the top of the file."
  • "Reduce the number of human-in-the-loop points in your workflow."

On documentation and identity

  • "There's no excuse for having poor documentation" — every ADW script self-documents its workflow at the top.
  • Documentation timing: "how you document and when to include your documentation is the tricky part."
  • "Why didn't you just do that by hand? You're missing the point… This isn't about you anymore. It's about teaching your agents to build on your behalf, so that it can be about you again."
  • "Do you want to be an agentic engineer, or an engineer of the past?"

The Workout

GOAL Add review and document agents to your pipeline, with image proof and conditional docs.
PREREQS TAC-5 pipeline; Playwright MCP; any public bucket (R2/S3) or GitHub image upload for screenshots.

  1. Write /review.md

    Variables at top (ADW ID, spec file, agent name, screenshot dir); instructions to git-diff against main, compare against the spec, capture screenshots of critical functionality, read each screenshot back in, and output JSON {success, review_summary, issues[{class: skippable|tech_debt|blocker}], screenshots}.

  2. Write /patch.md

    "Create a focused patch plan resolving one specific issue with minimal targeted changes" → plan into specs/patch/.

  3. Write adw_review.py

    Load state → run /review → upload screenshots → for each blocker, fresh patch-plan agent + fresh /implement agent (max 3 retries) → post results with image links.

  4. Write /document.md

    A template meta prompt generating a doc in app_docs/ from git diff + spec, then updating conditional_docs.md with when-to-read conditions.

  5. Wire in conditional docs

    Reference conditional_docs.md in the Relevant Files section of /chore, /bug, /feature, and /prime.

  6. Run the full lifecycle

    Plan → build → test → review → document on one feature; deliberately give a precise UI placement instruction and check whether review catches deviations.

DONE WHEN The review step posts screenshot proof with a severity-classified JSON verdict; a follow-up plan automatically pulls in the new documentation via conditional docs.
LEVEL UP Make review self-healing — auto-run the patch loop on blockers without your involvement — and upgrade proof from screenshots to screen-recorded video.
