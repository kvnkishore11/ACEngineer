One agent is not enough — go multi-team.

The step past Claude Code is multi-team agentic coding: a three-tier system of specialized agent experts that remember, stay locked to their part of the codebase, and are all driven through one chat interface — so your cognitive input stays flat as the agent count grows.

1

The Idea

The three-tier architecture. "You are just talking to the orchestrator, the orchestrator delegates to the teams, and the teams delegate to their workers." Thinkers get the best models; workers "just need to follow instructions and execute."

Multi-team agentic coding means "specialized teams of agents to outperform the normal distribution of results."

The three default teams map to the three key nodes of building software: planning, engineering, and validation. Discipline comes from a handful of small parts: a shared zero-micromanagement skill ("You're a leader — delegate, never execute"), an active-listener skill ("read the conversation log before every response") installed in all 10 agents, a conversational-response skill deliberately withheld from workers ("we want our builders to be very, very verbose and very detail-oriented"), and the delegate tool — which orchestrator and leads have and workers don't.

Domain locking is the enforcement layer: front-matter rules for "what the agents can and cannot do and where they can and cannot go" — per-path read/update/delete. Planners read everything, change nothing. "No one should be touching the DevOps files and folders except the DevOps agent — this is like the holy grail of operating mid-to-large-size codebases." And every agent is an agent expert: it loads a personal expertise file at boot and updates it after work — "a working mental model about how things work, and this grows over time" — governed only by a ~77-line mental-model skill. Dan never touches the files.

The scaling claim. "Your cognitive input into the system… doesn't need to increase as you increase the total number of specialized agents" — the chat interface plus a single orchestrator is what makes customization scale.

The Nuggets

We're not afraid to give our agents all the relevant context they need." And to the $8-per-session objection: "You're thinking about right now. You're not thinking far enough into the future. "You stopped using agents that forget and you started using agent experts."

Blocks are features

A lead stepping out of its domain and getting blocked "might seem like an annoyance or a waste of tokens, but it's actually very valuable" — the block routes work to the right specialist.

Where the ball is going

"Always be thinking about where the ball is going, not where it is." Three converging trends: rising intelligence + bigger context windows, agent expertise, customizable agent harnesses.

05

Multi-perspective answers

Ask all teams one question and you get consensus and split recommendations surfaced — "a multi-perspective answer."

06

Everyone hears everything

Every agent can see the conversation (session JSONL) — "every agent is aware of the conversation happening."

07

Leads never build

"The lead cannot do work. It is a thinker. It's a planner. It's a coordinator."

08

The edge moved

"The way that you're building your agentic coding system is the edge now."

09

Tier your models

Leads and orchestrator on Opus, workers on Sonnet — tune the tier-to-model mapping; "if you're going all out, you'll make everything the top best possible model."

10

Compounding memory

"Every time I boot this up, my agent teams, down to the individual workers, has a stacking, compounding set of memory."

11

Let go

"You can't have your fingers on everything… You have to let go. You have to teach your agents to operate as you would." The mental-model file is the prime example.

12

Guidelines, not shackles

Don't be over-rigid with agent experts — give guidelines (a 77-line skill) and let them maintain their own mental model.

13

Experts beat generics

"Agent experts will always outperform a generic agent" — the same reason you trust the engineer who's done it over and over.

14

Specific beats sprawling

"This isn't just Claude capturing memory with everything you've ever said to it over years. That's not going to go well. What is going to go well is specialized agents that have specific purposes."

15

Input stays flat

Your cognitive input doesn't need to grow with agent count — the single-orchestrator chat interface is what makes customization scale.

What Dan Did

Dan re-engineered the Pi harness into a chat room with agent teams.

The footer shows orchestrator, leads, context, and total cost; /toggle workers reveals the full roster — 10 specialized agents. Teams are config, not code: "At any point in time we can just copy our config, change up the teams, and specialize how we need." To prove it, he killed the validation team in the YAML and relaunched.

The working codebase was a prompt-complexity classifier that routes user prompts to high/medium/low-tier models — "You don't want to pay for intelligence that you don't need" — biased toward high as the safe default. j predict "summarize this code base" returned medium with confidences.

multi-team config — teams are one YAML edit away
orchestrator: agents/orchestrator.md
teams:
  - name: planning
    lead: agents/planning-lead.md
  - name: engineering
    lead: agents/engineering-lead.md
    members: [agents/front-end-dev.md, agents/back-end-dev.md]
  - name: validation      # kill or add a team by editing one file
    lead: agents/validation-lead.md
    members: [agents/qa-engineer.md, agents/security-reviewer.md]
a worker's domain block — the holy grail
domain:
  read:   ["**/*"]           # see everything
  update: ["front-end/**"]   # write only your own directory
  delete: ["front-end/**"]

  1. Climb the demo ladder

    ping (orchestrator ping-pong) → "ping each team lead" (two-layer fan-out and compose) → "have engineering present tree structure of the most important files" — the engineering lead hits a domain wall, then delegates to the front-end and back-end devs. Three tiers live on screen.

  2. Ask all teams one question

    "What are two additional scikit-learn classifiers we can test against?" Planner, engineer, and validator teams each delegate internally; the orchestrator synthesizes: LinearSVC + CalibratedClassifierCV unanimous, ComplementNB/SGD split noted.

  3. Run the classic workflow in one prompt

    "Plan, engineer, and then validate — add just commands to test both models (just prompt both)." The plan lead reads all context first, the back-end dev builds, and the QA engineer finds issues the security reviewer missed ("ship it, no issues" vs QA's findings — different context windows, different perspectives). The orchestrator composes. About 18 minutes of team work.

  4. Verify through the hierarchy

    New just commands (predict both, train both, head-to-head eval on the holdout set) — the orchestrator can't run them, so it delegates to the engineering lead, who delegates to the back-end dev.

  5. Walk the internals

    The multi-team YAML (teams/leads/members as paths to system prompts plus a team color); orchestrator front matter (expertise, max lines 10,000, skills); shared vs withheld skills; the domain blocks; runtime-injected variables (session dir, conversation log, teams from YAML); session storage of every tool call and each agent's fully-templated system prompt — and the back-end dev's ~5,000-token self-maintained mental model.

The Workout

GOALStand up a three-tier orchestrator → leads → workers team over a real small codebase, with domain locking and per-agent persistent mental models, driven through a single chat entry point.
PREREQUISITESA codebase with at least two separable domains (e.g. frontend/ + backend/, or src/ + tests/); Pi (or Claude Code with subagents as the limited fallback); just.

  1. Write the team config

    multi-team.yaml: one orchestrator (best model) and two teams — engineering (lead + backend-dev + frontend-dev workers) and validation (lead + qa-engineer) — each entry a name plus a path to a system-prompt .md.

  2. Write the shared skills

    Small markdown files: zero-micromanagement.md ("You're a leader — delegate, never execute"), active-listener.md ("Read the conversation log before every response"), conversational-response.md (orchestrator/leads only), mental-model.md (~75 lines: when to read, when to update, how to structure, max lines).

  3. Set the front matter

    Per agent: model (Opus-tier for orchestrator/leads, Sonnet-tier for workers), skills, expertise (path to its mental-model file), tools (only orchestrator/leads get delegate; only workers get write/edit/bash), and domain (workers: read **/*, upsert/delete only their own directory; leads: read-only everywhere plus their expertise dir).

  4. Enforce domains in code

    A tool-call hook (Pi hooks or a Claude Code PreToolUse hook): no matching rule = deny; the blocked message should say who to delegate to.

  5. Run the ladder

    ping → "ping each team lead" → "have engineering present tree structure of the most important files" — confirm the lead delegates instead of executing.

  6. Ship one feature in one prompt

    "Plan, engineer, and then validate: <small real feature>. Add just commands to test it." Watch plan → build → validate flow through the tiers.

  7. Let expertise grow

    Run 3+ sessions; inspect each agent's mental-model file growing; never edit the files yourself.

DONE WHENA lead attempting a file write gets blocked and delegates instead; the front-end worker cannot modify backend files (hard block, not just prompt); one prompt to the orchestrator produces planned + built + validated work with a composed summary; and the mental-model files contain content you didn't write after session 3.
LEVEL UPAdd a read-only expertise file (updatable: false) for a "billing"-style sensitive domain; add a team-based reusable plan-build-validate prompt; swap one worker to a different vendor's model via config; build a meta-agent whose job is critiquing and tuning the team's own prompts and skills.
