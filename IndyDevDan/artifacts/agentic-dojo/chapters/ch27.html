27 — The Repo Gym · Rebuilds
commit archaeology as curriculum

Rebuild what he built, in the order he built it.

Eight repos, decomposed into milestone rebuild paths — follow the real commit history where it exists, decompose the architecture where a single 🚀 commit holds the whole system, and finish every rebuild against a checkable definition of done.

In this chapter 1drop-zones 2hooks-mastery 3infinite-loop 4beyond-mcp 5bowser 6nano-agent 7observability 8finance-review

These eight weren't picked for popularity.

The selection criteria: density of transferable patterns, real commit history to follow, and how much of Dan's stack the rebuild forces you to internalize. Where a repo's history is one 🚀 commit, the path decomposes the system's internal structure instead — you rebuild the architecture, not the diff.

"The arc: trigger an agent → control an agent → parallelize agents → choose tool interfaces → compose layers → build and measure the agent itself → observe fleets → trust autonomous pipelines. That is, in order, how Dan thinks."

— the eight-rebuild learning arc
Climb in order. Each rung assumes the muscles built on the rung below — drop-zones takes an afternoon; finance-review assumes everything.
1

agentic-drop-zones

Minimal agentic infrastructure — one file, one YAML, huge leverage.

This is the best first rebuild: it teaches triggers, prompt templates, streaming output, and the autonomy trade-off without any web stack. The history is flat — the init commit contains everything and seven progress commits are README polish — so you rebuild by decomposing the single file itself.

agentic-drop-zones · 8 commits, 2025-08
init          # 2025-08-28 — the entire system in one commit
progress ×7   # README + architecture polish

# drops.yaml — one zone, declared not coded:
#   name · file_patterns · reusable_prompt · zone_dirs
#   events · agent · model · mcp_server_file

  1. M1 — Watcher skeleton

    Build sfs_agentic_drop_zone.py with watchdog observers and a rich console; detect created files matching patterns. You learn single-file uv apps ("sfs" naming) and event-driven triggers.

  2. M2 — Declarative zones

    Move every zone into drops.yaml — name, file_patterns, reusable_prompt, zone_dirs, events, agent, model, mcp_server_file. Config-not-code extensibility.

  3. M3 — Prompt templating + agent dispatch

    Load .claude/commands/<x>.md, substitute FILE_PATH, shell out to claude -p with bypassPermissions and stream JSON to styled panels. Prompts become reusable templates; full autonomy gets an explicit risk frame.

  4. M4 — Multi-agent + MCP

    Add the gemini_cli branch (yolo --sandbox) and per-zone .mcp.json. Agent-agnostic dispatch, per-zone tool scoping.

  5. M5 — Real zones

    Ship echo.md, create_image.md / edit_image.md, finance_categorizer.md, morning_debrief.md, more_training_data.md with example input files. One pattern, many workflows — the zone catalog is the product.

DONE WHEN Dropping echo.txt streams a response within seconds; an image-prompt file produces a generated image in the zone; and a malformed file fails loudly, not silently.

claude-code-hooks-mastery

The foundation layer every other repo copies from.

The hooks stack, TTS/LLM utils, sub-agents, meta-agent, output styles, and status lines all originate or mature here — and it has the cleanest real history in the catalog: each commit is a named capability. Rebuild it commit by commit and you retrace the exact order Dan layered deterministic control onto a nondeterministic agent.

  1. M1 — Core hooks + flow control (🚀)

    Wire pre_tool_use, post_tool_use, stop, notification, subagent_stop as uv single-file scripts in settings.json; block rm -rf and .env reads in PreToolUse; log every payload to logs/; add utils/tts (elevenlabs → openai → pyttsx3) and utils/llm.   2. M2 — Prompt-level control (UserPromptSubmit)

    Add user_prompt_submit.py for validation and context injection — intercepting before the model even sees the prompt.

  3. M3 — Sub-agents + the meta-agent (subagents)

    Build .claude/agents/ with hello-world, TTS completion-summary, research agents, crypto analyzers — and meta-agent.md, which generates new agent files from a description. Agents that build agents.

  4. M4 — Lifecycle completeness (add PreCompact and SessionStart)

    Cover session boundaries; inject dev context at SessionStart. Map the full 13-event lifecycle.

  5. M5 — Model-tier engineering (ccmodels)

    Restructure crypto agents into haiku / sonnet / opus variants — the performance-speed-cost trifecta as a file-naming discipline.

  6. M6 — Output styles + status lines + local LLMs (genui)

    Eight output styles including genui and tts-summary; status_line v1 → v9 pulling session data; utils/llm/ollama.py for local-model fallbacks.

  7. M7 — Teams + new hooks (Update Hooks)

    Add permission_request, subagent_start, post_tool_use_failure, session_end, setup hooks; team builder/validator agents with plan, build, and plan_w_team commands; a tts_queue. Builder/validator orchestration plus failure-path hooks.

DONE WHEN All 13 hooks log their JSON payloads; a dangerous rm -rf is blocked with exit 2; /plan_w_team runs builder then validator; the meta-agent generates a working new agent file; and TTS announces completion with your name.

infinite-agentic-loop

The purest lesson in spec-driven parallel orchestration — the whole system is two markdown files.

Its 18-commit history is a visible iteration loop on a spec (v1 → v4): you literally watch Dan learn what makes agent-facing specs work. Nearly every message says progress — the information is in what each commit adds.

infinite-agentic-loop · what each "progress" adds
progress  # .claude/commands/infinite.md + ai_docs/
progress  # specs/invent_new_ui.md → src/ui_innovation_1..10
progress  # invent_new_ui_v2.md → src_enhanced/
progress  # invent_new_ui_v3.md → themed_hybrids/ (then: broader)
progress  # prime.md + settings.json permissions + legacy/
progress  # README + src/ui_hybrid_10..18 — the scale run
progress  # 2025-06-10: v4 → src_group/ui_hybrid_N/ file sets

  1. M1 — The command

    Write the orchestrator prompt: parse $ARGUMENTS (spec, out_dir, count), analyze the spec, reconnoiter the output directory, deploy sub-agents. Slash commands as programs.

  2. M2 — First spec + first outputs

    specs/invent_new_ui.md, single and small-batch runs. Uniqueness comes from directory reconnaissance — agents never duplicate prior output.

  3. M3 — Spec iteration

    v2 and v3: tighten naming patterns, design dimensions, quality bars. The spec is the product — output quality tracks spec quality, not prompt cleverness.

  4. M4 — Repo hygiene + permissions

    prime.md, settings.json allowlists for Write/Edit/Bash, move old outputs to legacy/. Permissioning for autonomous loops.

  5. M5 — Scale run

    20-iteration batched waves; infinite mode until context exhaustion. Wave management and progressive sophistication under a finite context budget.

  6. M6 — Multi-file generations

    v4 upgrades the spec so each agent emits a file set — index.html, script.js, styles.css. Structuring specs for compound artifacts.

DONE WHEN /infinite specs/your_spec.md out 5 yields five genuinely distinct, spec-compliant artifacts with correct sequential naming — and infinite mode runs at least two waves with rising sophistication.
4

beyond-mcp

The clearest architectural-judgment lesson in the catalog.

The same domain — Kalshi prediction-market data — built four ways forces you to feel the context-cost, discoverability, and reusability trade-offs everyone argues about abstractly. The numbered apps are a built-in rebuild order, and the thesis is blunt: MCP's cost is instant context loss.

apps/ 1_mcp_server/ # FastMCP + .mcp.json — schemas eat context at start 2_cli/ # typer CLI + /prime_kalshi_cli_tools on demand 3_file_system_scripts/ # one uv script per operation 4_skill/ # SKILL.md — auto-discovered, context-cheap

  1. M1 — Domain client

    Shared Kalshi API access: status, events, markets.

  2. M2 — apps/1_mcp_server

    FastMCP server + .mcp.json; measure the context the tool schemas consume at session start. MCP mechanics and their instant context loss.

  3. M3 — apps/2_cli

    A typer/click CLI plus a /prime_kalshi_cli_tools command that teaches the agent the CLI on demand. Prime-on-demand beats always-loaded.

  4. M4 — apps/3_file_system_scripts

    One uv script per operation with its own /prime command. Scripts are the zero-infrastructure tool surface agents can read and edit.

  5. M5 — apps/4_skill

    SKILL.md wrapping the capability with a trigger description and progressive disclosure.

  6. M6 — The bake-off

    Run the same prompt set against all four; compare tokens at startup, tokens per task, latency, failure modes. Write the trade-off table yourself.

DONE WHEN You can answer "MCP, CLI, scripts, or skill?" for a new toolset in one sentence — backed by your own measured token numbers.
5

bowser

The best single artifact for Dan's composition philosophy.

Skill → Subagent → Command → justfile, each layer independently testable, each wrapping the one below. It's small — 30 files, 3 commits — but the architecture generalizes to any capability, not just browsers. Two skills give you the headed/headless duality: claude-bowser (Chrome MCP, observable) and playwright-bowser (playwright-cli, fast and silent).

Four doors into one capability. Skill for direct use, subagent for isolation, command for orchestration, justfile for one-liners.

  1. M1 — Layer 1, skills

    Write the claude-bowser and playwright-bowser SKILL.md files; test directly with just test-playwright-skill. Includes a just skill that teaches the agent the task runner itself.

  2. M2 — Layer 2, subagents

    playwright-bowser-agent, claude-bowser-agent, bowser-qa-agent wrap the skills for isolated parallel sessions with a structured report contract. Subagent = capability + isolation + report.

  3. M3 — Layer 3, commands

    /bowser:hop-automate runs saved workflows; /ui-review discovers YAML user stories in specs/, fans out QA agents, and collects reports into ai_review/. HOP orchestration over subagents.

  4. M4 — Layer 4, justfile

    One-liners per layer (just hop …, just ui-review) and the README's four-layer table — reusability for you, your team, and other agents.

DONE WHEN You can enter at every layer — the skill directly, one agent, a full /ui-review fan-out, and a just one-liner — and parallel QA produces per-story reports in ai_review/.

nano-agent

The only repo where you build the agent itself.

Loop, tools, provider abstraction — then expose it through MCP and evaluate models scientifically. Rebuilding it demystifies what Claude Code is under the hood: a tool-call loop, a provider interface, and a surface to invoke it from. The initial 🚀 contains the system; you decompose it into seven milestones.

nano-agent · the eval machinery
nano-cli run "<prompt>" --model gpt-5-mini --provider openai

# HOP: .claude/commands/perf/hop_evaluate_nano_agents.md
# LOP: lop_eval_1__dummy_test.md … 5__complex_engineering_test.md
# per-model wrappers in .claude/agents/nano-agent-*.md
# graded results committed as eval_results_*.md

  1. M1 — Agent core

    Typed file-system tools plus an OpenAI-SDK agent loop in apps/nano_agent_mcp_server. The tool-call loop all agents share.

  2. M2 — Provider abstraction

    Route gpt-5*, claude-*, and gpt-oss:* (Ollama) through one interface. OpenAI-compat as lingua franca; local models first-class.

  3. M3 — CLI

    nano-cli run with --model and --provider, plus test-tools — test the agent without any MCP client.

  4. M4 — MCP server

    Expose prompt_nano_agent via MCP with .mcp.json.sample and uv tool install. Agents-as-MCP-tools; delegation from Claude Code.

  5. M5 — Per-model sub-agent wrappers

    Nine .claude/agents/nano-agent-*.md files, all calling the same MCP tool with a pinned model. Fan-out parallelism via sub-agents.

  6. M6 — LOP evals

    Five graded eval prompts, from dummy test to complex engineering test, each with expected outputs and rubrics. Evaluations written as prompts.

  7. M7 — HOP + results

    hop_evaluate_nano_agents.md runs all agents in parallel on a LOP and grades performance / speed / cost; commit the eval_results. The trifecta — and cheap models often win.

DONE WHEN One HOP invocation runs ≥3 models in parallel on the same task and produces a graded comparison table with token counts, wall-clock, and cost — including a $0.00 local-model row.

agentic-finance-review

The capstone of the trust theme: specialized self-validating agents.

Hooks live inside the agent definitions — not in global settings.json — and every stage is checked by a deterministic Python validator. It composes nearly everything above (commands + subagents + hooks + orchestration) into an autonomous pipeline over bank CSVs with a checkable output. The formula, verbatim: Focused Agent + Specialized Validation = Trusted Automation.

Validation rides with the agent. Each stage agent embeds its own hook; each hook runs a deterministic script.

  1. M1 — Mock data + one validated stage

    mock-input-data/raw_*.csv and normalize-csv-agent.md with an embedded PostToolUse hook running csv-single-validator.py. Agent-scoped hooks — validation as part of the agent, not the harness.

  2. M2 — Stage agents

    categorize-csv-agent, merge-accounts-agent, csv-edit-agent — each with matching validators. One agent = one job = one validator.

  3. M3 — Visualization stages

    graph-agent generating eight plots with graph-validator.py; generative-ui-agent producing index.html dashboards with html-validator.py; Stop-hook validation (ruff / ty) on /build. Validating generated UI and code deterministically.

  4. M4 — Orchestrator

    /review-finances chains normalize → categorize → merge → accumulate → graph → dashboard over ROOT_OPERATIONS_DIR, with monthly and year-to-date outputs. Autonomy earned through verification.

DONE WHEN Dropping a new month of raw CSVs and running one command produces normalized and merged CSVs, eight graphs, and monthly + yearly dashboards — every stage's validator green, and any failure loudly halting the pipeline.
