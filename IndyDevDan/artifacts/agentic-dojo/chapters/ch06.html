The Idea

Tactic #5: Always Add Feedback Loops. "Your work, my work, any engineer's work is useless unless it's tested."

Closing the loop means "letting your agent operate on work, calling a command or tool to get feedback on the success of the work… your agent continues to build until the feedback is positive. When you do this, you let the code write itself."

Every closed-loop prompt has three parts: Request → Validation → Resolution. "This prompt instructs the agent to validate itself." Linters, unit tests, builds, Playwright browser tests — anything you would run by hand becomes a loop your agent runs for you.

Anatomy of a closed-loop prompt. Request → Validation → Resolution — the agent cycles until every validator passes, with no human diagnosis in between.

"Given a unit of valuable work that's production ready, how would you, the engineer, test and validate this work? If you can answer this for every class of work and encode the answers into a command or tool call, you will fly while other engineers run."

— the core validation question
01

Three loops, one vocabulary

In-loop = you prompting back and forth. Out-loop = a high-level prompt through the PITER system on an isolated machine. Closing the loop = the agent's own execute–validate–reflect cycle.

02

The hierarchy of trust

"The ultimate test will always be your users. The next best test used to be you. Now the next best test is an army of agents validating your entire codebase with regression tests and, most importantly, end-to-end tests."

03

Tests as rule of law

"What's more important, the code or your tests? The answer should be your tests. Your tests should be the rule of law in your codebase."

04

Playwright MCP

Browser control as a validation tool: open the browser, type, click, screenshot, read the images back, verify results — your agent clicks through the feature so you never have to.

05

The e2e test file

A markdown prompt: test name, test steps, verify IDK statements, success criteria — run through a HOP with preconditions (reset DB, ports, screenshot directory) and a JSON output format.

06

Validation, templated

The chore / bug / feature plan formats include a Validation Commands section by default — plus "if this bug affects UI or user interactions, create an end-to-end test."

On scale and mindset

  • "Our most valuable contribution is the experience we create for our users."
  • "Have your agents test on your behalf like you never could, at scales you never will achieve. This is the gift of generative AI."
  • "With every passing set of tests, you free your context window and you stop second-guessing."
  • "Test, let your agents scale your success. Same game, different day, new tools, exponential impact."
  • "Testing at its core is simple: did it do what you designed it to do, and did it break anything else along the way?"
  • "We will be the ones prompting the errors" — as models improve, your validators catch your mistakes.
  • "Lean into the future. Don't lean into the present, don't lean into the past."

On moving out of the loop

  • "We want end-to-end agents, not in-loop agents… we don't want to be babysitting."
  • "Everything starts with a single prompt. Everything starts in the loop, and then slowly move it out the loop."
  • "One agent running here, one agent running there" — parallel issue-fixing is normal once loops are closed.
  • The in-loop limitation: "You're pretty much limited to one agent unless you're conscious about everything that you're changing" — no worktrees yet.
  • "When you're setting up your ADW to test, you might point this at staging or even a production test account."
  • "Engineers that test with their agents win" is a scaling law, not a slogan — the loop count compounds.

The Workout

GOAL Convert your manual verification ritual into closed loops an agent runs, including one browser-level e2e test.
PREREQS TAC-3/4 setup; a linter, a test runner, and a build command in your repo; Playwright MCP configured in .mcp.json.

  1. Take your validation inventory

    Write down every step you personally take to verify a change ships — lint, tests, build, click-through. This is your validation inventory.

  2. Write one closed-loop prompt

    Request (one small refactor) + Validation (ruff check or equivalent) + Resolution ("if any issues, fix and re-run until clean"). Run it; watch the loop close.

  3. Scale to three validators

    Linter + unit tests + compile/build, with the instruction: "run in order top to bottom; if any step fails, stop, resolve immediately, then rerun EVERY validation step."

  4. Add the browser

    A validation prompt that starts your app, opens it via Playwright MCP, screenshots before/after a scripted interaction, and verifies a precise expected result.

  5. Bake validation into your templates

    Add a "Validation Commands" section to your /chore, /bug, /feature plan formats, plus "if this affects UI, create an e2e test file" with a test-steps / verify / success-criteria format.

  6. Prove the template carries its own validators

    Run one /bug through plan → implement and confirm the generated plan validates itself.

DONE WHEN An intentionally broken change gets fully repaired by the agent with zero human diagnosis, and one e2e screenshot pair proves a UI behavior.
LEVEL UP Build adw_test.py — run all tests, emit JSON results, spawn one fresh resolver agent per failure with a retry cap, then commit and PR the fixes.
