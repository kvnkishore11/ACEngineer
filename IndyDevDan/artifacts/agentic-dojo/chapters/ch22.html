Zero to skill, raw

yt-22 · "RAW Agentic Coding: ZERO to Agent SKILL" · dec 8, 2025 · 50:23

Building a skill from scratch — pen-and-paper plan first, then skill.md + tools + prompts + cookbook — is the fundamental craft. Skills package reusable prompts and code against a use case, and everything reduces to the core four.

  • Start off-computer: "Push the laptop aside... we never start by just blasting out prompts." Notebook first — purpose, problem, solution. "Begin with the end in mind": define the exact output file tree before any prompting.
  • "Those who plan the future tend to create it." On atrophy: "Engineers' brains are rotting due to this incredible technology... always understand what you're asking your agents to accomplish."
  • Canonical anatomy: skill.md (the "pivot file") + tools/ (single-file uv scripts) + prompts/ (user vs system, named explicitly) + cookbook/ (per-use-case docs, progressively disclosed).
  • The cookbook pattern is conditional prompting — if the user requests X and enable_X is true, read the file. "A conditional prompt — that's what progressive disclosure is."
  • Enable flags as static variables in skill.md (enable_gemini_cli: true) toggle capabilities without rewriting.
  • Prototype in the loop, then encode: "run it in the loop, write the prompt, observe the result, and then encode it in a skill." The osascript trick was validated live first.
  • Teach tools via --help: "Before executing the command, run command --help" — trades speed and context for reliability on fast-moving CLIs.
  • Information-dense keywords: "Astral UV single file script," "subprocess," a Python signature — each carries meaning the model already knows. Know your model's cutoff.
  • Agentic code reports: capture stdout + stderr, always return a string "so we can get concrete output every time it runs."
  • Debug order: "Don't assume it's the model's fault. First assume it's your fault, then... the tooling's fault."
  • Skills don't hot-reload — restart the session after editing skill.md; metadata loads at boot.
  • Fork-with-summary is a manual /compact: a YAML meta-prompt (summarized prompt/response pairs + next request) the base agent fills and hands to the fork. "The key is always to remember who's writing to who."
  • POC → MVP: "the simplest working version that gets our agents operating properly." Fresh context per task: "It's easy to know what your agent has seen when it's seen nothing."
  • "Everything always boils down to the core four: context, model, prompt, tools. If you master these, you'll master the agent, you'll master engineering."

Agents that actually learn

yt-23 · "Agent Experts: Finally, Agents That ACTUALLY Learn" · dec 15, 2025 · 18:54

The massive unsolved agent problem: agents forget. The fix is agent experts — self-improving template meta-prompts that maintain their own expertise file, a mental model of one domain, updated automatically after every job. No human in the loop.

  • "Your agents forget. And that means your agents don't learn." Traditional software improves with use; today's agents don't.
  • Everything existing fails the same way: memory files are "global forced context that always loads"; prime prompts, sub-agents, and skills all "have to be manually updated."
  • "The difference between a generic agent and an agent expert is simple. One executes and forgets, the other executes and learns."
  • "You don't need to tell an expert to learn. It's in their DNA." Experts don't relearn their craft per task; they update a mental model — "a data structure that evolves over time."
  • The definition: "The agent expert is a concrete form of a self-improving template metaprompt."
  • Meta-agentics first — prompts writing prompts, agents building agents, skills building skills: "There is no codebase I create that does not have meta-agentics." But alone, "they're acting, but they're not learning."
  • Anatomy: experts/<domain>/ with expertise.yaml (the mental model) + question.md + plan.md + self-improve.md. The question prompt's first step: read expertise, then "validate assumptions against the codebase."
  • The expertise file is not another source of truth: "The true source of truth is always the code... You have a working memory file. You have a mental model."
  • Payoff: "There's no searching here. There's just validating its mental model" — the websocket expert knows where everything is and one-shots plan → build → improve.
  • The three-step workflow chains sub-agents: plan (~80k tokens, context protected) → build → self-improve (diff-driven expertise update). Learning is a mandatory final step.
  • Scale for confidence: fire the same question at 3, 5, or 10 experts and cross-validate — "sometimes if you throw five agents at the problem, only one makes it... you compose that together, you get a better result."
  • "Three times marks a pattern" — build it thrice, automate it (he has a meta-expert that generates experts). Abstraction-agnostic: "I always focus on the foundational units: context, model, prompt, tools."

The codebase singularity

yt-25 · "The Codebase Singularity: 'My agents run my codebase better than I can'" · dec 29, 2025 · 16:35

The agentic layer — a graded, class-based ring of prompts, agents, tools, and workflows around your application layer — is the highest-ROI thing you can build. Powerful enough, and you hit the codebase singularity.

  • "The agentic layer... the new ring around your codebase where you teach your agents to operate your application on your behalf as well and even better than you and your team ever could."
  • The singularity moment: "My agents can now run my codebase better than I can. I trust them to ship more than I trust myself or my team. Nothing ships to production without my teams of agents."
  • Two layers in every codebase: the application layer (front end, back end, DB, scripts, DevOps) and the agentic layer wrapping it so agents "see everything."
  • The progression is Class 1→3 with grades inside each — a maturity model you can locate yourself on.
  • C1G1 (thinnest possible): prime prompt + memory file. "If you have this, you technically have an agentic layer." Prime beats a bloated memory file — "you can activate this whenever you want and fine-tune it to run any specific workflow."
  • C1G2: plan prompts, specs/, ai_docs/, sub-agents (fetch-docs, test-writer). "Many engineers have passed this level."
  • C1G3 (custom tools): skills, MCP servers, prime-with-tool-access. Key insight: "Skills and MCP servers can both be replaced with just a simple prompt" — a script + a prompt teaching psql often beats an MCP server.
  • G3 is where engineers silently fail: "their tools are terrible and they won't scale... chewing up tokens, burning cash, overengineering." Most common sin: way too many tools.
  • C1G4 (feedback loops): review / code-review / reproduce-bug / test-backend / test-frontend prompts; closed loops follow "request, validate, resolve" so "your agent can spin and spin until the job is done."
  • "You should always add feedback loops into your agentic layer" — "you're effectively adding more compute to get more confidence in your agents' results."
  • As the app grows, prompts specialize (generic plan/build → test-backend, test-frontend); the two layers grow side by side.
  • Class 3 preview: an orchestrator that can "kick off arbitrary end-to-end AI developer workflows" from a single prompt.
  • Self-correcting agents are "a massive massive win for your agentic layer."
The maturity ladder. Grade yourself honestly, move up one grade at a time — G4's closed loops are where trust compounds.

Damage control

yt-26 · "Claude Code is Amazing... Until It DELETES Production" · jan 5, 2026 · 22:23

One hallucinated command can evaporate years of work. Layer deterministic pattern-blocking, ask-permission patterns, path protection, prompt hooks, and global hooks into every production codebase — damage control removes the need for trust.

  • "It doesn't matter how fast, powerful, or autonomous your agents are. All of your months and years of hard work can be evaporated in a single misinterpreted or hallucinated command."
  • The stack — four damage controls: local project hooks, global (user-level) hooks device-wide, ask-permission patterns, and the prompt hook most engineers don't know exists.
  • The prompt hook: an LLM prompt run as a PreToolUse hook on every bash command — catches destructive commands "even though it's never seen it before." The "last-ditch effort... as soon as you find that command, you should add it to your deterministic hook."
  • The layered wrapper: settings.json hooks (PreToolUse on Bash/Edit/Write) → uv/bun scripts → patterns.yaml: blocked regexes, ask: true patterns (confirm with you), zero_access_paths (.ssh — no read/write at all), read_only_paths (.bashrc), no_delete_paths (hooks, commands).
  • Hooks in settings run in parallel — whichever finishes first wins the block.
  • "Not everything is a 100-to-zero command" — ask-patterns cover the gray zone, like SQL DELETEs on a prod-like DB.
  • The /install pattern: an agentic installation workflow on the AskUserQuestion tool (global or project? Python or TypeScript? merge or override?) — a reusable way to ship skills to a team, driven by a nine-step cookbook.
  • "You just don't want to think about your security over and over. You just want great defaults, and then run with it."
  • The confession behind it: "A few weeks ago, I almost ran a command that would have been catastrophic in one of my production applications."
  • Trust framing: "You can build trust or you can defer it or you can make sure that you don't need trust." Hooks = not requiring trust; sandboxes = deferring it ("so they don't even need damage control").
  • Odds math: "One out of 100,000 — that's enough to really ruin your day." At hundreds of thousands of tool calls, you will hit it.
  • The prompt hook is slow — "but running this prompt every single time is going to be faster than potentially deleting a valuable production asset." Claude Code's trained-in protections are good (it backed up .bashrc unprompted), but "there's going to be a moment where you miss something and your agent misses something."
Defense in depth. Build trust, defer it, or remove the need for it — layered hooks are the third option.

Think in threads

yt-27 · "AGENT THREADS. How to SHIP like Boris Cherny. Ralph Wiggum in Claude Code." · jan 12, 2026 · 31:00

Thread-based engineering — every unit of work as prompt → agent tool-calls → review — gives you a measurable framework: more threads, longer threads, thicker threads, fewer human-in-the-loop checkpoints.

  • The context is Karpathy: "I've never felt this much behind as a programmer." Dan's answer: "Agentic engineering is a new skill. New skills need new frameworks to measure progress against. If you don't measure it, you will not be able to improve it."
  • A thread is "a unit of work over time driven by you and your agents," with two mandatory human nodes: the prompt/plan at the start, the review/validation at the end. The middle is the agent's string of tool calls.
  • "Pre-2023 you and I were the tool calls." Now "tool calls roughly equal impact, assuming you're prompting something useful."
  • Base thread — one prompt, one line of work, one review.
  • P thread (parallel) — Boris Cherny "runs five Claude Codes in his terminal and numbers his tabs one through five," plus 5–10 more in the web UI. "Guess who's getting more done?"
  • C thread (chained) — intentional phase checkpoints for work too big for one context window, or risky production migrations. "These checkpoints aren't because your agent messed up — that's bad agentic coding." Use AskUserQuestion or notifications (Dan: a TTS hook that speaks the summary).
  • F thread (fusion) — same prompt to multiple agents, then aggregate: best-of-n or cherry-pick. "The future of rapid prototyping will be done with fusion threads. Mark my words." Demo: 9 agents at once — 3 Claude Code, 3 Gemini, 3 Codex — each in its own sandbox, watched via mprocs.
  • B thread (big/meta) — threads containing threads; "your prompts are firing off other prompts." Sub-agents are v1; orchestrator-kicks-off-primaries is next. From your seat it's still one prompt + one review; the inside is a black box you engineered.
  • L thread (long) — "high autonomy end-to-end long duration work"; Boris's 1-day-2-hour run. Same shape as base, just hundreds or thousands of tool calls. "Great planning is great prompting."
  • Ralph Wiggum is "literally a loop over an agent" (agents + code > agents alone) — ADWs hitting the mainstream (credit: Geoff Huntley). The stop hook is the primitive: agent tries to stop → deterministic code checks a progress file or runs validation → reloop or complete.
  • Boris's other tips: always Opus 4.5; a small CLAUDE.md in the repo; no dangerously-skip-permissions (curated allowlist); and #1 — "give it a way to verify its work."
  • The four ways to improve: more threads, longer, thicker, fewer checkpoints — the whole scoreboard. Hidden 7th: the Z thread (zero-touch), review node deleted. "It isn't that we don't look at the code, it's that we know we don't have to. That's the endgame." Maximum trust; explicitly not vibe coding.
