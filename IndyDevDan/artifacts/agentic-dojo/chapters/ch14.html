agent experts · act, learn, reuse

One executes and forgets. The other executes and learns.

The massive problem with agents is that they forget — which means they don't learn. An agent expert is "a concrete form of a self-improving template meta prompt": it acts, learns, and reuses its own expertise at runtime, with no human in the loop.

The Idea

Your agents forget. An expert doesn't — because it carries its own mental model with it, and updates it after every job.

The expert's secret is a mental-model data structure — an expertise file. And Dan is emphatic about what it is not: "This is not a source of truth... You have a working memory file. You have a mental model, a data structure that you constantly update." "The true source of truth is always the code." He keeps his in YAML with a MAX_LINES cap (1000) that the agent enforces on itself.

Seeding creates version one: "Ideally you run your self-improve prompt and it creates the expertise from blank... rerun it until your agent stops finding new things."

Act, learn, reuse. The build step acts; self-improve validates and surgically updates expertise.yaml; the next plan or question reads the mental model first instead of searching.
01

Act

Take a useful action — e.g. the build step. Meta-agentics act but don't learn, "so they are not agent experts."

02

Learn

Store new information — the self-improve prompt updating the expertise file after the work is done.

03

Reuse

Apply that expertise on the next execution — the plan and question prompts read the expertise file first.

Meta-agentics sit beside experts: "meta prompts, meta agents and meta skills... they help you build elements of the system that builds the system." Dan's rule: "Every codebase must have meta agentics."

The self-improve prompt is the learn step's anatomy: check git diff (conditional) → read current expertise → validate against the codebase → identify discrepancies → update expertise → enforce the line limit + validate YAML (closed loops). Its key lines: "Prioritize actionable, high value expertise over verbose documentation," and "after your thorough search, there may be nothing to do — this is perfectly acceptable."

The learn step, drawn. Conditional git diff in, surgical YAML out — with closed loops enforcing MAX_LINES and valid YAML before the agent may finish.
◵ deploy experts where
  • Billing — Dan's #1: "literally saved me money"
  • Database · DevOps · 3–4-way integrations
  • ML / data science · API (front/back sync)
  • Data types & models across microservices
  • "The higher the risk, the higher the intensity, experts are really great here."
  • Product experts: per-user expertise files powering adaptive, generative UI — "personalization to the max"
◴ skip the expert when
  • The problem doesn't evolve
  • Simple or brand-new codebases
  • "If you yourself do not have a mental model in place... you will build an expert that can't solve the problem because you can't."
  • Known trade-offs: seeding, the "another source of truth" objection, finite context, false expertise, too-granular expertise, too many experts

The Nuggets

01

Agents forget

"Traditional software improves as it's used... Agents of today don't. Your agents forget. And that means your agents don't learn."

In their DNA

"You don't need to tell an expert to learn. It's in their DNA." — "Real experts don't relearn their craft every time they have a new task."

The differentiator

"It first reads this expertise file... It didn't need to go search or find these files. It knew where they were. This is the differentiated factor of an agent expert."

Surgical changes

"I get super hyped when agents change just the right things... I wanna see surgical changes."

05

Revenue-catching

"My agentic experts have caught revenue changing details in these systems."

06

Compounding value

"If your product is successful, it will grow in complexity and speciality. As that happens, agent experts become more and more valuable."

◵ expertise files
  • "Expertise requires breaking rules when the time is right"
  • Loaded by the expert's own prompts, when relevant

The Workout

GOAL Stand up one complete agent expert (Act–Learn–Reuse) for a real domain in your codebase — e.g. your database layer.
PREREQUISITES AH-2 prompt formats internalized; a codebase with a non-trivial subsystem you understand well — you need your own mental model first.

  1. Scaffold the expert

    Create .claude/commands/experts/database/ with four files: expertise.yaml (empty), question.md, plan.md, self-improve.md.

  2. Write self-improve.md — the heart

    Variables, instructions, and the six-step workflow ending in the wc -l line-limit check + YAML validation. See the skeleton alongside.

  3. Seed

    Run /experts:database:self-improve on the empty file. Let the agent invent the structure. Rerun until it reports "nothing to be done."

  4. Write question.md

    "IMPORTANT: question-answering only — DO NOT write/edit files"; "validate the information from EXPERTISE_PATH against the codebase before answering"; report = direct answer + file/line evidence + mermaid where useful. Ask it a hard question; confirm it reads expertise first and skips searching.

  5. Chain it

    plan.md reads expertise before planning; plan_build_improve.md runs Task → plan, Task → build, Task → self-improve true. "DO NOT STOP between steps."

  6. Ship one real change

    Then git diff the expertise file to inspect exactly what the agent learned.

  7. Correct the teacher, not the notes

    If the expertise is wrong or too verbose, do NOT edit the YAML — edit self-improve.md and rerun.

.claude/commands/experts/database/self-improve.md
---
allowed-tools: Read, Grep, Glob, Bash, Edit, Write, TodoWrite
---
# Self Improve

## Variables
CHECK_GIT_DIFF: $1 (default false)
FOCUS_AREA: $2
EXPERTISE_FILE: .claude/commands/experts/database/expertise.yaml
MAX_LINES: 1000

## Instructions
- Think of the expertise file as your mental model,
  not a source of truth.
- Prioritize actionable, high value expertise over
  verbose documentation.
- There may be nothing to do — this is perfectly acceptable.

## Workflow
1. git diff (conditional)   2. read expertise
3. validate vs codebase     4. identify discrepancies
5. update                   6. wc -l line check + YAML validation

The learn step is a prompt like any other — which means your expert improves whenever you improve this file.

DONE WHEN The question prompt answers from the mental model with correct file/line citations; a plan → build → improve run ships a change AND the expertise diff shows only accurate, surgical updates; expertise stays under MAX_LINES with valid YAML.
LEVEL UP Build a meta expert — a template meta prompt that scaffolds question/plan/self-improve/expertise for any new domain — then add a second expert for your highest-risk system (billing/security) and wire both into your O-Agent as agent templates.
