See everything your agents do

yt-01 · I Can SEE EVERYTHING — Claude Code Hooks for Multi-Agent Observability

Once you scale past one Claude Code instance, observability is everything — hooks streaming every lifecycle event into a one-way client/server pipeline let you "see everything" your agents do.

"When it comes to multi-agent systems, observability is everything." Running a single agent "is just the beginning."

The architecture is deliberately minimal: hooks fire an HTTP POST to a Bun server, which persists to SQLite and streams over WebSocket to a Vue client. "This one-way data stream keeps things really simple." Every hook event is tracked — PreToolUse, PostToolUse, Notification, Stop, SubagentStop, PreCompact — with a session ID and source app on every row.

The whole stack, drawn. Hooks → HTTP POST → Bun → SQLite + WebSocket → Vue. No framework magic, no return path.
01

Color by hash

Hash the app name + session ID into a color so you can visually tell agents apart at a glance — cheap UX that matters at 5–10 agents.

02

Haiku summarizes first

Each event runs a summarization prompt via a small fast model before sending — "thousands of events... less than 20 cents." "This is where small fast models really shine."

03

Stop = the full transcript

The Stop event carries the full chat transcript path — the perfect time to copy the entire log and filter it: all reads, all globs, all assistant responses.

  • Hooks give "deterministic control over Claude Code's behavior" — steer, monitor, control.
  • "Frameworks are irrelevant when it comes to raw productivity. Your agent knows all of them" — the Vue client is disposable; convert it to any framework with a prompt.
  • The codebase-wrapping agentic layer (.claude/, hooks, apps) is a new layer around your code that "will change the way you engineer forever."
  • Endgame: "prompting back and forth, one prompt at a time is not the way to engineer. It's a great place to start. It's a terrible place to finish." Push toward off-device, fully programmable agentic coding.

"If you don't measure it, you can't improve it. If you don't monitor it, how will you know what's actually happening?"

A new engineering primitive

Claude Code isn't a tool or an assistant — it's a new engineering primitive, programmable from any terminal, and betting on that architecture is how you position for what's next.

"Just like deep learning worked, the agent architecture worked."

This is phase 2 of the generative AI age: we're not chatting with LLMs, we're "commanding compute." And the primitive has exactly three essential elements — powerful LLMs, the right tools, and the agent loop. "You can't have one of these. You can't have two of these. You need all three."

The architecture is everything.

— the three-element thesis, yt-02

Powerful LLMs

Agents building agents

yt-03 · My Claude Code Sub-Agents BUILD THEMSELVES

Sub-agents are tools of delegation for your primary agent — you write their system prompts, they respond to the primary agent (not to you) — and a meta-agent can generate new sub-agents on demand.

◴ the two big mistakes
  • Treating the agent .md file as a user prompt you're sending.
  • Assuming sub-agents report back to you.
◵ what's actually true
  • The .md file is the sub-agent's system prompt.
  • Sub-agents respond to the primary agent — "the flow of information here is absolutely critical."

The description field is the routing contract.

It's what the primary agent reads to decide when to invoke a sub-agent. Encode trigger phrases ("If they say TTS, TTS summary, use this agent") and even how to prompt it ("When you prompt this agent, describe exactly what you want them to communicate"). Raise adherence with Anthropic's information-dense keywords (IDKs): "use PROACTIVELY", "MUST BE USED", "IMPORTANT:". And write the report section explicitly: "Claude, respond to the user with this message."

Flow of information. You → primary → sub-agent → primary → you. Engineer both hops explicitly.
01

The meta-agent

A sub-agent whose system prompt knows how to generate complete new sub-agent files from a description — "my agents are building my agents." Dan has built 50–100+ agents with it. It re-pulls live Claude Code docs rather than trusting stale context.

02

Problem → solution → tech

Workflow discipline, in that order. "Noobs and beginners start with the technology and work backward." Validate the workflow manually in the primary agent first (run the ElevenLabs tools by hand), then encode it into an agent.

03

Context preservation — and the trap

A sub-agent has its own isolated context window, saving your primary's — but "it has only what your primary agent prompts it with": equivalent to a one-shot claude -p call with zero history.

  • Cons to watch: hard to debug (you don't see internal prompts/params); decision overload as agent count grows; dependency coupling in chained agents — "you're going to change the planner agent and it's going to ruin everything else"; and sub-agents can't call sub-agents.
  • Use /all_tools-style listing prompts to discover MCP tool signatures before wiring agents to them.
  • The only rule that scales: keep sub-agent workflows isolated and focused — "a focused agent is a performant agent" (foreshadows yt-09).
  • "If deleting causes you pain, you probably aren't deleting enough."

"Code is a commodity. Your fine-tuned prompts can be valuable."

— yt-03, on what to actually keep

Weak, base, strong

yt-04 · I'm ADDICTED to Claude Code — Rate Limits, Agent Models, and CC Alternatives

With sub-agent model selection you should run a weak/base/strong model stack — the right model for the job — while diversifying away from over-dependence on any one tool as rate limits arrive.

"Weak, base, strong. Three levels of model control."

Model selection solves two problems at once: model overkill (wasted tokens and money) and model underperformance (wasted time). Behind it sits the eternal trade-off triangle — performance, speed, cost — plus a "hidden fourth dimension": rate limits. And when it matters, "performance over everything": "When I want to use the best, I don't hesitate... You pay to play."

Haiku
weak — file naming, moves, quick summaries (CC's one-word status popup is a Haiku call)
Sonnet
base — the workhorse: "what model is responsible for the most code in the world... very clearly Sonnet 4"
Opus
strong — pedal to the metal, + thinking mode for serious/production work

Thinking mode is a second axis on top of model choice: "Sonnet 4 thinking beats Opus 4 base." IDKs: think hard / ultrathink.

01

A/B/C-test with thin wrappers

One shared prompt across models: cryptocoin-analyzer-haiku/-sonnet/-opus all reference the same _agent_prompt.md. Only the model, name, and color change. Test sub-agent prompts at the top level first — run the isolated prompt in a primary agent end-to-end before burying it in a sub-agent.

02

Grade strength by format obedience

Haiku goes off the rails, Sonnet gets close, Opus matches the header exactly. "You can always check for model strength by looking to see if it can obey your output formats." His prompt anatomy everywhere: Purpose / Variables / Workflow / Output format — "Output format... forces your agents to report their output."

  • We're "clawholics" — overexposed, too many eggs in one basket. "If you're an industry leader, you will always be copied and cloned." Diversify (Qwen3 Coder, Gemini CLI, open source) — "but let's be super real, no one is close to Claude Code."
  • Reusable prompts (custom slash commands) + sub-agents = the way to scale compute: prompt-chaining and fusion-chaining with bigger compositional units.

"There's nothing more important in the generative AI age as an engineer than your ability to scale up compute and use it to solve real engineering problems."

Flatten the field, then judge

yt-05 · GPT-5 Agentic Coding with Claude Code

To judge agentic models fairly you must flatten the playing field — a minimal "nano agent" MCP server gives every model the same context, tools, and prompt, then Claude Code (Opus 4.1) plays LLM-as-judge on performance, speed, and cost.

"It's not about a single prompt call anymore. It's about how well your agent chains together multiple tools to accomplish real engineering results."

"A single prompt eval is not enough anymore." The rig is HOP/LOP: a higher-order prompt (grading rubric, S–F grades, orchestration) that takes lower-order prompts (individual benchmark tasks) as input — a reusable eval harness in pure prompts. The nano agent itself is a micro Claude Code: one MCP tool (prompt_nano_agent) wrapping an OpenAI Agents SDK loop with ~7 primitive tools (read, write, list, edit...). Same scaffolding for every model = a fair fight.

The fair fight. One rubric, one task, identical nano-agent scaffolding per model, one judge.
  • Judged as a package (perf + speed + cost), GPT-5 nano/mini beat the giants on simple agentic tasks; judged on raw performance, Opus 4.1 / Opus 4 / Sonnet 4 stay S-tier. Both things are true — grade against the trade-off you care about.
  • GPT-OSS 20B/120B on an M4 Max (128GB, via Ollama/LM Studio): "viable agentic coding happening on device right now... total cost: $0."
  • Instruction-following is the eval: exact response formats, exact file outputs ("MODEL_NAME was here") — Sonnet lost points for preamble; nano nailed the format.
  • "Don't trust any individual benchmark. It's their job to tell you that they're doing a great job... crack open the hood of all these models." Most engineers can't feel what "+2% on a benchmark" means in agentic work — "it's actually massive." Run models on real problems to know.
  • It isn't just the model: "there's a lot of work that goes into something like Claude Code to make it the best... most consistent agent." Keep the SOTA top-level agent; delegate selected tasks downward. The OpenAI Agents SDK is a great way to learn the year's most important architecture — the agent loop — by building one. "The true value proposition of models is being exposed. It's real work end to end."

Atomize your units of compute so you can test them and scale them up.

Raise the information rate

yt-06 · Engineers… Claude Code Output Styles Are Here — Don't Miss This TREND

Output styles — system-prompt-level control of how the agent responds — plus stateful status lines increase the information rate between you and your agents. And the HTML style is the first useful generative UI.

"Never bet on your first initial reaction without doing the work."

Dan thought output styles were useless — until a dev session proved otherwise. They literally swap the system prompt: "I'm really happy that they're being clear about the fundamental unit this is updating." Big Three thinking makes new features instantly legible. Six styles demoed: default, table, YAML, ultra-concise, TTS summary, HTML. YAML "typically outperforms the rest" — highly structured output formats can improve agent performance — and ultra-concise cuts token consumption. Remember: "New features are only valuable in relation to existing features" — output styles × hooks × status lines compound.

"This is the first useful application of generative UI. This is not a gimmick."

— the GenUI style: the agent writes an HTML file per response and opens it, building UI on the fly
01

Better agents → output formats

"Two directions to grow: better agents or more agents. Output formats help us with better agents." Extension idea: conditional branches inside the output-style system prompt to pick the output type per prompt.

02

More agents → status lines

A status line is just a script that prints anything; combine it with a UserPromptSubmit hook writing per-session JSON state to show the last prompt (and trailing 3) per instance. Killer when juggling 3–10 instances: glance and know what each was doing. A local Ollama model generates one-word agent names (5-second timeout, fallback) — small local models for tiny jobs.

  • The /quest question prompt primes your agent while extracting decision-grade info — "ultra valuable for speeding up the information flow between you and your agent," and great for team onboarding.
  • Hot take / warning: Opus-plan-mode and background bash feel like "the beginning of loss of directional focus" — opinionated overreach. The guiding question for any feature: "Do I know exactly what the context, model, and prompt are at every step of the process?" Anything that obscures the Big Three is a red flag.

Increase the information rate between you and your agent.

The five-pattern ladder

yt-07 · 5 Agent PATTERNS to Simplify Your Agentic Coding

There are five agent interaction patterns — ad-hoc human-in-the-loop, reusable prompts, sub-agents, wrapper MCP server, full application — and you climb that ladder left-to-right only as the problem earns it. The bet behind everything: "a majority of the economic value of AI will come from AI agents."

The ladder. "Keep it simple, scale when needed... always go from left to right, never right to left."

  1. Iterative human-in-the-loop

    High control, but "you are quite literally stuck in the loop... you are in fact the bottleneck." Great start, terrible end.

  2. Reusable prompts (slash commands)

    "The 80/20 of agent interaction patterns... write it once, reuse all the time." "Three times marks a pattern" — automate on the third repetition.

  3. Sub-agents

    The decision rule is crisp: "only use sub-agents when you need specialization and parallelization. If you don't need to parallelize and you don't need to specialize, just create a reusable prompt." Every sub-agent is another context/model/prompt to manage — plus Claude Code lock-in, the "gray box" debugging problem, and the primary↔sub prompt flow you must engineer.

  4. Wrapper MCP server

    Build when you must integrate multiple services or expose repeat functionality behind your own interface. "The MCP server is an interface layer." Sleeper feature: MCP prompts — "the real value of the MCP server is in the prompts that represent the reusable workflows of specific tool calls... insanely underrated, insanely underused."

  5. Full application

    CLI + MCP + UI + API — only with a long-term vision or non-engineering consumers. "What's the difference between a customer-facing application and a developer tool? It's the interface layer."

  • "Larger working systems are almost always built from simple working systems." / "Don't overengineer. Let the patterns emerge naturally from usage."
  • Skipping levels 1–2 means "there are things you don't know about the problem... because you didn't do it by hand" — where "by hand" now means with your agent in the loop.
  • For the images-for-a-presentation example he'd stop at level 2, go to 3 only for 100+ images, and 4 only when other services join.

Complexity should be earned, not assumed.

— the master framework of yt-07

Reduce & Delegate

yt-09 · Elite Context Engineering with Claude Code

"A focused agent is a performant agent" — context engineering is managing the context window with only two moves, R&D: Reduce and Delegate, applied across beginner → intermediate → advanced → agentic levels.

"There are only two ways to manage your context window: R and D — reduce and delegate."

Reduce #1 — don't preload MCP servers. A default mcp.json ate 24.1k tokens (12% of the window) before work began. Delete it; load per-task with claude --mcp-config <file> (+ --strict-mcp-config to override globals). Reduce #2 — context priming over CLAUDE.md. "A CLAUDE.md file is incredible for one reason: it's a reusable memory file that's always loaded. Simultaneously it's terrible for the exact same reason." Memory files only ever grow (his bloated demo: 23k tokens ≈ 10% of the window). The rule: "only the absolute universal essentials that you're 100% sure you want loaded 100% of the time" — his trimmed file is 43 lines / ~350 tokens. Context priming = per-task-type /prime slash commands (prime_bug, prime_feature, prime_cc...) — "your hot-loading memory file," fully controllable per run.

R&D. Everything in context engineering is one of these two moves.
L1

Beginner · Reduce

Kill the default mcp.json; trim CLAUDE.md to universal essentials; prime per task with /prime commands.

L2

Intermediate · Delegate

Sub-agents are "a partially forked context window" — definitions are system prompts, costing the primary ~122 tokens for three agents. /load_ai_docs fanned out ~10 scraper sub-agents, keeping ~40k scrape tokens out of the primary.

L3

Advanced · Bundles

Hooks append a trimmed log (prompt + reads/searches, not writes) per session; after a context blowout, /load_bundle <path> re-mounts a fresh agent to ~60–70% of the prior agent's state.

L4

Agentic · Background

/background boots a whole background Claude Code instance (via CLI/SDK) with a report file it must write to and rename on completion — "compute orchestrating compute, agents orchestrating agents." Get out of the loop.

  • If you're losing track of a single agent's context, "you probably aren't yet ready for sub-agents" — master one window first. Track every agent's core four: context, model, prompt, tools.
  • The scaling-law justification: model performance degrades as context grows — "it's a safe bet to bet on context engineering."
  • Ladder mantra: "What's better than a prompt? A prompt chain. What's better than a prompt chain? An agent. What's better than an agent? Many focused, specialized agents."
  • Teaser: agent experts (.claude/commands/experts/ with expertise.yaml + self-improve) as potentially the most powerful technique.

"It's not necessarily about saving tokens. It's about spending them properly. We manage our context window so that we don't waste time and tokens correcting our agents' mistakes."
