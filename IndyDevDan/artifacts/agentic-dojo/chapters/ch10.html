The Idea — Reduce & Delegate

A focused agent is a performant agent.

Obsessively measuring and managing context is what separates agentic engineering from vibe coding. Every one of the twelve techniques in this lesson fits into one or both of two buckets: Reduce what enters the window, or Delegate work into other windows. What accumulates when context isn't laser-focused is context rot and context bloat — and "search and destroy is the real skill in context engineering."

"There are only two ways to manage your context window, R and D: reduce and delegate."

— quote of the lesson
The R&D framework. One window, two levers — every context-engineering move is a reduce, a delegate, or both.
The four levels. "There are three levels of context engineering and a fourth hidden level if you're on the bleeding edge."

Underneath it all sits the Core Four — context · model · prompt · tools. "When aligned with the right model, prompt, tools and the right range of context, we can hit the core four bullseye over and over."

The target is the context sweet spot — "a range of context where your agent performs to its maximum possible capability for the task at hand." Hitting it once is easy; hitting it consistently matters more as you scale to hundreds or thousands of executions.

The sweet spot fails on both sides: too little context and the agent guesses; too much and you get context rot — which is why technique one is always measure.

The 12 context engineering techniques, beginner → agentic

01

Measure your context

/context + an IDE token counter — "your most important tool for measuring and therefore managing your context window."

02

Purposeful MCP

Delete the default .mcp.json; load servers by hand with --mcp-config + --strict-mcp-config.

03

Priming over memory

"A dedicated reusable prompt… to set up your agent's initial context window specifically for the task type at hand." Prime, don't default.

04

Output styles

Output tokens cost 3–5x input. A "concise done" style cut a 150-token response to 2 — ~99% reduction.

05

Sub-agent delegation

Sub-agents are system prompts with a "partially forked context window." They respond to your primary agent, not to you.

06

Planner / builder

"One agent plans, the other agent executes the plan… an architect and an editor." Prompt chaining across two windows.

07

Reset + prime, not /compact

"After compact runs, do you know exactly what's in your context window every single time? No." /clear, then /prime. "Stop guessing and start knowing."

08

Context bundles

Hook-generated append-only logs per session; /load_bundle remounts a fresh agent to ~70% of the previous state.

09

One agent, one purpose

"There's no better way to control and manage your context window than to ship one thing at a time."

10

System prompt control

--append-system-prompt in print mode; the SDK's custom_system_prompt blows the whole system prompt away — "use this with caution."

11

Primary multi-agent delegation

A /background command boots a full background instance with its own prompt, model, report file. "Compute orchestrating compute."

12

Agent experts

"Fire off specialized agents that are experts at specific parts of your codebase… you have them auto update their own knowledge." Plan → build → improve.

The game

"Context engineering is the name of the game for high value engineering in the age of agents."

A temporal resource

"Your agent's context window is a precious, renewable, but limited temporal resource."

Measure it

"What gets measured gets managed. So measure your context window."

Or you're vibe coding

"If you aren't actively paying attention to the state of your agent's context, you're just vibe coding — and you'll only be able to tackle the lowest hanging fruit."

The real trick

"Adding the right context is usually the easy part. The real trick is finding the context agentically and then removing and delegating it."

The memory-file paradox

"The claude.md file is incredible for one reason: it's a reusable memory file that's always loaded. Simultaneously it's terrible for the exact same reason."

Always-on only grows

"The problem with always-on context is that it's not dynamic or controllable… the claude.md file only grows." Worst case: contradictory information in the window.

Universal essentials only

Shrink your memory file "to contain only the absolute universal essentials that you're 100% sure you want loaded 100% of the time."

Don't waste the window

"There are many places to be wasteful as an engineer… The context window of your agents is not one of them."

Track the flow

"The flow of information in these multi-agent systems is critical" — if you lose track of a single agent's core four, you're not ready for sub-agents.

Go overboard, then delete

"By the end of your planning phase you should be deleting information that isn't relevant… go overboard, then delete."

Operate the layer

"You want your agentic layer operating your codebase and you operate the agentic layer."

The standing question

"The focus should always be: better agents or more agents?"

Spend, don't hoard

"It's not necessarily about saving tokens. It's about spending them properly."

The escalation

"What's better than a prompt? A prompt chain. What's better than a prompt chain? An agent. What's better than an agent? Many focused, specialized agents."

Do the hard part

"If it's easy, a vibe coder is probably doing it — and that isn't irreplaceable."

What Dan Did

The full demo runs in disler/elite-context-engineering — twelve techniques, in order, on a live window.

  1. Measured on boot

    Ran /context: 63K tokens (31%) already gone — diagnosed MCP tools (24.1K) and CLAUDE.md (23K).

  2. Cut the MCP load

    Deleted the default .mcp.json; relaunched loading only Firecrawl (~4–6K tokens, suffix-labeled in the filename).

  3. Swapped the memory file

    claude.large.md → a 43-line claude.concise.md (350 tokens, 0.2%) → 92% free window on boot.

  4. Primed instead

    Ran /prime and /prime_cc — stacked prime commands with purpose / run / read / report structure.

  5. Output-style duel

    Side-by-side Sonnets, same codebase question: default vs a "done" output style — 150 output tokens vs 2.

  6. Sub-agent fan-out

    /load_ai_docs fired ~10 doc-scraper sub-agents to refresh ai_docs/ after a 24-hour staleness check; the primary window stayed at ~9K.

  7. Planner / builder

    /quick_plan (Opus) spec'd a 3-file TypeScript SDK wrapper; a fresh instance ran /build <spec> with zero priming, then ran it with bun.

  8. Reset over compact

    /clear + re-prime instead of /compact (Ctrl+R to inspect the compact summary first).

  9. Context bundles

    Inspected the per-session JSONL trail, then /load_bundle <path> replayed prior state into a fresh agent.

  10. System prompt control

    claude -p with an appended rule — "read in increments of 100 lines" — verified obedience in the bundle (read 100, read 100…).

  11. Backgrounded a plan

    /background — a background instance wrote a Python (uv/Pydantic) SDK-wrapper plan to a report file, renamed on completion.

  12. Agent experts preview

    The hooks expert ran plan (with an Expertise section) → build in a fresh instance (one-shot) → improve (reads git diff, updates the expertise sections).

The Workout

GOALCut your Claude Code boot context by >50% and replace always-on memory with priming, then delegate one job to a background context window.
PREREQUISITESClaude Code installed; any repo with a .mcp.json and/or CLAUDE.md; an IDE token counter extension.

  1. Baseline

    Run claude then /context. Record: total %, MCP tokens, memory-file tokens.

  2. Reduce MCP

    Move .mcp.json to .mcp.firecrawl.json (or per-server files). Relaunch with --mcp-config … --strict-mcp-config; re-run /context and confirm the drop.

  3. Trim the memory file

    Cut CLAUDE.md to <50 lines of universal essentials. Move everything else into .claude/commands/prime.md (Purpose / Run / Read / Report) plus a scoped prime_<area>.md.

  4. Control output

    Create .claude/output-styles/concise-done.md: "respond only with 'done' on success; explain only on failure or questions." Set it in a settings file; compare output tokens on the same prompt vs default.

  5. Planner / builder

    Write quick_plan.md (writes specs to specs/) and build.md (takes $1 = plan path, early-returns if missing). Plan in one terminal, /clear, build in a second.

  6. Go background

    Write background.md that shells out claude -p "<prompt>" --append-system-prompt "report progress to <report file>; rename file with -complete suffix when done" &. Fire one plan job through it.

  7. Break the compact habit

    On your next long session: /clear then /prime instead of /compact. Note the difference in confidence about window contents.
