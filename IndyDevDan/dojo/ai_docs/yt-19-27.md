## YT-19: E2B Agent Sandboxes: The Space to Place your Claude Agents
**Upload:** 2025-11-17 · 26:00 · https://www.youtube.com/watch?v=1ECn5zrVUB4

**Thesis:** Give each agent its own ephemeral cloud computer (agent sandbox) and you can solve one problem many times in parallel — isolation, scale, and agency are the natural next step after orchestration.

**Nuggets:**
- Agent sandboxes give your agents three things: **isolation, scale, and agency**. Dedicated environments that are "safe, destroyable, ephemeral."
- "Think about your agents as deletable resources with a single purpose" — spin up, do work, spin down; this bypasses many context problems instantly.
- **Best-of-n pattern:** "We can now solve one problem many times with compute." Run 3 prompt variants × 3 forks = 9 agents; LLMs are non-deterministic, so triple the attempts and pick the winner. Expect "complete duds" — that's fine, dismiss them fast.
- Real demo: turned a Reddit roast of his course landing page into 3 concrete prompts, spun 9 sandboxed agents, each cloned the repo, made fixes on its own branch, opened a GitHub PR, and hosted a public preview URL on e2b.app.
- Architecture layering: **CLI → wrapped by MCP server → (optionally) skill**. The CLI holds the key commands; the MCP wrapper lets any agent peer into a live sandbox.
- The sandbox fork agent is a **true custom agent** — its system prompt "completely overrides the Claude Code system prompt"; specialized to do one thing extraordinarily well.
- Sandboxes have lifetimes (1,800s here). They expire like the agents that own them.
- Once you deploy many versions, the bottleneck flips: "Planning and reviewing are the big areas of focus for engineering with agents" — this tooling turns generation into a review constraint.
- Trade-offs: costs API money (no Max/Pro subscription), and "you have to engineer your sandbox."
- Only Fortune-100s / big labs use this today (it's what Manus/ChatGPT/Claude run when they execute code) — "keep your eyes on this trend."
- "Engineering is about much more than just writing code" — research, RL, computer use, data analysis, planning, reviewing, prototyping.
- "The agent is the best tool for the job of engineering. How well can you use the best tool? This is the measure of our impact."

**Tools/tech:** E2B (sandbox host; also mentions Modal), Claude Code (Sonnet, YOLO mode), Claude Agent SDK custom agent, orchestrator-agent pattern (`prime obox` / outbox agent), CLI+MCP wrapper, GitHub PRs, best-of-n.

**Repo:** `disler/agent-sandboxes` — the sandbox orchestration codebase: `ox` CLI workflow (repo URL + branch + model + forks + prompt), sandbox-fork agent system prompt, MCP wrapper over the sandbox CLI, log playback per fork.

**Drill:**
1. Clone `agent-sandboxes`, get an E2B API key, and read `sandbox workflow` + the fork-agent system prompt.
2. Run one `uv run ox <github-url> <branch> "<prompt>" --model haiku --forks 4` against a toy repo.
3. Watch the 4 sandboxes appear in the E2B dashboard; open each hosted public URL.
4. Have the orchestrator agent review the logs and open the 4 PRs in Chrome.
5. Pick the best fork (best-of-n), close the dud PRs.
- **Done when:** 4 parallel forks each produced a branch + PR + live preview URL, and you selected one winner without touching the code yourself.

## YT-22: RAW Agentic Coding: ZERO to Agent SKILL
**Upload:** 2025-12-08 · 50:23 · https://www.youtube.com/watch?v=X2ciJedw2vU

**Thesis:** Building a skill from scratch — pen-and-paper plan first, then skill.md + tools + prompts + cookbook — is the fundamental craft; skills matter because they package reusable prompts and code against a use case, and everything reduces to the core four.

**Nuggets:**
- Process starts off-computer: "Push the laptop aside... we never start by just blasting out prompts." Notebook first: purpose, problem, solution. "Begin with the end in mind" — define the concrete output structure (the exact file tree) before any prompting.
- "Those who plan the future tend to create it." And on skill atrophy: "Engineers' brains are rotting due to this incredible technology... always understand what you're asking your agents to accomplish."
- **Canonical skill anatomy:** `skill.md` (the "pivot file" everything centers on) + `tools/` (single-file scripts, uv Python) + `prompts/` (explicitly named `*_user_prompt` vs system prompts) + `cookbook/` (per-use-case docs, progressively disclosed).
- The **cookbook pattern** = conditional prompts: "if user requests X and enable_X is true, then read <file>" — routing + progressive disclosure. "A conditional prompt — that's what progressive disclosure is."
- Enable flags as static variables in skill.md (`enable_gemini_cli: true` etc.) let you toggle capabilities without rewriting.
- **Prototype in the loop, then encode:** "Have your agent just run it in the loop, write the prompt, observe the result, and then encode it in a skill." (osascript to open Terminal windows was validated live first.)
- Teach agents tools via `--help`: "Before executing the command, run `command --help`" — trades speed/context for reliability on fast-changing CLIs the model hasn't seen.
- Information-dense keywords: "Astral UV single file script," "subprocess," a Python function signature — each carries embedded meaning the model already knows. Know your model's training cutoff.
- Agentic code = code that reports: capture stdout+stderr and always return a string "so we can get concrete output every time it runs."
- Debug order: "Don't assume it's the model's fault. First assume it's your fault, then... the tooling's fault."
- Skills don't hot-reload in Claude Code — restart the session after editing skill.md (metadata loads at boot).
- Fork-with-summary = manual `/compact`: a YAML template meta-prompt (history: summarized user prompt / response summary pairs + next request) that the base agent fills out and passes as the fork agent's starting prompt. "The key is always to remember who's writing to who."
- Aim for proof-of-concept → MVP; "the simplest working version that gets our agents operating properly." Fresh context windows per task: "It's easy to know what your agent has seen when it's seen nothing."
- "Everything always boils down to the core four: context, model, prompt, tools. If you master these, you'll master the agent, you'll master engineering."

**Tools/tech:** Claude Code (Sonnet 4.5), Cursor tab-completion, code snippets (AGP agentic-prompt, AG-SK skill template), osascript, Astral UV single-file scripts, Gemini CLI / Codex CLI / Claude Code as fork targets, `/prime` prompt, git checkpoint hotkey (GSTC).

**Repo:** `disler/fork-repository-skill` — the fork-terminal skill built live: skill.md with enable flags, `tools/fork_terminal.py` (uv + subprocess + osascript, Mac/Windows), cookbook for raw CLI/Claude/Codex/Gemini with fast/base/heavy model variables, and the fork-summary user prompt for context-window forking.

**Drill:** (highest replication value of the batch)
1. On paper: write purpose/problem/solution and the exact file tree for a small skill of your own (or re-derive fork-terminal).
2. Scaffold `.claude/skills/<name>/` with skill.md (description states trigger phrases), tools/, prompts/, cookbook/; verify it appears via an "all skills" prompt (restart the session).
3. Validate the core mechanic in-loop first (e.g., `use osascript to open a new terminal and run ffmpeg --help`), then encode it into the tool script + cookbook.
4. Add the `--help`-before-execute rule and one conditional cookbook route with an enable flag.
5. Add the fork-summary YAML meta-prompt; test: chat a few turns, then "fork session codex fast, summarize work done, <next task>" and confirm the new agent receives the summarized history.
6. Iterate on failures by fixing your prompt first, not blaming the model.
- **Done when:** the skill triggers on its keywords, routes via the cookbook, opens a working forked terminal in the cwd, and a summarized fork carries the conversation into a fresh agent.

## YT-23: Agent Experts: Finally, Agents That ACTUALLY Learn
**Upload:** 2025-12-15 · 18:54 · https://www.youtube.com/watch?v=zTcDwqopvKE

**Thesis:** The massive unsolved agent problem is that agents forget; the fix is agent experts — self-improving template meta-prompts that maintain their own expertise file (a mental model of one domain) and update it automatically after every job, no human in the loop.

**Nuggets:**
- "Your agents forget. And that means your agents don't learn." Traditional software improves with use; agents of today don't.
- Existing tools all fail the same way: memory files are "global forced context that always loads" (and expertise requires breaking rules); prime prompts, sub-agents, and skills all "have to be manually updated."
- "The difference between a generic agent and an agent expert is simple. One executes and forgets, the other executes and learns."
- "You don't need to tell an expert to learn. It's in their DNA." Real experts don't relearn their craft per task; they update a mental model — "a data structure that evolves over time."
- Definition: "The agent expert is a concrete form of a self-improving template metaprompt."
- **Meta-agentics first** (prompts writing prompts, agents building agents, skills building skills): "There is no codebase I create that does not have meta-agentics." But meta-agentics alone aren't experts — "they're acting, but they're not learning."
- Anatomy: `.claude/commands/experts/<domain>/` with `expertise.yaml` (the mental model), `question.md`, `plan.md`, `self-improve.md`. The question prompt's first workflow step: read the expertise file, then "validate assumptions against the codebase."
- The expertise file is **not another source of truth**: "The true source of truth is always the code... You don't have a source of truth in your mind. You have a working memory file. You have a mental model."
- Payoff: "There's no searching here. There's just validating its mental model" — the websocket expert knows where everything is and one-shots plan→build→improve.
- The three-step expert workflow chains sub-agents: plan (~80k tokens, context protected from the top-level agent) → build against plan → **self-improve** (diff-driven expertise update). Learning is a mandatory final step, not an afterthought.
- Scale for confidence: fire the same question at 3 (or 5, or 10) experts and cross-validate — "sometimes if you throw five agents at the problem, only one makes it... you compose that together, you get a better result."
- "Three times marks a pattern" — once you build something repeatedly, move it into automation (he has a meta-expert that generates experts).
- Abstraction agnosticism: "Build a skill if you want, build a custom agent if you want... I always focus on the foundational units: context, model, prompt, tools."

**Tools/tech:** Claude Code slash-command prompts, expertise.yaml, meta-prompt/meta-agent/meta-skill, multi-agent orchestrator app (Agentic Horizon lesson 4; Opus orchestrator, Postgres, websockets), sub-agent chaining, mermaid-diagram question prompt.

**Repo:** `agentic-horizon/agent-experts` (local course repo, symlinked) — experts for database and websocket domains: expertise.yaml + question/plan/self-improve prompts, plus the meta-agentics (meta_prompt, meta-agent, meta-skill) and the orchestrator app they operate on.

**Drill:**
1. In the agent-experts repo, read `.claude/commands/experts/websocket/` — expertise.yaml, question.md, self-improve.md.
2. Pick one domain in your own codebase (e.g., API layer). Create `experts/<domain>/expertise.yaml` seeded by an agent scan of the code.
3. Write a `question.md` whose workflow is: read expertise → validate against code → answer. Ask it 3 architecture questions; note it never searches.
4. Write `self-improve.md` that takes a git diff and updates expertise.yaml.
5. Chain plan → build → self-improve on one small feature; confirm expertise.yaml changed without you editing it.
- **Done when:** after a build, the expertise file was updated automatically by the agent, and a follow-up question answers correctly from the updated mental model.

## YT-26: Claude Code is Amazing... Until It DELETES Production
**Upload:** 2026-01-05 · 22:23 · https://www.youtube.com/watch?v=VqDs46A8pqE

**Thesis:** One hallucinated command can evaporate years of work, so layer deterministic pattern-blocking hooks, ask-permission patterns, path protection, prompt hooks, and global hooks into every production codebase — damage control is how you remove the need for trust.

**Nuggets:**
- "It doesn't matter how fast, powerful, or autonomous your agents are. All of your months and years of hard work can be evaporated in a single misinterpreted or hallucinated command."
- The stack (4 damage controls): local project hooks, **global (user-level) hooks** that apply device-wide, ask-permission patterns, and the **prompt hook** most engineers don't know exists.
- Prompt hook = an LLM prompt run as a PreToolUse hook on every bash command — catches destructive commands "even though it's never seen it before." It's the "last-ditch effort... as soon as you find that command, you should add it to your deterministic hook."
- Layered wrapper: `settings.json` hooks (PreToolUse matcher on Bash/Edit/Write) → uv/bun scripts → a **patterns.yaml** file with: blocked command regexes, `ask: true` patterns (agent must confirm with you), `zero_access_paths` (no read/write at all, e.g., .ssh), `read_only_paths` (e.g., .bashrc), `no_delete_paths` (hooks, commands).
- Hooks in settings run **in parallel** — whichever finishes first wins the block.
- "Not everything is a 100-to-zero command" — ask-patterns cover the gray zone (e.g., SQL DELETEs on a prod-like DB).
- `/install` interactive-installation pattern: an agentic workflow using the AskUserQuestion tool (global/project/personal? Python/TypeScript? merge/override existing settings?) — a reusable way to ship skills to a team. Nine-step cookbook drives it.
- "You just don't want to think about your security over and over. You just want great defaults, and then run with it."
- Confession that motivated it: "A few weeks ago, I almost ran a command that would have been catastrophic in one of my production applications."
- Trust framing: "You can build trust or you can defer it or you can make sure that you don't need trust." Hooks = not requiring trust; sandboxes = deferring it ("so they don't even need damage control").
- Odds math: "One out of 100,000 — that's enough to really ruin your day." At hundreds of thousands of tool calls, you will hit it.
- Yes the prompt hook is slow, "but running this prompt every single time is going to be faster than potentially deleting a valuable production asset."
- Claude Code itself has good trained-in protections (it backed up .bashrc unprompted) — but "there's going to be a moment where you miss something and your agent misses something."

## YT-27: AGENT THREADS. How to SHIP like Boris Cherny. Ralph Wiggum in Claude Code.
**Upload:** 2026-01-12 · 31:00 · https://www.youtube.com/watch?v=-WBHNFAB0OE

**Thesis:** Thread-based engineering — seeing every unit of work as prompt → agent tool-calls → review — gives you a measurable framework for improving with agents: run more threads, longer threads, thicker threads, and fewer human-in-the-loop checkpoints.

**Nuggets:**
- Context: Karpathy — "I've never felt this much behind as a programmer." "Agentic engineering is a new skill. New skills need new frameworks to measure progress against. If you don't measure it, you will not be able to improve it."
- **A thread** = "a unit of work over time driven by you and your agents" with two mandatory human nodes: the prompt/plan at the start, the review/validation at the end; the middle is the agent's string of tool calls.
- "Pre-2023 you and I were the tool calls." Now "tool calls roughly equal impact, assuming you're prompting something useful."
- The six threads:
  - **Base thread** — one prompt, one line of work, one review.
  - **P thread (parallel)** — Boris Cherny "runs five Claude Codes in his terminal and numbers his tabs one through five" plus 5-10 more in the Claude Code web UI. "Guess who's getting more done?"
  - **C thread (chained)** — intentional phase checkpoints for work too big for one context window or high-risk production migrations. "These checkpoints aren't because your agent messed up — that's bad agentic coding." Use AskUserQuestion or system notifications (Dan: TTS hook that speaks the summary).
  - **F thread (fusion)** — same/similar prompt to multiple agents, then aggregate/fuse (best-of-n or cherry-pick). "The future of rapid prototyping will be done with fusion threads. Mark my words." Demo: 9 agents at once — 3 Claude Code, 3 Gemini, 3 Codex — each in its own sandbox, via mprocs.
  - **B thread (big/meta)** — threads containing threads; "your prompts are firing off other prompts"; sub-agents are v1, orchestrator-kicks-off-primaries is the next level. From your seat it's still one prompt + one review; the inside is a black box you engineered.
  - **L thread (long)** — "high autonomy end-to-end long duration work"; Boris's 1-day-2-hour run. Same shape as the base thread, just hundreds/thousands of tool calls. "Great planning is great prompting."
- **Ralph Wiggum** = "literally a loop over an agent" (agents + code > agents alone); it's ADWs hitting the mainstream (credit: Geoff Huntley). The **stop hook** is the Claude Code primitive: agent tries to stop → deterministic code checks a progress file / runs validation → reloop or complete.
- Boris's other tips: always Opus 4.5; CLAUDE.md in the repo but kept small; no dangerously-skip-permissions (curated allowlist instead); and #1: "give it a way to verify its work."
- **The four ways to improve:** more threads, longer threads, thicker threads, fewer human-in-the-loop checkpoints. That's the whole scoreboard.
- Hidden 7th: **Z thread (zero-touch)** — review node deleted. "It isn't that we don't look at the code, it's that we know we don't have to. That's the endgame." Maximum trust; explicitly not vibe coding.
- Mission restated: "Build living software that works for us while we sleep."

**Tools/tech:** Claude Code (terminal + web/background sessions, `&` sessions), mprocs (multi-process terminal viewer), fork-terminal skill + pthread alias/skill, E2B sandboxes, stop hook / Ralph Wiggum plugin, AskUserQuestion, TTS notification hook, Opus 4.5.

**Repo:** `pvolok/mprocs` (third-party TUI for running/viewing multiple processes) — the tool he uses to watch 9 parallel agents in one screen; not a Dan-authored demo repo.

**Drill:**
1. Install mprocs; define a pthread-style command (or use the YT-22 fork-terminal skill) that launches n agents with the same prompt.
2. Run a P thread: 3 agents, same codebase-review prompt; compare answers for consensus (fusion by cross-validation).
3. Run an F thread across harnesses: same prototype prompt to Claude Code, Gemini CLI, Codex; fuse the best pieces.
4. Convert one recurring task to an L thread: write a longer closed-loop prompt with a verification step (or a stop hook checking a progress file).
5. Score yourself for a week on the four metrics: thread count, thread length (tool calls), thickness (nested agents), and human checkpoints removed.
- **Done when:** you have a one-command way to spawn n parallel agent threads, one fused multi-harness prototype, and a week-over-week log showing at least one of the four metrics moved.
