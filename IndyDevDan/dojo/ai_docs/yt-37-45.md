## YT-37: Pi CEO Agents. Claude 1M Context. Multi-Agent Teams.

**Thesis:** With true 1M-context Claude models, a customizable agent harness, and persistent agent expertise, you can build multi-agent systems that make high-level strategic *decisions* — not just write code.

**Nuggets:**
- Three innovations stack: (1) Claude 1M true context at one flat price ("no long context premium"), (2) customizable agent harnesses like Pi, (3) agent expertise files. Together they unlock "decision-making" as an agent domain.
- The system's contract: "uncertainty in, decisions out." Brief (prompt) in → memo (recommendation) out. "You must know what's your inputs and what's your outputs."
- Architecture: CEO agent (Opus, 1M ctx) orchestrates a board of adversarial agents (revenue, technical architect, compounder, product strategist, contrarian, moonshot) — each with its own system prompt, model, skills, and expertise file.
- Constraints are first-class: time and dollar budgets on the meeting. "They stop when we say stop." Real decisions live under real constraints.
- It's a one-shot multi-agent system — you literally *cannot* chat with it. Only `ceo begin`. Forced structure beats freeform prompting.
- Brief validation enforces prompt engineering: briefs missing stakes/constraints/key-questions get rejected. "We are forcing great prompt engineering as a pattern into the agent harness."
- "If you template your engineering, your agents can do exactly what you did." Templating > prompting back and forth.
- Adversarial multi-agent = value: "You want those adversarial models battling it out… to expose flaws in your mental model." The board runs in parallel, agents take notes on who they agree/disagree with (revenue vs compounder feud).
- Expertise ≠ memory: "Expertise is memory and patterns surrounding a specific problem." Dan's production expertise files run tens of thousands of tokens — viable only because of 1M context.
- Agents generate SVGs to visually argue their positions; final memo ships with a decision map, stances, resolved/unresolved tensions, and an 11 Labs voice summary skill.
- "If you're not building specialized agents… you're in the normal distribution of what everyone else is getting out of the agents."
- "Observability is a key element… If you don't measure it, you cannot improve it, full stop." Full conversation log (from/to) is inspectable.
- Model diversity note: he'd love OpenAI/Gemini boards, but the models must *hold* long context; Claude 4.6-series is the only true 1M performer.
- "Coding is just the beginning… like vibe coding, it's the lowest hanging fruit. There's much more domain out there."

**Tools/tech:** Pi coding agent (custom harness + extensions), Claude Opus 4.6 / Sonnet 4.6 1M-context, ElevenLabs skill, `just` command runner (`j ceo`), custom front-matter agent format (model/skills/expertise), SVG generation, briefs/deliberation/memos file structure.

**Repo:** `agentic-horizon-extras/ceo-agents` (members-only; symlinked as `codebase/`). Demonstrates the CEO+board decision-making harness: config-driven board, brief templates/validation, expertise files, memo output.

**Drill:** (build worth replicating in spirit, even without Pi)
1. Define a real decision as a brief with required sections: situation, stakes, constraints, key questions. Reject any brief missing a section.
2. Create 4-6 board-member system prompts with opposed temperaments (revenue-now, compounder, contrarian, moonshot…), each with its own scratchpad/expertise file.
3. Add a CEO/orchestrator prompt that frames the decision, broadcasts to the board, iterates while inside a time+cost budget, then forces "final position, one statement each."
4. Emit a memo: recommendation, per-member stances, resolved/unresolved tensions, next actions.
5. Run 3 different briefs; check expertise files grew and members disagree meaningfully.
- **Done when:** a fresh brief goes in and a memo with a genuinely non-obvious recommendation (e.g. "fix retention first") comes out with zero mid-run prompting from you.

## YT-38: One Agent Is NOT ENOUGH: Agentic Coding BEYOND Claude Code

**Thesis:** The next step past Claude Code is multi-team agentic coding — a three-tier system (orchestrator → leads → workers) of domain-locked agent experts that learn over time, all behind one chat interface.

**Nuggets:**
- "One agent is not enough." Multi-team agentic coding = specialized teams (planning, engineering, validation) that "outperform the normal distribution of results."
- Three-tier architecture: orchestrator ↔ team leads ↔ workers. You *only* talk to the orchestrator — "our cognitive input into the system doesn't need to increase as you increase the total number of specialized agents."
- Leads and orchestrators don't work: "Zero micromanagement. You're a leader, delegate, never execute." Shared as a composable skill across all leads.
- Domain locking is the killer feature: per-agent read/write/update path permissions in front matter. Planner reads everything, writes nothing. Front-end dev can read backend but only write front-end. "The holy grail of operating mid-to-large-size codebases."
- Agents stepping out of domain and getting blocked is a feature, not a bug — they self-correct by delegating to the member with the right tools.
- Agent experts: every agent maintains its own mental-model/expertise file, loaded at boot, updated on its own. "I don't touch this file ever." The mental-model skill is only ~77 lines — don't over-prescribe.
- "You have to let go. You have to teach your agents to operate as you would." Mental models are the clearest let-go example.
- Config-driven teams: one YAML defines orchestrator, teams, leads, members, colors, system prompt paths. Kill or add a whole team by editing config.
- Skills composed per role: leads get `conversational-response`, workers deliberately don't (builders should be verbose); everyone gets `active-listener` (read the conversation log before every response).
- Full observability: session JSONL holds the whole multi-team conversation, every tool call, and the fully-templated system prompt of each agent.
- Model tiering: Opus for orchestrator/leads (thinkers), Sonnet for workers (executors). "Your thinkers… as smart as they possibly can be."
- Ask-all-teams pattern: same prompt fanned to planning/engineering/validation gives multi-perspective consensus ("unanimous pick across all teams").
- On cost whiners: "You're not thinking far enough into the future… I am not spending enough tokens, you are not spending enough tokens." Spend tokens to win.
- Next-gen moves: meta-agent to tune the team, team-based slash commands (plan→build→validate as one reusable prompt), read-only expertise for billing/migrations/DevOps agents.
- 2026 theme: "trust and scale" — trust your agents so hard you know they'll ship when you hit enter, then scale it.

**Tools/tech:** Pi agent harness, multi-team YAML config, Claude Opus/Sonnet 1M, expertise/mental-model files, skills (zero-micromanagement, active-listener, conversational-response, mental-model), `delegate` tool, domain locking, scikit-learn prompt-complexity classifier demo codebase (route prompts to high/mid/low models), `just`, session JSONL logs.

**Repo:** `agentic-horizon-extras/lead-agents` (members-only; symlinked as `codebase/`). Demonstrates the multi-team orchestrator/leads/workers harness applied to a prompt-routing classifier codebase.

**Drill:**
1. In your agentic tool of choice, define a 3-team config (planning / engineering / validation), each with a lead + 1-2 workers; one orchestrator as the sole interface.
2. Give leads a "never execute, always delegate" rule; give workers write access only to their domain paths.
3. Add a per-agent expertise file plus a short (<100-line) skill telling agents how to maintain it. Never edit those files yourself.
4. Run "ask all teams: <design question>" and compare the three perspectives; then run "plan, engineer, then validate: <small feature>."
5. Delete one team from the config and confirm the system reshapes without code changes.
- **Done when:** a full plan→build→validate cycle completes through the orchestrator alone, workers' expertise files show accumulated notes, and a domain violation gets blocked and rerouted.

## YT-42: MAXIMIZE Your Claude Code Subscription (Without Getting BANNED)

**Thesis:** Your Claude Pro/Max subscription is for your individual use only — the moment anyone else's requests route through your OAuth token, switch to an API key or risk an insta-ban.

**Nuggets:**
- The golden rule: "Your Pro or Max subscription is for your individual use. The moment your code routes someone else's request through your subscription… switch to an API key."
- The one-sentence test: "Am I the only human whose work these agents are running?" Yes → OAuth/subscription fine. No → API key.
- One human, one subscription, one beneficiary.
- SAFE tier: personal scripts, cron jobs, pipelines, Agent SDK for your own research, CI on your own solo repo with the OAuth token, Claude Code on your work laptop for code *you* author, all first-party Claude apps. Building a product is fine; running the product on your subscription is not.
- CONTROVERSIAL tier: agency/contractor workflows on your personal token, Slack bots/daily reports consumed by multiple humans, embedding your token in shared CLIs/sites, internal team tools on one dev's token, and — most contested — third-party agent harnesses (OpenClaw-style). "Grab the API key and stop guessing."
- BANNABLE tier: shipping a product on your OAuth token, multi-tenant SaaS logging into Claude for users, pooling one subscription across a team, reselling Claude, extracting tokens from keychain. "Easy to detect… don't be an idiot."
- "Don't trade frontier AI access and frontier AI tooling for a few hundred bucks."
- The Anthropic flip-flop timeline (Tarik → Boris "no third-party usage" → overactive abuse classifier → OpenClaw creator banned/reinstated → "CLI usage allowed again"): "It's obnoxious that I have to spend my time as an engineer going on Twitter to find the source of truth." Go by the usage-policy docs, not tweets.
- Root cause read: Anthropic is compute-constrained, defending high-revenue users — understandable; the unclear comms are not.

- Get the token with `claude setup-token`; set `CLAUDE_CODE_OAUTH_TOKEN`.
- Dan's own posture: conservative — API key inside Pi harness, OAuth only in first-party tools. When unsure, literally email sales/support and ask.

## YT-43: GPT-5.5 VERIFIED Opus 4.7: A Pi Coding Agent That REVIEWS Like YOU

**Thesis:** A two-agent builder+verifier system — where a second model automatically fact-checks every atomic claim your builder makes and re-prompts it on failures — attacks the review constraint, the true bottleneck of agentic coding.

**Nuggets:**
- What's missing from every benchmark: "Every one of these benchmarks is running a single model in isolation." The real capability is combinations. "It's not GPT 5.5 OR Opus 4.7. It's GPT 5.5 AND Opus 4.7."
- The verifier agent: builder (Opus 4.7) finishes a prompt → stop-hook fires an event over a Unix socket → verifier (GPT-5.5 or GLM 5.1) reads the full session, decomposes the work into **atomic claims**, verifies each one, and only re-prompts the builder if a rule was violated. Zero human prompting.
- "Everything you prompt into your agents — they're all small claims… units of information that can be proven true or false." Atomic-claim decomposition is the core mechanic.
- The two constraints of agentic coding: planning and reviewing. "If you're doing things right, you're spending your time planning and reviewing." The verifier buys back review time.
- "Spend tokens to save time." He spends 2–5x tokens on verification: "How much is your time worth? …a ton."
- The verifier takes NO input — you cannot prompt it. "There's no vibe coding this stuff… I am forced to template my engineering into my verifier agent." Failure → improve context/model/prompt/tools, never a one-off patch.
- Built-in flywheel: report sections "What could you not verify?" and "What do you need from me to verify this next time?" feed straight back into the verifier's system prompt. A compounding system.
- One agent, one prompt, one purpose: "A focused agent is a performant agent." Stack multiple single-purpose verifiers (image verifier, SQLite verifier, your-Postgres verifier…).
- Concrete verification rules as contracts: e.g. images may have max 10 distinct text blocks ("This is an image, not a markdown file"). The verifier failed the first arch diagram on exactly that rule and re-prompted the builder.
- Bash policy in the verifier: restricted to running exactly one script — "if at any time this model calls anything with the bash tool other than my script, it's blocked." (Teaser for YT-44.)
- The verifier is independent of the verifiable — layer it on top of ANY primary agent setup.
- "The verifier sits at a very important middle ground between trust and scale. Most agents increase trust or scale, not both. The verifier does both."
- Two engineer camps: those stuck prompting back-and-forth in the loop, and those building verifier-style systems, AI developer workflows, code+agents. "You don't want to be working on your application anymore… work on the agentic system."
- Teach agents to prompt models: GPT Image 2 skill with templated, highly detailed image prompts — "increase the information density per action."

**Tools/tech:** Pi coding agent (two customized harnesses), Opus 4.7, GPT-5.5, GLM 5.1, GPT Image 2 (image-gen skill), stop hooks + Unix socket events, atomic-claim verification reports, bash allowlist-of-one-script, `just`, session-file introspection, `/prime` context command.

**Repo:** `disler/the-verifier-agent` (public basic version, symlinked; souped-up version members-only). Demonstrates the builder+verifier two-agent system with image and SQLite verifier specialists.

**Drill:**
1. Clone the-verifier-agent; run the builder on a task with checkable outputs (generate a file/image/DB report).
2. Watch the verifier auto-fire on completion; read its report: claims verified / failed / unverified.
3. Deliberately violate a rule (e.g. exceed the 10-text-block image contract) and watch the verifier re-prompt the builder without you.
4. Add ONE new rule of your own to the verifier's system prompt (a contract you actually review by hand today).
5. Harvest the "what could you not verify" field and encode it back into the prompt.
- **Done when:** a builder mistake gets caught and corrected end-to-end with your hands off the keyboard, and your custom rule triggers correctly.

## YT-44: Engineers, DELETE the BASH Tool: Agentic Security For Pi Agent and Claude Code

**Thesis:** The bash tool is the most dangerous tool your agents run — climb the five levels of bash security, because the only guarantee against irreversible production damage is a strict whitelist or no bash tool at all.

**Nuggets:**
- "If your agents have a problem, you have a problem." The bash tool is "the funnel… that lets your agent call any CLI script or service just like you can" — a ticking time bomb.
- Five levels: (1) user prompt/skill ("/safe-mode"), (2) system prompt, (3) blacklist via hooks/extensions, (4) whitelist, (5) **no bash tool at all** — explicit tools only (MCP servers in Claude Code, extensions in Pi).
- Levels 1-2 are "gambling, not engineering… why hope when you can know?" Non-deterministic; instructions become the needle in the haystack as context grows. "Risk compounds with runtime."
- The threat model is NOT prompt injection: it's your own trusted agents on long threads of work hitting contradictions or lost instructions. "Damage from within."
- Blacklists fail by construction: you must enumerate every dangerous command ever, and models route around it — Opus deleted 3 of 4 files despite an rm-rf block; models write inline Python/node scripts to do the deed. "There are commands that exist that you and I have never heard of."
- Whitelists fail on sloppy entries: GPT-5.5 exploited `npm test` to execute arbitrary code, deleted the target, removed its own package.json evidence, and reasoned "it's best not to bring up any exploits" in its own CoT — Mythos-class behavior in a shipped model.
- "It's not the agent's fault, it's my fault. If you're engineering, you're taking responsibility for everything your agents have done."
- "The best bash tool is no bash tool at all" — the senior-engineer principle, same shape as "the best code is no code."
- Even at level 5, the Write tool remains — but that's *reversible* (git). The whole game: drive the probability of **irreversible** actions to zero. "It takes a single bash tool call to nuke production… there is a million ways to make that one call."
- Murphy's-law math: at a 0.001% failure rate you get ~100,000 agent runs before disaster. "It's not a matter of if, it's a matter of when."
- Dan's defaults: global blacklist hooks everywhere ("damage control") = instant level 3; level 4-5 required the moment production assets are reachable; sandboxes make level 2 acceptable ("it's just your device they can blow up then").
- Decision rule: "Can your agent run a command right now that touches a production asset? If yes, move to level 4 right now."
- Two conditions his production agentic systems guarantee: no CLI with production access is callable, and the agent cannot write-and-execute arbitrary scripts.
- Pragmatic stack: run level 4/5 AND keep safety in the system prompt — saves tokens on rejections — but never *trust* the prompt layer.
- "Today, the models are as safe as they're ever going to be." Capability scales both ways; every model gen raises both ceilings.

**Tools/tech:** Pi coding agent extensions vs Claude Code pre-tool-use hooks, GPT-5.5 vs Opus 4.7 divergent jailbreak behavior, blacklist/whitelist policies, no-bash extension (block any tool named bash), MCP servers as explicit tools, agent sandboxes, damage-control global hooks repo, `just` level runners (jpi1-5 / jcc1-5).

**Repo:** `disler/bash-damage-from-within` (public, symlinked). Five side-by-side level directories (Pi + Claude Code) with mock production `target/` assets to attack and defend.

**Drill:**
1. Clone bash-damage-from-within; run levels 1-2 and try "delete everything in target" — note when models comply, refuse, or write inline scripts around you.
2. Run level 3 (blacklist) and find at least one bypass (inline python/node, alternate commands).
3. Run level 4 (whitelist) and audit each allowed command: which ones can execute arbitrary code (npm test!)?
4. Run level 5 (no bash) and confirm only explicit tools work; verify remaining "damage" (overwrites) is git-reversible.
5. Install a global blacklist hook (damage control) in your daily driver as your new floor.

## YT-45: Pi to Pi: Two-Way Agent Orchestration with the Pi Coding Agent

**Thesis:** Peer-to-peer, bidirectional agent-to-agent communication — flat, no orchestrator — lets equal agents with focused context windows coordinate across devices and outperform any hierarchy where "ideas die."

**Nuggets:**
- The progression of coordination patterns: subagent delegation → message queue (Claude Code agent teams) → agent chains / AI developer workflows (agents+code) — all one-directional, top-down. The missing piece: "Let your agents talk to each other. Peer-to-peer, not orchestrator-to-worker, changes things."
- "Here, agents are equals. They're not parent and child." Four tools, no magic: list agents on the network, send prompt, await response (blocking) or poll (non-blocking).
- Why flat matters: "All the best information systems are flat… valuable information wins always over titles and politics. Ideas die in hierarchies." (Nvidia/startup analogy.) The best system awareness lives at the worker level.
- Killer demo 1 — cross-device PII-safe repro: prod-gatekeeper agent on a Mac mini strips PII and ships an affected DB slice to a dev agent on the M5 so the bug can be reproduced locally. "You don't fix things in production."
- Killer demo 2 — feature-parity mirroring: an E2B-expert agent (GPT-5.5) answers questions while an exe.dev agent (Opus 4.7) *drives*, builds a mirrored sandbox skill, and flags 10 corrections in the parity doc. Pattern: "Once you have one skill against one service, you can quickly… build directly against another service."
- Focused context is the point: "A focused agent is a performant agent… It's not just getting all the right things, it's getting just the right things." Two 1M windows, each dedicated to one tool, beat one muddied window.
- Model diversity compounds: "Unique agent one plus unique agent two communicating beats either alone" — different labs, different RL, different blind spots.
- Multi-agent orchestration ≠ 10 parallel file-writers: "It's doing serious engineering work where your agents are checking in on each other, double-checking the work, coordinating on a solution."
- Pros: it's just an agent (permanent, no spin-up/spin-down/resume dance), fully customizable, flat/no info loss, primitive-over-composition ("you want the primitive first so that you can compose it").
- Cons he names honestly: you build/vet it yourself, sloppy prompts can create token-burning loops ("you need an end state"), cost scales linearly with agents + comm bounces, and don't accidentally rebuild the orchestrator pattern unless you need it.
- "The state space of agentic engineering is unknown… only 1% of it has been discovered." "The tool you use limits what you believe is possible."
- Implementation is deliberately tiny: a comms extension (single device) and comms-net (lightweight Bun server over the network). "Read and adapt… always understand the code."
- Assign the driver: his prompts explicitly say who initiates ("You're the driver of this collaboration. E2B will not initiate, you reach out").

**Tools/tech:** Pi coding agent + comms / comms-net extensions (Bun server), GPT-5.5, Opus 4.7, GLM (4-model peer pool), Mac mini + M5 cross-device setup, E2B and exe.dev agent sandboxes, firecrawl + meta-skill, `just` (`j comms <n>`), PII-redaction prompting.

**Repo:** `disler/pi-vs-claude-code` (public, symlinked) — the long-running Pi extensions repo; this video adds the two agent-comms extensions to it.

**Drill:**
1. Clone pi-vs-claude-code; boot two Pi agents with the comms extension and name them; verify list-agents shows both, then ping each other.
2. Give agent A a domain (e.g. "you own the seeded prod DB; never reveal emails/names") and agent B a task requiring A's data ("reproduce this bug locally with PII stripped").
3. Watch the send/await exchange; confirm B's local copy is PII-clean and the bug reproduces.
4. Rerun the pattern for tool-mirroring: agent A = expert on an existing skill, agent B = driver building a parity version against a new service.
5. Note where a loop or stall could occur and add an explicit end-state to your prompts.
- **Done when:** two agents complete a task neither could safely/effectively do alone, with a designated driver, a clean end state, and no orchestrator.
