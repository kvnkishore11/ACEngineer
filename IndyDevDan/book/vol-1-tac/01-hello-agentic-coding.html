00

Begin with the failure, not the slogan

You ask an AI to write a function. It gives you plausible code. You paste it into the repository, discover that it does not fit, repair two imports, run the tests, fix a test, create a branch, make the commit, and explain the result in Slack. The AI helped with one narrow slice. You still carried the workflow.

That is the concrete failure TAC-1 addresses. The problem is not that the generated code was bad. The problem is that the unit of delegation was too small. You delegated typing while retaining every transition that makes typing useful: reading the repository, choosing a safe branch, creating files, running programs, observing output, committing a coherent change, and reporting what happened. AI coding accelerated an activity. Agentic coding delegates an outcome-producing chain.

Dan’s lesson makes this distinction with almost comical economy. The source repository contains only seven files. Its README is exactly 35 lines. The generated programs print tiny messages. That smallness is deliberate. A realistic codebase would let you confuse complexity with the concept. Here the application code is so trivial that the only interesting variable is who moves the work through the engineering system.

The chapter’s one-sentence thesis

AI coding uses context, model, and prompt to generate code. Agentic coding keeps those three and adds tools that can be executed reliably in a long chain—so the prompt becomes a workflow and the agent performs engineering work.

What you are training

  • DiscriminationTell code generation apart from workflow execution even when both begin with a prompt.
  • DiagnosisLocate failures in context, model, prompt, or tools instead of blindly rerolling.
  • OperationReproduce the branch → write → run → commit → report cycle in the real TAC-1 repo.
  • TransferRecognize how claude -p turns an interactive agent into a programmable building block.

How to use this chapter

Do not read it as a transcript recap. Each major idea repeats the same ten learning moves: failure, picture, one demo move, term, worked example, a small action, failure repair, current-practice overlay, retrieval, and teach-back. That repetition is intentional. Expertise is not the ability to recognize Dan’s phrases. It is the ability to retrieve the idea under pressure, operate it in the course repository, notice when it fails, and explain it without the chapter open.

Prime directive for every exercise

You type zero lines of application code by hand. “Stop coding” is a behavioral constraint, not a discussion topic. You may type prompts and terminal commands. When a generated file is imperfect, repair it through the agent so you practice controlling the loop.

01

A new role: the Agentic Engineer

The title matters only if the work changes. “Agentic Engineer” is not a badge for someone who uses AI often; it names an engineer who builds systems able to take engineering actions.

1 · Hook — concrete failure

The prompt expert who is still the workflow engine

Imagine an engineer who can produce excellent code with a one-shot prompt. They know how to attach a specification, point at the right files, and ask for tests. Yet after every answer they manually copy code, open files, run commands, move changes onto a branch, decide whether the output succeeded, and write a summary. Their prompts improved. Their role did not. The human remains the glue between every step.

This is why “prompt engineer” is too narrow for Dan’s prediction. A clever request can improve a model’s answer. An agentic system changes who performs the sequence. If the human must relay every output into the next input, the human is still the orchestration layer. The system has intelligence but little agency.

2 · Picture — the two-phase map

Move the boundary of delegation

Phase 1 · AI coding

The agent produces code; the human carries the workflow.

Humancontext → prompt
Agentgenerate code
Humanwrite → run → fix → commit → report

Phase 2 · Agentic coding

The human specifies and reviews; the agent carries the workflow.

Humangoal + constraints + checks
Agentbranch → write → run → commit → report
Humanreview outcome + improve loop

The important movement is the boundary. The human does not disappear. The human moves from carrying transitions to designing them, setting constraints, and evaluating the result.

3 · Story of one move — Dan’s demo

A 2023 bet becomes a visible phase change

Dan opens with a concrete personal bet: in 2023 he bought agenticengineer.com, predicting a role centered on building systems capable of taking engineering actions. The claim is not that engineers vanish. It is that an engineer’s leverage shifts from personally performing actions to constructing systems that can perform them.

His one move is conceptual before it is technical: name the era change. In phase one, prompt-to-code makes code abundant and gives rise to vibe coding. In phase two, the engineering response is to command systems that take actions. That frame prevents the later terminal demo from shrinking into “Claude Code can run Git.” Git commands are merely the visible actions; role redesign is the lesson.

4 · Name it — Dan term + plain English

Phase-two Agentic Engineer

Dan’s term

Agentic Engineer: an engineer who builds systems that can take actions as engineers can.

In plain English: you build the worker and the work path, not merely the artifact at the end. The evidence is behavioral. Does your system know which files to read? Can it create or edit files? Can it execute commands and observe their results? Can it preserve state across steps? Can it report a result that another person or program can evaluate? If yes, you are designing agency. If you only ask for a snippet, you are using generation.

The title does not require full autonomy. TAC-1 demonstrates a tiny serial workflow with a person choosing when to launch it. The role begins as soon as you deliberately package actions into a repeatable system. Later tactics can improve triggers, context, focus, and closed loops; none are prerequisites for recognizing the role here.

6 · You try — 3 minute drill

Classify the work by who carries the transitions

  1. Write down one task where you ask an AI for code, then manually install the answer.
  2. Underline every transition you still carry: locate, branch, edit, run, inspect, commit, report.
  3. Rewrite the task as an outcome with explicit actions and a final report.
  4. Do not run it yet. Circle the actions that would require tools or permissions.

Your first draft is successful if it exposes the workflow you normally perform invisibly. The goal is not an elegant prompt. The goal is to see the human glue.

7 · Common fail + fix

Failure: a title change without a delegation change

Symptom: you say “agentic” because the tool has an agent mode, but you still approve and relay each micro-step. Or you send a long prompt that generates several files but never executes or verifies them.

Fix: ask a falsifiable question: What engineering action can the system complete without me moving information between steps? Start with one closed chain, not a grand autonomy claim. In TAC-1 that chain is branch → write → run → commit → report. Once the system carries it, your role really has moved.

8 · Current practice overlay

The ceiling is higher; the primitive is unchanged

Current practice · mid-2026

TAC-1 intentionally shows one agent, one terminal, one serial workflow. Current practice can fan the same shape into subagents, background tasks, and worktree-isolated parallel runs. Do not import that complexity into this first lesson. First learn to specify one reliable chain. Parallelism multiplies both good system design and confused system design.

Forward pointer: later TAC lessons scale the seed planted here.

02

The mission: command compute through leverage

The tactic is emotionally difficult because it asks you to retire a visible skill. The mission supplies the reason: move up the stack from producing keystrokes to designing systems that produce outcomes.

1 · Hook — concrete failure

The faster typist who cannot escape throughput

Suppose an engineer doubles their typing speed, memorizes every framework API, and uses autocomplete perfectly. They may produce more code per hour, but every additional unit still consumes their attention. Their throughput is coupled to presence. If they stop, the work stops.

Now suppose another engineer spends ten minutes creating a reliable workflow that can be fired again. The first run may be slower than hand-typing. The second run costs almost no new design attention. The tenth run makes the original time investment look tiny. This is why Dan says the 10x engineer does not come from 10x time or effort. The multiplier is leverage, and the number could be 2x, 10x, or 100x depending on the leverage point.

2 · Picture — attention versus repeatability

Effort is linear; a reusable system bends the curve

3 · Story of one move — Dan’s demo

He names the enemy, then changes the identity

Dan states the mission with uncomfortable specificity: become an engineer “they” cannot replace—where “they” means your boss, the company, the industry, and AI. The point is not permanent safety; he explicitly says nothing in technology lasts forever. The point is to choose the adaptation with the greatest asymmetric advantage.

The story’s one move is to replace a threatened identity with a higher-order one. If “real engineer” means “person who types the best code,” an agent that types better feels like a rival. If engineering means building systems of leverage that produce valuable outcomes, a capable coding agent becomes new machinery. You are measured by what you can make the machinery reliably accomplish.

4 · Name it — Dan term + plain English

Commander of compute

Dan’s term

Commander of compute: the phase-two engineer who aims powerful models and agentic systems at valuable outcomes, building systems that build systems.

Plain English: stop treating the model like a faster pair of hands and start treating it like programmable capacity. Commanding does not mean shouting more prompts. It means deciding the target, furnishing context, declaring constraints, granting a bounded tool surface, defining success evidence, and choosing when the workflow should run.

Dan’s end-state phrase—self-operating machine—should be read incrementally. TAC-1 does not claim that a codebase becomes autonomous in one lesson. It shows the smallest seed: one workflow can recreate a branch, files, executions, commit, and report without an interactive human. Every later improvement can move another piece of attention out of the repeated path.

6 · You try — leverage ledger

Measure attention, not impressiveness

  1. Choose one repeated engineering task from your week.
  2. Write the minutes you spend per repetition and the number of repetitions per month.
  3. List which steps are judgment and which are deterministic transitions.
  4. Mark the smallest complete chain an agent could carry while returning evidence to your judgment point.
  5. Estimate break-even: design minutes ÷ minutes saved per run.

A boring five-minute workflow repeated 40 times may be a better leverage point than an impressive hour-long task performed once. This chapter does not authorize using any non-course repository in the lab; this ledger is a planning exercise for transfer after mastery.

7 · Common fail + fix

Failure: confusing more output with more leverage

Symptom: you celebrate that an agent generated 2,000 lines, even though reviewing and repairing those lines consumed more attention than the old workflow. Or you automate a one-off task because the demo looks impressive.

Fix: evaluate the ratio Dan’s mission actually cares about: valuable outcome per unit of your attention. Count reruns, intervention points, review load, and evidence quality. A short stable workflow with a clear report is more agentic than a spectacular uncontrolled generation.

8 · Current practice overlay

Period detail changes; leverage does not

Current practice · mid-2026

The course-era Claude Code interface and model names are period detail. Newer interfaces, plan modes, and background execution can reduce friction, but they do not change the leverage test. Dan future-proofs the lesson directly: newer models and a different UI are welcome; do not let them distract from the tactic.

Use today’s tool, but grade it with the same question: how much reliable outcome does one unit of attention purchase?

Reveal answer

Because the multiplier comes from the leverage point you find. It could be 2x, 10x, or 100x; it does not come from a fixed amount of greater effort.

2. What makes the programmable demo leverage rather than just automation theater?

Reveal answer

The workflow can be recreated repeatedly from a known state with low additional human attention, and it returns evidence through the report.

3. What does a commander of compute decide?

Reveal answer

03

Tactic #1: Stop Coding

The provocation is precise: stop hand-typing application code. Keep generating code. Keep understanding code. Move your scarce cycles to planning, reviewing, and building closed loops.

1 · Hook — concrete failure

The ninety-percent trap

An agent produces a nearly correct file. One import is wrong and one edge case is missing. You think, “It will be faster if I just fix those two lines.” You open the editor, type the repair, and move on. The task is complete, but the learning loop is broken.

The immediate edit feels efficient because you compare two minutes of hand work with another agent turn. Dan’s tactic compares something larger: a lifetime of carrying repairs versus learning to design prompts, feedback, and checks that make the system repair itself. Every time you silently take the keyboard back, you hide a failure mode from the system. You get the file, but you do not improve the mechanism that will create the next hundred files.

This is the behavioral edge of “stop coding.” It does not ask whether you are capable of the fix. It asks whether your personal typing is still the best lever for an outcome you expect to repeat.

2 · Picture — reallocate the engineering cycle

Do not remove engineering; move it around the code

3 · Story of one move — Dan’s demo

The tactic is said twice because the easy interpretation is wrong

At 6:47, after establishing the mission and leverage frame, Dan reveals the first tactic: “Stop coding.” He repeats it. Then he sharpens the claim: your hands and your mind are no longer the best tool for the job of writing code. The directness is meant to break a default behavior, not to erase engineering knowledge.

Dan grounds the discomfort in his own history. He spent more than a decade hand-coding across startups and large companies, mastering the familiar craft, and says he misses it. That confession matters pedagogically: the tactic is not offered by someone who never valued coding. It is an argument that the best instrument for code production has changed, and that engineers must move their attention to the work the instrument cannot own.

4 · Name it — Dan term + plain English

Stop coding ≠ stop engineering

Exact distinction

Stop coding: stop typing application code by hand. Continue generating more code than before, understanding what it does, reviewing it, and designing systems that can validate and improve it.

Three reallocations make the phrase operational:

  • Planning: express outcomes, starting state, constraints, ordered actions, and pass conditions before compute begins.
  • Reviewing: inspect behavior, diffs, architecture, risks, and evidence. Code understanding becomes more—not less—important when production accelerates.
  • Closed-loop structures: connect generation to execution and observation so failure becomes feedback the system can act on.

The tactic is therefore a constraint on who makes the keystrokes, not a license to be ignorant. If your agent generates ten times more code, your ability to frame, inspect, and govern code must become more systematic.

5 · Worked example — walk the course codebase

Zero application-code keystrokes in TAC-1

The README’s phase-one prompt contains a description of main_aic.py:

CREATE main_aic.py:
    print goodbye ai coding

The course artifact does not ask you to open main_aic.py and type the print statement. You give the instruction to Claude Code. The agent writes it. Later, programmable/prompt.md describes both runtime files and the agent writes both again. The lab’s prime directive extends the same rule to stretch changes: even when you add a branch name to the REPORT or create a fourth launcher, you ask Claude Code to make the edit.

Notice what you still do. You read .claude/settings.json. You understand the prompt. You watch the plan. You inspect generated files. You run independent verification commands. You compare the report to real output. You observe how the workflow fails when a permission is removed. Nothing about that work is passive. The difference is that your keystrokes go into instructions and probes, not into application code.

Why the constraint matters

When an exercise is trivial, hand-editing always looks faster. The zero-typing rule makes you practice the control surface before tasks become too large for manual rescue.

6 · You try — repair without reclaiming the keyboard

Use the next imperfection as the exercise

  1. During the TAC-1 lab, wait until an output differs from your expectation.
  2. Before touching the file, state the discrepancy as observed versus expected behavior.
  3. Give the agent the observation, the expected result, and the command that should prove success.
  4. Let the agent edit and rerun.
  5. Review the diff and evidence. If still wrong, repeat with a more precise observation.

The drill is passed when the system repairs the artifact and you can name what improved in your feedback. Speed is secondary on this first repetition.

7 · Common fail + fix

Two opposite misunderstandings

“No more code”

Why it fails: code remains a primary asset that produces features and products. TAC expects you to generate more of it.

Fix: say “stop hand-typing” every time you teach the tactic.

“No need to understand code”

Why it fails: faster generation magnifies the cost of weak review and weak system judgment.

Fix: move reading, execution, tests, and diff review into explicit pass criteria.

A third failure hides between them: ritualistically never touching code while also never reviewing it. That is not Dan’s tactic. The goal is engineering leverage, not ideological purity. The lab’s zero-typing rule is a training constraint that forces better control habits.

04

Big Three → Core Four

The phase change adds one diagnostic dimension: tools. The novelty is not that tools exist. The breakthrough is that a prompt can reliably carry a long chain of tool calls at useful scale and performance.

1 · Hook — concrete failure

The reroll reflex

An agentic run stops before committing. A weak operator submits the same prompt again, perhaps adding “please make sure to commit.” The second run stops too. The operator concludes that the model is flaky.

A Core Four diagnosis asks four different questions. Did the agent see the repository state and instruction file it needed? Was the model capable of the reasoning? Did the prompt state a valid starting branch and commit expectation? Did the tool surface actually allow git commit? In TAC-1 stretch drill S3, removing one permission creates exactly this lesson: prompt quality cannot compensate for a missing tool.

Without a diagnostic vocabulary, every failure looks like “bad AI.” With the Core Four, you can isolate the broken dimension before spending another token.

2 · Picture — the Core Four visual

Four interacting primitives, one newly emphasized dimension

Context

“Can it see what matters?”

Model

“Can it reason through this?”

Prompt

“Does it know the outcome and checks?”

Tools

“Can it take the required actions?”

3 · Story of one move — Dan’s demo

The full trace makes the fourth circle visible

After the agentic prompt checks out a branch, writes main_tac.py, runs both programs, stages files, commits, cleans up its todos, and reports, Dan names what changed. AI coding had always involved context, model, and prompt—even if the user did not see all three. Agentic coding adds tools.

Dan anticipates the obvious objection: tool calling is not new. His answer is exact and portable: “It’s not a question of new. It’s a question of scale and performance.” A single calculator call proves a model can use a tool. A branch → write → run → observe → stage → commit → report chain proves that tool use can form a unit of engineering work.

4 · Name it — Dan term + plain English

The Big Three and the Core Four

Canonical terms

Big Three: context, model, prompt. Core Four: context, model, prompt, tools. Precise delta: prompts that can reliably execute long chains of tools.

Tools should not be reduced to a list of commands. The tool dimension has at least three properties:

  1. Availability: a tool exists that can perform the needed action.
  2. Permission: the system allows that action in the current context.
  3. Chain reliability: the agent can choose, order, execute, and learn from several calls without losing the goal.

This explains why all four interact. A correct Git tool with no repository context is useless. A capable model with an ambiguous starting state may choose the wrong branch. A precise prompt asking for a forbidden commit cannot cross the permission boundary. Diagnostics work because you ask which dimension prevented the next state transition.

5 · Worked example — .claude/settings.json

Read the tool surface before running the prompt

The lesson’s settings file is the tools circle made concrete:

{
  "permissions": {
    "allow": [
      "Read", "Write", "Edit",
      "Bash(uv run:*)",
      "Bash(git checkout:*)",
      "Bash(git branch:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "WebSearch"
    ]
  }
}

Classify the list. Read, Write, and Edit let the agent inspect and change files. uv run lets it execute the generated programs. Four Git patterns let it checkout, inspect/create branches, add files, and commit. WebSearch is the single non-local tool. There is no git push permission.

Now predict the README workflow. The agent can create the branch because checkout/branch are allowed. It can write main_tac.py. It can run both files with UV. It can add and commit. It cannot push the commit under this allowlist. You have understood the possible behavior before spending tokens.

7 · Common fail + fix

Failure: treating the Core Four as a memorization diagram

Symptom: you can chant “context, model, prompt, tools” but respond to every error by rewriting the prompt.

Fix: before retrying, write one sentence per dimension: what context was present, which model property mattered, what the prompt required, and which tool/permission enabled the failed transition. Eliminate dimensions with evidence. The Core Four becomes valuable only when it changes your debugging behavior.

A related failure is giving the tools circle unlimited power so the workflow cannot be blocked. That avoids permission friction by deleting a safety boundary. TAC-1 teaches the opposite habit: inspect and deliberately bound what the agent may do.

8 · Current practice overlay

Permissions became richer; the audit habit survived

Current practice · mid-2026

The flat allowlist shown in TAC-1 still communicates the primitive cleanly. Current Claude Code practice also includes permission modes, deny rules, hooks around tool use, sandboxed Bash, and settings layered across user, project, and local scopes. The modern surface is larger; the timeless habit is unchanged: inspect what the agent may do before you run it.

Teaching rule: learn the visible allowlist first, then add richer gates when the workflow requires them.

05

Two prompts, one monumental difference

The chapter’s A/B test holds repository, model, and operator constant. Prompt A creates a file. Prompt B carries an engineering workflow. Run both; the delta is the lesson.

1 · Hook — concrete failure

“Both made files, so they are basically the same”

A learner runs both prompts and notices that main_aic.py and main_tac.py now exist. They conclude that the second prompt is merely a longer code-generation request. The visible artifacts conceal the real difference because files are the residue of both processes.

To see the delta, ignore the final directory for a moment and compare state transitions. Before Prompt A, one file is absent; afterward, it exists. Before Prompt B, the repository is on a starting branch with incomplete artifacts; afterward, a named branch exists, a second file exists, two programs have been executed, their output has been observed, changes have been staged and committed with a named message, a todo sequence has drained, and a report has been returned. The second prompt did not merely produce more. It moved the repository through an ordered series of verified states.

2 · Picture — AI coding versus agentic coding

Compare verbs, states, and evidence

Phase 1

AI Coding Prompt

A request to create code.

CREATE main_aic.py:
    print goodbye ai coding
  • Verb: create
  • State change: one file appears
  • Execution: human runs it later
  • Repository action: none requested
  • Evidence: file content

Phase 2

Agentic Coding Prompt

A runbook for engineering work.

RUN: checkout branch
CREATE: main_tac.py
RUN: execute both files,
     add + commit
  • Verbs: run, create, run
  • State changes: branch, file, index, commit
  • Execution: agent runs both programs
  • Repository action: explicit Git workflow
  • Evidence: trace, outputs, commit, report

A useful test: if you can describe a prompt’s success only by naming generated files, you may be looking at AI coding. If you can describe ordered state transitions and evidence, you are looking at an agentic workflow.

4 · Name it — Dan term + plain English

The Agentic Coding Prompt

Dan’s term

Agentic Coding Prompt: a prompt containing a sequence of tool calls. In plain English, it is a workflow specification that an agent can execute.

The README uses a compact runbook grammar: RUN, CREATE, RUN. These headings separate kinds of action. The first RUN establishes repository state. CREATE defines an artifact. The final RUN executes and records the work. In programmable/prompt.md, a fourth heading—REPORT—makes the output contract explicit.

The headings are not magic syntax. Their value is structural clarity. A weak prompt mixes goal, starting state, implementation, commands, and success into a paragraph. A runbook shape lets both human and model see the sequence. It also makes omission easier to detect. If no REPORT block exists, a headless caller may receive an unhelpful narrative. If no starting branch is declared, reruns may begin from ambiguous state.

Line one establishes isolation. The CREATE block specifies two observable behaviors without dictating a full implementation. The next two commands turn code into evidence: uv run main_aic.py should print goodbye ai coding; uv run main_tac.py should print hello agentic coding followed by a concise definition. The final two commands preserve the result in Git.

The five-action delta you should write in Checkpoint 1 is:

  1. Checkout the named branch.
  2. Create the second file to a behavioral specification.
  3. Execute both programs and expose their outputs.
  4. Stage and commit the change with the specified message.
  5. Manage the sequence and report completion.

Why this tool class works

The lesson names three essential elements behind reliable agentic coding: a reasoning-capable model, consistent long tool chains, and the right agent architecture. Treat them as a transferable evaluation checklist.

1 · Hook — concrete failure

A model that can code but cannot carry the work

Programmable agentic coding

Because Claude Code runs in the terminal, any language with terminal access can call it. The agent stops being a place you visit and becomes a function-like component inside a larger system.

1 · Hook — concrete failure

The workflow that only exists while you are chatting

You develop a strong interactive routine. You paste a runbook, answer one question, watch the agent work, and receive a useful result. Tomorrow you perform the same ritual again. The prompt is reusable, but the trigger is still you. The workflow is stored as a habit in your head: open the terminal, start the agent, find the prompt, paste it, wait, copy the result.

This is phase two in capability but not yet in reach. The agent can carry engineering work, yet the system cannot invoke that capacity from anywhere else. It cannot be called by a script, a scheduled process, a CI job, or another agentic environment. 4 · Name it — Dan term + plain English

Programmable agentic coding

Dan’s term

Programmable agentic coding: invoking an agentic coding tool from a program so your own systems can fire agentic prompts across the software development lifecycle.

Plain English: treat the agent like a function with a deliberately imperfect analogy:

result = agent(prompt, repository_context, allowed_tools)

The analogy helps because a caller supplies input and receives output. It is imperfect because the agent has side effects: it edits files, runs programs, and changes Git state. That is why permissions, starting state, reports, and exit codes matter. You are not calling a pure text transformer. You are invoking a bounded actor.

Dan’s key expansion is spatial: the prompt matters, but so does where the system can invoke it. A prompt trapped in an interactive session depends on your presence. A prompt callable from code can live inside triggers and environments where you are absent. TAC-1 names triggers as later-course material; this lesson only proves the callable primitive.

5 · Worked example — all four programmable files

One shared invocation pattern, three error-handling choices

Start with the shared behavior file, programmable/prompt.md. It differs from the README’s agentic prompt in two important ways: it also creates main_aic.py, making the run self-contained, and it ends with a report contract:

REPORT:
    respond with the exact output of both .py files

The Shell launcher is the pattern without ceremony:

PROMPT_CONTENT="$(cat programmable/prompt.md)"
OUTPUT="$(claude -p "$PROMPT_CONTENT")"
echo "$OUTPUT"

The Python launcher makes process behavior explicit:

with open("programmable/prompt.md", "r") as f:
    prompt_content = f.read()

result = subprocess.run(
    ["claude", "-p", prompt_content],
    capture_output=True,
    text=True,
)
print(result.stdout)
sys.exit(result.returncode)

The actual course file also prints standard error when present and catches exceptions. Those details make it the most production-shaped of the three: the caller can distinguish useful output from errors and preserves the child process’s success or failure for an outer system.

The TypeScript/Bun launcher reads the same file and uses Bun’s shell template:

const promptContent = readFileSync("programmable/prompt.md", "utf-8");
const output = await $`claude -p ${promptContent}`.text();
console.log(output);

The shared core is more important than syntax, but the wrappers are not equally defensive:

Readprompt.md
Invokeclaude -p
Capturetext output
Returnprint report
Differentiateerror policy

Shell reads, invokes, captures standard output through command substitution, and echoes it. It does not explicitly capture standard error or preserve the child exit code after the final echo. Python explicitly prints standard error and exits with Claude’s return code. The Bun wrapper catches a thrown command error and exits with status 1. Language choice is irrelevant to the agentic semantics because all three can access the terminal; wrapper quality still determines what an outer system can learn about failure.

The contradicting truth: replace yourself

What gets replaced is your repeated execution. What becomes harder to replace is your judgment and ownership of the systems that perform it.

1 · Hook — concrete failure

The indispensable bottleneck

A team has one engineer who knows how to complete a fragile release ritual. They know which branch to create, which files to touch, which commands to run, what output is safe, and how to write the final update. Because only they can carry it, the engineer appears indispensable. In reality the team is dependent on an undocumented human workflow.

The engineer can protect that dependency, repeating the ritual forever, or encode it into a bounded, reviewable system. Encoding seems to remove their immediate necessity. It also changes their contribution from “person who remembers the steps” to “person who understands, improves, and governs the release system.” The first kind of indispensability is a bottleneck. The second is leverage.

  6. Cross-check report truth by running both programs yourself. A report that sounds plausible but disagrees with execution is not a pass.
  7. Reset branch state between runs. Then execute: 
    sh programmable/programmable.sh
  8. Reset again and execute the Bun variant: 
    bun run programmable/programmable.ts

    Bun is optional during the initial tool audit only in the sense that it supports the TypeScript variant; the full Checkpoint 2 requires all three launchers. Install/enable Bun before claiming a complete lab pass.

Checkpoint 2 · one sentence. “The host language does not matter because any program with terminal access can pass the shared prompt to claude -p; the prompt and agent runtime define the engineering workflow.”

Pass criteria

  • Python, Shell, and Bun TypeScript all carry the identical workflow headlessly.
  • Every comparable run begins from main without the demo branch.
  • The report matches independent execution.
  • You can explain why the wrapper language is incidental.

Lab 3 · Stretch the loop without typing code

  • 15–30 minutes
  • S1–S4
  • Course repo only

S1 · Extend REPORT: close one more loop

  1. Inside Claude Code—not your editor—ask the agent to edit programmable/prompt.md so REPORT also includes the current Git branch name.
  2. Review the prompt diff. Confirm the existing exact-output requirement remains.
  3. Reset the branch and run the Python launcher.
  4. Compare the reported branch with git branch --show-current.

Learning target: report-back is part of workflow design. The new field creates a new externally checkable claim.

S2 · Add a fourth launcher: prove language independence

  1. Ask Claude Code to inspect the existing Shell, Python, and TypeScript launchers.
  2. Ask it to add a launcher in another language already available on your machine—plain Node, Ruby, or Go are examples from the lab specification, not requirements.
  3. Require the same invariants: read prompt.md, invoke claude -p, return output, surface errors/failure.
  4. Reset, run, and verify the same repository end state.

Learning target: separate host syntax from the shared agentic workflow.

S3 · Break one permission: feel the tools boundary

  1. Ask Claude Code to remove "Bash(git commit:*)" from .claude/settings.json. Review the diff.
  2. Reset the demo state and rerun the agentic prompt.
  3. Record the exact transition where the system halts, refuses, or asks. Do not summarize it as “Claude failed.”
  4. Restore the permission through Claude Code and review the restored file.
  5. Complete the sentence: “The prompt described the commit, but the workflow could not cross that state boundary because ___.”

Learning target: the tools circle bounds what even a correct prompt and capable model can accomplish.

S4 · Transfer map: classify your real work

  1. Time the interactive phase-one and phase-two runs.
  2. List real tasks that are AI-coding-prompt-shaped: the needed outcome is primarily generated code.
  3. List tasks that are agentic-prompt-shaped: success requires ordered repository or system actions and evidence.
  4. Circle one candidate whose repeated transitions could be encoded after the course. Do not run it outside TAC-1 in this lab.

Learning target: transfer the distinction without expanding the authorized lab scope.

Mastery check · retrieve, diagnose, teach

Recognition is not the finish line. Close the chapter, answer on paper, then return to reveal. Score operations and reasoning, not exact prose.

Round 1 · Foundations

1. What are the Big Three?

Reveal answer

Context, model, prompt—present in AI coding whether or not they are visible in the interface.

2. What upgrades them to the Core Four?

Reveal answer

Tools, specifically prompts that can reliably execute long chains of tool calls.

3. What does “Stop Coding” forbid, and what does it preserve?

Reveal answer

It forbids hand-typing application code as the default instrument. It preserves and intensifies code generation, understanding, review, planning, and closed-loop design.

4. Define Commander of Compute without saying “uses AI.”

Reveal answer

An engineer who aims compute by specifying outcomes, context, constraints, bounded actions, evidence, and triggers to build systems that build systems.

Round 2 · Trace the demo

5. Reconstruct Prompt B’s state transitions without looking.

Reveal answer

Checkout the demo branch; create main_tac.py; run main_aic.py; run main_tac.py; stage files; commit with the specified message; report completion.

6. Which runtime artifact must exist before the README Agentic Coding Prompt runs, and why?

Reveal answer

main_aic.py, because Prompt B runs it but does not create it. The interactive A/B order supplies it.

7. What exact commit subject proves the Git portion completed?

Reveal answer

Demo agentic coding capabilities.

8. What makes prompt.md self-contained and observable?

Reveal answer

It creates both Python files, performs the branch/run/commit chain, and demands exact program outputs in REPORT.

Round 3 · Diagnose with the Core Four

9. The prompt says commit; the model plans commit; the agent cannot execute it after S3. Which dimension failed?

Reveal answer

Tools/permission: the commit tool pattern was removed from the allowlist.

10. The agent edits the wrong prompt.md in a larger repo. What two dimensions should you probe first?

Reveal answer

Context—what paths and repository content it saw—and prompt—whether the target path was explicit.

11. A tool calls all commands but forgets the first program’s output before REPORT. Which essential element is most suspect?

Reveal answer

The agent architecture’s state/observation management, though the combined system should be evaluated rather than blaming a label alone.

12. Why is repeated rerolling a weak diagnostic method?

Reveal answer

It changes stochastic output without isolating whether context, model, prompt, or tools caused the failed state transition.

Round 4 · Transfer and judgment

13. A prompt generates five excellent files, but a human runs tests, commits, and reports. AI coding or agentic coding?

Reveal answer

Primarily AI coding. Output quantity does not move the workflow boundary; the human still carries the engineering transitions.

14. Why is exact report-back a seed of closed-loop engineering?

Reveal answer

It turns internal work into an externally checkable claim that a human or another program can compare with reality and use for the next decision.

15. When is a tiny workflow a better leverage point than a huge one?

Reveal answer

When it repeats often, has clear state transitions and evidence, and can be carried reliably with low marginal human attention.

16. Resolve “replace yourself” in one sentence.

Reveal answer

Automate your repeated execution so your scarce attention moves to judgment, system ownership, and the next leverage point.

Scoring

13–16 correct: ready to teach and proceed. 9–12: rerun the lab checkpoint associated with each miss. 0–8: redraw the phase map and Core Four, then reproduce the A/B test again. A recognized answer that you cannot use in diagnosis counts as half credit.

  1. Why reliable long tool chains—not tool calling itself—separate agentic coding from AI coding.
  2. How the two README prompts provide evidence.
  3. What the Core Four are and how to use them to diagnose a failed commit.

TAC-1 glossary

Use Dan’s terms consistently. Each definition below is narrow enough to test against the lesson repository.

TAC
Tactical Agentic Coding: eight lessons, eight tactics, and one course codebase per lesson.
Loot box
The per-lesson collection of prompts, links, notes, and assets. The transcript may mishear it as “loop box.”
AI coding
Phase-one prompt-to-code work governed by context, model, and prompt. Useful and foundational, but the human often carries the surrounding workflow.
Agentic coding
Phase-two engineering in which the Big Three gain tools and a prompt reliably carries a chain of actions.
Agentic Engineer
An engineer who builds systems that can take engineering actions, rather than only prompting for isolated artifacts.
Commander of compute
The engineer who aims model capacity through outcomes, context, constraints, tools, evidence, and eventually triggers.
Big Three
Context, model, prompt—the primitives present in every AI coding interaction.
Core Four
Context, model, prompt, tools—the phase-two diagnostic vocabulary.
Context
Everything the model can see while working: repository files, current state, settings, instructions, and tool observations.
Model
The language model performing interpretation, reasoning, generation, and decisions inside the agentic system.
Prompt
The instruction describing outcome, starting state, constraints, actions, checks, and report. In TAC-1 it becomes a runbook.
Tools
The bounded actions an agent may perform. Phase-two significance comes from reliable long chains, not mere tool existence.
Agentic Coding Prompt
A workflow specification containing a sequence of tool calls. TAC-1 uses RUN, CREATE, RUN, and later REPORT.
Long tool chain
Several ordered actions whose observations and state must carry forward reliably toward one outcome.
Programmable agentic coding
Calling an agentic tool from code. In TAC-1, Shell, Python, and TypeScript all pass prompt.md to claude -p.
REPORT
The prompt block requiring returned evidence. TAC-1 asks for exact outputs of both generated Python files.
Closed loop
A structure where action produces observations that can be checked and used for the next decision rather than ending at generation.
System that builds systems
Dan’s description of moving up the stack: construct mechanisms that create and operate software-producing mechanisms.
Self-operating machine
The incremental end-state of a codebase whose agentic workflows increasingly run at the right time with bounded oversight.
Leverage
More valuable outcome per unit of scarce human attention. The “10x” label is arbitrary; the leverage point determines the multiplier.
Stop Coding
Tactic #1: stop hand-typing application code while increasing planning, review, code understanding, and closed-loop design.
Contradicting truth
The paradox that automating your repeated execution moves you toward higher-order judgment, improvement, and system ownership.
