Agent mission

Train a human commander to encode a class of engineering work into a reusable planning prompt, hand the resulting spec to a fresh implementation agent, and close the loop with tests, behavior, and a diff—so success depends on versioned interfaces rather than the human staying in the conversation.

01 · WHO ACTS?

A cast with sharp boundaries

Do not call every moving part “the agent.” TAC-3 works because judgment, action, and proof have different owners.

In the loop

Human commander

Names the outcome, chooses chore vs bug vs feature, reviews the generated plan, controls authority, repeats the key checks, and improves the reusable prompt when the run misses.

Planning phase

Fresh Claude Code planner

Receives /chore, /bug, or /feature; starts from README.md; researches the declared file surface; writes a durable plan under specs/. It does not implement.

Building phase

Fresh Claude Code implementer

Boots without the planning conversation. /implement passes in the spec, the agent changes code, runs plan-defined checks, and reports a summary plus diff stat. Any deeper self-review is observed behavior, not guaranteed by this prompt.

Deterministic helpers

Scripts as agent tools

copy_dot_env.sh, start.sh, and stop_apps.sh package repeated environment actions. They are not reasoning agents; they are callable, observable capabilities.

Verification role

Agent self-check + human check

There is no shipped verifier-agent file. The plan instructs the implementer to run embedded validation; the commander independently inspects the evidence and repeats the decisive test or behavior.

Not configured here

No subagent fleet

agents/README.md and adws/README.md are empty. TAC-3 achieves isolation with fresh top-level CLI processes; headless chaining is previewed, not implemented in this repo.

02 · WHAT CAN THE AGENT TOUCH?

The repository is shaped as an agent surface

The useful map is not every directory. It is the chain of interfaces that tells an agent what to know, what it may do, how it is invoked, what it must leave behind, and how failure travels upstream.

03 · HOW DOES CONTROL MOVE?

Plan → act → verify → recover

Dan moves the human to high-leverage boundaries. The agent gets long stretches of work; the commander retains classification, approval, and acceptance.

Why fresh agents matter

The process boundary is a test. If the implementer needs the old conversation, the plan is not yet a reusable asset. Freshness buys focus, exposes hidden dependencies, and prepares the same phase for headless invocation.

04 · WHY THESE FILES EXIST

Four contracts make the agent capable

Each contract answers a different systems question: What should the agent understand? What may it do? How is it called? What counts as done?

1. Prompt contract · turn a class into a plan

chore.md, bug.md, and feature.md are meta-prompts. Each fixes a research boundary and output shape while $ARGUMENTS supplies the unique request. Their differences encode engineering judgment: bugs require reproduction and root cause; features require user value, phases, tests, and acceptance.

Era note: THINK HARD was a course-era information-dense reasoning trigger. Keep the principle—allocate more reasoning to planning-grade work—but use the explicit thinking controls available in your current agent runtime.

Dan's design intentThe agent should not improvise how your team plans every time. Solve the class once in the template; let each run fill the facts.
.claude/commands/chore.mdabridged · exact headings
# Chore Planning

specified markdown Plan Format.

## Instructions
- Start your research by reading the README.md file.
- Use your reasoning model: THINK HARD about the plan.

## Chore
$ARGUMENTS

2. Tool and permission contract · bound capability

.claude/settings.json pre-approves 12 patterns: selected shell operations, npm/uv, file writes, and the environment-copy script. It explicitly denies force-push variants and rm -rf. A command outside the allow list is not thereby granted; it remains outside the pre-approved set.

Dan's design intentCapability should be programmable and reviewable. Give repeated safe work a smooth path, and make destructive shortcuts hit a hard boundary.
.claude/settings.jsonselected allow · complete deny
{
  "permissions": {
    "allow": [
      "Bash(uv:*)", "Bash(npm:*)",
      "Write",
      "Bash(./scripts/copy_dot_env.sh:*)"
      // 8 more entries on disk
    ],
    "deny": [
      "Bash(git push --force:*)",
      "Bash(git push -f:*)",
      "Bash(rm -rf:*)"
    ]
  }
}

3. Harness and launcher · call the system repeatedly

install.md composes priming, dependency installation, and copy_dot_env.sh. start.md delegates to scripts/start.sh, which checks environment state, launches backend and frontend, tests that both processes survived startup, prints their URLs, and traps shutdown.

The executor is even smaller: implement.md is a higher-order prompt. It accepts the plan path through $ARGUMENTS, tells the agent to implement it, and requires a summary plus git diff --stat.

Dan's design intentKeep the launcher generic and put task detail in the plan. Replaceability comes from a stable call shape, not from a giant omniscient prompt.
.claude/commands/implement.mdcomplete contract
# Implement the following plan
Follow the Instructions to implement the Plan
then Report the completed work.

## Instructions
- Read the plan, think hard about the plan and implement it.

## Plan
$ARGUMENTS

## Report
- Summarize the work in concise bullets.
- Report files and total lines with git diff --stat.

4. Verification contract · convert claims into evidence

Every planning template includes Validation Commands before its closing Notes section and requires the final step-by-step task to run them. The shipped floor is cd app/server && uv run pytest. The implementation report adds the diff stat. The commander still restarts the app and repeats the behavior or reproduction that matters.

Dan's design intentAn agent report is a claim, not proof. Close the loop with commands and observations that can contradict the agent; the human then repairs the plan or template and re-fires.
Plan Format · shared floorprompt evidence
## Validation Commands
Execute every command to validate the work with
zero regressions.

- cd app/server && uv run pytest

The last Step by Step Task must run these commands.
05 · WORKED AGENT RUN

Operate like Dan

First establish a trustworthy machine, then separate planning from building. The setup commands below come from the repository README; the agent commands come from the shipped command files.

  1. Establish the runtime

    Install both dependency sets and create the server environment file. Add at least one API key before starting.

    README · setup
    cd app/server
uv sync --all-extras
cp .env.sample .env
# edit .env: add OPENAI_API_KEY or ANTHROPIC_API_KEY

cd ../client
npm install
cd ../..
./scripts/start.sh
    SOURCE · README.md §§ Setup, Quick Start

  2. Prove the baseline before delegating

    At http://localhost:5173, load users.json from the sample-data UI and run “Show users with age between 20 and 40.” Record the working behavior and current stdout messages. This gives the later logging chore something observable to preserve.

    SOURCE · README.md § Usage + course run

  3. Generate a plan in a fresh agent

    Choose the work-class interface. This invocation asks the planner to research and write a spec; it does not authorize implementation.

    fresh agent A · planning only
    claude
/chore "Replace all server print statements with proper python logging. Use proper log levels. Preserve the exact same log output. Make sure all output is written to standard out"

    Open the new specs/*.md. Reject it if any placeholder remains, if the 18 prints in server.py plus one in main.py are not accounted for, or if the validation cannot prove stdout behavior and zero regressions.

    SOURCE · .claude/commands/chore.md + audited repo

  4. Cross the phase boundary

    Open a new agent with no planning conversation. Invoke /implement with the exact plan path returned by the planner. Do not re-explain the chore; missing context belongs in the plan. This companion does not print a pretend path because the shipped tree contains only the initial application spec.

    SOURCE · .claude/commands/implement.md

  5. Grade evidence, then improve upstream

    Require the plan's tests, a zero-hit search for remaining target prints, the same app behavior through scripts/start.sh, and a diff that matches scope. If a check fails, amend the plan or template and re-run with another fresh agent.

    commander · independent checks
    cd app/server && uv run pytest
cd ../..
rg -n 'print\(' app/server/server.py app/server/main.py
git diff --stat

    The shipped repo has 37 test_* function definitions, of which three are fixtures. Grade zero regressions and the intended behavior—not a video run's magic test total.

Now name the pattern

One phase, one fresh agent, one durable handoff. The planner produces the plan; the implementer consumes it; evidence decides whether the human accepts or repairs and re-fires.

Programmatic preview · course-era command

The lesson then invokes the same /feature planner through claude -p, streams JSONL, and produces a plan without an interactive session. That demonstrates a machine interface. The filmed --dangerously-skip-permissions flag removed a control for a narrowly scoped planning demo; treat it as historical evidence, not the default production posture. Prefer scoped tools, isolation, and explicit policy.

filmed shape · stream emitted to stdout
claude -p "/feature \"<feature description>\"" \
  --output-format stream-json \
  --dangerously-skip-permissions \
  --model <available-model> \
  --verbose
06 · FAIL CLOSED

Common agent-system failures

Most misses are not “the model was bad.” They are broken contracts around the model.

Misconfiguration diagnosis matrix
Failure signalSystem causeRepair
The build only works in the planning chatThe plan depends on hidden conversational memory.Move the missing facts into the spec; retest with a fresh implementer.
/chore starts editing codeThe planning/execution role boundary was blurred.Reassert the output contract: planner writes specs/*.md; /implement acts later.
A copied template produces generic mushRelevant Files still names another repo's surface, or one format is used for every work class.Specialize paths, questions, and acceptance evidence before re-firing.
The report says “done,” but behavior is wrongValidation checked activity or tests alone, not the user-visible claim.Add a claim-to-check matrix and repeat the decisive behavior independently.
The agent asks for broad permission bypassThe harness confuses convenience with required capability.Narrow tools, filesystem, credentials, and environment; preserve explicit denies.
The commander watches and corrects every movePresence is masking weak prompts and a missing recovery loop.Let the phase run, inspect artifacts at the boundary, then improve the reusable interface.
Setup guidance contradicts policyThe README suggests rm -rf node_modules, but settings deny rm -rf; it also says Python 3.10+ while troubleshooting says 3.12+.Let the deny rule win for agent actions and trust the executable manifest's >=3.10; repair documentation drift.
The planner claims 20 prints or requires 52 testsA run-specific narration was mistaken for a repository invariant.Count current disk evidence: 18 + 1 prints; require zero regressions and meaningful coverage.
Someone expects subagents or hooks to rescue the runNo such interface exists in TAC-3.Operate the shipped system: fresh CLI agents, command files, settings, scripts, specs, and human gates.

Failure injection

Give a fresh implementer a thin plan and resist the urge to explain. Its questions are useful telemetry: every missing fact points to the exact upstream artifact that failed.

07 · LAB · AGENT OPS

Change the system, not the application

Harden the chore planner so every generated plan assigns proof to an owner. No application logic may change.

Lab · add an evidence contract to chore.md

Hook: the current template seeds pytest, but it does not force every requested behavior to name an observable check or distinguish agent-run proof from the commander's independent check.

  1. 01 · BASELINE

    Run the old interface

    In a disposable branch or clone, fire the logging /chore request with a fresh planner. Inspect the plan. Can you map each claim—no prints, same message shape, stdout, zero regressions—to a named check and owner?

  2. 02 · CHANGE

    Edit one agent interface

    Modify only .claude/commands/chore.md. Add ## Verification Matrix to its Plan Format. Require one row per behavioral claim with columns for claim, check, expected observation, and owner (agent or human).

  3. 03 · RE-FIRE

    Test replaceability

    Open another fresh planner and send the exact same logging request. Do not mention the new section in chat. The template—not conversational memory—must cause the stronger output.

In a plain shell, set PLAN_PATH to the exact generated path the second planner reports, then run these checks.

observable checks · PLAN_PATH is the real path returned by the planner
rg -n '^## Verification Matrix$' "$PLAN_PATH"
rg -n '<[^>]+>' "$PLAN_PATH"
git diff -- .claude/commands/chore.md specs/
git diff --quiet -- app/; echo $?

Pass criteria

  • ✓ The new spec contains exactly one ## Verification Matrix.
  • ✓ No angle-bracket placeholder remains in the generated plan.
  • ✓ The matrix covers pytest, remaining-print search, stdout, and message-shape behavior.
  • ✓ At least one check belongs to the agent and one to the human commander.
  • ✓ git diff --quiet -- app/ exits 0: no application code changed.
  • ✓ A fresh planner produced the improvement without being coached about the new section.

What the lab proves

A one-time chat correction helps one run. A template correction changes every future run of that class. That is the leverage move.

08 · RETRIEVAL

Explain this agent OS in six sentences

Close the page. No notes, no “the AI handles it,” and exactly six sentences.

Your six-sentence frame

  1. State what the human commander owns and why that is a leverage boundary.
  2. Explain what the chore/bug/feature planner consumes and what it must produce.
  3. Explain how README, Relevant Files, and a durable spec replace conversation memory.
  4. Name the permission file, what its allow/deny boundary does, and why broad bypass is a separate decision.
  5. Explain how /implement plus scripts turns the reviewed plan into repeatable action by a fresh agent.
  6. Finish with the verification and recovery loop: evidence, independent check, upstream repair, re-fire.
Reveal the pass test

Pass if a listener can draw the loop, place the human at review/authority/acceptance gates, identify the real files at every interface, and predict why same-session success is weaker evidence than a fresh-agent rerun.
