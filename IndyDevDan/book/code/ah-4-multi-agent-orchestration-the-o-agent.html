Agentic Horizon · Multi-Agent Orchestration

Command the system, not every worker.

This lesson trains you to operate a fleet through one thin O-agent: the human commander chooses the outcome, working directory, risk boundary, and acceptance evidence; the orchestrator translates intent into agent lifecycle calls; focused primary agents do the engineering; and hooks, persistence, diffs, costs, and a reviewer decide whether the system can stop or must recover. The codebase is a reference operating system around agents—not a web-app tour.

one interface + CRUD for agents + observability → controllable compute

The hook: three agents can run in parallel while your attention remains serial. The O-agent is leverage only when it removes you as the message bus and keeps verification able to change the next move.

01 · Who acts?

The conductor owns coordination; specialists own the work

The easiest orchestration failure is role collapse: the human becomes a polling script, or the O-agent becomes the builder. Dan’s system separates authority, routing, execution, and evidence so each actor stays small and replaceable.

ActorOwnsMust not absorb
Human commander
authority		Outcome, acceptable cost, --cwd, risk tolerance, named acceptance evidence, and final escalation decisions.Polling every terminal, copying every handoff, or rescuing a worker by silently doing its task.
Orchestrator Agent
meta-agent		Analyze, plan the fleet, create, command, monitor, interrupt, report cost, read logs, and archive agents through eight management tools.Implementation detail. Its prompt says command-level agents do writing, editing, and testing.
Managed primary agents

Dan’s ordering is the point: orchestration comes after you can build useful custom agents and observe them. Ten vague agents are not a fleet; they are ten simultaneous ambiguities.

02 · Agent surface map

The fleet sees a mounted operating surface

Read from the agent’s perspective. “The repository” is too vague. The real world is the prompt, tools, project settings, working directory, session state, lifecycle methods, and evidence mounted by the harness.

03 · Control loop

Out of the loop does not mean out of control

In-loop work asks the commander to make the next move. Out-of-loop work encodes that move in a harness and returns only on completion, a failed gate, or a bounded escalation. Both use plan → act → verify → recover; the difference is who carries the loop.

In loopchat + one worker
PlanHuman chooses the next prompt and watches the conversation.
ActOne agent answers or calls a bounded tool.
VerifyHuman reads the response and decides if it is enough.
RecoverHuman rephrases, supplies context, or stops.
Out of loopO-agent + fleet
PlanO-agent selects roles; workflow prompt declares phases and receipts.
ActPrimary agents run in separate resumable contexts.
VerifyHooks prove completion; tests, diffs, and reviewer verdict judge results.
RecoverRe-command/replace the worker, re-review, compact, or escalate.
Report FAIL and stop = open loop← verdict routes the next move →Repair → re-verify → accept/escalate = closed loop
P · Prompt inputCmd+K message states the desired result.
T · TriggerFastAPI starts process_user_message() with asyncio.create_task.
E · Environmentcwd, project settings, templates, tools, database, and running processes.
R · ReviewEventStream, status, costs, file ledger, diffs, tests, and reviewer verdict.

PITER is the lesson’s conceptual mapping, not a string in the repository. The real mechanics are prompt input → HTTP trigger → mounted environment → observability review.

04 · One worked agent run

Plan → build → review without becoming the workflow engine

The climax workflow is encoded in apps/orchestrator_3_stream/.claude/commands/orch_plan_w_scouts_build_review.md. The orchestration is mostly prompt-driven: the O-agent follows a reusable recipe and uses management tools plus Bash(sleep 15).

Commander states one outcome

Use Cmd+K and invoke the workflow with a concrete change and acceptance criteria. The commander does not pick files for every worker.

receipt · one prompt

O-agent creates three primary agents up front

A dynamic planner gets a custom system prompt; the builder uses build-agent; the verifier uses review-agent. Each receives its own persisted session.

receipt · 3 create_agent calls

Planner explores and writes a spec

The O-agent commands the planner, then sleeps and checks status until a response event is followed by a Stop hook. It reads the resulting path, not the planner’s whole hidden context.

receipt · spec path + response → Stop

Builder receives the artifact handoff

The next prompt names the original outcome, plan path, target files, and implementation approach. The builder edits and runs the checks it was given.

receipt · diff + tool events + validation output

Reviewer compares request, plan, and diff

The review template is analysis-only. It uses git evidence, writes a risk-tiered report, and ends PASS or FAIL.

receipt · review report + verdict

Commander reviews the system, not every token

Inspect the final artifacts, event order, costs, context bars, and verdict. Keep agents for follow-up or archive them when the artifact—not the personality—is what matters.

receipt · accept, recover, or escalate

Your job during the run

  • Protect the outcome and acceptance criteria.
  • Watch whether roles remain separate.
  • Use evidence, not confident prose, to judge progress.
  • Intervene on a failed gate, runaway cost, wrong cwd, or missing authority decision.
  • Do not hand-carry planner context into the builder; pass the artifact path.
Name the pattern: single interface + primary-agent lifecycle + observable artifact relay. A subagent template is “pulled up a level” when create_agent(subagent_template=...) gives it a name, session, card, cost, and re-promptable lifecycle. The O-agent stays thin by reducing and delegating; concrete files carry the work between roles.

05 · Why these files exist for agents

Four contracts make the fleet operable

The snippets below are contract evidence, not a source tour. Each answers one operating question: what may the agent understand, what may it do, how is it mounted, and what counts as evidence?

Prompt contract · what the O-agent is allowed to understand

apps/orchestrator_3_stream/backend/prompts/orchestrator_agent_system_prompt.md

The full overwrite names a meta-agent, gives it an eight-tool vocabulary, teaches compacting and monitoring, and draws the crucial boundary: it may use Bash for information or debugging, but command-level agents do the heavy lifting.

The {{SUBAGENT_MAP}} placeholder is filled at runtime from <cwd>/.claude/agents/*.md. The prompt therefore becomes an inventory of currently mountable workers instead of a hard-coded fleet.

Dan’s design intent: keep coordination knowledge centralized and implementation knowledge delegated, so the O-agent’s context remains small while worker contexts stay focused.

Tool and permission contract · capability is explicit

apps/orchestrator_3_stream/backend/modules/orchestrator_service.py · agent_manager.py · .claude/agents/*.md

The O-agent receives exactly eight qualified management tools plus Bash, Read, SlashCommand, and Skill. Managed agents receive a prompt, model, cwd, hook set, allowlist, denylist, and acceptEdits mode.

Template frontmatter is a compact capability declaration: the fast scout says tools: Read, Glob, Grep; the builder adds Write, Edit, and Bash; the reviewer can write reports but is instructed not to fix code.

Dan’s design intent: tools are part of the program. A role is credible only when its tool surface supports the work and denies accidental scope.

Harness and launcher · how the agent becomes a running system

apps/orchestrator_3_stream/start_be.sh · backend/main.py · modules/orchestrator_service.py · modules/agent_manager.py

The shell launcher chooses --cwd and optional --session. FastAPI constructs one orchestrator and one scoped AgentManager. The service mounts the eight Python tools as an in-memory MCP server; the manager starts managed agents in the background and resumes their stored sessions.

POST /send_chat returns immediately after scheduling work. Results travel back through WebSocket events, so the browser is an observer and control surface rather than the agent runtime.

Dan’s design intent: make agents callable infrastructure. A prompt becomes a trigger; a working directory becomes an environment; session IDs and Postgres make workers replaceable across interactions.

Verification contract · completion is not correctness

backend/modules/command_agent_hooks.py · frontend/src/components/event-rows/FileChangesDisplay.vue · .claude/agents/review-agent.md

A response followed by a Stop hook answers “did this run finish?” It does not answer “is the change right?” Correctness evidence comes from validation commands, produced-file diffs, consumed-file context, git review, and a PASS/FAIL verdict tied to the original request.

The observer plane persists raw events, adds short Haiku summaries, broadcasts through WebSocket, and exposes filters by agent, tool, response, thinking, hook, level, and regex. You can open a produced file directly in the editor.

Dan’s design intent: measure the fleet closely enough to improve and scale it. Verification is useful only when its evidence can route the system backward.

Execution receipt
response event → Stop hook
Behavior receipt
real command output, test, build, or browser evidence
Change receipt
Consumed / Produced ledger + inline git diff
Decision receipt
review report with risk tiers and PASS / FAIL

  • Backend is on 9403; frontend is on 5175.

07 · Common agent failures

Misconfiguration turns leverage back into supervision

Agent failures are often operating-system failures: the wrong role, capability surface, working directory, receipt, or recovery branch. Diagnose the ring before blaming the model.

1 · Mis-prompted conductor

Symptom: the O-agent reads, edits, and tests the feature itself. Its context becomes the project’s junk drawer.Repair: restore the meta-role boundary and command a focused primary agent with a concrete artifact.

2 · More agents, no decomposition

Symptom: workers overlap, contradict, or all inspect the same files. Compute rises; synthesis ownership disappears.Repair: give each agent one prompt, one purpose, and one result. Name the artifact handoff.

3 · Wrong cwd, wrong agent OS

Symptom: templates or commands are missing, agents edit the wrong project, or the UI lists a different capability palette.Repair: treat --cwd as an authority decision; verify it in /get_orchestrator before dispatch.

4 · Tool name without a mounted server

Symptom: the Playwright or Firecrawl template advertises MCP tools that do not exist at runtime.Repair: activate and verify the optional .mcp.json.sample servers, or choose a template whose real tools are mounted.

5 · Completion mistaken for correctness

Symptom: response → Stop is treated as PASS. The workflow reports success without running the plan’s validation commands.Repair: separate execution receipt from behavioral receipt and reviewer decision.

6 · Reviewer writes a report into a void

Symptom: the shipped plan/build/review workflow reports FAIL and stops; no repair or re-review is encoded.Repair: add a bounded verdict branch: FAIL → builder repair → reviewer re-check → accept or escalate.

7 · Human stays in the loop

Symptom: you manually ask every agent if it is done and relay every response.Repair: let the workflow’s prompt-driven sleep/check cadence carry monitoring; review artifacts and exceptions.

8 · Observability without consequence

Symptom: costs, context pressure, tool errors, and diffs are visible, but nothing changes course.Repair: attach thresholds and branches: compact at pressure, interrupt runaway work, reject bad diffs, replace a blocked worker.

Source-audit warning · template permissions widen on re-command

Creation honors a template’s tools frontmatter. The current command_agent() resume path rebuilds ClaudeAgentOptions with the comprehensive default allowlist instead of the original template allowlist. A “read-only” scout is therefore prompt-bounded after creation, not reliably tool-bounded on later commands. Treat this as a real harness gap: persist the effective allowlist with the agent and reuse it on resume before claiming least privilege.

08 · Agent ops lab · close the verifier loop

Make FAIL change the next move

Change the agent system, not Vue or FastAPI business logic. You will reprogram the orchestration prompt so reviewer evidence routes backward through one bounded repair pass.

Work only in the workflow contract

apps/orchestrator_3_stream/.claude/commands/orch_plan_w_scouts_build_review.md

  1. Baseline the open loop. Find the Review Complete and Final Report instructions. Write one sentence describing what currently happens after a FAIL: it is reported, but no repair command or re-review is required.
  2. Add a bound. Define MAX_REPAIR_PASSES: 1 in Variables. A closed loop without a cap can oscillate and burn tokens.
  3. Add a verdict branch. If review is PASS, continue to the final report. If FAIL and the repair count is below the cap, command the existing builder with the review report path, exact blocker/high-risk findings, original task, and plan path.
  4. Reuse the real completion contract. Sleep 15 seconds and call check_agent_status until the repair run shows a response followed by Stop.
  5. Re-verify independently. Command the existing reviewer to inspect the new diff and prior report. Monitor it to response → Stop and record its new PASS/FAIL verdict.
  6. Escalate honestly. If the second verdict still fails, stop autonomous repair and report the unresolved findings to the human. Do not silently declare success.
  7. Test the prompt surface. Restart the backend from apps/orchestrator_3_stream, confirm the command remains visible in the Cmd+K palette, and ask the O-agent to explain the command’s PASS and FAIL routes before running it on a small documentation-only task.
  8. Review the trace. Filter the EventStream to builder and reviewer. Verify the sequence and inspect cost, tool calls, Stop hooks, produced report, and final decision.
Review 1PASS or FAIL
FAILsend report
Repairsame builder
Review 2independent check
Stopaccept or escalate

Expected first failure: adding “retry on FAIL” without a pass limit, artifact path, completion signal, or escalation rule creates a vague recursive prompt. Fix the contract until every branch names its input, actor, receipt, and terminal condition.

Observable pass criteria

  • Only the orchestration command changes.
  • MAX_REPAIR_PASSES: 1 is explicit and used.
  • PASS skips repair; FAIL routes the review artifact to the existing builder.
  • Repair and re-review each require response → Stop.
  • The same independent reviewer performs the second check.
  • A second FAIL escalates to the commander; it cannot loop again.
  • The command remains discoverable under the intended cwd.
  • EventStream evidence shows review → repair → re-review when the FAIL branch is exercised.
  • The final report distinguishes completed execution from accepted correctness.

09 · Retrieval

Explain the agent OS in six sentences without looking

Cover one idea per sentence. If you cannot fill a box, return to the surface map or control loop—not the raw source.

The human commander owns…
The O-agent is thin because…
--cwd changes capability by…
A managed primary agent differs from a Task subagent because…
Hooks, Postgres, WebSocket, and the UI together provide…
A closed loop reacts to reviewer FAIL by…
Reveal a six-sentence model answer
  1. The human commander owns the outcome, working directory, risk, cost boundary, and acceptance evidence, not the manual relay between every worker.
  2. The O-agent stays thin because its overwritten prompt and eight management tools make it coordinate primary agents while delegating implementation.
  3. The --cwd value mounts the project, agent templates, slash-command workflows, and file authority that the fleet can see.
  4. A managed primary agent has its own name, prompt, model, resumable session, cost, card, and artifacts, while a Task subagent is nested inside another agent’s run.
  5. Hooks, Postgres, WebSocket, and the observer UI turn prompts, tool calls, status, costs, consumed files, produced diffs, and Stop events into reviewable receipts.
  6. A closed loop routes a FAIL report through a bounded repair and independent re-review, then accepts or returns authority to the human.
