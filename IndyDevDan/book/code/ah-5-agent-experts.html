Agent mission · not a code tour

Build an expert that can earn its next starting point

This lesson trains you to command a narrow agent system whose useful work survives the session: the human chooses the domain and risk boundary; prompts focus the agent; tool and permission contracts bound its actions; launchers make it programmable; an expertise file carries a fallible mental model; and verification closes the loop before that model is reused.

human intent + scoped context + bounded tools + Act → Learn → Reuse + proof

The leverage test: run one should change the validated starting state of run two. If the agent only produces an answer and forgets, you automated execution—not expertise.

03 · Agent surface map

The repo is shaped as an operating surface

The agent does not need every file at once. It needs interfaces that tell it what to know, what it may do, how it is invoked, what state persists, and what counts as proof.

04 · Control loop

Put execution inside the loop; keep judgment at the gates

Dan’s leverage move is not removing the human. It is moving the human from keystroke supervision to system design and evidence review.

Inside loopagent-owned execution
ReuseRead expertise first; validate relevant claims against current code.
PlanTurn the outcome into an artifact a fresh builder can consume.
ActMake the useful, scoped change through the build contract.
VerifyRun builds/tests and inspect runtime or diff evidence.
LearnUpdate expertise from validated changes; allow no-op.
↺ next invocation starts from the updated mental model, then validates again
Outside loopcommander-owned gates
Choose domainPrefer evolving, complex, high-risk territory you can evaluate.
Set boundaryName outcome, working directory, tools, cost, and stop conditions.
Launch onceInvoke the composite workflow; avoid narrating each keystroke.
Review proofInspect behavior, tests, and the learned-state diff—not confidence.
RecoverTighten prompt/harness, rerun, reseed, or reject the learned update.
One agent · one purposePlan, build, and self-improve are fresh stages, not one swollen context.
Replaceable workersThe plan and diff are handoff artifacts; any capable worker can consume them.
Closed before cleverA modest agent with feedback beats an impressive agent with no proof or persistence.

05 · Why these files exist for agents

Four contracts make the agent operational

Read the snippets as interface evidence. The application code matters only where it proves what the agent is allowed to understand, do, invoke, or trust.

1 · Prompt contract — scope the mind

.claude/commands/experts/database/question.md

The question agent is not told “know the repo.” It gets a narrow domain, a mandatory first read, a validation rule, a no-write boundary, and a report schema with file-and-line evidence.

Dan’s design intent: expertise is an index, not an oracle. “Read expertise → validate code → answer” turns stored state into faster navigation without surrendering truth.

question.mdprompt
## Instructions
- IMPORTANT: ... DO NOT write, edit, or create files
- ... validate ... EXPERTISE_PATH against the codebase

## Workflow
- Read the EXPERTISE_PATH file
- Review, validate, and confirm ... against the codebase

2 · Tool & permission contract — scope the hands

.claude/commands/experts/database/question.md · apps/orchestrator_3_stream/backend/modules/agent_manager.py · apps/nile/server/src/services/agent_expert.py · .claude/settings.json

Command frontmatter declares available tool families. The orchestrator’s SDK harness uses acceptEdits for working agents, while Nile gives its product expert only two shopping tools and denies filesystem, shell, delegation, and planning tools.

.claude/settings.json is primarily a hook map here—not a complete permission manifest. Its pre-tool hook blocks dangerous recursive removal; the commented-out environment-file guard does not currently protect secrets.

Dan’s design intent: capability should follow purpose. The product expert can recommend and stream; it cannot wander the machine. Broad command agents are powerful, so the commander must treat prompt scope and diff review as real safety gates.

database/question.mdfrontmatter
allowed-tools: Bash, Read, Grep, Glob, TodoWrite
agent_expert.pySDK options
allowed_tools=[
  "mcp__shopping__find_related_products",
  "mcp__shopping__stream_section",
]
disallowed_tools=["Read", "Write", "Bash", ...]

3 · Harness / launcher — make the agent callable

apps/nile/server/src/services/agent_expert.py

The harness selects tools, injects the per-user mental model into the system prompt, resumes a user session when one exists, sends a deterministic task prompt, and consumes streamed tool calls. The model is one replaceable field inside the system.

At the outer shell, start_be.sh chooses working directory and optional session, while start-orchestrator/SKILL.md packages those launch actions for an interactive agent.

Dan’s design intent: once the call is code, the agent stops being a chat trick. It becomes infrastructure you can start, observe, interrupt, test, and swap.

agent_expert.pylauncher
shopping_server = create_sdk_mcp_server(
  name="shopping_expert", tools=[...]
)
options = ClaudeAgentOptions(
  mcp_servers={"shopping": shopping_server},
  system_prompt=system_prompt,
  resume=existing_session_id,
)
async with ClaudeSDKClient(options=options) as client:
  await client.query(streaming_user_prompt)

4 · Verification contract — close the loop

.claude/commands/experts/*/self-improve.md · apps/orchestrator_3_stream/backend/tests/ · apps/orchestrator_3_stream/frontend/package.json

Self-improve reads the current mental model, checks implementation, records discrepancies, updates only useful expertise, enforces a 1,000-line budget, and validates YAML. Application proof adds real-database tests, real-agent integration tests, WebSocket observers, frontend builds, and browser validation.

The shipped self-improve snippets call raw python3, but root CLAUDE.md says every Python command goes through uv. The policy-compliant repair belongs in the learning prompt—exactly the system-layer change the lesson teaches.

Dan’s design intent: do not reward activity. Reward a claim that survived source validation, a command that passed, or a behavior you observed. A no-change Learn pass is valid when the model is already aligned.

State: wc -l .../expertise.yaml stays within MAX_LINES.
Syntax: parse YAML through a uv-managed Python environment.
Code: npm run build and relevant uv run pytest suites pass.
Behavior: UI or WebSocket observer shows the requested outcome.
Learning: git diff -- .../expertise.yaml is accurate, concise, and reviewable.

06 · Operate like Dan

One worked run, with commander gates

These commands come from the checked-out README and launch scripts. Run shell commands from the repository root unless a step changes directories; run slash commands inside Claude Code.

Provision the harness

Install prerequisites, copy environment configuration into both orchestrator apps, and create the database schema.

cp .env.sample .env cp .env apps/orchestrator_3_stream/.env cp .env apps/orchestrator_db/.env uv run apps/orchestrator_db/run_migrations.py

Start the system in two terminals

The real launcher defaults are backend 9403 and frontend 5175.

cd apps/orchestrator_3_stream ./start_be.sh # second terminal, same directory ./start_fe.sh

Prime with a safe Reuse run

Ask the partial database expert a read-only question. Watch for expertise as the first read, followed by current models and migrations.

/experts:database:question "Does information flow between our database tables? Cite the exact current files and lines."

Run Learn without demanding churn

Let the self-improve contract validate the entire database mental model. “Nothing to do” is a clean result if the evidence supports it.

/experts:database:self-improve false

Understand the complete expert as a shipped trace

The course run used one command to plan the WebSocket counter, build it, and improve expertise. The final tree already contains that counter, plan, and learned state—study it as loop archaeology rather than pretending it is a fresh change.

/experts:websocket:plan_build_improve "Add a session-based counter to the app nav bar that displays the total number of WebSocket events."

Verify the result and the learner

Separate application proof from learned-state proof. Build the frontend, run relevant backend tests when its real database is available, and inspect expertise independently.

git diff -- .claude/commands/experts/websocket/expertise.yaml cd apps/orchestrator_3_stream/frontend npm run build cd ../backend uv run pytest tests/ -v

Commander checklist

  • Can I evaluate this domain?
  • Is the action useful and observable?
  • Are the tools narrower than the job?
  • What is the source of truth?
  • What proves application success?
  • What proves the mental model improved?
  • Will I inspect the diff before reuse?

Never do this: repair a non-empty expertise file by hand. Repair the self-improve rubric and rerun it.

07 · Common agent failures

Most failures are system failures wearing model-shaped masks

Diagnose the contract, boundary, harness, or feedback path before reaching for a larger model.

Mis-prompting: “be a database expert”

No first read, ground-truth rule, write boundary, or report evidence exists.

Repair → encode expertise-first, source-second workflow and exact proof.
Broad hands on a narrow job

A read-only question still exposes Bash and TodoWrite; a general command agent gets a large tool set under acceptEdits.

Repair → remove tools the prompt does not need; keep product agents tool-only.
Settings mistaken for permissions

Hooks log and sometimes block, but root settings do not express a comprehensive permission policy. The environment-file block is commented out.

Repair → inspect frontmatter, SDK options, hook behavior, and secrets handling as separate layers.
Expertise trusted as truth

Stale ports, line counts, or architecture claims slip into answers because the agent skips source validation.

Repair → make current code and runtime behavior win every disagreement.
Learning forced to produce a diff

The agent adds prose because the operator treats “nothing changed” as failure.

Repair → grade the search and validation; accept a justified no-op.
Verification exists only in prose

The plan says “test it,” but no command, observable behavior, or learned-state diff closes the loop.

Repair → specify build/test commands, UI evidence, and diff review before launch.
Context delegation without handoff discipline

Fresh agents receive vague tasks or the entire transcript, so replaceability and focus vanish.

Repair → pass the plan path to build and the code diff to self-improve.
Observability mistaken for enforcement

send_event.py can fail to reach localhost:4000/events and still exits zero so agent work continues.

Repair → decide which failures should merely report and which must block the loop.
Staying in the loop

The commander narrates every search, edit, and check, recreating manual software work through an agent-shaped terminal. The repository’s composite prompt exists to move the human to scope, launch, evidence review, and recovery.

Repair → program the loop once; intervene at explicit gates, not every keystroke.

08 · Lab · agent ops, not application logic

Harden the partial database expert

Change only the agent system. Tighten what question mode can do, repair the learning verifier to match repository policy, then prove the expert still answers and learns safely.

Mission · 25–40 minutes

  1. Capture a baseline with git status --short and copy the current frontmatter/tool list from .claude/commands/experts/database/question.md into your notes.
  2. Change question mode’s allowed-tools to the minimum its workflow requires: Read, Grep, Glob. Do not change application code or expertise.yaml.
  3. In .claude/commands/experts/database/self-improve.md, replace the raw-Python YAML check with a uv-managed check. Preserve MAX_LINES: 1000 and the rule that no change may be the correct result.
  4. Add one verification instruction requiring the final report to include git diff -- .claude/commands/experts/database/expertise.yaml, or explicitly state that the diff is empty.
  5. Run /experts:database:question "Which tables carry agent activity, and how are they related?". Confirm its first meaningful read is expertise and its answer cites current models/migrations.
  6. Run /experts:database:self-improve false. Review the report and diff. If expertise changes, the agent—not you—must author every changed expertise byte.
  7. Run git status --short again and explain every changed path as prompt-system work or agent-authored learned state.

Fail → try: if the narrowed question agent cannot validate a fact, do not restore broad Bash by reflex. Identify the exact missing operation and add only the smallest capability that supplies it.

Observable pass criteria

  • Question mode exposes no write, shell, or task-management tool.
  • The answer reads expertise first and verifies with current source.
  • No application file changes.
  • No human-authored expertise edits.
  • Self-improve’s YAML check runs through uv.
  • Final expertise stays at or below 1,000 lines.
  • The report contains a reviewable expertise diff or an explicit empty-diff statement.
  • You can explain why tool minimization improved replaceability and risk control without changing the model.

09 · Teach-back · close the page

Explain this lesson’s agent OS in six sentences

No notes. One sentence per box. Name roles and contracts—not file contents for their own sake.

What the human commander decides and refuses to do.
What makes this agent an expert rather than a generic executor.
How prompts, context, tools, and permissions bound the work.
How a shell/Skill/SDK harness turns the agent into a callable system.
How plan → act → verify → learn → reuse closes the loop.
How the system detects drift and recovers without hand-editing expertise.
Reveal a six-sentence model answer

The human commander chooses an evolving domain, sets the outcome and authority boundary, reviews proof, and never repairs learned expertise by hand. The expert is an ordinary narrow agent whose useful actions update a persistent mental model that a later run loads and revalidates. Prompt files scope purpose and evidence, CLAUDE.md supplies project invariants, tool allowlists and SDK options bound capability, and hooks observe or block selected events. Shell scripts and Skills start the environment, while ClaudeSDKClient makes models, tools, sessions, prompts, and working directories programmable. Fresh agents hand a plan to a builder, verify code and behavior, pass the change evidence to self-improve, and reuse only the reviewed mental model. When drift or false expertise appears, the commander fixes the prompt, permission, launcher, or verifier and reruns the loop instead of treating YAML as truth.
