Tactic #5 · Always Add Feedback Loops

The agent OS that proves its own work

The NL→SQL app is the workbench. The lesson is the control plane around it: prompts that name success, tools that emit evidence, launchers that create fresh agents, and bounded recovery loops that keep going until the evidence is green—or fail loudly.

OS
Agent mission

Train the commander to turn “I would check this myself” into a callable validator, attach that validator to every agentic request, and then move the whole request→validate→resolve cycle into a reusable ADW node—so fresh, replaceable agents can plan, build, test, recover, and leave auditable proof without borrowing the human’s attention.

01 · WHO ACTS?

The “agent” is a cast, not a blob

TAC-5 gains leverage by separating who chooses, who reasons, who executes deterministic checks, and who decides whether the run is trustworthy.

The TAC-5 agent cast and its responsibility boundaries
ActorOwnsMust not quietly own
Commander
Human engineer		 Chooses the issue and workflow, audits authority, defines acceptance, reviews the PR and the evidence. Manually repairing every red check or becoming the permanent click-through tester.
Reasoning
Planner + implementer		 /bug, /feature, or /chore writes the plan; a fresh /implement agent changes the repo from that durable handoff. Inventing scope outside the issue, or declaring success without the plan’s validators.
Judge
Test runner agents		 /test turns compiler, linter, test, and build output into typed results. /test_e2e drives the browser and saves screenshots. Owning retry policy. Deterministic Python code decides when to retry or stop.
Repair
Resolver agents		 One fresh /resolve_failed_test or /resolve_failed_e2e_test context per failure, using a reproducible command or test path. Hiding infrastructure failures, deleting the rule, or changing unrelated code.
Control
ADW Python scripts		 State, sequencing, retry bounds, branch checkout, issue comments, commits, pushes, and PR creation. Semantic judgment. Code schedules; agents interpret.
Tool
Scripts + Playwright		 reset_db.sh makes assertions deterministic; start.sh boots the app; Playwright turns user behavior into observable evidence. Deciding what “good UX” means without an explicit success criterion.

IndyDevDan pattern

Code decides; agents judge; humans command. That split makes each agent replaceable. A better model can enter later without rewriting the deterministic state, retry, and evidence machinery.

02 · WHAT MAKES THE AGENT CAPABLE?

The repository is an operating surface

The useful map is not “frontend here, backend there.” It is the chain of interfaces a fresh agent touches before it can safely act on either.

03 · HOW DOES CONTROL MOVE?

Close the inner loop, then move it outward

“In-loop,” “out-of-loop,” and “closing the loop” are different. The first two describe where the human sits. The third describes whether the agent receives feedback and acts on it.

One worked agent run

A failing backend validator shows the whole operating system in miniature.

1 · Plan/bug writes the contract

The generated spec ends with exact validation commands.

2 · Act/implement changes code

A fresh agent consumes the file, not the planner’s chat.

3 · Fail/test returns JSON

The failing item includes its purpose, error, and pasteable command.

4 · TryResolver reproduces it

A new agent receives only that failure payload and makes a targeted repair.

5 · ProveThe harness reruns

Green continues to E2E; red stops at a bound and reports honestly.

Name the pattern

Request → Validate → Resolve. The validator’s output is not a postscript; it is the next input to the agent. That feedback edge is what changes a one-shot generator into a closed-loop system.

04 · WHY THESE FILES EXIST

Four contracts make the loop programmable

Each contract answers a different systems question: What does the agent understand? What may it do? How is it called? What counts as success?

1. Prompt contract · success travels with the request

.claude/commands/bug.md does more than ask for a fix. It creates a plan that must carry reproduction, root cause, ordered tasks, and validators. UI work conditionally creates a natural-language E2E spec.

Dan’s design intentDo not rely on remembering to ask for proof. Put the validation block in the prompt that creates every future plan.
.claude/commands/bug.mdabridged · exact phrases
## Step by Step Tasks
IMPORTANT: Execute every step in order, top to bottom.

## Validation Commands
Execute every command to validate the bug is fixed
with zero regressions.

- cd app/server && uv run pytest
- cd app/client && bun tsc --noEmit
- cd app/client && bun run build

2. Tool and permission contract · declared policy versus effective policy

.claude/settings.json names a narrow allowlist, three deny patterns, and five lifecycle hooks. pre_tool_use.py also intends to block real .env access and dangerous recursive deletion.

Dan’s design intentAuthority should be versioned, reviewable, and smaller than the agent’s imagination.
Audit finding: the programmatic launcher later enables --dangerously-skip-permissions, while the hook command ends in || true, which masks the hook’s non-zero blocking exit. The settings file is therefore documentation of intended policy—not a complete proof of effective enforcement.
.claude/settings.jsonabridged · exact entries
{
  "allow": ["Bash(uv:*)", "Write", "Bash(ls:*)"],
  "deny": [
    "Bash(git push --force:*)",
    "Bash(git push -f:*)",
    "Bash(rm -rf:*)"
  ]
}

3. Harness contract · a CLI agent becomes a callable phase

adws/adw_modules/agent.py converts an AgentTemplateRequest into a fresh Claude Code process. It saves the slash-command prompt first, requests stream-json, writes raw JSONL, finds the result message, and returns a typed response.

Dan’s design intentKeep the agentic layer callable from Python, shell, cron, or webhook. The phase should be replaceable because its boundary is data, not a live chat.
adws/adw_modules/agent.pyabridged · evidence
cmd = [CLAUDE_PATH, "-p", request.prompt]
cmd.extend(["--model", request.model])
cmd.extend(["--output-format", "stream-json"])
cmd.append("--verbose")

if request.dangerously_skip_permissions:
    cmd.append("--dangerously-skip-permissions")

4. Verification contract · evidence can drive code

test.md asks the test agent for structured results. TestResult and E2ETestResult let deterministic Python count failures, fan out resolver agents, gate browser work on green unit checks, and choose a final exit code.

Dan’s design intentMake every failure reproducible by the next agent. A name and error are not enough; carry the exact command or E2E path.
Current packaging: this course version says “return ONLY JSON” and parses text. A schema-validated structured-output boundary is the stronger modern form, but the architectural split is unchanged.
.claude/commands/test.mdexact output shape
[
  {
    "test_name": "string",
    "passed": true,
    "execution_command": "string",
    "test_purpose": "string",
    "error": "optional string"
  }
]
05 · OPERATE LIKE DAN

Run the system from authority to evidence

The real README supplies the commands. The operator’s job is to add the missing control checks around them.

  1. Install the two workbenches and set authority

    Start each commented group from tac/tac-5/. The coding agent needs GitHub and Claude credentials; the NL→SQL app needs a server provider key. Copy the samples, edit locally, and never place real secret values in an agent prompt or trace.

    # From tac/tac-5/
cp .env.sample .env

export GITHUB_REPO_URL="https://github.com/owner/repository"
export ANTHROPIC_API_KEY="sk-ant-..."
export CLAUDE_CODE_PATH="/path/to/claude"
gh auth login

# From tac/tac-5/
cd app/server
cp .env.sample .env
uv sync --all-extras

# From tac/tac-5/
cd app/client
bun install

  2. Audit authority before execution

    Read .claude/settings.json, .claude/commands/install.md, adws/adw_modules/agent.py, and the trigger you intend to expose. The effective permission mode comes from all four—not the settings file alone.

  3. Make the test world deterministic

    # From tac/tac-5/
./scripts/reset_db.sh
./scripts/start.sh

    Confirm the frontend at http://localhost:5173 and backend at http://localhost:8000. Resetting backup.db into database.db is what makes exact row-count assertions meaningful. start.sh stays in the foreground; leave it running and open a second terminal at tac/tac-5/ for the remaining steps.

  4. Fire the smallest useful phase

    # In terminal 2, from tac/tac-5/
cd adws
uv run adw_plan.py 456
uv run adw_build.py
uv run adw_test.py 456

    Those are the README forms. The live checkout has drifted: adw_build.py actually requires 456 <adw-id>; adw_test.py accepts the ADW ID as an optional second argument. Until docs and entry points agree, trust each script's usage guard. The ADW ID is the join key across state, prompts, raw output, logs, issue comments, branch, and PR.

  5. Then compose the full closed loop

    # In terminal 2, from tac/tac-5/
cd adws
uv run adw_plan_build_test.py 456

    Plan must finish before build; build must finish before test; counted unit failures block E2E. The wrapper stops when a child returns non-zero, and the test phase exits non-zero for counted failures. That is not fully fail-closed: malformed unit-result JSON, zero E2E discovery, and push/PR failures can still become green or log-only outcomes. The evidence audit in the next step is part of operation, not decoration.

  6. Read proof, not vibes

    Look for the issue’s 📊 Test Run Summary, the PR, and the run tree under agents/<adw-id>/. For browser coverage, require a log line that reports three E2E files plus screenshots—not merely a successful process.

    Stateadw_state.json
    Intentprompts/*.txt
    Traceraw_output.jsonl
    Experienceimg/**/*.png

Working-directory trap

The README runs commands after cd adws, while adw_test.py discovers E2E specs with the relative glob .claude/commands/e2e/*.md. If the run says “Found 0 E2E test files,” do not call it green; run the phase from the repository root (for example, uv run adws/adw_test.py 456 <adw-id>) or fix the path contract.

06 · FAIL LOUDLY

Common agent-system failures

These are failures around the code. The application can be perfectly written while the system that operates it is unsafe, blind, or falsely green.

Open-loop prompting

Symptom: “Implement this feature” ends with a confident summary and no compiler, test, build, or browser evidence.

Repair: require Request → Validate → Resolve in the prompt template, not as a follow-up the commander must remember.

Decorative permissions

Symptom: the allow/deny file looks narrow, but execute_template() always sets permission bypass; the pre-tool hook’s exit code is swallowed by || true.

Repair: test the effective launcher path. Make bypass explicit per workflow and let blocking hooks return a blocking status.

Webhook-shaped remote execution

Symptom: trigger_webhook.py accepts a GitHub-shaped body and launches a background ADW, but the route contains no webhook-signature verification.

Repair: keep it local/course-only until request authenticity, replay handling, and least-privilege credentials are enforced.

Contradictory verifier contract

Symptom: test.md says both “execute all tests” and “stop processing tests” on the first non-zero exit. Coverage depends on which sentence the agent follows.

Repair: choose fail-fast or collect-all, encode one behavior, and test the output shape with an intentional harmless failure.

False green from missing discovery

Symptom: malformed unit JSON becomes zero counted failures, or E2E returns an empty list; the overall run can exit successfully because no failure was counted.

Repair: make parse errors fatal, assert the expected number of discovered E2E files, and fail closed when required evidence is absent.

Unbounded self-correction

Symptom: agents repeatedly “fix” the same failure, burn tokens, and drift farther from the issue.

Repair: retain TAC-5’s bounds—four unit rounds, two E2E rounds, stop when no resolver reports progress, and preserve honest failure.

Non-deterministic browser proof

Symptom: “exactly seven rows” fails randomly because the database was not reset or stale services were still running.

Repair: encode the starting state: reset DB, boot known ports, name the URL, assert visible behavior, save screenshots.

Staying in the loop

Symptom: the commander watches every tool call and manually performs the ultimate click-through after every run.

Repair: improve the validator and trace until the human can move to trigger, authority, and acceptance boundaries.

Current practice · packaging moved, the loop did not

Reusable command prompts can now be packaged as discoverable skills; non-negotiable validators can become lifecycle gates; text-parsed JSON can become schema-validated structured output; and physical AFK machines can become managed sandboxes or CI runners. Keep TAC-5’s split: prompts for judgment, hooks for rails, deterministic code for control, and agents for interpretation.

07 · LAB · AGENT OPS

Make the verifier contract unambiguous

Change the agent system, not application logic. Your observable target: one intentional failed check must not prevent later validators from appearing in the result array.

Lab 5.1 — Prove collect-all verification

  1. Create a scratch branch and read .claude/commands/test.md, adws/adw_test.py, and adws/adw_modules/data_types.py.
  2. Rewrite only the contradictory instruction in test.md: every listed validator must run even after a non-zero exit; capture each failure and continue; return one final JSON array.
  3. Temporarily insert a first validator named harness_contract_probe whose command is python -c "raise SystemExit(7)". Its purpose is to prove continuation; it changes no files.
  4. Invoke /test directly in Claude Code. Do not run adw_test.py, because the repair loop would correctly try to resolve your intentional probe.
  5. Validate the output with a JSON parser. Confirm the failed probe is first and a later result named frontend_build is still present.
  6. Remove the probe, keep the unambiguous collect-all contract, rerun /test, and inspect git diff to prove no app/** file changed.
CHECKPOINT AOutput parses as one JSON array with no prose wrapper.
CHECKPOINT BA failed early probe and a later frontend result coexist.
CHECKPOINT CThe diff touches the agent prompt only—not application logic.

Pass criteria

  • The prompt has one consistent failure policy: collect all, then report.
  • The intentional exit-7 result is passed: false and carries the exact reproduction command.
  • All five real validator names still appear after the probe in the same run.
  • After cleanup, the only retained change is the verifier contract; app/** is untouched.
  • You can explain why deterministic Python owns retry policy even though an agent owns test interpretation.

Weak-student path

Hook: a green badge can be false. Picture: follow the control loop above. Run: inject one harmless failure. Name: verifier contract. Fail: watch a later result disappear under the old ambiguity. Try: repair the prompt and prove complete coverage.

08 · RETRIEVAL

Explain the Agent OS in six sentences

Close the page. If you cannot say all six ideas without file-by-file narration, the system model is not yours yet.

Your six-sentence scaffold

  1. The human commander owns…
  2. The planning and implementation agents are replaceable because…
  3. The prompt contract closes a loop by…
  4. The effective permission contract is determined by…
  5. The harness verifies and recovers by…
  6. The run is trustworthy only when the evidence shows…
6
sentences

Self-check: What is the shortest correct summary?

Reveal only after speaking

The commander encodes acceptance into prompts and tools; fresh agents plan, act, judge, and repair; deterministic scripts own state and bounds; permissions define real authority only when the launcher honors them; validators feed failures back into the next agent; traces, screenshots, a green sweep, and an honest exit code decide whether the loop closed.
