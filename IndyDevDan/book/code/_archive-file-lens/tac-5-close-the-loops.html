01 · Hook

“The agent finished” is not a terminal state

Imagine an implementer changes the SQL app and says “done.” What, exactly, would make that claim true?

The failure this repo is designed around

A plausible diff with no returning signal

The Python may not compile. The security suite may fail. TypeScript may be broken. The page may load but the Query button may do nothing. A human can discover all four, but then the “autonomous” workflow has quietly assigned its last mile back to the human.

Dan’s answer is architectural: represent validation as data, run it as a distinct phase, feed each failure to a resolver, and run the validator again. TAC-5 makes that answer visible at four levels:

1 · Function loop

Unit tests exercise file parsing, LLM routing, SQL execution, and security helpers.

2 · Test/repair loop

adw_test.py retries deterministic checks up to four times.

3 · Browser loop

Playwright executes written user stories and keeps screenshots.

4 · Delivery loop

GitHub issues, comments, branches, commits, logs, and PRs make the run observable.

Keep this distinction

The SQL app has a user-facing loop—upload → ask → generate SQL → execute → render. The ADW has an engineering loop—issue → plan → build → test → repair → deliver. The second loop validates changes to the first.

04 · Mental model

Three facts make the code much easier to read

If you miss these, adw_test.py looks like a pile of subprocesses. If you hold them, it reads like a state machine.

Prompts are modules

The Markdown files in .claude/commands/ are executable interfaces. Python chooses a command and supplies typed arguments; the command supplies judgment and procedure.

State is intentionally tiny

ADWStateData persists only five identifiers. Large outputs live as files. That keeps process hand-offs cheap and inspectable.

Success is re-observed

A resolver’s successful exit does not prove the test passes. The outer while-loop re-runs the whole validator and trusts the new observation.

The five-field spineadw_modules/data_types.py · 185–196
class ADWStateData(BaseModel):
    adw_id: str
    issue_number: Optional[str] = None
    branch_name: Optional[str] = None
    plan_file: Optional[str] = None
    issue_class: Optional[IssueClassSlashCommand] = None

Notice what is absent: issue bodies, model transcripts, test arrays, screenshots, and commit history. Those are artifacts, not routing state. A fresh process needs only enough information to find the right branch, plan, and run directory.

Why Dan split Python from Markdown

Python is good at deterministic sequencing, retry budgets, exit codes, files, and subprocesses. Prompt templates are good at classification, planning, diagnosis, and repair. TAC-5 puts each kind of work where it is easiest to change.

05 · Walk the orchestration code

From one issue to three bounded phases

Open the cards in order. Each one answers a single control-flow question.

Important files are collapsible; the first pass should follow wrapper → state → adapter → phase.

adws/adw_plan_build_test.pyThe outer, fail-fast phase sequencer.start here

Purpose. Accept an issue number, establish one ADW ID, then launch planning, building, and testing as separate Python processes. If any process returns non-zero, the chain stops.

One identity, three processeslines 34–80
issue_number = sys.argv[1]
adw_id = ensure_adw_id(issue_number, adw_id)

plan = subprocess.run(["uv", "run", plan_script, issue_number, adw_id])
if plan.returncode != 0:
    sys.exit(1)

build = subprocess.run(["uv", "run", build_script, issue_number, adw_id])
if build.returncode != 0:
    sys.exit(1)

test = subprocess.run(["uv", "run", test_script, issue_number, adw_id])
  • Input<issue-number> [adw-id].
  • DecisionOnly process exit codes; the wrapper contains no agentic judgment.
  • OutputSide effects from the three phases; the test phase also writes state JSON to stdout.
  • BoundaryNo automatic rollback. “Fail fast” means stop the next phase, not undo the previous one.
Why this shapeSeparate processes make each phase runnable alone, restartable from durable state, and visible in its own log directory.
adws/adw_modules/state.pyThe continuity layer between fresh processes and fresh context windows.

Purpose. Keep the run addressable even when planning, building, and testing are launched independently. State is written to agents/<adw_id>/adw_state.json.

Persist and resumelines 53–103
def save(self, workflow_step=None):
    state_path = self.get_state_path()
    state_data = ADWStateData(**self.data)
    with open(state_path, "w") as f:
        json.dump(state_data.model_dump(), f, indent=2)

@classmethod
def load(cls, adw_id, logger=None):
    data = json.load(open(state_path))
    state_data = ADWStateData(**data)
    state = cls(state_data.adw_id)
    state.data = state_data.model_dump()
    return state
  • Filterupdate() silently accepts only five core fields.
  • ValidatePydantic checks the shape before every save and after every load.
  • Two channelsFile persistence is the real path used by the wrappers; from_stdin()/to_stdout() also support shell pipes.
  • Failure modeload() returns None on malformed state, so callers must handle absence explicitly.
Why this shapePassing full transcripts through stdout would couple phases and invite parsing failures. Tiny state plus addressable artifacts gives loose coupling.

adws/adw_plan.pyClassify issue → create branch → write plan → commit → PR.

Purpose. Convert an unstructured GitHub issue into a plan file and a branch that later phases can resume.

  1. Load environment, ensure/load state, and fetch the typed GitHub issue.
  2. Call /classify_issue; store /chore, /bug, or /feature.
  3. Call /generate_branch_name, create the branch, and save its name.
  4. Call the selected planning template. The agent writes a spec under specs/.
  5. Call /find_plan_file, persist the path, generate a commit message, then finalize push/PR work.

The repeated issue comments are not decoration. Each comment is an out-of-process trace checkpoint for a human watching the run.

Design choiceThe plan is committed before implementation. That creates a reviewable intent artifact and a restart point.
adws/adw_build.pyResume exact state → implement exact plan → integrate the change.

Purpose. Require both issue-number and adw-id, load the exact saved plan and branch, call /implement, then commit and push.

  • Guard 1No state file means hard stop: run planning first.
  • Guard 2No branch_name or plan_file means hard stop.
  • Mutationimplement_plan() delegates the plan to the sdlc_implementor agent.
  • FallbackIf state lacks classification, classify again; if that fails, default to /feature.

This phase does not run the full validation node itself. The combined wrapper closes that larger loop by launching adw_test.py next.

adws/adw_modules/workflow_ops.py + git_ops.py + github.pyShared business operations and external boundaries.

workflow_ops.py is the vocabulary of the workflow: classify, plan, find a plan, implement, name a branch, create a commit request, create a PR request, and locate existing work.

git_ops.py centralizes deterministic git subprocesses and the final push/PR decision. github.py centralizes gh CLI calls and converts issue JSON into Pydantic models.

Agentic operations

Return AgentPromptResponse or (value, error). They can interpret unstructured text.

Deterministic operations

Return subprocess status and stderr. They sequence observable system changes.

Typed boundary

GitHubIssue, TestResult, and E2ETestResult stop arbitrary JSON from leaking inward.

06 · Walk the validation code

The loop closes in adw_test.py

This is the load-bearing file: 1,106 lines coordinating a four-attempt deterministic loop and a two-attempt browser loop.

adws/adw_test.pyRun → parse → resolve each failure → run again → report honestly.core loop

Purpose. Make validation its own resumable workflow node. It can follow planning/building or create a test-only branch when run alone.

The deterministic repair looplines 411–517
while attempt < max_attempts:
    attempt += 1
    test_response = run_tests(adw_id, logger)
    results, passed_count, failed_count = parse_test_results(
        test_response.output, logger
    )

    if failed_count == 0:
        break
    if attempt == max_attempts:
        break

    failed_tests = [test for test in results if not test.passed]
    resolved, unresolved = resolve_failed_tests(
        failed_tests, adw_id, issue_number, logger, iteration=attempt
    )
    if resolved == 0:
        break
  • Observerun_tests() calls the /test template and expects a JSON array of TestResult.
  • LocalizeEach failed item carries its own exact execution_command, purpose, and error.
  • RepairA new resolver agent is named by iteration and index, so its prompt and output cannot overwrite another attempt.
  • Re-observeThe next while-loop iteration runs the validator again. Resolver success alone is never the final verdict.
  • BoundFour unit attempts; stop early when green, on high-level runner error, at the budget, or when no resolver reports progress.
The browser gatelines 977–1011

The ordering is deliberate: browser tests are slower and noisier, so the workflow refuses to spend them while the cheaper deterministic layer is known red. E2E files run sequentially and stop on the first failure; the resolver fixes that failure, then the suite restarts from the beginning.

Why this shapeThe loop is not “agent keeps trying.” It is a bounded state machine with explicit observations, typed failure payloads, unique artifacts, retry budgets, and a non-zero terminal failure.

Crucially, the output is not prose. Each test becomes a repair ticket with test_name, passed, execution_command, test_purpose, and optional error.

Prompt contradiction to notice

The command says both “execute all tests even if some fail” and “stop processing tests” on the first non-zero result. A fresh agent must reconcile those instructions. Strong validation contracts avoid mutually exclusive control rules.

.claude/commands/resolve_failed_test.mdA deliberately narrow inner repair loop.

Purpose. Take one typed failure, reproduce its exact command, make the smallest relevant fix, and re-run only that command.

  1. Understand the test’s name, purpose, and error.
  2. Inspect only recent changes, a relevant spec, and files that can affect this test.
  3. Run the payload’s execution_command to reproduce the red state.
  4. Apply a minimal change.
  5. Re-run the same command; do not run the whole suite inside this resolver.

The full suite belongs to the outer loop. This prevents every resolver from paying the cost of all validators and keeps diagnosis focused.

.claude/commands/test_e2e.md + commands/e2e/*.mdA generic browser runner paired with three concrete user stories.

Runner. Reset the database, start both services, open http://localhost:5173, execute the selected E2E Markdown file with Playwright MCP, save screenshots under the run/agent/test directory, and return one E2ETestResult-shaped JSON object.

  • test_basic_query.md checks the page contract, query submission, SQL translation, results, and Hide button.
  • test_complex_query.md checks natural-language filtering and a generated WHERE clause.
  • test_sql_injection.md checks that a destructive request is blocked and tables remain intact.

resolve_failed_e2e_test.md is the visual equivalent of the unit resolver: re-open the named test file, reproduce the exact failed step, inspect screenshots, fix minimally, and re-run only that story.

Why MarkdownThe E2E contract is legible as a user story and executable as browser instructions. Product intent and test procedure stay adjacent.
.claude/settings.json + .claude/hooks/Guardrails and trace capture around every agent tool call.

Permissions. Allow common build operations; deny force-push variants and rm -rf. Hooks. Run before tools, after tools, on notification, on stop, and on subagent stop.

  • PreToolUseBlocks real .env access and dangerous recursive removal; logs accepted tool calls.
  • PostToolUseAppends tool-result events to a session JSON file.
  • NotificationRecords notification events; the --notify flag is parsed but no TTS call is made here.
  • StopRecords stop events and optionally converts the session transcript JSONL into chat.json.
  • SubagentStopCaptures the equivalent subagent boundary.

Hooks are the observability substrate. They do not decide whether the application works; they make the agent’s behavior inspectable and block a few high-risk actions before execution.

07 · Walk the application under test

The workflow needs a real workload

The app is a deliberately small vertical slice: files become SQLite tables, natural language becomes SQL, validated SQL becomes rows, and TypeScript renders those rows.

Purpose. Wire Pydantic models to five core modules and expose upload, query, schema, insights, health, and table-deletion endpoints.

Why this shapeA thin route layer keeps file parsing, model calls, SQL execution, statistics, and security independently testable.
app/server/core/file_processor.pyCSV/JSON/JSONL bytes → sanitized SQLite table + schema preview.

CSV and JSON. Sanitize the filename, build a pandas DataFrame, normalize columns, replace the SQLite table, then query its schema, five-row sample, and count through the security helper.

JSONL. First scan every line to discover the union of flattened fields. Then scan again, fill missing fields with None, create a DataFrame, and persist it. Nested objects use __; array positions use _0, _1, and so on.

Recursive flatteninglines 169–194
def flatten_json_object(obj, prefix=""):
    result = {}
    if isinstance(obj, dict):
        for key, value in obj.items():
            new_key = f"{prefix}__{key}" if prefix else key
            result.update(flatten_json_object(value, new_key))
    elif isinstance(obj, list):
        for i, value in enumerate(obj):
            result.update(flatten_json_object(value, f"{prefix}_{i}"))
    else:
        result[prefix] = obj
    return result

The JSONL spec says “line by line for memory efficiency,” but the implementation decodes the whole file, builds a full records list, and then a DataFrame. It is logically line-oriented, not streaming-memory-bounded.

app/server/core/llm_processor.pyDatabase schema + user question → cleaned SQLite query.

format_schema_for_prompt() serializes every table, column type, and row count. The OpenAI and Anthropic functions use nearly identical prompts, low temperature, a 500-token cap, and strip Markdown fences.

generate_sql() routes by key availability before request preference: an OpenAI key wins even when the request says Anthropic; Anthropic is used only when OpenAI is absent. The request field is therefore a fallback, not a strict selector.

This module proposes SQL. It does not establish safety. The returned string crosses a separate security/execution boundary next.

app/server/core/sql_security.py + sql_processor.pyValidate identifiers and generated queries before SQLite sees them.

sql_security.py validates table/column identifiers, escapes them with SQLite brackets, substitutes identifier placeholders, binds value placeholders, blocks DDL unless explicitly allowed, detects dangerous query patterns, and provides small safe builders.

sql_processor.py uses those rules in two paths: schema discovery safely interpolates identifiers; generated SQL is checked by validate_sql_query(), then executed as a complete statement because its values cannot be retroactively parameterized.

Security boundary, not a proof of perfect parsing

The generated-query path is a regex denylist, not an SQL AST allowlist. The tests prove the named attacks are blocked; they do not prove every mutation syntax is impossible. The safest design would enforce read-only SQLite access or a parsed SELECT-only policy as another independent layer.

app/client/src/main.tsOne vanilla TypeScript controller for query, upload, modal, tables, and rendering.

On DOMContentLoaded, four functions attach behavior and load schema. Query submission disables the button, calls the API, renders the SQL and table, then restores the button. File upload supports browse and drag/drop. Sample buttons fetch static files, wrap their blobs as File, and reuse the same upload path.

Results rows are built with DOM nodes and textContent, but the natural-language query, generated SQL, and server error are inserted with innerHTML. That mixed rendering policy is an important review seam because those strings can contain markup.

Each call to displayResults() adds another click listener to the same Hide button. After several queries, one click may toggle multiple times. This is exactly the kind of user-path issue an E2E loop can reveal even when TypeScript and backend tests are green.

app/client/src/api/client.tsTyped fetch wrapper and five API methods.

Development calls use /api and Vite proxies to port 8000; production uses http://localhost:8000/api directly. apiRequest<T> spreads request options, checks response.ok, parses JSON, and rethrows network/status errors.

The wrapper deliberately does not set a default Content-Type, which lets the browser create the correct multipart boundary for FormData. JSON methods add their own header.

app/client/src/types.d.ts + app/server/core/data_models.pyMirrored contracts across the HTTP boundary.

Pydantic owns runtime validation and JSON serialization; global TypeScript interfaces own compile-time expectations in the browser. Both define upload, query, schema, insight, and health shapes.

The comment “must match exactly” is a human-maintained invariant—there is no schema generator in this repo. The deterministic loop catches many mismatches indirectly through type-check/build and backend tests, but not contract drift that still compiles on both sides.

09 · End-to-end flow

How one full run actually works

Follow the identity a1b2c3d4. The same ID ties together state, prompts, logs, comments, screenshots, and agent outputs.

A GitHub event asks for adw_plan_build_test

The webhook extracts workflow and optional ID, prevents bot-comment recursion, and returns immediately after Popen.

trigger_webhook.py
The wrapper establishes one ADW ID

ensure_adw_id() loads or creates agents/a1b2c3d4/adw_state.json.

adw_plan_build_test.py
Planning fetches and classifies the issue

Typed GitHub JSON goes to /classify_issue; the chosen class enters state.

adw_plan.py
A branch name is generated and created

The branch embeds issue number and ADW ID, making run ownership visible in git.

/generate_branch_name
The selected planning prompt writes a spec

Bug/chore/feature templates research the real repo and include validation work.

/bug · /chore · /feature
The plan path is discovered and persisted

Later processes now need only the ADW ID to locate the exact intent.

/find_plan_file
Build checks out the saved branch and implements the saved plan

The implementer’s prompt and event stream get their own artifact directory.

adw_build.py
The deterministic test agent runs the stack

It returns typed results, failed first, with exact reproduction commands.

/test
Each red result gets a focused resolver

Agent names include iteration and index; the payload carries the reproduction command.

/resolve_failed_test
The whole deterministic stack runs again

Green stops the loop. Red repeats within the four-attempt budget. No progress stops early.

run_tests_with_resolution()
Only a green deterministic base unlocks browser tests

Each E2E Markdown story is run in sequence; screenshots become durable evidence.

run_e2e_tests()
The first red browser story gets a visual resolver

After repair, the E2E sequence restarts, bounded to two attempts.

The architecture in one sentence

Deterministic Python owns when to stop; typed result payloads say what failed; focused agents decide how to repair; a fresh validation pass decides whether the repair worked.

10 · Common fail

Where a weak reading goes wrong

These are not trivia. Each one changes how you would safely extend the workflow.

“Plan+build always tests.”

No. adw_plan_build.py stops after implementation. Only adw_plan_build_test.py includes the validation node. The cron trigger currently launches plan+build, not the full pipeline.

“Resolver success means green.”

No. It means the resolver process completed. Proof comes from the next full validation observation.

“All state is piped.”

No. The wrappers reuse a file-backed ADWState. Pipe helpers exist, but persistent state is the active combined-script seam.

“Specs list real files.”

No. The query-history spec names files and endpoints absent from this checkout. Repository inventory outranks planning prose.

“Security is parameterization everywhere.”

No. Identifiers are validated/escaped; values can be bound in helper queries; a complete LLM-generated query is instead screened before execution.

“A 200 response means query success.”

No. Several FastAPI error paths return a typed payload with error. Client behavior must inspect the body.

A side-effect seam worth reviewing

workflow_ops.create_commit() sounds like a pure message generator, but it calls the /commit template, whose instructions stage and commit. Planning and building then also call commit_changes(). When function names hide agent-driven side effects, duplicate or empty commits become possible. A safer interface would separate “generate message” from “perform commit.”

Lab: shrink one loop budget and prove it

You will change exactly one real constant, verify both meaning and syntax, then explain the trade-off. This lab does not call GitHub, an LLM, or the browser.

Change the deterministic retry budget from four attempts to two

  1. Open tac/tac-5/adws/adw_test.py. Find MAX_TEST_RETRY_ATTEMPTS = 4 near line 59.
  2. Change only the value to 2. Do not change the E2E budget.
  3. Verify the code still compiles from tac/tac-5/:
    syntax feedbackno network calls
    cd adws
uv run --with python-dotenv --with pydantic \
  python -m py_compile adw_test.py adw_modules/*.py
  4. Verify the runtime value without starting a workflow:
    semantic feedbackassert exact value
    uv run --with python-dotenv --with pydantic \
  python -c "import adw_test; assert adw_test.MAX_TEST_RETRY_ATTEMPTS == 2; print('budget=2')"
  5. Use git diff -- adws/adw_test.py. Confirm the diff contains one changed line.

Pass criteria

  • Compilation exits 0.
  • The assertion prints budget=2.
  • The diff changes only MAX_TEST_RETRY_ATTEMPTS.
  • You can explain the trade-off: lower compute and faster terminal failure, but fewer repair opportunities.

Why this is a closed loop

The request is one bounded edit. The first validator catches syntax/import damage. The second checks intended runtime meaning. The diff check catches scope creep. If any signal is red, repair and repeat all three.

12 · Teach-back

Can you rebuild the system from memory?

Close the page before answering. Reveal only after you have spoken or written a complete response.

1. Why does the outer unit-test loop rerun the whole test command after a resolver reports success?

Reveal answer

Resolver success means the agent process finished, not that the application is green. A fresh independent observation supplies the verdict and also catches regressions outside the targeted test.

2. What are the five durable ADW state fields, and why are outputs not stored there?

Reveal answer

adw_id, issue_number, branch_name, plan_file, and issue_class. Large outputs live as addressable artifacts so phase hand-offs stay small, validated, and loosely coupled.

3. Why do E2E tests wait for unit checks, run sequentially, and stop at the first failure?

Reveal answer

They are slower and noisier. A green deterministic base removes cheap causes first; sequential first-failure execution gives the resolver one localized visual problem and avoids wasting browser compute.

4. Which combined entry point truly “closes the loops,” and which similar entry point does not test?

Reveal answer

adw_plan_build_test.py runs all three phases. adw_plan_build.py stops after implementation.

Dan did not build one magical autonomous agent. He built small deterministic rails around several narrow agent judgments, gave every run an identity, turned failures into typed inputs, bounded every retry, and preserved enough evidence for a human to audit the result.
