00 · HOOK

The most consequential code is Markdown

A weak request asks an agent to “add a feature.” Dan’s templates ask the agent to research first, preserve repository patterns, name files, order tasks, define tests, and spell out validation before implementation begins.

Unplanned ask

Intent disappears into a session

The agent must infer scope, architecture, acceptance criteria, and proof at the same time it edits. Every missing decision becomes variance.

Templated plan

Intent becomes a reviewable artifact

bug.md, chore.md, and feature.md compile different work types into a stable specs/*.md shape.

The plan is not paperwork after the thinking. In this repo, the plan is the interface between thinking and building.

The mental model

Treat each planning command like a function: it accepts an argument through $ARGUMENTS, combines it with repository constraints and an output schema, and returns a spec that another fresh agent can execute.

Why the demo app matters

The natural-language SQL app gives planning something concrete to control. It has browser state, HTTP contracts, two LLM providers, a database, security boundaries, lifecycle scripts, and tests. A vague change can cross many seams; a good plan names them before code moves.

01 · DIAGRAM

Map of the repo

There are two connected systems. The clay lane builds software. The green lane runs the software. The checked-in spec is the bridge: it records what the builder intended before the runtime files existed.

Control plane

Markdown sets policy

The commands define what to read, what to ignore, which questions to answer, and what proof must exist.

Data plane

Code moves values

A browser File becomes bytes, a DataFrame, a SQLite table, schema text, generated SQL, row dictionaries, and JSON.

Why this design

The planning side is text-first so humans can review and agents can consume it. The runtime side uses a thin vertical slice—vanilla TypeScript, FastAPI, focused Python modules, SQLite—so ownership stays visible. The same preference drives both halves: explicit seams beat hidden magic.

.claude/commands/bug.md · chore.md · feature.mdplanning compiler · 216 lines

Purpose. Three task-specific commands turn a short request into a plan under specs/. They share a skeleton—research, relevant files, ordered tasks, validation, notes—but add the questions appropriate to each kind of work.

  • bug 1–18Demands reproduction, root-cause analysis, surgical scope, and regression prevention before any fix is described.
  • chore 1–24Keeps the lighter work type simple while still requiring repository research and an exact completion check.
  • feature 1–29Adds existing-pattern research, extensibility, dependency notes, and a larger cross-client/server file scope.
  • $ARGUMENTSIs the input slot. The command is reusable because the policy stays fixed while the task changes.
.claude/commands/bug.mdoutput schema excerpt
## Steps to Reproduce
<list exact steps to reproduce the bug>

## Root Cause Analysis
<analyze and explain the root cause of the bug>

## Step by Step Tasks
IMPORTANT: Execute every step in order, top to bottom.

Why three files? A bug plan must explain causality; a feature plan must explain value, design, acceptance, and integration; a chore does not need that ceremony. One universal mega-template would either omit important questions or burden every small change.

Beginner trap

The templates’ “Relevant Files” sections are planning boundaries, not a complete repository map. They intentionally tell the planning agent what to ignore for that task.

async def process_natural_language_query(request: QueryRequest) -> QueryResponse:
    schema_info = get_database_schema()
    sql = generate_sql(request, schema_info)

    start_time = datetime.now()
    result = execute_sql_safely(sql)
    execution_time = (datetime.now() - start_time).total_seconds() * 1000

    if result['error']:
        raise Exception(result['error'])

    return QueryResponse(

        results=result['results'],
        columns=result['columns'],
        row_count=len(result['results']),

def sanitize_table_name(table_name: str) -> str:
    if '.' in table_name:
        table_name = table_name.rsplit('.', 1)[0]

    sanitized = re.sub(r'[^a-zA-Z0-9_]', '_', table_name)
    if sanitized and not sanitized[0].isalpha() and sanitized[0] != '_':
        sanitized = '_' + sanitized
    if not sanitized:
        sanitized = 'table'
    return sanitized

Why pandas plus SQLite? Pandas handles input parsing and type inference; SQLite gives every uploaded dataset a common query surface. The tradeoff is memory use: the full upload becomes a DataFrame before persistence.

def generate_sql(request: QueryRequest, schema_info: Dict[str, Any]) -> str:
    openai_key = os.environ.get("OPENAI_API_KEY")
    anthropic_key = os.environ.get("ANTHROPIC_API_KEY")

    if openai_key:
        return generate_sql_with_openai(request.query, schema_info)
    elif anthropic_key:
        return generate_sql_with_anthropic(request.query, schema_info)

    if request.llm_provider == "openai":
        return generate_sql_with_openai(request.query, schema_info)
    return generate_sql_with_anthropic(request.query, schema_info)

B. An application run: question to rows

01
Data becomes queryable.

main.ts wraps an uploaded browser file in FormData; server.py awaits its bytes; file_processor.py parses a DataFrame and replaces a SQLite table.

02
The client refreshes server truth.

After upload, loadDatabaseSchema() calls GET /api/schema and renders the complete current catalog.

03
The question crosses the typed HTTP boundary.

The click handler sends { query, llm_provider: 'openai' } through api.processQuery; Pydantic constructs QueryRequest.

04
Live schema becomes model context.

get_database_schema() reads every table and column; format_schema_for_prompt() serializes that structure beside the user’s question.

05
The provider returns a SQL string.

generate_sql() chooses a provider from configured keys, the provider function calls its SDK, and Markdown fences are stripped.

06
The SQL gate checks, executes, and shapes rows.

execute_sql_safely() runs the blocklist, executes SQLite, uses sqlite3.Row, and returns dictionaries plus column names.

07
The browser renders explicit output.

QueryResponse serializes SQL, results, columns, count, and timing; displayResults() shows the query and SQL, then builds cells with textContent.

The connection

A useful plan follows the same boundaries as a runtime value. If a feature changes “provider choice,” a strong plan names the browser input, TypeScript contract, Pydantic model, router, tests, and verification—not just llm_processor.py.

Why is specs/init_nlq_to_sql_to_table.md more than documentation?

Reveal answer

It is an executable handoff contract: it constrains architecture, names seams and models, orders work, and supplies validation commands a separate builder can follow.

Why does the client refetch schema after upload and deletion?

Reveal answer

SQLite and the server remain the catalog source of truth. Refetching returns the whole normalized state after replace or delete semantics.

What is the difference between a typed boundary and a validated boundary here?

Reveal answer

TypeScript describes expected JSON to the compiler, but Pydantic validates and serializes actual HTTP data at runtime. The two definitions are manually synchronized.
