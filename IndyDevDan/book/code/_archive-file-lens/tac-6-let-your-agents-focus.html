TAC-6 · Code deep dive

Let Your Agents Focus

Dan’s system does not make one agent remember the whole software lifecycle. It gives a fresh agent one bounded question, saves the answer as an artifact, and lets a small Python workflow decide what happens next.

Hook

Who should remember the last four hours?

Imagine one developer must plan a feature, implement it, run tests, review the UI, repair blockers, write docs, and open the PR—without ever clearing their desk. By review time, the desk is the problem.

Dan’s answer: clear the desk between jobs. Keep the branch, spec, test result, screenshots, and five tiny identifiers. Do not keep the worker’s entire conversation.

That is the lesson hiding in this repo: focus is an architectural property. The separation is enforced by subprocess boundaries, slash-command contracts, typed JSON, files on disk, and retry limits—not by politely asking a mega-agent to “stay focused.”

Diagram first

Map of the repo

1 · GitHub request Issue body or comment carries intent and an adw_* signal.
2 · Trigger Cron or webhook classifies the requested workflow and starts one script.
3 · Orchestrator Plan → build → test → review → document; stop on a non-zero phase.
4 · Focused agent A fresh claude -p process receives one slash command and one role.
5 · Durable handoff Spec, branch, commit, JSON result, screenshots, docs, and logs outlive the session.
What is wanted? Which workflow? Which phase? One bounded task Evidence, not memory

The product in app/ is the patient. The ADW system in adws/ is the operating team. The prompt files in .claude/commands/ are each specialist’s checklist.

The architecture in four moves

What Dan built—and why it stays understandable

01

Processes isolate attention

Every slash-command invocation starts a new Claude Code CLI process. The reviewer does not inherit the implementer’s rationalizations.

02

Artifacts carry truth

The branch, spec, test JSON, review screenshots, commit, and docs are inspectable handoffs. A transcript is not the database.

03

Types narrow interpretation

Pydantic models turn fuzzy prose into results such as TestResult, E2ETestResult, and ReviewResult.

04

Loops have budgets

Tests can try four times, E2E twice, review three times. A loop that cannot stop is not autonomy; it is drift.

Walk the code · seam 1

The fresh-agent boundary

adws/adw_modules/agent.pyTurns one slash command into one isolated Claude Code execution. core seam

Purpose. This module chooses a model, builds the tiny prompt, launches the CLI, captures stream-JSON output, and returns one response object. There is no “resume the planner session” call. That absence is the focus mechanism.

agent.pylines 262–299
def execute_template(request: AgentTemplateRequest) -> AgentPromptResponse:
    if request.slash_command in SLASH_COMMAND_MODEL_MAP:
        mapped_model = SLASH_COMMAND_MODEL_MAP[request.slash_command]
        request = request.model_copy(update={"model": mapped_model})
    else:
        request = request.model_copy(update={"model": "sonnet"})

    prompt = f"{request.slash_command} {' '.join(request.args)}"
    output_dir = os.path.join(
        project_root, "agents", request.adw_id, request.agent_name
    )
    output_file = os.path.join(output_dir, "raw_output.jsonl")

    prompt_request = AgentPromptRequest(
        prompt=prompt,
        adw_id=request.adw_id,
        agent_name=request.agent_name,
        model=request.model,
        dangerously_skip_permissions=True,
        output_file=output_file,
    )
    return prompt_claude_code(prompt_request)
  1. Role determines model. Planning/implementation/review work maps to Opus where needed; classification, tests, docs, and git chores mostly map to Sonnet.
  2. The prompt stays narrow. It is a slash command plus arguments, such as /review specs/x.md ADW-123.
  3. Evidence gets a home. Each role writes under a runtime-created agents/{adw_id}/{agent_name}/ directory.
  4. A new process does the work. prompt_claude_code() calls subprocess.run([CLAUDE_PATH, "-p", ...]).
Read this with both eyes open

The process uses --dangerously-skip-permissions. The repo compensates with narrow prompts, an allowlisted subprocess environment, hooks, git controls, and a dedicated working copy—but this is still a high-trust local automation design.

adws/adw_modules/utils.pyIDs, logs, JSON cleanup, and the safe subprocess environment. support

utils.py makes the boundary operational: it generates short ADW IDs, creates per-phase execution logs, strips code fences before JSON parsing, and passes only approved environment variables into child processes. Focus is partly about what context you withhold.

Five fields cross the phase boundary

adws/adw_modules/state.py + data_types.pyA deliberately tiny durable handoff. contract

Purpose. Connect independent scripts without sharing their conversation history. The state file is generated at runtime as agents/{adw_id}/adw_state.json.

def update(self, **kwargs):
    # Filter to only our core fields
    core_fields = {
        "adw_id", "issue_number", "branch_name", "plan_file", "issue_class"
    }
    for key, value in kwargs.items():
        if key in core_fields:
            self.data[key] = value
FieldQuestion it answersWhy the next phase needs it
adw_idWhich run is this?Locates logs and generated artifacts.
issue_numberWhich request is authoritative?Fetches issue text and posts progress.
branch_nameWhere is the work?Lets build, test, review, and docs check out the same branch.

Weak-student checkpoint

The state file is not “the agent’s memory.” It is a set of pointers. The substantial truth lives in the issue, spec, git branch, test output, and screenshots.

A real sharp edge in this checkout

Some phase scripts call state.update(review_screenshots=...), patch_file=..., or documentation_path=.... ADWState.update() silently drops those non-core keys. Documentation has a directory-scan fallback for review images; do not assume every attempted update persists.

Walk the code · seam 3

The orchestrator is boring on purpose

adws/adw_sdlc.pyComposes five phase scripts and stops on failure. composer

The full workflow does not contain the planning prompt, test logic, or review rubric. It only establishes an ADW ID, calls each phase with that ID, and checks the return code. That keeps composition separate from specialist behavior.

adw_sdlc.pycondensed from lines 52–126
plan = subprocess.run(["uv", "run", "adw_plan.py", issue_number, adw_id])
if plan.returncode != 0:
    sys.exit(1)

build = subprocess.run(["uv", "run", "adw_build.py", issue_number, adw_id])
if build.returncode != 0:
    sys.exit(1)

test = subprocess.run([
    "uv", "run", "adw_test.py", issue_number, adw_id, "--skip-e2e"
])
if test.returncode != 0:
    sys.exit(1)

review = subprocess.run(["uv", "run", "adw_review.py", issue_number, adw_id])
document = subprocess.run(["uv", "run", "adw_document.py", issue_number, adw_id])

Why skip E2E here? The standalone test phase supports browser tests, but the composed SDLC passes --skip-e2e. UI evidence still appears in the separate review phase. That is an implementation fact, not a general recommendation.

adws/adw_plan.py + adw_build.pyTurn issue prose into a spec, then hand only that spec to implementation. phases

adw_plan.py fetches the issue, classifies it, creates a branch name, invokes the matching /bug, /feature, or /chore planner, validates the plan path, commits, pushes, and opens/updates a PR. adw_build.py loads state, checks out the branch, invokes /implement with the plan, commits, and updates the PR.

The important handoff is issue → spec → implementation. The build agent need not inherit the planner’s hidden chain of thought; it receives the inspectable result.

adws/adw_plan_build*.pySmall menu of reusable compositions. variants

Six thin wrappers select how far the workflow should go: plan+build; add test, review, or document; combine test+review; or run the complete SDLC. The trigger can choose a composition without teaching a general-purpose agent how to improvise the lifecycle.

Walk the code · seams 4–5

Tests and review are different closed loops

adws/adw_test.pyRun evidence → isolate each failure → repair → rerun. test loop

The tester returns structured TestResult objects. If tests fail, the workflow sends each failed result to a dedicated /resolve_failed_test agent, then runs the suite again. It stops when all pass, nothing was repaired, a high-level agent error occurs, or four attempts are used.

adw_test.pylines 396–470
while attempt < max_attempts:
    attempt += 1
    test_response = run_tests(adw_id, logger)
    results, passed_count, failed_count = parse_test_results(
        test_response.output, logger
    )

    if failed_count == 0 or attempt == max_attempts:
        break

    failed_tests = [test for test in results if not test.passed]
    resolved, unresolved = resolve_failed_tests(
        failed_tests, adw_id, issue_number, logger, iteration=attempt
    )

    if resolved == 0:
        break

E2E has its own result model, repair command, and smaller budget of two attempts. Keeping unit/build evidence separate from browser evidence gives the repair agent a smaller problem.

adws/adw_review.pyCompare the implementation to the spec, capture proof, repair blockers only. review loop

Review is not another test run. The /review contract asks for spec verification, UI interaction, screenshots, and severity. The workflow uploads screenshots to R2 when configured, posts results to GitHub, and creates focused patch-plan/patch-implement agents for blocker findings. skippable and tech_debt issues remain visible but do not trigger automatic repair.

Notice the independence

The reviewer reads the spec and the running application. It does not ask the implementer whether the implementation is correct. Independent evidence is the point of a fresh context.

adws/adw_patch.py + adw_document.pyFocused correction and focused explanation. specialists

adw_patch.py reads the latest human patch request, creates a narrow patch plan, then gives that file to a separate patch implementer. adw_document.py uses the branch diff, spec, and reviewer screenshots to create feature documentation and update conditional retrieval rules. Neither job needs the full SDLC transcript.

Conditional context is another focus tool

conditional_docs.md tells an agent to read README, styling, classifier, or ADW docs only when its current task matches. More context is not automatically better context.

The code being changed

The inner product has its own clean request flow

The ADW machinery exists to evolve a small natural-language SQL application. Understanding that application matters because tests and review need a real behavioral target.

app/client/src/main.ts + api/client.tsDOM behavior, upload/query interactions, and typed fetch calls. frontend

The vanilla TypeScript entry binds the fixed HTML controls, loads samples, uploads CSV/JSON/JSONL, disables/debounces query input, renders schemas and result tables, deletes tables, and requests random natural-language questions. api/client.ts keeps the HTTP calls out of the DOM code. Vite proxies /api to port 8000 during development.

app/server/server.pyFastAPI boundary for uploads, queries, schema, insights, health, random queries, and deletion. backend

For a natural-language query, the route reads the SQLite schema, asks an LLM for SQL, validates/executes it, and packages the rows in a Pydantic response.

server.pylines 111–135
@app.post("/api/query", response_model=QueryResponse)
async def process_natural_language_query(request: QueryRequest) -> QueryResponse:
    schema_info = get_database_schema()
    sql = generate_sql(request, schema_info)

    start_time = datetime.now()
    result = execute_sql_safely(sql)
    execution_time = (datetime.now() - start_time).total_seconds() * 1000

    return QueryResponse(
        sql=sql,
        results=result["results"],
        columns=result["columns"],
        row_count=len(result["results"]),
        execution_time_ms=execution_time,
    )

End-to-end flow

How one adw_sdlc run works

  1. A human states intent in GitHub.

    The issue or comment contains the request. The webhook looks for adw_; cron recognizes a new issue or exact adw comment.

  2. The trigger selects a composition.

    /classify_adw returns a workflow name; the trigger launches the matching Python script without waiting for the whole lifecycle.

  3. Planning makes the first durable handoff.

    A classifier chooses bug/feature/chore, a branch-name agent names the branch, and a planner writes specs/*.md. State saves the issue, branch, plan, class, and ADW ID.

  4. Build reads the plan, not the planner’s session.

    A new implementer changes the app, runs the plan’s checks, and leaves a commit/PR update.

  5. Test turns failures into small repair prompts.

    The tester emits JSON. Each failing test gets its own resolver. The suite reruns, bounded by four attempts; the composed SDLC skips E2E.

  6. Review compares behavior with the promise.

    A fresh reviewer uses the spec and running UI, captures screenshots, classifies findings, and automatically patches only blockers. It can re-review up to three times.

  7. Documentation explains the shipped result.

    A documenter reads diff, spec, and screenshots, writes product-facing docs, updates conditional retrieval, commits, and pushes.

  8. Artifacts make the run debuggable.

    GitHub comments, phase logs, saved prompts, raw JSONL, parsed JSON, state, specs, screenshots, commits, and docs let a human reconstruct what happened.

Common fail

Four ways to undo the focus

One forever-session

Plan, implement, test, and review in one conversation. The reviewer inherits sunk-cost bias and irrelevant detail. Keep the artifact; replace the worker.

State becomes a junk drawer

Stuff every output into adw_state.json. Soon every phase depends on every other phase. Keep identifiers in state and substantial evidence in named files.

“Looks good” is the result model

Free-form success prose is hard to branch on. The Pydantic models make pass/fail, severity, screenshots, commands, and errors explicit.

Retry means “try forever”

An unbounded repair loop burns tokens and can oscillate. TAC-6 caps attempts and stops when no repair was made.

Implementation-specific caution

adws/README.md describes webhook signature validation, but trigger_webhook.py in this checkout does not perform it. Do not expose that endpoint to untrusted traffic without adding and verifying authentication.

Teach-back

Close the page, then explain these aloud

Open the answers only after you have committed to your own wording.

1. What—not who—carries truth from planning to building?

The spec file, branch, issue, and five-field state pointers. The planner’s live conversation does not cross the boundary.

2. Why is review a fresh agent instead of the implementer’s final task?

It needs independent judgment against the spec and running behavior. A fresh context avoids inherited rationalizations and keeps only relevant evidence.

3. Trace one failing unit test through the system.

/test emits a failed TestResult; adw_test.py extracts it; a new /resolve_failed_test agent receives that specific failure; then a fresh tester reruns the suite. The loop stops on success, no repair, high-level error, or attempt four.

4. What is the deepest lesson in one sentence?

Agent focus comes from boundaries—fresh processes, narrow contracts, durable artifacts, typed results, and bounded loops—not from a larger context window.
