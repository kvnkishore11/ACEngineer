00 · Hook

The interesting code is not the code that gets created

A beginner opens this repo expecting an application. There is no application yet. There is a mechanism that asks an agent to create one, run it, commit it, and report the evidence.

The eventual main_aic.py and main_tac.py are intentionally absent from the starting codebase. They are runtime artifacts. Dan keeps the programs trivial so you look at the real architecture: where behavior is described, which tools the agent may use, how an outside program starts the agent, and what comes back.

The design in one sentence

prompt.md says what work to perform; each launcher says how this host language starts Claude; project settings say which actions Claude may take.

The beginner trap

The README demo is sequential: its first prompt creates main_aic.py, and its second prompt later runs that file. The headless programmable/prompt.md fixes that dependency by creating both Python files itself.

03 · Walk the code

Start at the behavioral center, then work outward

Open any file. Each panel gives its job, the complete source, and line-range notes. The first three are expanded because they form the core contract.

programmable/prompt.md behavior · 18 lines +
Purpose

The single reusable specification. It declares the starting Git move, two file outcomes, validation commands, a commit, and the evidence the caller must receive.

programmable/prompt.mdcomplete source · 18 logical lines
RUN:
    checkout a new/existing "demo-agentic-coding" git branch

CREATE main_aic.py:
    print "goodbye ai coding"

CREATE main_tac.py:
    print "hello agentic coding"
    print a concise explanation of the definition of ai agents

RUN:
    uv run main_aic.py
    uv run main_tac.py
    git add .
    git commit -m "Demo agentic coding capabilities"

REPORT:
    respond with the exact output of both .py files
1–2
Establish mutable state. “New/existing” makes the instruction work on a fresh run or a repeated demo, but it does not guarantee a clean starting branch.
4–9
Describe outcomes, not implementation syntax. Claude decides how to create the files. Both runtime artifacts are included, so this prompt is self-contained.
11–15
Validate before preserving. The agent runs both programs before staging and committing everything in the working tree.
17–18
Define the return value. Exact program output gives the outer caller concrete evidence. Without REPORT, stdout could be a vague narrative.

Hidden assumption

git add . stages every unignored change under the current directory. Run this only from a clean, disposable lesson checkout—not beside unrelated work.

Purpose

The project-level capability boundary. It allows the file, UV, selected Git, and web tools the agent may need; it notably does not grant an unrestricted shell or Git push.

1–3
Open the project permission document and its allowlist. This is configuration, not an instruction sequence.
4–6
Read, Write, and Edit let the agent inspect and create the requested Python files.
7
The scoped UV pattern covers the two validation commands. The :* suffix permits arguments after uv run.
8–11
Only the Git verbs used by the workflow are named: checkout, branch, add, and commit. There is no push permission.
12–15
WebSearch is available but unused by this prompt. The closing lines complete the JSON structure.

Why separate policy from prompt?

A prompt can request a commit; the policy independently decides whether the runtime may execute it. Intent and authority are different concerns.

programmable/programmable.py adapter · 31 lines +
Purpose

The most explicit launcher. It reads the prompt, invokes Claude without a shell, separates stdout from stderr, and preserves Claude’s exact exit code.

programmable/programmable.pycomplete source · 31 lines
import subprocess
import sys


def main():
    with open("programmable/prompt.md", "r") as f:
        prompt_content = f.read()

    command = [
        "claude",
        "-p",
        prompt_content,
    ]

    try:
        result = subprocess.run(command, capture_output=True, text=True)

        print(result.stdout)

        if result.stderr:
            print(result.stderr, file=sys.stderr)

        sys.exit(result.returncode)

    except Exception as e:
        print(f"Error executing command: {e}", file=sys.stderr)
        sys.exit(1)


if __name__ == "__main__":
    main()
1–2
subprocess starts the external CLI; sys provides stderr and process exit.
5–7
Read the shared behavior as one string. The relative path means the expected working directory is the tac-1 root.
9–13
Build an argument vector. Passing a list avoids shell parsing: the complete multiline prompt is one argument after -p.
15–23
Run synchronously, capture both channels as text, print each to the matching host channel, then exit with the child’s return code.
25–27
Catch launch-time failures such as a missing claude executable and convert them into a readable error plus status 1.
30–31
The main guard runs the workflow only when this file is executed directly, not when imported.

Precise edge case

The open(...) call occurs before the try. If you launch from the wrong directory and the prompt path is missing, Python emits an uncaught traceback; the friendly “Error executing command” handler does not run.

programmable/programmable.sh adapter · 5 lines +
Purpose

The smallest proof of programmability: read text, call a terminal program with that text, print the returned text.

programmable/programmable.shcomplete source · 5 logical lines
PROMPT_CONTENT="$(cat programmable/prompt.md)"

OUTPUT="$(claude -p "$PROMPT_CONTENT")"

echo "$OUTPUT"
1
Command substitution reads the whole prompt. The surrounding quotes preserve internal spaces and newlines when stored.
2, 4
Blank lines visually separate the three-stage pipeline: input, invocation, output.
3
Invoke Claude in print mode. Quoting passes the multiline content as a single argument. Claude’s stdout is captured; stderr still flows to the terminal.
5
Print captured stdout. Command substitution removes trailing newlines, then echo adds one back.

Failure signal is lossy

There is no set -e or saved $?. If Claude exits nonzero, the script still reaches echo; the script’s final status is usually the successful echo, masking Claude’s failure from an outer caller.

programmable/programmable.ts adapter · 19 lines +
Purpose

The Bun-flavored adapter. It keeps the same read → invoke → print shape while expressing async process execution and explicit error handling.

programmable/programmable.tscomplete source · 19 logical lines
import { $ } from "bun";
import { readFileSync } from "fs";

async function main() {
    try {
        const promptContent = readFileSync("programmable/prompt.md", "utf-8");

        const output = await $`claude -p ${promptContent}`.text();

        console.log(output);
    } catch (error) {
        console.error(`Error executing command: ${error}`);
        process.exit(1);
    }
}

if (import.meta.main) {
    main();
}
1–2
Import Bun’s shell template and Node-compatible synchronous file reading.
4–6
Enter an async main function and read the same root-relative prompt as UTF-8. Unlike Python, this read is inside the try.
8–10
Await Claude, collect stdout as text, then log it. The prompt file—not the template wrapper—still owns the workflow.
11–14
Convert read or process failures into a console error and exit status 1. This preserves failure as a signal, though not Claude’s specific nonzero code.
17–19
Bun’s direct-execution guard prevents the launcher from firing if another module imports it.

04 · Compare

Same agentic behavior, different host guarantees

The language does not change what Claude is asked to do. It does change what the calling system can learn when something goes wrong.

Shell · 3 operations

Smallest concept demo. Captures stdout, inherits stderr, but normally loses Claude’s failing exit status after the final echo.

failure fidelity: low

Bun · async wrapper

Catches read or invocation errors and returns status 1. Clear and compact, but collapses specific child failure codes.

failure fidelity: medium

Python · subprocess

Separates output channels and propagates Claude’s exact return code. Its prompt-file read still sits outside the handler.

failure fidelity: highest

Name the pattern

These files are process adapters: tiny pieces of host-language code that translate “run our workflow” into a call to an external agent runtime. They should stay boring. The workflow belongs in the shared prompt.

05 · End to end

How one programmable run works

This is control flow and data flow together. Notice when responsibility crosses from your launcher into the agent.

  1. You start one adapter from the repository root.

    For example, uv run python programmable/programmable.py. The current working directory matters because prompt and project settings are located relative to the repo.

  2. The adapter loads prompt.md as data.

    No launcher interprets RUN, CREATE, or REPORT. It merely preserves the text and passes it forward.

  3. The adapter starts claude -p.

    The multiline prompt becomes the print-mode request. At this point the host program waits for the child process.

  4. Claude combines request, repository context, and allowed tools.

    The prompt supplies intent. .claude/settings.json supplies project permissions. The model/runtime decides the concrete tool-call sequence.

  5. The agent mutates Git and the working tree.

    It checks out or creates demo-agentic-coding, creates both Python programs, runs them with UV, stages the working tree, and commits.

  6. Execution results become observations.

    The outputs from both generated programs are available to the agent. REPORT tells it which observations must cross back to the caller.

  7. Claude returns text and a process status.

    The report arrives on stdout; diagnostics may arrive on stderr; success or failure arrives as an exit code.

  8. The adapter translates the result for its own caller.

    All three print a result, but only Python preserves the exact child status. This last boundary determines whether automation above the launcher can respond reliably.

Where is the “agent”?

Not in the Python, Shell, or TypeScript logic. Those files only create a process. Agency appears inside the Claude runtime’s repeated loop: interpret → choose a tool → act → observe → continue until the report contract is satisfied.

06 · Common fail + fix

Four ways a tiny demo still breaks

Most failures are boundary failures—starting state, working directory, authority, or error propagation—not mistakes in the generated print statements.

SymptomCauseRepair
prompt.md not foundYou launched outside the tac-1 root; all wrappers use the same root-relative path.cd to the lesson root before running the documented command.
main_aic.py is missingYou ran only the README’s second, sequential prompt instead of first performing the AI coding demo.Run the README prompts in order, or use the self-contained programmable prompt.
Claude asks for authorization or cannot actAuthentication or tool permissions are unavailable; text in a prompt does not itself grant authority.Authenticate the CLI, inspect project settings, and grant only the bounded capabilities you intend.
Shell caller says success after Claude failedThe final echo overwrote the useful child exit status.For automation, use the Python wrapper or explicitly capture and return Claude’s status in Shell.
Unexpected files enter the commitgit add . staged pre-existing changes alongside generated artifacts.Begin from a clean disposable checkout and inspect git status before firing the workflow.

A permission list is not a safety proof

The allowlist is a useful boundary, but git add . and git commit still have broad effects inside the checkout. Bounded verbs, clean starting state, and post-run verification work together.

07 · You try

Lab: make the report prove its branch

Modify one behavioral requirement, then verify the change traveled through the unchanged Python adapter.

One prompt edit · one headless verification

  1. Work in a clean, disposable copy of tac/tac-1. Confirm with git status --short.
  2. Ask your coding agent—not your editor—to add one REPORT requirement to programmable/prompt.md: return the current Git branch name before the two program outputs.
  3. Do not edit programmable.py. Predict why the launcher should require no change.
  4. From the lesson root, run uv run python programmable/programmable.py.
  5. Verify independently with git branch --show-current, uv run main_aic.py, and uv run main_tac.py.
  6. Compare those three observations with the returned report. Then inspect git log -1 --oneline and git status --short.

Pass criteria

  • The report names demo-agentic-coding and includes both exact program outputs.
  • The three launchers remain untouched; behavior changed only in the shared prompt.
  • The latest commit has the requested lesson message and the working tree contains no surprise files.
  • You can explain why this edit affects every launcher.

What the lab proves

The adapters transport behavior; they do not own it. A new report field belongs in prompt.md, so Shell, Bun, and Python inherit it without coordinated code changes.

08 · Teach-back

Close the page and explain the system

If you can answer these without file names becoming a blur, you understand the architecture rather than merely recognizing it.

1. Why are there three launchers if all three do the same thing?

Reveal answer

To prove the agent is callable from any language with terminal access. The wrappers are replaceable adapters; the shared prompt carries the workflow.

2. What is the difference between the README’s agentic prompt and programmable/prompt.md?

Reveal answer

The README prompt is the second half of a staged demo and assumes main_aic.py already exists. The programmable prompt creates both files and adds an exact-output REPORT, so it can run unattended.

3. Why is Python the strongest wrapper here?

Reveal answer

It keeps stdout and stderr distinct and exits with Claude’s exact return code. An outer system can therefore distinguish success from failure more precisely.

4. Does the prompt grant permission to commit?

Reveal answer

No. The prompt expresses intent. .claude/settings.json separately allows the Git commit command. Request and authority are different layers.

60-second challenge

Teach the repo from memory: “A caller enters through one of three doors. Then…” Continue through prompt loading, Claude’s tool loop, repository side effects, report, and exit status.

Pass if you name the behavior/policy/adapter boundaries and one wrapper failure difference. Bonus: explain why main_aic.py is absent before the run.
