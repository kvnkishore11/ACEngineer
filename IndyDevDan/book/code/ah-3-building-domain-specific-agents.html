Agentic Horizon · Building Domain-Specific Agents

Program the specialist around the code.

This lesson trains you to turn a repeated domain job into an operable agent system: the human commander chooses the job and risk boundary; prompts encode the role; tool and permission contracts bound action; a launcher mounts the worker; and observable artifacts decide whether to continue, recover, or stop. The eight apps are not eight code tours—they are evidence that the same operating pattern can inhabit a script, REPL, stream, backend, or multi-agent product.

intent → core four → mounted agent → tool evidence → persisted state → verify / recover

The hook: the model is replaceable. Your leverage lives in the operating ring that makes useful behavior repeatable.

01 · Who acts?

The commander designs the job; agents carry it

A specialist is not “Claude with a clever prompt.” It is a cast with explicit ownership. If the human still shuttles every artifact and decides every retry, the system is wearing an agent costume but remains human-powered.

ActorOwnsDoes not own
Human commander
in authority		Selects a domain-shaped task, risk tolerance, model class, acceptance evidence, and whether custom is justified.Should not be the message bus between every plan, build, review, stream read, or retry.
Claude Code / SDK worker
probabilistic		Interprets the prompt, chooses permitted tools, reasons across context, and emits response blocks plus a result receipt.Cannot grant itself tools, enlarge its file boundary, or prove its own output correct by assertion.

02 · Agent surface map

The agent touches interfaces, not “the repo”

Adopt the worker’s perspective. Its world is the context and capabilities you mount—not every file that happens to exist on disk.

Outer operating layer. Root .claude/settings.json, slash commands, output styles, and command hooks shape an interactive Claude Code session in this repo.
Embedded operating layer. Each Python product builds its own ClaudeAgentOptions, inline hooks, custom tools, session policy, and form factor. Outer settings are not a substitute for these contracts.

03 · Control loop

Plan → act → verify → recover changes shape by loop position

In-loop work keeps the commander at the next decision. Out-of-loop work moves evidence through a harness until a gate fails, the job finishes, or authority returns to the human.

In loopPong, Echo, Calc, QA
PlanHuman frames one question or calculation.
ActAgent answers or calls a bounded tool.
VerifyHuman sees text, tool call, error, cost, and session.
RecoverRephrase, clear, quit, or change the contract.
Out of loopSocial, SDLC, Ultra
PlanPrompt and controller encode the repeated workflow.
ActAgents consume streams or artifact paths and call tools.
VerifyHooks, stored summaries, review artifacts, and state events observe.
RecoverDeny, retry, clear/reconnect, mark Errored, or escalate.
Failure evidence must route backward. If it only appears in a log while the controller keeps shipping, the loop is open.
Name the pattern · core-four specialistConfigure only the context, intelligence, instructions, and tools the domain needs.
Name the pattern · artifact relayPass a spec path, produced-log row, or session ID—not copied chat memory—between stages.
Name the pattern · replaceable workerKeep deterministic state and acceptance evidence outside the model so another worker can continue.

04 · Why these files exist for agents

Four contracts turn capability into an operable system

These snippets are evidence of contracts, not a source walkthrough. Read each as a boundary between the commander, model, deterministic runtime, and next stage.

Prompt contract · what the agent is allowed to understand

apps/custom_7_micro_sdlc_agent/backend/system_prompts/PLANNER_AGENT_SYSTEM_PROMPT.md

The planner does not receive “be smart.” It receives a domain procedure: inspect the real codebase, ground the plan in existing patterns, write only a specific artifact class, and make it implementable by someone else.

Prompt placement also chooses identity. A string overwrites the generalist; preset: claude_code keeps it; append extends it. The SDLC uses all three judgments: planner/reviewer extend, builder stays generalist, the stream agents are complete custom specialists.

Dan’s design intent: teach the workflow once, then make every fresh worker perform the role without a human re-explaining it.

prompt evidenceplanner
### CRITICAL: Research the Codebase First

Before writing any plan, ALWAYS search the codebase:

1. Use `Grep` to find similar features, patterns, and conventions
2. Use `Glob` to understand project structure and organization
3. Use `Read` to examine key files that will be affected

Never make assumptions - verify everything by searching.

Tool / permission contract · what it can do

.claude/settings.json · apps/custom_5_qa_agent/qa_agent.py · apps/custom_3_calc_agent/calc_agent.py

The outer settings intercept Bash before execution and log lifecycle events. Inside the SDK apps, options and inline hooks form a separate boundary: QA keeps read/search/Task but disallows editing; Calc removes built-ins and exposes only its two custom tools; planner/reviewer hooks restrict writes to specs/ and reviews/.

allowed_tools gates calls. It does not promise that every other definition is absent from context; the Echo→Calc comparison makes disallowed_tools the context-pruning control.

Dan’s design intent: make the least authority needed obvious in configuration, then enforce conditional rules at the tool boundary.

{
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{

      "timeout": 5
    }]
  }]
}

Harness / launcher · how you call the agent programmatically

apps/custom_7_micro_sdlc_agent/backend/main.py · backend/modules/agent_orchestrator.py

The kanban UI does not “become agentic.” A deterministic controller watches an allowed stage transition, launches planner, passes its returned specs/*.md path to builder and reviewer, stores session IDs, broadcasts progress, and owns terminal state.

The smaller agents teach the same seam: Pong uses one-off query(); custom tools require ClaudeSDKClient; Calc captures ResultMessage.session_id and passes it back through resume=.

Dan’s design intent: turn agent behavior into a callable component that can live behind a CLI, stream, API, or UI—and be replaced without losing workflow state.

launcher evidencemicro SDLC
# controller owns the relay
plan_result = await run_planner_agent(...)

if not plan_result["plan_path"]:
    raise Exception("Planner failed to create a plan")

build_result = await run_builder_agent(
    plan_path=plan_result["plan_path"], ...

review_result = await run_reviewer_agent(
    plan_path=plan_result["plan_path"], ...
)

Verification contract · how you know it succeeded

apps/custom_7_micro_sdlc_agent/backend/user_prompts/REVIEWER_AGENT_USER_PROMPT.md · apps/custom_5_qa_agent/test_inline_hooks.py

The reviewer is told to compare the actual diff with the plan across functionality, tests, security, performance, and documentation. QA’s direct hook test proves the deny function returns the expected payload. Response parsers expose calls, errors, duration, cost, and session identity.

But there is an intentional systems lesson in the shipped controller: after the reviewer returns, the ticket moves to Shipped without parsing a pass/fail verdict or requiring tests. A review artifact is evidence; it is not yet a closing gate.

Dan’s design intent: give agents stdout-like evidence so the next decision can be programmed. Your production step is to make that evidence branch control flow.

Plan gate
Planner must return a path or the workflow raises and moves to Errored.
Behavior signal
Tool blocks, WebSocket stage changes, stored rows, and direct hook tests show what ran.
Missing closure
Reviewer completion currently advances to Shipped; no verdict parser blocks the transition.

05 · One worked run

Operate like Dan: audit the ring, then let it carry the work

The worked run uses the Micro SDLC because it makes role separation and artifact handoff visible. Run it only against a codebase you are willing to modify: the builder uses permission_mode="bypassPermissions".

Start from the real backend project

The README treats each Python agent as its own UV project.

cd agentic-horizon/building-specialized-agents/apps/custom_7_micro_sdlc_agent/backend uv sync uv run python main.py

Start the observer surface

In a second terminal, launch the Vue kanban and open the README’s port.

cd agentic-horizon/building-specialized-agents/apps/custom_7_micro_sdlc_agent/frontend npm install npm run dev # open http://127.0.0.1:5174

Command, do not implement

Create a narrow ticket such as “update the HTML title and header to ‘Plan, Build, Review, Ship Agents’.” Choose the model and confirm the codebase path before granting authority.

Trigger one state transition

Drag Idle → Plan. From here the controller—not the human—launches Planner → Builder → Reviewer and broadcasts each stage over WebSocket.

Inspect handoffs and authority

Confirm a real specs/*.md artifact, builder changes, a reviews/*-review.md artifact, tool-call counts, and separate session IDs. The shipped config uses specs/, despite older README wording that says plans/.

Close the human gate

Run the affected project’s tests and inspect git diff. Treat the board’s Shipped state as “workflow finished,” not proof that acceptance criteria passed. Stop both processes when done.

Commander gate

Before Idle → Plan, answer:

  • Is this repeated or domain-specific enough to justify a custom system?
  • Which prompt is overwrite, append, or pure preset?
  • Which directory can each role write?
  • What artifact crosses each seam?
  • What evidence can stop shipping?
  • Who recovers when a worker returns malformed output?

06 · Fail, name, repair

Most “agent failures” are operating-system failures

Inspect the contract that shaped behavior before blaming the model. These signatures are visible in the lesson’s own contrasts and wiring.

Mis-prompting replaces the wrong agent

A generic engineering job receives a full system overwrite, throwing away the useful Claude Code preset.Repair: generalist → append → overwrite; move right only for a named domain mismatch.

Allowed is mistaken for unloaded

Echo can call only its custom tool, yet other built-in definitions may still occupy context.Repair: use explicit disallowed_tools when the domain does not need those definitions.

Outer hooks are assumed to protect embedded agents

Root command hooks and SDK inline hooks are separate operating layers. Configuring one does not prove the other is governed.Repair: trace the exact launcher and observe a denied call in that runtime.

A file on disk impersonates capability

.claude/hooks/context_bundle_builder.py exists, but shipped .claude/settings.json does not invoke it.Repair: capability means mounted, triggered, and observed—not merely committed.

A chat-shaped UI impersonates memory

A REPL or browser can look continuous while the backend starts a fresh session every request.Repair: capture the result session ID, persist it, and supply it through resume=.

Over-permission becomes invisible

The SDLC builder uses bypassPermissions; root aliases also demonstrate skip-permission modes. Convenience can exceed the apparent tool story.Repair: run in a disposable scope, narrow cwd, audit commands, and make the exception explicit.

The human stays in the loop as middleware

The commander copies plan text, restarts each worker, and manually advances every state.Repair: pass artifact paths and let a deterministic controller own valid transitions and receipts.

Context “clear” is taken literally

Ultra Stream’s clear_context tool resets a counter and broadcasts status; the outer loop disconnects and reconnects around its threshold.Repair: verify actual session/reconnect behavior; do not infer a full context wipe from a tool name.

Review exists, but the loop still ships open

Micro SDLC checks that a plan path exists, then awaits build and review. After reviewer completion it advances to Shipped without parsing a verdict or requiring a test result. This is the perfect “missing verify” lesson: a review document is observable evidence, but until failure changes control flow it cannot close the loop.Repair: define a machine-readable verdict, require behavioral checks, and route fail/needs-work to patch, retry, Errored, or human escalation.

07 · Lab · Agent operations

Strengthen QA’s evidence contract—without touching app logic

Your target is the prompt interface around the QA worker. The exercise makes prompt behavior observable and proves that a prompt cannot override a permission hook.

Change the agent system

  1. From apps/custom_5_qa_agent, run uv sync, then uv run python qa_agent.py.
  2. Baseline: ask “How does block_env_files enforce the .env denial?” Save the answer and its cited paths.
  3. Edit only prompts/QA_AGENT_SYSTEM_PROMPT.md. Add a short Evidence Ledger report contract requiring each conclusion to include claim, file path + line, evidence type (direct or inference), and a final Verification: PASS | INCOMPLETE.
  4. Exit and restart the process. QA loads the prompt in QAAgentREPL.__init__; the shipped /clear path rebuilds the client but does not reread the prompt file.
  5. Ask the same question. Confirm the response shape changed while the Python launcher and application files did not.
  6. Make it fail safely: ask it to read .env.sample. The PreToolUse hook must deny the call even if the prompt wants comprehensive evidence.
  7. Run the shipped direct hook check:
    uv run python test_inline_hooks.py
  8. Use git diff -- prompts/QA_AGENT_SYSTEM_PROMPT.md and git status --short to inspect your agent-OS-only change. Restore or commit it intentionally.
Name the pattern: prompt shapes judgment and output; permission gates authority; a fresh mount activates changed system instructions; direct tests and observed denials are different layers of proof.

Observable pass criteria

  • The second answer contains a structured Evidence Ledger.
  • Claims cite real files and lines.
  • Direct evidence and inference are labeled separately.
  • The answer ends in PASS or INCOMPLETE.
  • .env.sample is denied by the hook.
  • test_inline_hooks.py completes and reports the deny condition.
  • No .py, frontend, or application behavior file changed.
  • You can explain why restart—not /clear—activated the edited prompt.

08 · Retrieval check

Explain this lesson’s agent OS in six sentences—without looking

The human commander owns…
The core four control…
The prompt and permission contracts differ because…
The launcher makes a specialist programmable by…
Verification closes the loop only when…
Dan’s leverage and replaceability move is…
Compare with a model answer
The human commander owns task choice, authority, risk, and final acceptance. The core four—context, model, prompt, and tools—make a model behave like a repeatable specialist. The prompt defines what the worker should understand and produce, while permissions independently constrain what it may do. A launcher mounts those choices behind a query, client, stream, API, or multi-agent controller and keeps state outside the worker. Verification closes the loop only when observable evidence can stop, retry, patch, or escalate the run. Dan’s leverage move is to improve this operating ring so workers remain programmable and replaceable while the human stops serving as runtime.
