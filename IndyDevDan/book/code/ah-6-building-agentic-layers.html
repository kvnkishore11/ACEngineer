Agentic Horizon · Building Agentic Layers

Build the operating system around the code.

This lesson trains you to turn a repository into a surface agents can reliably operate: the human commander states outcomes and risk; prompts program focused behavior; tool and permission contracts bound capability; launchers move agents out of the terminal; hooks and artifacts expose what happened; and verification decides whether the system stops, repairs, or returns authority. The goal is not “more AI files.” It is a specialized, replaceable, closed-loop system that builds the system.

context + prompt + tools + harness + evidence → programmable engineering

The hook: an agent is only as capable as the world mounted around it. Change the mount—working directory, prompt, tool list, hook, launcher, or acceptance receipt—and you have changed the agent system.

Class 1 · in-loopYou invoke prompts, subagents, skills, and review loops in the terminal.
Class 2 · out-loopDeterministic code launches and carries a multi-step agent workflow.
Class 3 · orchestratedAn O-agent selects workers or starts an ADW through typed tools.

01 · Who acts?

The commander owns intent; the layer owns execution

The first design move is role separation. If the human becomes the scheduler, verifier, and recovery script, the system is still in-loop. If the agent chooses its own authority and success test, the system is uncontrolled.

ActorOwnsBoundary / receipt
Human commander
authority		The outcome, working directory, acceptable cost, risk tolerance, and observable acceptance evidence.Does not hand-carry plan → build → review. Intervenes on a failed gate or a decision the harness cannot safely make.
Claude Code / CLI agent
in-loop operator		Loads CLAUDE.md, project commands, settings, tools, and the active prompt; performs one interactive job.Its effective capability is the intersection of prompt, tools, settings, hook gates, and current working directory.
Focused subagents
specialists		Seven root templates package a purpose, model, and tool vocabulary: planner, builder, scouts, docs scraper, validator, and meta-agent.A scout promises read-only analysis; a builder promises one-file implementation plus checks. Their reports are handoff contracts.
ADW phase agents
ephemeral workers		Separate plan, build, review, and optional fix sessions created by deterministic workflow code.Each step writes lifecycle events and durable artifacts; the workflow owns order and failure transitions.
Orchestrator agent
lead / router		Ten typed tools: eight for agent lifecycle and two—start_adw, check_adw—for out-loop workflows.Its prompt says command-level agents do heavy writing, editing, and testing. It should coordinate, not absorb their work.
Reviewer / verifier
gate		Reads prompt, plan, and diff; writes a risk-tiered report and a PASS/FAIL verdict.Analysis only. A FAIL becomes input to a separate fix agent rather than quiet self-approval.
Hooks + launcher scripts
deterministic operators		Block dangerous calls, emit events, spawn detached processes, start services, update state, and announce completion.They are not reasoning agents; they are the reliable mechanics that let reasoning agents operate out of loop.

Dan’s replaceability test: if the model changed tomorrow, could the prompts, tool boundary, launch protocol, and evidence still explain the job? If yes, you engineered a system instead of a personality cult.

03 · Control loop

Out of the loop still needs a loop

The same four moves appear at every class: plan → act → verify → recover. Maturity changes who carries the transition. The human carries it in Class 1; deterministic code and typed tools carry it in Classes 2 and 3.

In-loop movesHuman operates the pieces.
/plan
inspect spec/build
watch edits/review
read verdict/fix
choose repair
Out-of-loop movesPython and the O-agent carry transitions.
start_adw
create rowPopen
detach runStepEnd
persist proofverdict
skip or fix
FAIL → find review artifact → launch fix agent → re-run validation, or mark the ADW failed with the exact error step

Isolation rule: every composite remains runnable in pieces. Because /plan, /build, /review, and /fix are independent contracts, one bad phase can be diagnosed without replaying the whole system.

04 · One worked agent run

Follow the receipts, not the chat

A plan_build_review_fix run is the cleanest picture of the lesson. The model reasons inside each box; the layer controls the boxes, the handoffs, and the proof.

Commander names the outcome and boundary

Provide a task, workflow type, and working directory. Via the orchestrator, intent becomes a typed start_adw call—not a host parser looking for the literal phrase “start adw:”.

Receipt · adw_id

Launcher makes the work independent

adw_scripts.py maps the workflow type to a real adw_*.py file and spawns uv run … --adw-id … with a new session.

Receipt · PID + pending DB row

Planner creates an addressable handoff

The workflow starts a fresh agent with /plan <prompt>. The prompt contract requires a file under specs/; the harness extracts or discovers its path.

Receipt · specs/*.md

Builder acts from the plan

A separate agent receives /build <plan-path>, edits the mounted working directory, and must run the plan’s validation commands before stopping.

Receipt · diff + command results

Reviewer decides the branch

A verifier reads intent, plan, and git changes, then writes a risk-tiered report to app_review/ ending in PASS or FAIL.

Receipt · review_*.md + verdict

Harness closes or recovers

PASS skips the fix phase. FAIL finds the newest review file and launches a dedicated /fix agent, which writes app_fix_reports/. Any failed step records error_step and ends the workflow as failed.

Receipt · terminal ADW status

Your job during the run

  • Choose the smallest workflow that can produce the needed confidence.
  • Mount the correct cwd; it is a capability boundary.
  • Name evidence before launch: spec, diff, validation, verdict.
  • Do not become a polling loop. Ask for status when a decision depends on it.
  • Escalate authority when recovery would widen scope or risk.
Name the pattern: deterministic shell, probabilistic workers. Python owns state, order, process identity, and branches. Agents own interpretation and creation. Durable artifacts bridge the two.

05 · Why these files exist for agents

Four contracts turn capability into operation

These snippets are evidence of interfaces, not a source tour. Read each one as a promise made to an agent—or a promise the harness makes about that agent.

Prompt contract · what “done” means

.claude/commands/build.md

The build command converts an ambiguous request into a strict operational promise: take one plan path, execute all steps in order, and refuse to stop without validation. That is more useful than telling a model to “be careful.”

Dan’s design intent: program the engineering method, then make the method composable. The output of /plan is valid input to /build because both sides agree on the artifact.

prompt evidencemarkdown
# Build
Implement the plan top to bottom.
Do not skip any steps.
If you have not run validation commands,
DO NOT STOP until the work is validated.

Tool / permission contract · what action is possible

.claude/agents/scout-report-suggest-fast.md · .claude/settings.json · apps/orchestrator_3_stream/backend/modules/agent_manager.py

The root scout template declares only Read, Glob, Grep. The project settings register hooks but contain no permission allowlist. More importantly, the orchestrator reads template tools at creation but command_agent later grants its own broad defaults with permission_mode="acceptEdits". Tool policy must be verified at the actual invocation boundary.

Dan’s design intent: one agent, one prompt, one purpose—and just the tools that purpose needs. Least privilege is part of focus, not merely security.

Current wiring gap: a “read-only” template is not sufficient proof that an orchestrator-launched worker remains read-only.
template evidenceyaml
name: scout-report-suggest-fast
tools: Read, Glob, Grep
model: haiku
CLI template: three read-only tools.
Orchestrator init: zero tools.
Orchestrator command: broad default tool set.
ADW phases: explicit allowlist plus bypass_permissions=True.

Harness / launcher · how the agent becomes a program

adws/adw_triggers/adw_scripts.py

The launcher does not ask one giant agent to remember a workflow. It resolves a workflow file, passes one durable identifier, starts from the project root, disconnects stdin/stdout, and creates a new process session. The database row is the handoff between caller and worker.

Dan’s design intent: code should own the boring certainty. A detached process makes “out of loop” literal; an adw_id makes the run addressable after the chat is gone.

launcher evidencepython
cmd = ["uv", "run", str(workflow_path),
       "--adw-id", adw_id]

subprocess.Popen(
    cmd,
    cwd=str(project_root),
    start_new_session=True,
)

Verification contract · what may change the branch

.claude/commands/review.md · adws/adw_workflows/adw_plan_build_review_fix.py

The reviewer is explicitly analysis-only and produces a timestamped artifact with a verdict. The workflow treats that verdict as data: PASS closes; FAIL locates the report and starts a separate repair phase.

Dan’s design intent: more compute should create more warranted trust. Separate generation from judgment, persist the judgment, and connect it to a recovery move.

verification evidenceprompt + branch
# review.md
Operate in ANALYSIS AND REPORTING mode.
End every report with PASS or FAIL.

# workflow
if verdict == "FAIL":
    review_path = await extract_review_path(...)
    await run_fix_step(...)

07 · Common agent failures

Most “model failures” are system failures in disguise

Debug the operating surface before swapping models. A stronger model cannot repair a missing acceptance contract, a wrong mount, or a verifier disconnected from recovery.

Mis-prompted purpose

One worker is asked to explore, plan, implement, and approve. It optimizes for narrative completion instead of one observable job.Repair · one agent, one prompt, one purpose; hand off through files.

Template says read-only; runtime says write

The root scout frontmatter is narrow, but the orchestrator’s command path grants broad defaults. The policy exists in prose but not at the invocation boundary.Repair · persist template tools and enforce them when constructing ClaudeAgentOptions.

Over-permissioned ADW

Plan/build/review/fix phases set bypass_permissions=True. A wrong prompt or wrong cwd can therefore become a large blast radius.Repair · narrow allowlists per phase and add blocking hooks for irreversible operations.

Hooks mistaken for a policy

.claude/settings.json wires event hooks, but no permission allowlist. pre_tool_use.py blocks dangerous recursive deletes; its .env guard is present but commented out.Repair · state the policy explicitly, enable the gate, and test both allow and deny cases.

Open-loop verification

A review report exists, but nothing consumes its verdict. The system looks observable while bad work keeps moving.Repair · turn PASS/FAIL into a branch that closes, fixes, stops, or escalates.

Chat as memory

The next phase depends on text buried in the previous conversation. A compact, crash, or new process loses the handoff.Repair · write addressable artifacts under specs/, app_review/, and app_fix_reports/.

Wrong working directory

Templates and commands are discovered relative to cwd; the agent sees a different operating system than the commander expects.Repair · print and verify the mount before launch; treat --cwd as authority.

Staying in the loop

The human polls every 15 seconds, translates every message, and manually starts each phase. The “orchestrator” has merely moved the toil into chat.Repair · encode cadence and phase transitions; return only on evidence or escalation.

Generic layer syndrome

A reusable fleet accumulates every tool, every framework rule, and every workflow. Context and token costs grow while the agents know less about the one codebase that matters.Repair · specialize the layer to this repository and this use case. Replaceability means workers can change; it does not mean the operating system must be generic.

08 · Lab · agent ops

Close one permission loop without touching app logic

Change the agent system itself. The existing pre-tool hook already contains an is_env_file_access detector, but the call that blocks access is commented out. Your job is to activate, test, and explain that boundary.

  1. Hook. Open .claude/settings.json and prove pre_tool_use.py is registered for PreToolUse.
  2. Picture. Draw one line: agent tool request → pre-tool hook → allow or exit 2 → tool execution. Mark where the model stops having authority.
  3. Worked baseline. Pipe a synthetic Read event for .env.sample to the hook and record exit 0. Then pipe one for .env; before your change, it also exits 0.
  4. Name the pattern. Write “pre-action policy gate”: deterministic code evaluates a proposed agent action before side effects.
  5. Fail. In .claude/hooks/pre_tool_use.py, enable the existing is_env_file_access block. Do not invent a new hook or touch application code.
  6. Try again. Re-run both synthetic events. .env.sample must remain allowed; .env must print the existing BLOCKED message and exit 2.
  7. Explain the scope. State why this protects Claude Code sessions using project settings but does not automatically prove every Agent SDK path is protected—especially ADWs using SDK hooks plus bypass_permissions=True.
printf '%s' '{"tool_name":"Read","tool_input":{"file_path":".env.sample"}}' \ | uv run .claude/hooks/pre_tool_use.py echo $? printf '%s' '{"tool_name":"Read","tool_input":{"file_path":".env"}}' \ | uv run .claude/hooks/pre_tool_use.py echo $?

Observable pass criteria

  • No file under apps/ changes.
  • .env.sample test exits 0.
  • .env test exits 2 and emits the repo’s existing BLOCKED message.
  • The settings file still parses as JSON.
  • You can point to the exact hook registration and the exact blocking branch.
  • Your explanation distinguishes a prompt instruction, an allowlist, and a pre-action gate.
If the allowed case also fails: inspect the negative look for .env.sample and test the detector directly. A safety gate that blocks the legitimate template path is not “more secure”; it is a broken contract.
HOOKSecrets are exposed to a proposed tool.
PICTURERequest passes through a gate.
RUNBaseline proves the gap.
FAILPolicy changes behavior.
TRYAllow + deny both pass.

09 · Retrieval · no notes

Explain the agent OS in six sentences

Close the page. Speak one sentence for each prompt below. You pass only if every sentence names a real responsibility or evidence path.

The human commander owns…
Prompts and memory program the agent by…
Tools, permissions, hooks, and cwd bound the agent by…
The launcher makes the workflow out-of-loop by…

Reveal one acceptable six-sentence answer
The human commander owns the outcome, working directory, risk boundary, cost, and acceptance evidence. Prompts, CLAUDE.md, agent templates, and skills program focused behavior for this codebase. Tool lists, permission modes, hooks, and the mounted cwd define what action is actually possible. adw_scripts.py turns a database-backed request into a detached workflow whose Python code owns step order and status. The loop closes when a reviewer’s PASS/FAIL artifact changes the next move to complete, fix, fail, or escalate. Dan calls the layer leverage because replaceable agents can carry more closed-loop engineering while the human commands the system instead of hand-operating every worker.
