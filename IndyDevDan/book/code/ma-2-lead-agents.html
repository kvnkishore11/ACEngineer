Multi-Team Agentic Coding / Lead Agents

The lesson is not “ten agent Markdown files.” It is an agent operating system: one human command surface, a depth-2 delegation tree, prompts that specialize judgment, runtime gates that constrain action, and a harness that keeps working until it can return evidence.

01 · Hook · Agent mission

Stop being the router for every line of work

This lesson trains you to command a team-producing system instead of repeatedly steering one generalist. You choose the mission, operating config, authority boundaries, and acceptance evidence; the Orchestrator classifies the request, leads decompose it, workers execute inside owned domains, and the harness brings one synthesis back. Your work moves upward—from doing and dispatching to designing an agent OS you can trust, measure, replace, and scale.

↗

Dan’s leverage move: if you spend the day re-prompting one agent, you are still the orchestrator. Program routing, specialization, memory, and verification into the system so your cognitive load stays flat as capability grows.

04 · Plan → act → verify → recover

One human turn opens a nested closed loop

You remain in-loop for mission design and acceptance. During an agent turn, the Orchestrator, leads, and workers run out-of-loop until the hierarchy can return one evidenced answer or a real blocker.

In-loopcommander boundary
PlanChoose goal, config, writable scope, budget, and pass criteria.
LaunchSend one message through the Orchestrator interface.
VerifyRead output, logs, tree, cost, diffs, and tests.
RecoverRepair prompt, config, gate, or launcher—then relaunch cleanly.
Human owns why + limits⇄Agents own routing + work
Out-of-loopnested agent turn
PlanOrchestrator classifies, creates TillDone items, selects one team by default.
ActLead reads context and delegates execution to the right specialist.
VerifyWorker returns evidence; lead synthesizes; tasks and costs update.
RecoverDenied calls reroute, incomplete tasks trigger a nudge, dependent teams run sequentially.

A worked run · “ping each team lead”

1 · CommanderTypes one real README smoke test.
2 · OrchestratorTargets Planning, Engineering, and Validation.
3 · LeadsEach answers at its coordination tier; workers are unnecessary.
4 · HarnessStreams three lanes, aggregates usage, records JSONL.
5 · CommanderChecks three lead replies, team tree, footer cost, and log.

Name the pattern: a narrow-waist, depth-2 hierarchy. One stable commander interface sits above replaceable teams; coordination seats reason, execution seats act, and structural gates keep the layers honest.

05 · Why these files exist for agents

Four contracts make the team operable

These excerpts are evidence of interfaces. The lesson lives in the promises between them, not in a line-by-line tour.

Prompt contract · what the seat is allowed to understand

.pi/multi-team/agents/orchestrator.md · .pi/multi-team/skills/*.md

The Orchestrator prompt defines its purpose, runtime placeholders, routing defaults, tools, skills, personal expertise, and the instruction to synthesize. Leads receive the same shape but a member list; workers receive precise execution roles.

Dan’s design intent: specialization is a package, not a persona. Give every seat a job, a memory, a set of behaviors, and a reason to stop.

prompt contractorchestrator.md
skills:
  - active-listener.md
  - zero-micro-management.md
  - high-autonomy.md
tools: # selected entries
  - read
  - delegate
  - tilldone

# routing instruction
Default to ONE team.
Synthesize into YOUR answer.

Tool / permission contract · what the seat can actually do

agents/*.md front matter · extensions/domain-enforcer.ts · extensions/lead-delegate.ts

A tool name grants a capability; domain rules constrain where it applies. Team leads can read broadly and write only their own expertise; the Orchestrator can write under the expertise directory; workers receive file and bash tools. The enforcer blocks unlisted tools and denied paths; deleting LEAD_MEMBERS_JSON before spawning a worker caps recursion.

Dan’s design intent: make autonomy safe by shrinking blast radius. A soft “delegate, never execute” skill teaches behavior; a hard runtime gate refuses violations.

permission contractbackend-dev.md
tools:
  - read
  - write
  - edit
  - bash
domain:
  - path: apps/
    read: true
    upsert: true
    delete: true

Harness / launcher · how the system becomes callable

justfile · apps/multi-team-chat/extensions/multi-team-chat.ts · extensions/modules/subprocess.ts

The launcher turns the system into one short command. The extension loads the roster, resolves prompts and shared context, replaces the Pi chat surface, and registers delegation and task tools. Every child is the same pi binary in JSON mode with only three explicit runtime extensions.

Dan’s design intent: package orchestration as a reproducible program. Agents should be replaceable behind a stable command and a stable conversation surface.

launcher evidencejustfile + subprocess.ts
just team
└─ pi -e extensions/multi-team-chat.ts

child seat:
pi --mode json -p --no-extensions
  -e domain-enforcer.ts
  -e lead-delegate.ts
  -e tilldone-lead.ts
  --session <agent.jsonl>

Verification contract · how the commander knows it worked

.pi/multi-team/sessions/<session>/conversation.jsonl · TUI team tree · TillDone · specs/

The chat shows routing and tool events; /toggle-workers reveals all ten seats and per-agent cost; TillDone exposes unfinished work; the session log preserves every tier’s messages. The cost-tracking spec is a reminder that even the meter needs verification.

Dan’s design intent: close the loop with receipts that can change the next run. Confidence is not a completion signal.

Route proof · expected team / lead bubble appears
Boundary proof · forbidden write returns a domain denial
Work proof · TillDone reaches complete and tests/artifacts exist
Accounting proof · team tree, JSONL usage, and provider dashboard agree

Preflight

  • pi, Bun, Node, Claude Code, and just are installed.
  • .env exists with the required provider key; never print or commit it.
  • Every config path resolves to a real agent Markdown file.
  • You understand that a delegated test spends paid tokens.
  • You have an observable pass condition before launch.

Do not confuse the two orchestration layers. just team runs the Pi agent team with delegate/tilldone. /plan-w-team, /build, and just metacc belong to the Claude Code build harness that maintains the system.

High-trust boundary. The install/meta recipes use --dangerously-skip-permissions. That broad Claude Code authority is not the same as the per-seat domain gates inside the Pi runtime.

07 · Common agent failures

Most team failures are operating-system failures

A stronger model cannot rescue a stale launcher, vague routing contract, false permission boundary, or missing receipt.

Mis-prompting · every task fans out

Delegating greetings or trivial lookups adds latency and spend without specialist value.

Repair · preserve “answer simple questions directly; default to one team.”
Misrouting · the wrong expert gets perfect context

Everything downstream can be excellent and still answer the wrong question.

Repair · sharpen consult-when, inspect route receipts, test classification.
Soft rule mistaken for permission

“Delegate, never execute” in a skill can influence behavior but does not itself block a tool call.

Repair · pair prompt discipline with tool allowlists and path enforcement.
Over-permission · maintainer authority leaks

A --dangerously-skip-permissions bootloader is treated as if every runtime seat were safely scoped.

Repair · separate Claude Code authority from Pi seat domains; review install targets and overwrites.
Bash gate mistaken for a sandbox

The domain enforcer uses command-pattern heuristics for bash writes/deletes; it is not OS-level isolation.

Repair · narrow worker tools and run high-risk work in a real sandbox.
Missing verify · polished synthesis wins

No one checks the team tree, JSONL, task state, changed files, tests, or actual provider bill.

Repair · define a receipt bundle before spending the first token.
Stale process · ghost messages

Drive/tmux reuses a live Pi session or sends another prompt before the Orchestrator is idle.

Repair · fully kill and recreate the session; wait for completion.
Empty expertise mistaken for breakage

All ten shipped mental-model files start at zero lines.

Repair · let each specialist grow codebase-specific memory; do not seed it with stale project facts.
Horizontal clones mistaken for diversity

team-scale repeats Engineering seats to add capacity, not independent expertise.

Repair · use duplicate teams for throughput; new prompts/domains for cognitive diversity.
Staying in the loop

The human addresses workers, schedules handoffs, and becomes the coordination bottleneck again.

Repair · speak to the Orchestrator; improve the OS between runs.
Reality check · three pieces of drift

The shipped roster is 3 teams / 10 agents, despite one “2 teams” description line. The shipped Frontend and Backend workers both own broad apps/; the narrower apps/frontend/ vs apps/backend/ split was a live demo edit. The shipped Orchestrator includes write, edit, and tilldone, which the earlier recording frame did not yet show.

Docs drift is itself an agent failure

.claude/commands/prime.md says just multi launches the system, while the real justfile and README use just team. A priming prompt can be stale; triangulate prompts, executable launchers, and observed runtime behavior.

08 · Lab · Agent operations

Change the roster, not the application

The experiment makes agents visibly replaceable through configuration. Keep the task trivial so you are measuring the operating system, not model brilliance.

Experiment · prune a team through a real preset

  1. Run just team-list. Predict the exact rows the Planning + Engineering preset will show.
  2. Launch just team-pe. This selects the real .pi/multi-team/planning-and-engineering-config.yaml.
  3. Type ping. Confirm the Orchestrator answers directly without delegation.
  4. Type ping each team lead. Confirm only Planning Lead and Engineering Lead answer; Validation must not appear.
  5. Run /toggle-workers. Count exactly 7 seats: Orchestrator + 2 leads + 4 workers.
  6. Open the newest conversation.jsonl and confirm the two lead routes exist while Validation events do not.
  7. Stop the process. Launch just team and confirm the default ten-seat roster returns.

Fail → try: if Validation still appears, you likely reused a live Pi/tmux session or launched just team. Kill the process, verify the command, and relaunch. If a config fails to load, trust the named path error before blaming the model.

Observable pass criteria

  • just team-pe shows exactly 7 expected seats.
  • Simple ping stays at the Orchestrator.
  • Lead ping routes to exactly 2 teams.
  • The session JSONL matches the visible routing.
  • No application source was edited.
  • just team restores 10 seats afterward.

Stretch · prove the hard gate

  • On a disposable branch, narrow a worker’s domain: in its agent Markdown.
  • Ask the lead to delegate one harmless write outside that path.
  • Pass only if domain-enforcer blocks it and the target remains unchanged.
  • Restore the agent file before the next run.

09 · Teach-back · close the page

Explain this agent OS in six sentences

Do not look back. One idea per sentence; if you cannot separate prompts from permissions, the model is still fuzzy.

The human commander owns …
The Orchestrator owns …
Leads differ from workers because …
The repository makes agents operable through …
The loop is closed when …
Dan’s highest-leverage move is …
Reveal one strong six-sentence answer

The human commander owns the mission, operating config, risk boundary, spend, and final acceptance. The Orchestrator keeps one interface while classifying work, managing TillDone, routing to the smallest useful team, and synthesizing results. Leads read, coordinate, delegate, and update their own memory, while workers alone receive execution tools and code-writing domains. Prompts, skills, config, injected context, launchers, subprocess extensions, domain gates, sessions, and logs turn general models into an operable team. The loop closes when task state, changed files, tests, routing logs, and trustworthy cost accounting support acceptance or a specific repair. Dan’s leverage move is to program replaceable agents around the code so the human can stop scheduling every action and start improving the system that performs them.
