# Plan: Context Size Scaling Benchmark (GraphWalks)

## Task Description

Create a new "context-scaling" benchmark for the live-bench platform that measures how prefill speed, decode speed, wall time, and **accuracy** change as prompt size increases from ~200 tokens to 64K tokens. Uses the [OpenAI GraphWalks](https://huggingface.co/datasets/openai/graphwalks) dataset (MIT-licensed) as context content — a long-context multi-hop reasoning benchmark where the model must trace paths through directed graphs described as edge lists. The two smallest sizes (ctx_200 and ctx_500) use **synthetic** GraphWalks-style graphs generated by the extraction script, since the dataset's smallest sample is ~750 tokens. This tests both raw engine throughput AND whether the model can actually use the context at each size.

M4 Max vs M5 Max side-by-side, Gemma 4 MLX vs Qwen 3.5 MLX as bars at each context size.

Four deliverables: a GraphWalks fixture extraction script, a YAML benchmark definition, a benchmark runner script with warm-isolated harness, and justfile recipes.

## Problem Statement

The `gemma4` project has static context scaling charts using **repeated filler text** as context content. This measures raw prefill throughput but doesn't test whether the model actually *uses* the context — the model can ignore 99.9% of the filler since only the suffix task prompt matters. Attention patterns on repeated prose are trivially easy.

The [OpenAI GraphWalks benchmark](https://huggingface.co/datasets/openai/graphwalks) solves this: prompts are directed-graph edge lists with hashed node IDs (e.g. `c9f0f895fb -> a3d2f8e1bc`). Correct answers require tracing multi-hop paths through the **entire** context — no shortcuts, no semantic tricks, no skipping. This lets us measure both speed and accuracy at each context size.

## Solution Approach

### Why GraphWalks instead of filler text

| | Filler text (old approach) | GraphWalks (new approach) |
|---|---|---|
| Content | Same paragraph repeated N times | Directed graph edge lists with hash node IDs |
| Compressible? | Yes — attention patterns trivially repetitive | No — every edge is unique, uniformly distributed |
| Model must read it? | No — can ignore filler, only suffix matters | Yes — answer requires tracing paths anywhere in context |
| Accuracy measurable? | No — summarize_metrics has no ground truth | Yes — exact set of nodes, F1 scored |
| What it measures | Engine speed only | Engine speed + model capability |

### Architecture

Mirror the `qwen35-vs-gemma4` benchmark structure with one addition:

- **Fixture extraction** (one-time): `extract_fixtures.py` generates 2 synthetic GraphWalks-style samples for ctx_200 and ctx_500 (below the dataset's minimum) AND pulls 7 real samples from HuggingFace (one per remaining context size, filtered for non-empty `answer_nodes`). All 9 saved to `fixtures.json`. This avoids pulling the 1.7 GB dataset at runtime.
- **YAML**: 8 charts (prefill/decode/wall/accuracy x M4/M5) with per-chart groups using YAML anchors

- **Justfile**: recipes for both machines + fixture extraction

| `ctx_16k` | 16,384 | HuggingFace | ~57,300 chars, 50K-100K bucket (100 samples) |
| `ctx_32k` | 32,768 | HuggingFace | ~114,700 chars, 100K-200K bucket (100 samples) |
| `ctx_64k` | 65,536 | HuggingFace | ~229,400 chars, 200K-400K bucket (100 samples) |

**Synthetic sample design:** The two smallest sizes use generated graphs matching the GraphWalks format: truncated MD5 hash node IDs, directed edge lists, 4-shot preamble copied from a real GraphWalks sample, `parents` problem type (simpler than BFS — "find all nodes with an edge to X"). The extraction script generates these deterministically with a fixed random seed so `fixtures.json` is reproducible.

**Why cap at 64K, not 131K:**
- Gemma 4 26B-A4B advertised context is 128K — 131K exceeds spec
- KV cache at 131K: ~25-32 GB (Gemma) / ~32-40 GB (Qwen) on top of model weights
- Total memory at 131K: ~41-61 GB — at the edge of 64 GB M4/M5 Max, likely OOM for Qwen
- 64K is safely within both models' range on 64 GB machines
- Each 131K run takes 3-10 min; 64K is ~1-3 min — keeps total benchmark runtime reasonable

### Key design decisions

| Decision | Choice | Why |
|---|---|---|
| Context content | GraphWalks edge lists | Tests real long-context reasoning, not just throughput |
| X-axis groups | 9 context sizes (200-64K) | 2 synthetic baselines + 7 from dataset, capped at 64K for memory safety |
| Metrics (bars) | 2 models: Gemma 4 MLX + Qwen 3.5 MLX | Focused MLX-vs-MLX comparison |
| Charts | 8 (prefill/decode/wall/accuracy x M4/M5) | Speed + correctness, side-by-side hardware |
| Accuracy metric | F1 score (0.0-1.0) | Standard set-comparison metric; penalizes both missing + hallucinated nodes |
| Fixture strategy | 2 synthetic + 7 extracted to JSON | Avoids 1.7 GB dataset download at runtime; synthetics cover sub-750-token range |
| Default iterations | 1 | Long-context runs expensive; N=3 via `--iterations` |
| `max_tokens` | 1024 | GraphWalks answers can be lists of many nodes — need more headroom than filler approach |
| `think` mode | False | Thinking adds unpredictable tokens; isolate raw context scaling |

### F1 scoring

GraphWalks answers are **sets of node IDs**. The model's response is parsed for `Final Answer: [node1, node2, ...]`, then compared to ground truth:

```python
def f1_score(predicted: set[str], truth: set[str]) -> float:
    if not truth and not predicted:
        return 1.0
    if not truth or not predicted:
        return 0.0
    correct = predicted & truth
    precision = len(correct) / len(predicted)
    recall = len(correct) / len(truth)
    return 2 * precision * recall / (precision + recall) if (precision + recall) else 0.0
```

- **F1 = 1.0** — found every node, no hallucinations
- **F1 = 0.0** — complete failure (wrong nodes or unparseable response)
- Emitted as a value 0.0-1.0 to the `accuracy_m4`/`accuracy_m5` charts

**F1 scoring:**
```python
import re

def parse_final_answer(response: str) -> set[str]:
    """Extract node IDs from 'Final Answer: [node1, node2, ...]' in the response."""
    match = re.search(r"Final Answer:\s*\[([^\]]*)\]", response, re.IGNORECASE)
    if not match:
        return set()
    raw = match.group(1)
    nodes = {n.strip().strip("'\"") for n in raw.split(",") if n.strip()}
    return nodes

def f1_score(predicted: set[str], truth: set[str]) -> float:
    """Compute set-level F1 between predicted and ground-truth node sets."""
    if not truth and not predicted:
        return 1.0
    if not truth or not predicted:
        return 0.0
    correct = predicted & truth
    precision = len(correct) / len(predicted)
    recall = len(correct) / len(truth)
    return 2 * precision * recall / (precision + recall) if (precision + recall) else 0.0
```

```python
            iterations=iterations,
            max_tokens=1024,
            num_ctx=num_ctx,
            timeout=1200.0,
        )

        # Score accuracy
        response = m.get("text", "") or ""
        if m.get("raw_runs"):
            response = m["raw_runs"][-1].get("text", "") or response
        predicted = parse_final_answer(response)
        f1 = f1_score(predicted, truth)

        tracker.emit_and_track(cs["key"], cfg["metric"], m,
                               f1=f1, response_text=response, truth=truth, predicted=predicted)
```

**CLI args:**
- `--hw m4|m5` (required) — determines chart_id suffix
- `--iterations N` (default 1) — measured runs per context size
- `--smoke` — 1 context size (ctx_4k), 1 iteration
- `--server URL` (default `http://127.0.0.1:8787`)

**Main flow:**
1. Parse args, load fixtures from `fixtures.json`
2. Create CompletionTracker
3. Run `bench_ollama()` — Qwen MLX at all context sizes
4. Run `bench_gemma4_mlx()` — Gemma MLX at all context sizes
5. Print summary table (prefill/decode/wall/f1 per model per size)

**Important implementation notes:**
- `max_tokens=1024` — GraphWalks answers can be lists of many nodes (the 32K sample has 95 answer nodes). 1024 tokens gives enough room for the Final Answer line.
- `num_ctx` set to `fixture.target_tokens + 1024` — Ollama needs this for large contexts
- `think=False` — isolate raw context reasoning, no thinking overhead
- For smoke mode: use `ctx_200` — the synthetic baseline, runs in seconds, fast sanity check
- Nonce prefixing is tricky with GraphWalks prompts — the nonce goes BEFORE the edge list so the 3-shot examples remain intact. `run_warm_isolated` already handles this via `nonce_prompt()`.
- The warmup call uses a short "Say hi." prompt, not a GraphWalks sample

### GraphWalks Dataset
- **Source**: `huggingface.co/datasets/openai/graphwalks` (MIT license)
- **1,150 rows** across two parquet files: `graphwalks_128k_and_shorter.parquet` (up to ~128K chars) and `graphwalks_256k_to_1mil.parquet` (256K-1M chars)
- **Problem types**: `bfs` (breadth-first search to depth N) and `parents` (find nodes with edges to target)
- **Format**: 3-shot prompted, edge list context, `Final Answer: [node1, node2, ...]` response format
- **Node IDs**: truncated MD5 hashes — no semantic shortcuts, no memorization
- Each size bucket has 100+ samples; we extract 1 per target context size
- We only pull the parquet files during extraction (one-time `extract_fixtures.py` run), not at benchmark runtime

### Fixture File Strategy
The 9 samples (2 synthetic + 7 from HuggingFace) are saved to `fixtures.json` and committed to the repo. This avoids:
- 1.7 GB dataset download at runtime
- HuggingFace availability dependency during benchmarks
- Non-deterministic sample selection between runs

The file is ~250 KB (the 64K sample is ~230K chars, smaller samples are tiny). To regenerate: `just bench-ctx-extract`.

### Synthetic Samples (ctx_200, ctx_500)
The GraphWalks dataset's smallest sample is ~750 tokens (2,638 chars). To test whether local models can handle the GraphWalks task format at all, we generate two smaller samples:

- **ctx_200** (~200 tokens): ~5 nodes, ~8 edges, `parents` problem. This is trivially small — if the model can't get this right, GraphWalks is too hard for it entirely.
- **ctx_500** (~500 tokens): ~12 nodes, ~20 edges, `parents` problem. A slightly larger graph but still well within short-context territory.

Both use the same format as real GraphWalks: truncated MD5 hash node IDs, directed edge list, 4-shot preamble, `Final Answer: [...]` format. The 4-shot preamble is copied from a real sample to ensure format consistency. Generation uses `random.Random(42)` for deterministic, reproducible output.

### Nonce Prefixing with GraphWalks
The `run_warm_isolated` harness prepends a `[run:<nonce>] ` prefix to defeat prompt caching. For GraphWalks prompts this means the nonce goes before the 3-shot examples. This is fine — the nonce defeats the cache without breaking the prompt format, since the model sees a unique prefix on every measured run.

### Memory Budget at 64K
At 64K tokens, both models are safely within 64 GB unified memory:
- Gemma 4 MLX: ~15.6 GB weights + ~12 GB KV cache ≈ 28 GB
- Qwen 3.5 MLX: ~21 GB weights + ~16 GB KV cache ≈ 37 GB
- Both fit comfortably; runs are sequential, not simultaneous

### Warm-Isolated Methodology
Same 5 rules from `_harness.py`:
1. MLXRunner for Gemma: long-lived subprocess
2. Ollama for Qwen: `keep_alive=-1`
3. Discarded warmup call before measured runs
4. Nonce-prefixed prompts defeat cache hits
5. N=1 default (long-context runs expensive)
