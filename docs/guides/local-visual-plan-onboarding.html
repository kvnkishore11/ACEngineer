01 — The idea
Own the file, not the server

A plan you can open, work in, and keep.

/local-visual-plan produces one HTML file that is both the deliverable and the source of truth — no companion files, no render step, nothing running but your browser.

manual triggeroffline-friendlygit-trackable

A hosted plan lives behind a service you don't own. The rendering, the clickable prototype, the comment anchors — all execute remotely.

That means you can't open a plan offline, in a privacy-sensitive context, or without the hosted engine being up. The local skill flips that: it bakes the look, the interactivity, and the feedback loop into one owned HTML file. You open it with a file:// path; you move it, archive it, commit it beside the code it describes.

The single accepted dependency is the Google Fonts CDN — and even that falls back to system fonts offline. Content is never network-blocked; only typography may change.

Same review surface, no remote engine. The file carries everything.
≡

When to reach for it

◵ use local-visual-plan
  • You want the plan owned and local — offline, privacy-sensitive, or repo-tracked.
  • The work is better seen than read: a UI surface, a small workflow, a before/after, an architecture decision.
  • You want to review, comment, and approve a direction before any code is written.
◴ skip it
  • Truly trivial, unambiguous work — a typo, a one-line fix, a single well-specified function.
  • Anything whose diff you could describe in one sentence — just make the change.
  • You specifically want the hosted collaboration / commenting surface (that's visual-plan).
Newcomer note The skill gates thoughtfully. It won't pad a plan with filler or ship a single-step plan — and planning is read-only until you approve, so it never touches project code while drafting.

02 — The workflow
One command, one file

Invoke it, and read a real plan.

You give it a task; it researches read-only, drafts the sections, fills an owned template, writes the file, and hands you back a clickable path.

In this chapter 1The command 2What the agent does 3Where it lands
1

The command

terminal
# manual trigger — type the slash command with your task
/local-visual-plan add a settings page for notification preferences

# the agent works, then prints a clickable path:
Wrote plans/settings-notifications.html
file:///Users/you/project/plans/settings-notifications.html

Pass the task in plain words after the command.

It is manual-trigger only for now, so it never collides with the auto-firing hosted planner. Give it the same kind of task you'd hand any planner: a feature, a refactor, a UI change, an architecture decision.

When it finishes, it surfaces a file:// path — click it (or paste it into a browser) to open the plan.

2

What the agent does

Every step is local. No MCP call, no hosted request, no localhost.

The local workflow replaces every remote call from the hosted planner with a local step:

  1. Research, read-only

    Inspects the codebase, names real files and data shapes. Writes nothing but the plan.

  2. Read the quality bar

    Grounds in the skill's reference docs, not memory.

  3. Draft & fill

    Composes the sections, including a hand-authored inline SVG diagram, into the owned template.

  4. Surface the path

    Prints the file:// link and asks you to review — that is the approval gate.

3

Where it lands

your-project/ plans/ # created if it doesn't exist settings-notifications.html # one self-contained file — the source of truth src/ # untouched while planning
Slug & path The file always lands at plans/<slug>.html in the current project. The slug is a short kebab-case name derived from the task. One .html per plan — re-running the same slug edits it in place rather than spawning a -v2.

03 — Anatomy
One file, three ways to look

Plan body, wireframe, prototype.

Every plan has a document body. Screen-facing plans add two optional modes — a static wireframe and a click-through prototype — all in the same HTML.

In this chapter 1Plan body 2Wireframe 3Prototype
1

The plan body

A serious technical plan — outcome-first, prose-first, specific.

It reads like a strong implementation plan: objective and what "done" means, scope & non-goals, the approach with key decisions, ordered steps that name real files and lead with reuse, risks, a verification step that exercises the real workflow, and a single open-questions section.

At least one diagram is a hand-authored inline SVG — the only zero-dependency option, no external image or remote renderer.

The document, sectioned. Each id is a feedback anchor and a state key.
2

The wireframe

A flat mock, annotated. Real layout, real product content — no lorem.

A static, annotated mock of one screen or state.

It's plain HTML composed with the template's own helper classes and palette — never hand-coded colors or fonts. Each region worth explaining gets a numbered callout below the frame, so the explanation of the plan lives in the callouts, not baked into the product screen.

No clicks here A wireframe is not interactive — clicking does nothing. Walking a flow is the prototype's job.
3

The prototype

Several screens in one HTML, navigated by show/hide.

A click-through flow — e.g. Welcome → Connect → Done. Each screen is a div; a hotspot click swaps which is visible. A Back button restores the prior screen and a counter shows Screen N / M.

It's deliberately limited and honest about it: no faked backend, no simulated data. Show/hide only — so the artifact never overpromises what a local file can do.

showScreen() / goBack(). Honest, zero-server navigation.
Optional Both screen modes are optional. A non-UI plan ships the plan body alone; the wireframe and prototype sections are deleted rather than left as empty mocks.

04 — In the browser
Check, note, persist

The plan is workable, not just readable.

Open the file and work in it: check off steps, type notes against any section. Everything persists in the browser — no server, no account.

Every step and risk gets a checkbox; every section gets a note.

State is saved to localStorage, namespaced per plan so two plans never clobber each other. It survives a refresh — and it survives the agent's later edits to the HTML, because state is keyed on each section's stable id, not on its content.

A fixed toolbar in the corner carries two buttons: Copy feedback and Reset state.

Per-plan, per-section keys. Isolation and survival, by construction.
the keying rule (window.LVP)
stateKey(slug, sectionId) // → "lvp:<slug>:<sectionId>"
stateKey("workspace-onboarding", "step-2")  // → "lvp:workspace-onboarding:step-2"
BUTTON 01

Copy feedback

Serializes every touched section into anchored markdown and writes it to your clipboard — the exact text the agent parses back.

BUTTON 02

Reset state

Clears this plan's notes and checkboxes only, after a confirm. Other plans' state is untouched.

Survives Refresh the page, or let the agent edit the file — your checkboxes and notes re-bind by id on reload. The agent never hand-edits your localStorage; it just edits the document, and your state finds its home again.

05 — Converge
From browser back to agent

One paste, and the plan edits itself.

Click Copy feedback, paste the block into chat, and the agent applies each comment to the exact spot — no hand-editing the file.

what Copy feedback puts on your clipboard
## Feedback · plans/<slug>.html

[§step-3 "Add refresh token"]
  ☐ unchecked
  ✎ needs key rotation too

[§risk-2 "Token leak"]
  ☑ checked
  ✎ out of scope — drop this

Sections with neither a note nor a changed checkbox are omitted.

Each block is anchored to a section id.

The [§id "title"] line is the anchor — the agent finds the element with that id and edits it in place. The ☑/☐ shows the checkbox state; the ✎ line is your note.

The id is the contract, not the title. The title is just a human label and may go stale; the agent trusts the id.

The loop closes. Review → copy → paste → edit → reload, and your state survives.

  1. Split the paste into blocks

    Each block starts with [§<id> "<title>"].

  2. Find each id, edit in place

    The agent applies your note's intent and reacts to the checkbox state, preferring targeted edits over a rewrite.

  3. Preserve ids & titles

    So your persisted state survives — state is keyed on the id, not the content.

  4. Re-surface the path

    You reload and keep reviewing. Ordinary chat feedback works the same way.

The linchpin Section ids are the anchor for both feedback and persisted state. The agent assigns them once and never regenerates them on an edit — doing so would orphan your notes and checkboxes.

06 — Hands-on
Your first round-trip in five minutes

Walk a new user through it once.

The fastest way to learn the skill is to run one plan end to end. Here's the quickstart to hand someone on day one.

  1. Invoke it

    Type /local-visual-plan <your task> and let it draft.

  2. Open the file

    Click the printed file:// path — it opens in any browser, no server.

  3. Read & review

    Walk the sections; if it's screen-facing, click through the prototype with the pager.

  4. Check & note

    Tick the steps you accept; type notes where you want changes.

  5. Copy feedback

    Hit the toolbar button — the anchored markdown is on your clipboard.

  6. Paste it back

    Drop it into chat. The agent edits the file by id and re-surfaces the path.

  7. Approve

    When it reads right, approve — and only then does code work begin.

Climb once. After one round-trip the loop is muscle memory.
Try the sample A worked example ships in this repo: plans/workspace-onboarding.html exercises all three modes together. Open it, check a step, add a note, hit Copy feedback, and watch the anchored markdown appear — that's the whole loop in one file.
