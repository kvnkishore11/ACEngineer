## YT-10: Agentic Prompt Engineering with Claude Code (For you, your team, and your AGENTS)
**Thesis:** "The prompt is now the fundamental unit of engineering," and to get 2-100x returns you must engineer every reusable prompt for the stakeholder trifecta — you, your team, and your agents — using seven levelled prompt formats built from consistent, swappable Lego-block sections.
**Nuggets:**
- "One well-crafted prompt can generate tens and hundreds of hours of productive work. One bad prompt compounds failure at the same rate."
- The stakeholder trifecta: prompts now have three audiences — you, your team, and your agents. "There's a new user... it's your agent."
- The Workflow section is S-tier usefulness, C-tier difficulty — "the most important section you'll write is the workflow," the step-by-step play your agent maps directly into its todo list.
- Every prompt reduces to a three-step pattern: **input, workflow, output** (Variables in, Workflow does the work, Report defines what comes back).
- Variables are "super underappreciated" (A-tier): dynamic variables (`$1`, `$ARGUMENTS`) take input; static variables (e.g. an output directory) are defined once and referenced everywhere — change one line, the whole prompt updates.
- Metadata (allowed-tools, model, argument-hint) and Codebase Structure are only C-tier — Codebase Structure is really "a context map" that speeds the agent up instead of burning tokens on search.
- Instructions vs Workflow: instructions are auxiliary guardrails around the steps — "instructions are going to be a lot more valuable for your system prompt versus your workflow" in reusable user prompts.
- Control flow (level 3) is plain natural language: conditionals, loops, and early returns — "If no path to plan is provided, immediately stop and ask the user to provide it."
- Delegate prompts (level 4) are S-tier usefulness, A-tier skill: "we're writing prompts that write prompts" — your primary agent becomes the prompt engineer for its subagents, and nondeterminism becomes a feature when you fan out N agents on one task.
- "Consistency is the greatest weapon against confusion for both you and your agent." / "Consistency beats complexity."
- "Great prompting is great communicating" — the coworker test: if you handed the prompt to a colleague, could they complete the work top to bottom?
- Only add the sections you need — they're composable pieces; no output requirements means no Report section.
- Use information-dense keywords (IMPORTANT, exclusively) when the agent must not deviate.
- Push to at least B-tier skill to "capture most of the value"; 90% of the time levels 3-4 are all you need — then template metaprompts (level 6, "the prompt that builds the prompt, the agent that builds the agent") scale velocity hardest.
- Goal: CRUD your reusable prompts "at light speed at the right level" — delegation is the "D" in the R&D (Reduce & Delegate) context-engineering framework.

**Tools/tech:** Claude Code slash commands (`.claude/commands/*.md`), YAML frontmatter metadata (allowed-tools, model, argument-hint, description), `$ARGUMENTS`/positional args, `{{variable}}` referencing, subagents and parallel subagents, background Claude Code instances via CLI with custom system prompts, Replicate MCP server (image generation demo), tier-list grading of sections, references to TAC course and Claude Code SDK.
**Repo:** `agentic-prompt-engineering` (agentic-horizon) — a reference codebase documenting the 7 levels of agentic prompt formats (High Level → Workflow → Control Flow → Delegate → Higher Order → Template Metaprompt → Self-Improving), each backed by working example commands in `.claude/commands/` (prime, build, quick-plan, create_image, parallel_subagents, load_ai_docs, background, metaprompts, experts), plus a section-by-section dictionary of all 12 prompt sections, a system-vs-user-prompt guide, and Claude Code bash aliases.
**Drill:**
1. In a test repo, create `.claude/commands/prime.md` as a level-2 workflow prompt: Metadata frontmatter, Title, Purpose, a numbered Workflow, and a Report section.
2. Create `build.md` with a dynamic variable (`$1` = path-to-plan) referenced throughout, plus a control-flow guard: if no path is provided, stop and ask.
3. Create a `quick-plan.md`-style prompt with one static variable (e.g. plan output directory) referenced in multiple workflow steps; change the directory once and confirm the whole prompt follows.
4. Create `parallel_subagents.md` (level 4) taking a prompt-request and a count, whose workflow has the primary agent design self-contained input/workflow/output prompts for each subagent.
5. Run all four as slash commands and verify each behaves per its Report section.
Done when: `/build` with no argument early-returns asking for the plan path, and `/parallel_subagents <task> 5` fires 5 subagents whose results come back in your specified report format.

## YT-11: Agentic Coding ENDGAME: Build your Claude Code SDK Custom Agents
**Thesis:** The single path of agentic engineering is better agents → more agents → custom agents — and because out-of-the-box tools are "built for everyone's codebase, not yours," the endgame is building your own specialized agents on the Claude Code SDK, starting with the system prompt.
**Nuggets:**
- "The system prompt is the most important element of your custom agents with zero exceptions." It multiplies everything: "The system prompt affects every single user prompt the agent runs... all of your work is multiplied by your system prompt."
- Overwrite the system prompt and "the Claude Code agent that you know and love is now gone... We now have a new product. This is not Claude Code anymore" — the system prompt is truly what builds the agent.
- Two modes: overwrite the system prompt to build a true custom agent, or append to it to merely extend Claude Code — both are valid, know which you're doing.
- The SDK loop is three steps: "You set up your options, you set up your agent... you run the query, and then you handle the response." All the pieces are incrementally adoptable.
- `query` is for one-off prompts; `ClaudeSDKClient` is for continuous conversations with memory.
- Custom tools ship as an in-memory MCP server (`create_sdk_mcp_server`) — decorator + name + description; "the description of your tool tells your agent how to use it."
- Watch the default toolset leak: ask a custom agent to "list your available tools" and you'll find ~15 Claude Code tools you didn't ask for. "Everything that's going into your agent winds up in the context window... it consumes space in your agent's mind." Control it with `allowed_tools`.
- Downgrade the model when the job is simple — the echo agent runs Haiku: "This is a simple agent. It doesn't need powerful intelligence."
- "Keep track of the core four. If you understand the core 4 [context, model, prompt, tools] and how each element flows and controls your agent, you will understand compute."
- Micro SDLC agent: planner → builder → reviewer agents on a kanban board, streaming via WebSockets, operating on their own codebase — "This work shipped with a single prompt outside the loop," a working out-loop review system (in-loop → out-loop → ZTE).
- "If you're doing one-size-fits-all work, use the out-of-the-box agent. Don't think super hard about this." Custom agents are for the specialized, high-ROI, domain-specific work — "this is where all the alpha is in engineering."
- "Agentic coding is not so much about what we can do anymore. It's about what we can teach our agents to do."
**Tools/tech:** Claude Code SDK / Claude Agent SDK (Python), system prompt override vs append, `query` vs `ClaudeSDKClient`, `create_sdk_mcp_server` in-memory MCP tools, `allowed_tools`/`disallowed_tools`, model selection (Sonnet vs Haiku), message/result blocks and session stats, `/context` command, uv single-file scripts, FastAPI + Vue.js agent UIs, WebSockets, hooks/permission interception, Rich terminal panels, TAC course.
**Repo:** `building-specialized-agents` (agentic-horizon) — a ladder of 8 custom agents on the Claude Agent SDK, each adding one concept: pong (system prompt override), echo (custom tool + allowed_tools), calculator (REPL + resume + multi-tool), social hype (Bluesky firehose monitor), QA agent (parallel-search read-only REPL), tri-copy-writer (Vue/FastAPI web app with structured JSON), micro SDLC (planner/builder/reviewer kanban orchestration), ultra stream (dual-agent infinite log processing).
**Drill:**
1. Write a single-file uv script using the Claude Agent SDK that fully overwrites the system prompt with three lines ("You are a pong agent. Always respond exactly with pong."), runs `query`, and parses the agent/result message blocks.
2. Build an echo agent: one custom tool (message, repeat, transform) registered via `create_sdk_mcp_server`, model dropped to Haiku.
3. Prompt it to "list your available tools" — count the baked-in Claude Code tools, then strip them with `allowed_tools` and verify context shrinks.
4. Convert from `query` to `ClaudeSDKClient` and run a follow-up prompt that summarizes the conversation, proving session memory.
5. Run the micro SDLC kanban app (`apps/custom_7_micro_sdlc_agent`), drag a trivial ticket to Plan, and watch planner → builder → reviewer ship it hands-off.
Done when: your pong agent answers "pong" to everything, your echo agent runs on Haiku with only your custom tool exposed, and one kanban ticket ships end-to-end without you touching the loop.

## YT-13: Claude Code 2.0 Agentic Coding: No, other agents aren't even close.
**Thesis:** Claude 4.5 Sonnet inside Claude Code's purpose-built harness — especially CC 2.0's new composable slash commands — enables chained, context-frugal agentic workflows (scout → plan → build) and out-of-loop agent devices that "CodeX CLI, Gemini CLI" simply cannot replicate.
**Nuggets:**
- "CodeX CLI, Gemini CLI, they're nowhere near as close as you think they are... You can't be close to the leader when you just copy their feature set over and over."
- CC 2.0 killer feature: custom slash commands can call custom slash commands — "You can compose your agentic prompts. Okay, this is huge." One `/scout_plan_build` chains `/scout` → `/plan_w_docs` → `/build`.
- The scout step exists to protect the planner: "There are only two ways to manage your context window, R&D, reduce and delegate." Four parallel cheap/fast sub-agents (Gemini Flash, opencode, Codex, even Haiku) search the codebase and emit a `relevant_files.md` — with byte offsets and read lengths, not just filenames — deliberately mixing model families for multiple perspectives.
- "Looking through files isn't exactly planning" — keep the planner's window free to actually plan.
- Manage the "core four" for every agent you spin up: context, model, prompt, and tools.
- "Prompt engineering is critically important. It's just as important as context engineering." And: "I can guarantee you you're not pushing your prompts far enough."
- Adopt your agent's perspective when writing high-level prompts — walk through what it will see and you'll catch what it will miss (e.g., the system-prompt-no-longer-default gotcha in the Agent SDK migration).
- Auto-compact hot take: Claude Code's auto-compact buffer ate 22% of the context window ("absolutely cooked") — turn it off via `/config` to get back to ~91% free. "You want a focused, clear agent with as many tokens as you can spend."
- Even with delegation, the chained workflow burned ~51% of context — the hard limit of single in-loop agents; the escape hatch is out-loop ADWs (AI Developer Workflows) with isolated context windows.
- Dedicated agent device: an `/AFK agents` handoff prompt sent a plan → build → ship job to an M4 Mac mini that built three OpenAI Agents SDK prototypes and git-pushed them end-to-end, with 60-second status polling. "You don't need to sit in the loop for every single task."
- Rapid-prototyping ladder: have the agent build something simple, validate it, then step up in complexity — same as you'd manage a junior engineer.
- Hot take on CC 2.0's UI: hard-truncating agent output makes Claude Code "the tool for everyone, not just the tool for engineers" — Dan counters with a custom Observable output style (tools + diffs + TTS).
- Higher-order prompts: `/build` "passes a prompt into a prompt."
- "There is a direct causal link between your ability to control, build, and use agents, and your engineering output." The endgame: "build the system that builds the system" — "What if your code base could ship itself?"
**Tools/tech:** Claude Code 2.0 (composable slash commands, `/context`, `/config` auto-compact toggle, output styles, ctrl+R backtick prompt history search, thinking mode, yolo mode), Claude 4.5 Sonnet, Claude Agent SDK (migration from Claude Code SDK), OpenAI Agents SDK (web search tool, function tools, Realtime voice API), sub-agent fleet via Gemini CLI/Flash, Codex CLI, opencode, Haiku, Firecrawl MCP, uv, ElevenLabs TTS, M4 Mac mini agent device, Cursor; Tactical Agentic Coding / Agentic Horizon course (private "Building Specialized Agents" codebase).
**Repo:** `codebase/` → gist disler/c7719b79a107 — a single file, `claude-code-output-style-tools-diffs-tts.md`: the "Observable — Tools + Diffs + TTS" Claude Code output style demoed in the video. It appends three report formats to every response: a git-diff report of changed files, a chronological tool-call listing in TypeScript-interface syntax, and an ElevenLabs TTS audio summary spoken directly to the user. The main scout/plan/build codebase is private (course material); this gist is the only public artifact.
**Drill:** Replicate the composed scout-plan-build workflow from scratch:
1. Write a `/scout` slash command that fans out 3-4 parallel sub-agents (mix models) to find files relevant to a task and write `relevant_files.md` with offsets.
2. Write `/plan_w_docs` that reads `relevant_files.md`, scrapes given doc URLs into local `ai_docs/`, and writes a plan file.
3. Write `/build` as a higher-order prompt that executes the plan.
4. Compose them into one `/scout_plan_build <prompt> <doc-urls>` command and run it on a small real migration.
5. Turn off auto-compact and use `/context` before/after to verify how much window the delegation saved.
6. Optionally drop the gist's output style into `~/.claude/output-styles/` and wire your own TTS script.
Done when: a single `/scout_plan_build` invocation completes the task end-to-end and `/context` shows your primary agent kept a majority of its window free.

## YT-15: Claude HAIKU 4.5 is LIGHT SPEED Agentic Coding… BUT can it BEAT Sonnet?
**Thesis:** Haiku 4.5 is "cheap fast compute for agents" — roughly twice as fast and a third the price of Sonnet 4.5 — so the real engineering skill is knowing which work you can offload down your model stack and which work still demands Sonnet.
**Nuggets:**
- "For every Sonnet prompt you write, you could have written three Haiku prompts" — and caching drops the effective price even further; "this model is cheaper than you think it is."
- Side-by-side swim lanes showed Haiku averaging nearly a second faster between tool calls and finishing a find-and-summarize task in about half Sonnet's time — but it missed 1 of 32 files (a 3% failure rate that's "completely unacceptable" in some domains, "more than enough" in others).
- Haiku loses instruction detail under complexity: it ignored the two-sentence summary requirement (2 hits on "used" vs Sonnet's 12) and violated an explicit "do not use sub-agents" instruction.
- "Haiku is a fast hard worker, but it won't work for very long" — its plan was a third to a quarter the length of Sonnet's; "Haiku is not a good planner."
- Haiku is a "scouter model": great for search, summarization, structured-data extraction, docs gathering, pattern matching, and simple code generation.
- The build test proved the point: Haiku shipped a working regex search bar and 10-minute pulse timer, but the three new UI themes were created and never wired up. "Would Sonnet have missed this? Absolutely not."
- Capability passes down the stack with each release: "there are problems that Haiku can now solve that only Sonnet or Opus could solve" — same pattern as Sonnet 4.5 replacing Opus.
- Build a model portfolio — "an agent model stack, weak, base, strong" — vendor-agnostic; what matters is "the optionality to use the right one at the right time."
- Performance, speed, and cost are "the three dials you and I have as engineers to tweak and tune."
- "To scale your impact, scale your compute" — tool calls are a rough corollary for results, assuming the work is worth doing.
- Recommended split: Haiku for summarization, docs, simple codegen, pattern matching; Sonnet for planning, architecture, complex debugging, long-running pipelines — e.g. Sonnet plans, Haiku sub-agents execute the refactor, Sonnet double-checks with cheap read tokens.
- Habit shift: "I stop and I first ask myself, do I even need Sonnet for this, or can I drop down to Haiku?"
- Verdict: Haiku 4.5 lands "a notch below Sonnet 4" — maybe 3.5/3.7-Sonnet level — not a Sonnet replacement.
- Dogfooding proof: the observability dashboard itself uses Haiku 4.5 to summarize hundreds of incoming hook-event payloads in real time — "a perfect use case for a cheap, fast model."
- "Observability and orchestration is the next frontier for agents right now" — without it you're vibe coding at scale.
**Tools/tech:** Claude Haiku 4.5, Claude Sonnet 4.5 (Opus 4.1 referenced), Claude Code (hooks, thinking toggle, ultrathink keyword, sub-agents, plugins, skills, slash commands), multi-agent observability dashboard with swim lanes, higher-order prompts (/build with a plan), agentic prompt structure (purpose/variables/instructions/workflow/report), model distillation, Tactical Agentic Coding / Agentic Horizon courses.

## YT-16: I finally CRACKED Claude Agent Skills (Breakdown For Engineers)
**Thesis:** Skills are not a replacement for MCP, sub-agents, or slash commands — they're a higher-level compositional unit for packaging repeat, agent-invoked solutions, and the prompt (custom slash command) remains the primitive underneath everything.
**Nuggets:**
- Skills' distinguishing pattern: agent-triggered + context-efficient + a "dedicated modular directory structure" — it's "the approach that's new," not the capability.
- Progressive disclosure is the killer feature: three levels (metadata, SKILL.md instructions, on-demand resources). "Unlike MCP servers, which just straight-up tortures context window."
- Feature-to-use-case map: skills = automatic behavior, MCP = external integrations (Jira, DBs, weather APIs), sub-agents = isolated/parallelizable workflows, slash commands = manual triggers.
- "Whenever you see parallel, you should always just think, just jump to sub-agents" — nothing else supports parallel calling; you must be OK losing that context afterward.
- Engineers converting all their slash commands to skills are making "a huge mistake." The wrong way: using a skill for a one-off job a prompt or sub-agent can do.
- The rule for when to graduate: one prompt creates a worktree; managing worktrees (create, list, remove, merge) is a problem set — "this is where one prompt is not enough" — that's a skill.
- "Do not give away the prompt. The prompt is the fundamental unit of knowledge work and of programming. If you don't know how to build and manage prompts, you will lose."
- Everything reduces to the core four: context, model, prompt, tools. "Every agent is the core four" and every feature is built on top of them.
- Composition hierarchy: skills sit at the top — skills can use prompts, other skills, MCP servers, and sub-agents; MCP is a lower-level unit; slash commands are a "super primitive" (both primitive and composer); sub-agents can't nest sub-agents.
- Dan's demo skills compose downward: the worktree-manager skill's instructions literally say "use the {slash} command tool" — skill calls prompt.
- Starting out? "Just build a prompt. Don't build a skill. Don't build a sub agent. Don't build out an MCP server. Keep it simple."
- Biggest complaint: skills "don't go all the way" — no dedicated commands/ or agents/ directories inside the skill bundle for nesting prompts and sub-agents.
- Reliability concern: can you chain five skills and trust the agent to call them back-to-back? A sequence of explicit slash commands is guaranteed to run in order; skills aren't (yet).
- Hot take on innovation: "skills are effectively opinionated prompt engineering plus modularity... What's actually new here? I think the answer is not that much" — yet still a solid 8/10.

## YT-17: The One Agent to RULE them ALL - Advanced Agentic Coding
**Thesis:** The next level of agentic engineering after custom agents is multi-agent orchestration — a single orchestrator agent that gives you CRUD over a fleet of focused, disposable agents, combined with real-time observability, so you scale compute instead of your own presence.
**Nuggets:**
- "The rate at which you can create and command your agents becomes the constraint of your engineering output. When your agents are slow, you're slow."
- The engineer progression: base agents → better agents → more agents → custom agents → **orchestrator agent**. "At each step, you scale your compute to scale your impact."
- The orchestrator is "the single interface pattern applied to your fleet of agents" — a decades-old engineering paradigm now applied to agents.
- Three pillars must combine: (1) orchestrator agent as unified interface, (2) CRUD for agents (create/command/check/delete), (3) observability for real-time performance, cost, and results monitoring.
- "If you can't measure it, you can't improve it... If you have 10 agents doing the wrong thing, does it matter that you have 10? Of course not." Observability is why the orchestrator comes last, after custom agents.
- These are NOT sub-agents: they're persistent primary agents you can "tap into over and over until that specific job is done" — context isn't blown away like one-off sub-agents.
- Protect the orchestrator's context window: it creates and commands agents but "is not always observing the logs. It cannot be." It orchestrates; it never does the work itself.
- The core four — "context, model, prompt, tools" — underlies every agent UI any lab ships: "Don't let anyone confuse you." Monitor the core four of every agent you boot up.
- "200k context window is plenty. You're just stuffing a single agent with too much work, just like your boss did to you at your last job." Force focus, then "let the agents go home" — delete them.
- The code journey ends in deletion: "the best code is no code at all"; likewise "you must treat your agents as deletable, temporary resources that serve a single purpose."
- The orchestrator does "serious prompt engineering" — it takes your high-level prompt and writes far more detailed concrete instructions to each agent; scout → builder → reviewer chains pass plans, logs, and results between agents.
- Sleep-loop pattern: the orchestrator sleeps, fires agents, then polls `check_agent_status` every ~15 seconds — scaling compute to monitor the multi-agent workflow.
- "Compute can solve so many of your engineering problems if you put the compute to work" — deploy more compute for more confidence and trust.
- Specialized beats generic: "these [cloud] tools are designed for everyone's codebase, not yours. When you build something like this, you get specialization all the way down."
- Every agent "must produce a concrete result. Otherwise, what's the point?" — the UI shows consumed vs. produced assets per agent, one click from your editor. PR-based systems "miss a lot of the story."
- Trade-off acknowledged: the O-agent costs upfront investment (plumbing, database, websockets), but you want an out-of-loop system plus the ability to "hop in the loop" when needed — a spectrum of engineering modes.

## YT-18: Why are top engineers DITCHING MCP Servers? (3 PROVEN Solutions)
**Thesis:** MCP servers torch your agent's context window before it does any work, and three raw-code alternatives — CLI + prime prompt, file system scripts, and skills — give you the same tool access with progressive disclosure, full control, and a fraction of the token cost.
**Nuggets:**
- "My MCP server just ate 10,000 tokens before my agent even started working" — one modest MCP server burns ~5% of context; "stack up two or three more MCP servers, and I'll be bleeding 20% plus context in no time."
- The unifying theme of all three alternatives: "use raw code as tools." Everything reduces to the core four — "context, model, prompt, and tools."
- CLI approach: a ~25-line prime prompt (`/prime_kalshi_cli_tools`) tells the agent to read ONLY a README + the CLI file. "We're in full control over everything… do not read any other Python files." Cut context from ~10% to ~5.6%.
- Scripts approach: a README maps "a condition mapped to files — this is a powerful agentic data structure you can use to activate or ignore context." Context drops under 1% (~2K tokens) — "10% of the original."
- Key prompt-engineered trick: "I will not read scripts themselves unless --help doesn't provide information needed." You get Anthropic's progressive disclosure by hand — "and it's not a complex prompt."
- "Even before context comes prompt engineering… it is THE critical skill for engineers in 2025 and beyond. The prompt shows up before the context gets in your context window."
- Skills vs scripts: same scripts, different invocation — "with a skill, the prime prompt is the skill.md file." Model-invoked, self-contained directory, but "skills is a Claude-specific lock-in mechanism."
- Anthropic's "code execution with MCP" blog wraps scripts around MCP calls; Dan and Mario argue "you can just cut the MCP server out completely if you're going to script it out yourself." Benchmarks show "no degradation in quality by going right for scripts."
- Single-file UV scripts (deps declared at top) buy isolation and portability; the code duplication tradeoff is worth it because "when you have less garbage context, your agent can perform better."
- MCP still wins on features engineers gloss over: "tools, resources, prompts, elicitation, completion, sampling" — and on zero-effort setup for external servers.
- External tools rule of thumb: 80% just use MCP ("don't waste your time trying to reinvent the wheel"), 15% CLI when you need to modify/control tools and context, 5% scripts/skills for serious context preservation.
- New tools rule of thumb: 80% build CLI-first — "CLI works for you, your team, and your agents. The trifecta." 10% wrap that CLI in an MCP server for agents at scale (each MCP tool just calls into the CLI), 10% scripts/skills.
- "You can sidestep every single context engineering problem by just focusing your agents on one problem and then you delete them when they're done."
- Bonus mental model: prediction markets as "info finance" (Vitalik) — agents reading Kalshi order books "help us understand the future before it occurs."
**Tools/tech:** Claude Code (Haiku 4.5 as the driver model), MCP servers / FastMCP, `/context` and `/mcp` slash commands, prime prompts (slash commands), Claude Agent Skills (SKILL.md), Astral UV single-file Python scripts, click/typer CLIs, Kalshi prediction markets API (read-only, no auth), pandas search cache, Anthropic "code execution with MCP" blog, Mario Zechner's "you don't need MCP" post, Vitalik's info-finance essay.
**Repo:** `disler/beyond-mcp` — four parallel implementations of the same Kalshi prediction-market toolset (`apps/1_mcp_server` with 15 FastMCP tools wrapping the CLI, `apps/2_cli` with 13 typer commands hitting the API directly, `apps/3_file_system_scripts` with 10 self-contained UV scripts + prime prompt, `apps/4_skill` bundling those scripts under a SKILL.md), plus a full trade-off matrix (context, portability, composability, lock-in) and Dan's 80/15/5 and 80/10/10 decision heuristics.
**Drill:**

2. Restart with no MCP server, run `/prime_kalshi_cli_tools`, prompt "kalshi: search markets <topic>", and record `/context` again.
