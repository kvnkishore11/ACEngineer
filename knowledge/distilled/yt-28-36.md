## YT-28: The Claude Code Feature Senior Engineers KEEP MISSING
(27:29 · 2026-01-19 · https://www.youtube.com/watch?v=u5GkG71PkR0)

**Thesis:** Claude Code now lets you run hooks *inside* skills, subagents, and slash commands — which means you can build specialized, self-validating agents whose validation is deterministic and guaranteed to run, and that's how you buy trust (and therefore time) from your agents.

**Nuggets:**
- "If you want your agents to accomplish loads of valuable work on your behalf, they must be able to validate their work." Validation → trust → saved engineering time.
- The big release everyone missed: hooks in the front matter of prompts, subagents, and skills (PreToolUse, PostToolUse, Stop supported).
- Key pattern: a `PostToolUse` hook on Read/Edit/Write that runs a validator script (e.g. a pandas CSV validator); on failure it returns "Resolve this CSV error in <path>" plus the error list, and the agent self-heals immediately.
- "A focused agent with one purpose outperforms an unfocused agent with many purposes." A 20-line CSV-edit prompt is not overkill — it's the point. Focused agents win over tens, hundreds, millions of runs.
- The self-validation must be *hyper-focused on the purpose of that prompt* — specialized validation, not generic linting.
- Organize validators under `.claude/hooks/validators/`; every validator writes its own log file — observability, "you want proof that these things ran."
- Hook-vs-prompt tradeoff: you *can* prompt "validate your work with X," but putting it in a hook is a guarantee — it always runs. This is the closed-loop prompt without prompt engineering.
- Rule of thumb: use `PostToolUse` to validate the single file just touched (you get the path); use `Stop` to run global validators over everything at the end.
- "Merge slash commands and skills — they're the same thing. It's a prompt." Every abstraction boils down to the Core Four: context, model, prompt, tools.
- Prompts give you the base; subagents add parallelization + context isolation; skills same idea — the hook pattern extends to all three.
- Do the agentic layer by hand: "when you're working on your agents… slow down and do it by hand." Reusable prompt formats mean you and your agents never think about structure again.
- Rant: read the documentation yourself. "Don't delegate learning to your agents… that is how you begin the self-deprecation process."
- Bonus: `claude -p --settings <json>` lets you pass an entire settings file (including hooks) into a headless primary agent.
- "Agents plus code beats agents. That's what self-validation is. That's the closed-loop prompt." (Why Ralph Wiggum-style techniques work.)

**Tools/tech:** Claude Code hooks in prompt/subagent/skill front matter; PostToolUse/Stop hooks; uv-run Python validators (pandas); Opus 4.5; agentic prompt template (AGP snippet); generative UI report; `claude -p --settings`.

**Repo:** `disler/agentic-finance-review` — a multi-agent monthly-finance pipeline (`/review_finances`) where every step (CSV categorize, merge accounts, normalize, generative-UI HTML) has its own embedded validator hook; demonstrates specialized self-validation end to end plus a parallel "one CSV-edit agent per file" subagent demo.

**Drill:** (build-worthy)
1. In any repo create `.claude/hooks/validators/csv_single_validator.py` that parses a CSV and prints "Resolve this CSV error in <path>: <issues>" on failure.
2. Create `/csv-edit` slash command with front matter tools (Read/Write/Edit/Search) and a `PostToolUse` hook on Edit|Write|Read invoking the validator via `uv run`.
3. Run it on a valid CSV; confirm the validator log shows a pass.
4. Break the CSV (delete a closing quote), rerun — watch the agent detect and fix it before reporting.
5. Clone the same front matter into a subagent and fan out one agent per CSV file in parallel.
- **Done when:** the agent autonomously repairs a corrupted CSV with zero extra prompting, and validator logs prove every parallel edit was checked.

## YT-29: One Prompt Every AGENTIC Codebase Should Have (For Engineering Teams)
(22:36 · 2026-01-26 · https://www.youtube.com/watch?v=3_mwKbYvbUg)

**Thesis:** Every codebase should have a standardized `/install` (and maintenance) prompt that combines Claude Code's new setup hook (deterministic scripts) with an agentic prompt (intelligence + interactivity), because "you can tell how great an engineering team is by the time it takes for a new engineer to run the project locally."

**Nuggets:**
- 15 years / 50+ codebases heuristic: great teams onboard with "one link to one doc… and a few commands"; most teams burn 1–2 days of pair programming and Slack archaeology.
- "Agents when combined with code beats either alone" — the whole video is one instantiation of this.
- Claude Code's new `setup` hook (`claude --init`, and a `maintenance` matcher) runs *before* session start — for installs, migrations, periodic maintenance you don't want on every session. Note: it doesn't appear in the hooks lifecycle diagram.
- The script alone "is not that novel. Most production codebases already have scripts like this… raw deterministic code, it's not that valuable." Value appears when a prompt wraps it: run `/prime`, run the init hook, read its log, write install-results doc, report — and resolve second/third-order failures.
- `justfile` as launchpad: "you, your team, and your agents don't need to remember or look up flags more than once." Commands like `just cli`, `just clmm` encode every Claude CLI flag permutation.
- Human-in-the-loop variant: `/install --hil` branches into an interactive Q&A (database fresh/keep? full/minimal install? env-var guided setup?) — pair-programming onboarding replaced by an agent. Claude Code asks max ~4 questions at a time.
- Encode recurring failures back into the prompt: a "Common issues" section — `problem:` / `solution:` pairs ("If you encounter exactly any of the following issues, follow the steps to resolve them"). The prompt becomes a living runbook.
- "When you have to update something, you don't look at the docs. You look at the script and this prompt." The install prompt is "a living document that executes."
- Maintenance same pattern: dependency updates, migrations, artifact cleanup, security/dead-code checks — deterministic hook then agent validation on top.
- This is where agent sandboxes tie in: standardized install = you can spin the codebase up on any new machine/sandbox with one command.
- Mintlify independently pitched the same idea ("a standard for LLM executables") — "I don't think we need a standard. It's just the idea that matters."
- 2026 channel theme declared: **increase the trust we have in our agents.**

**Tools/tech:** Claude Code setup hook (`--init` / maintenance matchers), `just` command runner, `/prime` command, `/install` + `/install-hil` prompts, uv/npm/SQLite mock stack, logging + install-results docs.

**Repo:** `disler/install-and-maintain` — mock full-stack app demonstrating the setup/maintenance hooks, the justfile launchpad, and the one-shot + interactive install prompts.

**Drill:** (build-worthy)
1. Add a `setup` hook to `.claude/settings.json` with `init` and `maintenance` matchers pointing at scripts that install deps and log to a file.
2. Write `/install`: run `/prime`, read the setup log, resolve failures, write `install_results.md`, report.
3. Add an interactive `--hil` branch that asks 3–4 setup questions (db mode, install depth, env vars).
4. Put `just cli` / `just install` / `just maintain` recipes in a justfile.
5. Delete your env/deps and re-onboard yourself with one command.
- **Done when:** a fresh clone reaches a running app via a single `just` command with the agent reporting success/failure, and one deliberately broken step is auto-resolved via the "common issues" section.

## YT-30: Claude Code Task System: ANTI-HYPE Agentic Coding (Advanced)
(28:26 · 2026-02-02 · https://www.youtube.com/watch?v=4_2j5wgt_ds)

**Thesis:** The under-the-radar Claude Code task system (task_create/update/list/get) lets you reliably build *teams* of agents, and its real power unlocks when you encode it into a template metaprompt — `/plan_w_team` — that combines self-validation, team orchestration, and templating.

**Nuggets:**
- "More agents, more autonomy, and more compute doesn't always mean better outcomes. What we want is more organized agents that communicate toward a common goal."
- The plan-with-team metaprompt has three powerful components: **self-validation** (Stop hooks: `validate_new_file` — right type, right dir — and `validate_file_contains` — required sections), **agent orchestration**, and **templating**.
- Template metaprompt = "a prompt that generates another prompt in a very specific, highly vetted, consistent format." Sounds fancy, isn't. It's how you teach agents to build like you would.
- The generated plan gives every task an *owner* — a named team member — plus dependency blockers so tasks run in the right order and parallelize where possible.
- Task system tools: `task_create`, `task_get`, `task_list`, `task_update`. "Task update is the big one" — it's how subagents and the primary agent communicate. Superior to the old to-do list + ad hoc Task-tool calls because tasks can block/depend and events ping back — no bash sleep loops.
- Minimal viable team: **builder + validator**. "Have an agent build the thing and then have another agent validate the thing." 2x compute per task to buy trust.
- The builder itself carries micro-validation (PostToolUse on Write/Edit → ruff + ty on Python files); the validator is the macro check. Layered validation.
- Teams live in `.claude/agents/team/`; the plan step says "identify team members from .claude/agents/team or use general-purpose."
- The orchestration prompt is a second input: a high-level prompt ("create one builder and one validator per hook") that guides how the planner composes the team — a hop-like pattern.
- Self-critique moment: "I missed an opportunity — every validator agent could have fired `claude -p` to validate the log file." Tighter loops always available.
- The two constraints of agentic coding are **planning and reviewing** — this system attacks planning.
- "Don't work on the application anymore. Work on the agents that build the application for you."
- Agentic path recap: base agent → better agent (context/prompt engineering) → more agents → custom agents → orchestrator agent.
- Anti-hype framing vs Moltbot/Clawbot/OpenClaw: fine for people who know what's underneath; dangerous for everyone else. "This entire feature set is just tools and prompts" — portable to any harness if needed.

**Tools/tech:** Claude Code task system (task_create/update/list/get), Stop-hook validators, template metaprompts, builder/validator team agents, sub-agent TTS stop hooks, Opus, ruff + ty (Astral).

**Repo:** `disler/claude-code-hooks-mastery` — the long-standing hooks-education repo, updated live in the video by an agent team (new hooks: session_end, permission_request, setup, post_tool_use_failure, etc. + README updates); contains the `/plan_w_team` template metaprompt and team agents.

**Drill:** (build-worthy)
1. Create `.claude/agents/team/builder.md` (PostToolUse lint hooks) and `validator.md` (reports pass/fail only).
2. Write `/plan_w_team` metaprompt: inputs = user prompt + orchestration prompt; workflow defines team members from the team dir and step-by-step owned tasks; plan format template with embedded per-task prompts.
3. Add Stop hooks `validate_new_file` (spec .md in `specs/`) and `validate_file_contains` (required sections like "Team Orchestration").
4. Run it against a real chore (e.g. "document + implement missing X"), then execute the generated plan in a fresh agent.
5. Watch builders parallelize, validators gate, blocked tasks unblock.
- **Done when:** the plan file passes both validators automatically, and the executed plan lands verifiable diffs (each build task followed by a validation task that actually checked it).

## YT-32: My 4-Layer Claude Code Playwright CLI Skill (Agentic Browser Automation)
(27:15 · 2026-02-16 · https://www.youtube.com/watch?v=efctPj6bjCY)

**Thesis:** Don't stop at skills — stack a four-layer architecture (skills = capability → subagents = scale → commands = orchestration → justfile = reusability) to automate two whole classes of work: browser automation and agentic UI testing.

**Nuggets:**
- The four layers: **skills** are raw capabilities at the bottom; **subagents** scale them (parallelism + context isolation); **commands/prompts** orchestrate ("the API layer"); **justfile** is the reusability cherry on top — "functions for your commands."
- "You want to be using CLIs, not MCP servers. MCP servers chew up your tokens, and they're very rigid… CLIs give us the massive benefit: we can build on top of them in our own opinionated way." (Playwright CLI over Playwright MCP.)
- Two core technologies: `claude --chrome` (Claude with Chrome — reuses your real browser session, great for personal automation, but **cannot run in parallel**) and the Playwright CLI (headless by default, parallel sessions, persistent named profiles for login state — great for scaled UI testing).
- Agentic UI testing = user stories as tiny files (name, URL, workflow steps); agents execute them like a real user and screenshot every step — "a trail of success and a trail of failure." No "sea of testing configuration for your Jest/Vitest."
- Swap the URL to staging/prod to re-target the whole suite; have agents write new user stories on the fly as you build. "At the drop of a dime" test creation is the advantage over deterministic UI test frameworks.
- `/ui-review` is an orchestration prompt that creates an agent team, and *teaches the orchestrator how to prompt each subagent* ("for each task call, use this prompt") — meta prompt engineering downward.
- HOP pattern — **higher-order prompt**: `/hop_automate` takes another prompt file as its argument ("a function that takes a function"), wrapping any stored workflow (e.g. `amazon_add_to_cart.md`) in consistent parse→load→execute machinery. Consistent pieces in the HOP, details in the LOP.
- The Amazon demo: 20-minute fully autonomous shopping run that "walked right up to the doorstep of the purchase" and stopped as instructed — Opus 4.6 instruction adherence praised, and the risk acknowledged.
- "Code is fully commoditized. Anyone can generate code. That is not an advantage anymore. What is an advantage is your specific solution to the problem you're solving — all the way down to how you write your skills."
- "Everyone is just spamming skills right now… subagents got a massive buff and will be a centerpiece as agent orchestration becomes the primary paradigm."
- Bowser is a *mold*: solve the class of problem once, template it, deploy it into every codebase, specialize per repo (user stories dir, commands, etc.).
- Closing warning: "Don't outsource learning how to build with the most important technology of our lifetime… If you're always using plugins and someone else's prompts, you'll be limited by what everyone else can do." Plus: prompt injection is one of the most dangerous vulnerabilities for browser agents.

**Tools/tech:** `claude --chrome` (Claude with Chrome), Playwright CLI, Claude Code skills/subagents/commands, agent teams for parallel story validation, justfile (`j` alias), user-story file format, screenshots-as-evidence, Opus 4.6.

**Repo:** `disler/bowser` — the four-layer browser-automation + UI-testing system: 2 skills (playwright-browser, claude-browser), 3 agents (playwright-browser, claude-browser, bowser-qa), orchestration commands (`/ui_review`, `/hop_automate` + stored workflows), and a justfile on top.

**Drill:** (build-worthy)
1. Write a `playwright-browser` skill wrapping the Playwright CLI with your defaults (headless, named sessions).
2. Create a `bowser-qa` subagent: parse user story → step through → screenshot each step → report pass/fail → close browser.
3. Add 2–3 user-story .md files (name, URL, steps) against a site you know (or localhost).
4. Write `/ui_review`: discover stories, spawn one teammate per story with an explicit embedded prompt, collect results.
5. Top it with `just ui-review`; run twice to prove repeatability.
- **Done when:** one command fans out parallel story agents, every step has a screenshot on disk, and a deliberately-broken story reports FAIL with visual evidence.

## YT-34: I Studied Stripe's AI Agents... Vibe Coding Is Already Dead
(40:31 · 2026-03-02 · https://www.youtube.com/watch?v=V5A1IU8VVp4)

**Thesis:** Stripe's "minions" — fully unattended Slack-to-production-PR coding agents shipping 1,300 PRs/week with zero human-written code on a hundreds-of-millions-LOC Ruby codebase — prove that serious-stakes engineering is agentic engineering, not vibe coding, and their agentic layer is a blueprint (literally) you can steal from.

**Nuggets:**
- The definitions, canonical form: "Agentic engineering is knowing what will happen in your system so well you don't need to look. Vibe coding is not knowing and not looking."
- Stripe's numbers: 1,300 merged PRs/week from minions, zero human-written code, $1.9T total volume (~1.6% of global GDP), hundreds of millions of lines of Ruby with homegrown libraries LLMs have never seen. "Do you think Stripe can afford to vibe code?"

- Why build their own: "Vibe coding a prototype from scratch is fundamentally different from contributing to Stripe's codebase." Specialization is how you win — "your tooling and your code must also be specialized."
- **Blueprints** = workflows designed in code that direct a minion run: agent steps interleaved with deterministic nodes (linters, git, config, push). "Agents plus code beats agents alone, and agents plus code beats code alone." Dan: TAC members know this as an ADW (AI Developer Workflow). Blueprint steps also make subagent context engineering easy — constrain tools/system prompt per step.
- Deterministic steps stay deterministic: "Adding an agent to specific steps actually makes the whole system worse, more brittle, and more expensive."
- Context at scale: no unconditional global rules — cursor-style `.rules` MDC files with glob front matter, "almost exclusively scoped to specific subdirectories, automatically attached as the agent traverses the file system."
- **Toolshed**: a centralized internal MCP server — a meta-tool to discover/select among ~500 MCP tools without token explosion. "A tool that unlocks tools." Net-new concept to Dan.
- In-loop vs out-loop: engineers show up "at the beginning and the end — during planning and during review, and ideally not once in the middle." Minions = out-loop; Claude Code/Cursor remain available for in-loop. Recommendation: spend 50%+ of your time building the system of agents that builds your application.
- Dev-box logic: "If you want your agent to perform like you, give it the tools and environment you have." Git worktrees/containers "fall apart at certain scales" — eventually each agent needs its own device. Engineers run half a dozen boxes in parallel.
- "Shift feedback left" — catch issues as early (locally) as possible; CI as the safety net.
- Dan's score: **8/10**, with two critiques: (1) capping minions at two CI feedback rounds is a mistake — "has anyone ever said to you: solve this problem, you have two attempts?"; (2) it's not truly end-to-end — there's still a review step. The North Star is **ZTE: zero-touch engineering, prompt to production (P2P)** — "the value is in the journey of the question: what would it take to trust your system to ship without human oversight?"
- Prediction: in 2026 a company at tens-of-millions revenue scale publishes a blog on shipping prompt-to-production with ZTE.
- Meta-agentics everywhere: prompts that create prompts, agents that build agents, tools that select tools — "it's not about what you can do anymore, it's about what you can teach your agents to do for you."

**Tools/tech:** Stripe Minions, Block's Goose (forked harness), EC2 dev boxes, blueprint engine (ADW analog), cursor-style scoped rules files, toolshed meta-MCP (~500 tools), 3M-test CI, Slack/web/CLI triggers, GitHub PRs.

**Repo:** none (blog-analysis video; CODEBASE.md confirms no public code). Primary source: Stripe engineering blog posts on Minions (parts 1 & 2, by Alistair Gray et al.).

**Drill:** watch-and-absorb. Internalize: (1) the blueprint principle — interleave deterministic code nodes with agent nodes and never give an agent a step code can do; (2) the toolshed/meta-agentics pattern — at tool/rule scale, build the thing that selects the thing (scoped rules, tool routers); (3) in-loop vs out-loop with ZTE as North Star — keep asking what it would take to remove the review step for one low-risk task class.

## YT-35: Mac Mini Agents: OpenClaw is a NIGHTMARE... Use these SKILLS instead
(26:21 · 2026-03-09 · https://www.youtube.com/watch?v=LOazLNQnB80)

**Thesis:** OpenClaw/clawbot agents are vibe-coded security nightmares, but their core insight is right — agents deserve whole devices, not terminals — so build the minimal professional version yourself: an HTTP-triggered Claude agent on a Mac mini with two skills (steer = GUI, drive = terminal) and four small CLIs.

**Nuggets:**
- "The open claw, nano claw, and claw variants were an absolute nightmare… they exposed the worst of vibe coding at scale: buy a Mac mini, set up a claw, generate vulnerable slop code, share it with the world, and get prompt injected."
- The bright side: claws "pushed vibe coders and engineers to give their agents more autonomy. When you increase your agents' autonomy, you increase your own."
- "Our agents are stuck in the terminal. They're stuck in a box." The unlock: the agent uses the terminal to reach the GUI.
- Full architecture, four apps + two skills: **listen** (HTTP job server on the agent device), **direct** (client CLI to submit/query jobs), **steer** (Swift CLI for macOS GUI control — accessibility trees, OCR, clicks, typing), **drive** (opinionated tmux wrapper so the agent spawns/reads/writes terminals); skills teach usage (steer skill is ~130 lines: know your screens, focus-then-verify, observation loop).
- YAML job system means it scales to multiple Mac devices; `j jobs` / `j job <id>` give observable job state. Trigger from anywhere: `just send "<prompt>"`.
- Demo 1: one prompt → agent researches the new M5 MacBooks, writes a markdown report, **AirDrops** the result to Dan's MacBook. Demo 2: a spec-driven engineering task — update the claude-code-hooks-mastery repo with new hooks, screenshot visual proof per hook, summarize in TextEdit, commit to a new branch and push, AirDrop the proof bundle. It spun up its own agent team and terminals to do it.
- Time-boxing inside the spec: "If you work longer than 5 minutes, wrap it up and send what you have. Periodically check by comparing to your start time" — the agent audibly self-monitors ("it's 8 minutes, let me wrap up efficiently").
- Proof-of-work as a first-class deliverable: screenshots + logs grouped in a folder — trust through evidence, not vibes.
- "This is my agent's device. I'm never going to touch it. If something's wrong, I'm not going to fix it myself — I'm going to teach my agent how to do it." Template your engineering; build the system that builds the system.
- "If you want your agent to perform like you do, they must have the tools you have. The only way to truly get that experience is to give them their own device." (Stripe dev-box idea carried forward.)
- Harness-agnostic: Claude, Pi, Gemini, Codex, whatever — "the interesting part really isn't your agent harness anymore, it's the systems of agents that you're building."
- Karpathy cosign: claws are a security nightmare; prompt injection is Dan's top concern; claws "install packages very, very aggressively."
- "Agents are and will run everything. So it's very important to know how this stuff works."
- Recurring line of the era: "It's not about what you can do anymore, it's about what you can teach your agents to do for you."

**Tools/tech:** Mac mini (+ M5 Mac lineup hype), Claude Code in tmux, listen/direct/steer/drive CLIs (Python + Swift), YAML job queue, justfile triggers, AirDrop as agent→human notification, spec prompts, macOS accessibility/OCR.

**Repo:** `disler/mac-mini-agent` — the minimal claw-alternative: 4 CLIs, 2 skills, install command for a dev box, and the driving user prompt; deployable to any macOS device (Windows port feasible).

**Drill:** (build-worthy — requires a second Mac or VM)
1. Clone mac-mini-agent onto a spare Mac; run the install command; start `j listen`.
2. From your main machine, `j send "write your favorite OOP pillar to a file and AirDrop it to me"` — verify the HTTP → tmux → Claude flow.
3. Read the steer skill and drive wrapper source before granting anything else.
4. Write a spec (tasks + deliverable + 5-minute timebox + screenshot proof) and send it as a job.
5. Query `j jobs` / `j job <id>` mid-run instead of watching the screen.
- **Done when:** a one-line command from machine A produces a proof-of-work bundle (files + screenshots) delivered back from machine B with zero manual intervention on the agent device.

## YT-36: The Library Meta-Skill: How I Distribute PRIVATE Skills, Agents and Prompts
(26:32 · 2026-03-16 · https://www.youtube.com/watch?v=_vpNQ6IwP9w)

**Thesis:** Once you work across 10+ codebases, multiple devices, and multiple agents, your private skills/agents/prompts rot into out-of-sync duplicates — so manage them with "the library": a pure-agentic meta-skill plus one YAML reference catalog (a package manager for agentics, no code required).

**Nuggets:**
- Explicit audience gate: "If you're an engineer working on one to two repos, this doesn't matter at all. If you install skills or plugins from the public internet without reviewing them, this video is not for you either."
- The problem: "endless skills everywhere — out of sync, duplicated, hard to coordinate" across repos, teammates, and each teammate's agents.
- The solution shape: a **meta-skill** — "a skill that unlocks other skills, agents, and prompts." Stripe's toolshed idea, broadened from tools to all agentics.
- The catalog is references, not copies: `library.yaml` points at private/public GitHub repos or local paths — "think package.json / pyproject… staying synced is super simple because there's one source of truth."
- API surface: `add` (catalog an existing artifact), `use` (install locally or globally), `push` (send an edit back to the source repo), `list`, `search`, `sync` (pulls latest from source repos, not just the catalog).
- Workflow: **build → catalog → distribute → use.** Build natively in the value-generating repo ("don't interrupt the flow"), then `library add` a pointer.
- "This is a pure agent application. There is no code associated with this. The application is the skill" — it runs entirely as skill.md + library.yaml + per-command cookbook files. Prediction: "we're going to see a lot of pure agentic solutions this year."
- Cookbook organization: one file per command inside the skill dir — "individual agentic workflows the skill describes when to use."
- Mental model restated: **skills = raw capabilities; agents = scale/parallelism; prompts = orchestration of the two; justfile on top.** "A lot of people are overkilling skills."
- Privacy stance: "Your top-notch skills, agents, and prompts should absolutely be private… we need a way to distribute this privately." Two repos: the library (catalog, public template) vs the engineer library (the actual private artifacts).
- Demo spans harnesses and models: adds meta-agentics (meta-agent, meta-prime, meta-prompt, meta-skill) to the catalog, installs them locally then globally, installs on the Mac mini agent device, generates a new prompt with Qwen 3.5 via Pi, edits a skill with Gemini flash-lite, then `library push` (on Sonnet 4.6) lands the change back in the source repo — "freshly updated right from our agent device."
- Meta-agentics reminder: "These are the skills that build the skills… if you don't have these at the ready, definitely build this out" — build your own rather than using stock skill-builders, so your ~800-line meta-prompt encodes *your* format identically on every device, human- or agent-operated.
- Versioning is deliberately absent — latest-only, "very much like a package system for prompts, skills, and agents."
- Path recap + closing: base → better → more → custom → orchestrator agents; the orchestrator needs your agentics organized in one place to operate whole devices and domains for you.

**Tools/tech:** the-library meta-skill (`/library` command), library.yaml catalog, private GitHub repos, cookbook-per-command skill layout, meta-agentics suite, Claude Code + Pi (customized harness), Qwen 3.5 / Gemini flash-lite / Sonnet 4.6, Mac mini agent device, justfile.

**Repo:** `disler/the-library` — public template of the pure-agentic distribution system: blank library.yaml, the /library skill with add/use/push/list/search/sync cookbooks; you fork it and build your own private catalog.

**Drill:** (build-worthy)
1. Clone the-library into `~/.claude/skills/library/`; keep the blank library.yaml.
2. In a real repo, `/library add <skill-name> from <repo-url>` for 2–3 skills/prompts you actually reuse.
3. In a fresh temp dir, `/library use <name> install locally` and verify with `tree .claude`.
4. Install one globally; confirm it loads in a *different* harness (Pi or another agent) too.
5. Edit the installed copy, `/library push <name>`, and confirm the source repo received the commit.
- **Done when:** the same skill installs identically on two machines/harnesses from one YAML file, and a round-trip edit lands back in the source repo without you touching git manually.
