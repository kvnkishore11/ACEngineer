Tactic 06 · Let Your Agents Focus

One agent. One prompt. One purpose.

This lesson trains you to command a software delivery system without becoming its runtime. You define the mission and the acceptance gate; a launcher gives fresh CLI agents narrow jobs—plan, build, test, review, patch, document—and machine-readable artifacts carry the work forward. The win is not a clever chat. It is a replaceable team of programmed workers inside a closed loop.

human intent → focused agent → artifact → verifier → recover or accept

01 · Who actually acts?

The cast around the code

Do not picture one omniscient assistant. Picture a relay team. Roles are separated by prompts, and the filesystem plus GitHub carry the baton.

Commander

Human

Owns intent, authority, and acceptance. Writes or selects the issue, chooses a workflow, provides credentials, inspects proof, and decides whether to merge or improve the system.

Composer

ADW orchestrator

Chooses the sequence. Files such as adws/adw_sdlc.py run plan → build → test → review → document and stop when a stage returns nonzero.

Focused workers

Fresh Claude CLI processes

Do one prompted job. Each claude -p invocation receives one slash command and writes its own prompt and JSONL trace under the run directory.

Verifiers

Tester and reviewer

Ask different questions. Tests check whether behavior works. Review compares the result with the spec and gathers screenshot evidence. Blockers can enter a patch/re-review loop.

Deterministic helpers

Scripts

Provide reliable hands, not judgment. scripts/start.sh, reset_db.sh, and stop_apps.sh make repeatable environment moves the reasoning agents can call.

Relay

Issue, Git, state, and artifacts

Carry context between replaceable workers. The issue, plan file, branch, diffs, screenshots, result JSON, and adw_state.json are shared memory—not a long chat transcript.

SOURCE REALITY This repository has no native .claude/agents/ fleet or lesson-local skills. “Subagents” here are separate headless CLI processes launched for separate purposes. The settings include a SubagentStop hook, but the course implementation’s isolation boundary is the process.

02 · Agent surface map

The repo is an operating surface

These are the interfaces an agent touches. Application files sit inside the workspace, but the agent system is defined by the path from intent to evidence.

03 · Control loop

You touch the loop at the leverage points

“Out of the loop” means out of repetitive execution, not absent from responsibility. The human controls the mission and the gate; the system controls the repeated middle.

When the same failure repeats, repair the prompt, permission boundary, launcher, state schema, or verifier—not the agent’s latest conversation.

04 · Why these files exist for agents

Four contracts make the workers programmable

The application is what gets changed. These contracts decide whether an agent can change it deliberately, safely, and repeatedly.

.claude/commands/review.md · prime.md · conditional_docs.md

1 · Prompt contract

The command file defines one job, its inputs, required context, evidence, and output shape. prime.md inventories tracked files and reads the two READMEs; conditional_docs.md keeps extra context conditional instead of making every worker ingest everything.

The real review prompt also exposes contract drift: it says “ONLY JSON array” while its example and parser expect an object. It points to ./claude/commands/e2e, while the real directory is .claude/commands/e2e/.

Dan’s design intent: put the role in a reusable prompt, then kill the process. A new worker can pick up the same contract without inheriting old attention residue.

review.mdprompt evidence
# Review

adw_id: $1
spec_file: $2

- IMPORTANT: To be clear, we're not testing.
- IMPORTANT: Aim for `1-5` screenshots…
- IMPORTANT: Return ONLY the JSON array…
.claude/settings.json · .claude/hooks/ · .mcp.json

2 · Tool and permission contract

The settings pre-approve a small command vocabulary—package managers, basic file operations, and writing—and explicitly deny force-push and recursive deletion patterns. Hooks log lifecycle events and can block access to .env. Playwright MCP supplies the browser surface.

But the ADW launcher explicitly passes --dangerously-skip-permissions. That is a broad, course-era automation choice: do not mistake the visible allowlist for the entire runtime boundary. Hooks also use || true, so their logging failures do not stop work.

Dan’s design intent: capability is engineered. The agent should receive enough power to finish the role, while the harness—not hope—defines the blast radius.

settings.jsonpermission evidence
{
  "allow": [
    "Bash(uv:*)", "Bash(npm:*)",
    "Bash(ls:*)", "Write", …
  ],
  "deny": [
    "Bash(git push --force:*)",
    "Bash(git push -f:*)",
    "Bash(rm -rf:*)"
  ]
}
adws/adw_modules/agent.py · adws/adw_modules/state.py · adws/adw_sdlc.py

3 · Harness and launcher

execute_template() turns a slash command into a saved prompt, selects a model, launches a fresh process, records raw stream JSONL, and extracts the result. Composers call these workers in sequence. A deliberately tiny state object carries issue, branch, plan, and classification between stages.

claude -p "/review <adw-id> <spec-file>" \ --model <routed-model> \ --output-format stream-json --verbose \ --dangerously-skip-permissions

Dan’s design intent: the worker is disposable; its inputs, outputs, and invocation are durable. That makes roles schedulable, observable, and replaceable.

InterfaceWhat crosses it
Prompt captureagents/{id}/{agent}/prompts/
Raw traceraw_output.jsonl
State relayfive whitelisted fields in adw_state.json
Composerstage exit code decides continue/stop
adws/adw_test.py · adws/adw_review.py · adws/adw_modules/data_types.py

4 · Verification contract

Tests and review are separate control surfaces. Unit testing retries up to four times; E2E has a two-attempt path. Review parses a typed result, treats blocker differently from tech_debt and skippable, and can patch/re-review up to three attempts.

Important source truth: every shipped composer that includes the test stage currently passes --skip-e2e. The review prompt asks for screenshots, but a screenshot only becomes proof when the reviewer actually reads it.

review → blockers? → patch plan → implement patch → re-review ↘ no blockers → success ↘ attempt 3 → stop nonzero

Dan’s design intent: do not ask the actor whether it succeeded. Give success a second role, a structured vocabulary, evidence, and a bounded recovery path.

RoleQuestion
PlanWhat exactly are we building?
BuildDid we make the planned change real?
TestDoes the behavior work?
ReviewIs it what we asked for—and where is the proof?
DocumentHow will the next worker understand it?

05 · Worked agent run

Operate like Dan: command the system

This path uses the commands and prerequisites documented by the lesson. Replace angle-bracket placeholders with your real issue and ADW identifiers.

Provision the operating surface

Authenticate GitHub, create the server environment file described by the README, install both dependency sets, and export the ADW variables listed in adws/README.md—including GITHUB_REPO_URL and ANTHROPIC_API_KEY.

gh auth login cd app/server uv sync --all-extras cp .env.sample .env cd ../client bun install cd ../../

Prove the app can be operated

The launcher and reviewer depend on a startable system. The real helper starts the backend on 8000 and frontend on 5173.

./scripts/start.sh

Give the commander’s intent a durable home

Create a GitHub issue with observable acceptance criteria. The issue number—not a sprawling chat—is the workflow’s entry point.

gh issue create

Launch the full composer

The SDLC composer runs plan, build, test, review, and document in sequence. On this checkout, its test call skips the E2E phase; plan your acceptance gate accordingly.

cd adws/ uv run adw_sdlc.py <issue-number>

Inspect the relay, not the keystrokes

Find the printed ADW id. Inspect its small state file, per-worker prompt, raw output, diff, review result, and screenshot directory. Ask: did every stage receive the artifact it expected?

ls ../agents/<adw-id> git diff origin/main

Re-run one role when the contract needs proof

The README exposes focused workflow entry points. --skip-resolution gives you review without the patch loop, useful for comparing prompt changes in the lab below.

uv run adw_review.py <issue-number> <adw-id> --skip-resolution uv run adw_document.py <issue-number> <adw-id>

Exercise the human gate

Read the spec, structured review, screenshots, checks, and PR. Merge only when the evidence meets the issue—not merely because every process exited.

The commander owns

  • A bounded, testable issue
  • Repository and credential authority
  • The workflow choice
  • The definition of acceptable proof
  • The final merge decision
  • System fixes when failures repeat

Leverage test: if you are narrating each implementation move, the system has handed control back too early.

06 · Fail, name, repair

Common agent-system failures in this lesson

These are not reasons to abandon agents. They are evidence that a programmable interface needs repair.

Prompt and parser disagree

review.md says JSON array while ReviewResult expects an object. The prompt also names a non-existent E2E path spelling.Repair: make the output grammar and real path exact.

Authority is broader than it looks

The settings show an allow/deny list, but the headless launcher requests permission bypass.Repair: choose one enforceable boundary and test it from the launched process.

Evidence is produced but not consumed

The reviewer is told to take screenshots, not explicitly to read every captured image before judging.Repair: bind capture, inspection, and finding in the prompt contract.

A stage name overpromises

The three shipped composers that include testing all pass --skip-e2e to that stage.Repair: inspect composer arguments; never infer coverage from a filename.

State silently drops the baton

Review, documentation, and patch workflows try to store fields that ADWState does not whitelist. Later stages must fall back to directory conventions.Repair: version and validate the state schema at every producer/consumer edge.

Classifier and trigger drift

The classifier prompt can return workflows omitted by the webhook’s typed and runtime allowlists.Repair: derive all selectors from one registry, then test every advertised value.

Hooks look stricter than they are

Lifecycle hooks are invoked with || true; a hook failure becomes a log gap, not necessarily a stopped agent.Repair: make safety hooks fail closed; keep telemetry hooks fail open.

The human becomes middleware

Hand-copying every result and coaching every edit destroys replaceability.Repair: externalize the baton as state, artifacts, typed results, and capped recovery loops.

07 · Agent ops lab

Make the reviewer consume its own proof

Change the agent system, not the application. Your target is .claude/commands/review.md.

Run the experiment

  1. Choose an existing run with an issue number, ADW id, branch, and plan. Commit or stash unrelated work so the comparison is clean.
  2. Run the focused reviewer once with --skip-resolution. Save its structured result and note whether each screenshot is actually examined in the reasoning/output.
  3. Edit only .claude/commands/review.md: require the reviewer to read every screenshot it captures before deciding; require every visual finding to name its evidence; make the final output instruction say JSON object, matching ReviewResult.
  4. Run the same reviewer command against the same issue, ADW id, branch, and plan. Compare parse success, evidence references, and findings.
  5. If it fails, resist fixing app code. Diagnose which interface broke: prompt, Playwright access, runtime authority, artifact path, or result schema. Repair that interface and repeat.
cd adws/ uv run adw_review.py <issue-number> <adw-id> --skip-resolution

Observable pass criteria

  • git diff --name-only shows the review prompt, not files under app/.
  • The agent result parses as one ReviewResult object.
  • Every captured screenshot is read before the final judgment.
  • Every visual issue names the screenshot or visible observation that supports it.
  • A second run receives the same fixed inputs, so the before/after comparison is meaningful.

Stretch: repair trigger drift

Make every workflow advertised by classify_adw.md agree with both ADWWorkflow and AVAILABLE_ADW_WORKFLOWS. Pass when a small test proves every advertised selector is launchable.

08 · Retrieval check

Explain this agent OS in six sentences—without looking

The human commander is responsible for…
A focused CLI worker receives… and returns…
Prompts, permissions, launchers, and state each control…
Testing differs from review because…
When a blocker appears, the closed loop…
The system creates leverage and replaceability when…
Check a model answer

The human commander defines the issue, grants authority, chooses the workflow, and owns acceptance. A fresh CLI worker receives one slash-command contract plus explicit artifacts and returns a saved, machine-readable result. Prompts bound understanding, settings and hooks shape capability, the launcher creates process isolation, and state carries the baton. Testing asks whether behavior works, while review asks whether the result matches the specification and proves it. A blocker enters a capped patch-and-re-review loop, and a persistent failure sends us back to repair the agent interface. The system creates leverage when workers are replaceable, evidence closes the loop, and the human is needed mainly at mission input and the final gate.
