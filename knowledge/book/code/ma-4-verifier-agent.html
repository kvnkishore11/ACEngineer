The Pi Verifier Agent

The application is not the main character. The main character is a two-process Agent OS that gives one model authority to build, gives another a narrower authority to judge, and closes the correction loop without turning the human into a message router.

  • 1 builder
  • 1 verifier
  • 4 shipped personas
  • 3 correction loops by default
  • 1 verifier per builder

01 · Agent mission

Move reviewing from a human habit into a programmable system

Work this lesson trains

Command a builder with a claim-style request, let a sibling verifier wake on the builder’s stop event, prove or disprove the builder’s atomic claims against real state, and improve the durable verifier persona, prompt, or checker whenever the system lacks an oracle. You are training the move from “I inspect every done message” to “I engineer the loop that produces evidence.”

Human sets intentChoose the goal, verifier domain, authority, and what counts as proof.
Harness carries workSpawn, observe, transport lifecycle, inject correction, cap retries.
Evidence closes trustThe builder’s prose is a claim. Script output, image bytes, and test results are proof.

02 · Cast of agents

Know who thinks, who acts, and who merely enforces

The repo uses the word “agent” precisely for model-driven roles. Launchers and scripts can feel agentic because they act automatically, but they are deterministic control surfaces—not extra minds.

ActorJobAuthorityBoundary
Human commanderChooses the domain, writes the request as checkable claims, watches the first proof cycle, and handles escalation.Can change persona, prompt, script, model, or launcher.Does not type instructions into the verifier or manually relay corrections.
Claude Code / coding agentActs as setup bootloader for /install and context loader for /prime.Checks prerequisites, installs package deps, validates config, type-checks.It is not the runtime verifier. Any compatible agent may perform setup.
Builder PiReceives the human request and performs normal write/edit/run work.Its normal tool surface; cross-agent.ts additionally exposes compatible commands and skills.It does not decide when to verify. verifiable.ts observes it from the harness layer.
Verifier PiReads one bounded builder-turn slice, decomposes claims, checks actual state, reports, and sends concrete feedback.Persona-selected tools plus the system’s verifier_prompt channel.Human input is locked; one verifier connection per builder; correction loop is capped.
Domain personaPrograms purpose, model, tools, loop limit, evidence focus, workflow, and Report shape.Frontmatter becomes runtime flags; body becomes the verifier’s full system prompt.Generic/image omit script-only bash policy; SQLite/Python declare it.
Launcher + socket supervisorSpawns the child, opens a sibling tmux/OS window, handshakes, pings, diagnoses startup, and cleans up.Process, tmux, temp prompt/wrapper files, local Unix socket.Transports lifecycle/control; it does not judge application correctness.
Verifier scriptActs as a deterministic oracle: SQLite inspection or Python checks.Only its CLI and subprocess routes.Not an LLM agent. It should make truth cheap and repeatable for the verifier.

Where are the subagents? They are not part of the builder→verifier runtime. .claude/commands/plan-w-team.md describes a separate planning/team workflow, while cross-agent.ts only discovers commands, skills, and agent metadata for the builder. The verifier child deliberately does not load that cross-agent extension.

04 · Control loop

Plan → act → verify → recover, with the human mostly outside

“Out of the loop” does not mean absent. The commander chooses the contract and receives escalation; the harness handles the repetitive routing between those moments.

Human boundary
1 · Plan proofChoose persona, fixture, claim-style request, and success evidence.
2 · LaunchRun one just v* recipe and prompt only the builder.
3 · ObserveRead the Report; do not relay messages or type at the verifier.
4 · Improve / decideTemplate a missing oracle or handle max-loop escalation.
Closed system loop
ActBuilder uses its normal tools and ends the turn.
Tickagent_end emits stop with prompt + line bounds.
ReadVerifier reads only that JSONL slice.
AtomizeRequest and claims become independently testable propositions.
CheckPersona-selected tools compare claims with actual state.
RecoverOn actionable failure, verifier_prompt sends a follow-up.
ProveReport records pass, fail, gaps, feedback, counts, confidence.

Bounded return path: corrective turns do not reset loopCount. More than the persona’s max_loops causes a human-facing escalation instead of an infinite agent argument.

Worked run · a planted SQLite defect

Course drill: the builder first creates the lab’s runtime fixture, tmp/mock_shop.db, with orders.user_id referencing a mistyped table, user instead of users.

  1. The commander launches just vsql and asks the builder to confirm every primary key and foreign key.
  2. The builder finishes. The verifier wakes without a human prompt and reads the bounded turn slice.
  3. The verifier decomposes “foreign keys are valid” into table, source column, target table, and target column claims.
  4. SQLite evidence disproves the target-table claim. The verifier sends an exact correction through verifier_prompt.
  5. The builder repairs the schema in a follow-up. The next stop produces another verification cycle and a clean Report.

What makes this a closed loop?

Trigger: builder agent_end, not a second human prompt.
Ground truth: PRAGMA foreign_key_list(...), schema inspection, and integrity checks—not the builder summary.
Recovery: the verifier names the broken atom and fix; the harness injects it as followUp.
Stop condition: verified Report or bounded escalation.

05 · Why these files exist for agents

Four contracts turn two model calls into an Agent OS

Each contract answers a different question: what should the verifier understand, what may it do, how is it invoked, and what evidence lets the system declare success?

Prompt contract

.pi/verifier/agents/verify_sqlite.md

The persona frontmatter selects model, tools, domain, loop bound, and bash policy. Its Markdown body becomes the verifier’s complete system prompt. verify_on_stop.md then supplies turn-specific intent and JSONL line bounds.

tools: read, grep, find, ls, bash, verifier_prompt
model: openai/gpt-5.5
domain: sqlite
max_loops: 3
bash_policy:
  mode: script-only

Dan’s design intent: one agent, one prompt, one purpose. When a verification rule changes, edit a durable persona or cycle template—not an ephemeral chat.

Tool / permission contract

apps/verifier/verifier.ts

The launcher forwards only the persona’s tools. SQLite and Python additionally declare a script-only policy; the verifier extension blocks non-matching bash calls before execution.

const expected = `${state.bashPolicy.runner} ${state.bashPolicy.allowed_script}`;

if (cmd.startsWith(expected)) return;
return { block: true, reason: "Bash is restricted…" };

Dan’s design intent: place authority outside model intent. Remove write/edit, narrow bash, then make the checker reject mutation again.

Audit boundary: this implementation uses a string-prefix test, not parsed argv. Generic and image personas have no bash_policy. This is narrowing, not a universal sandbox.

Harness / launcher contract

justfile → launcher.ts

The recipe names a verifier persona; the builder extension starts the socket server; the launcher renders the system prompt, generates a wrapper, pins model/tools, and spawns the sibling Pi in tmux.

vsql:
  pi -e ./apps/verifier/verifiable.ts \
     -e ./apps/verifier/cross-agent.ts \
     --verifiable \
     --verifier-agent verify_sqlite

Dan’s design intent: make specialization an operator command. Keep the lifecycle fixed while swapping the verifier’s purpose, model, and oracle.

Verification contract

verify_*.py + ## Report

The agent must end each cycle with parseable status, confidence, evidence, gaps, feedback, next requirements, and atom counts. The SQLite checker adds a read-only connection beneath the LLM.

def open_ro(path: str) -> sqlite3.Connection:
  return sqlite3.connect(
    f"file:{path}?mode=ro&immutable=1", uri=True
  )

Dan’s design intent: make every success claim carry proof and every missing proof become the next system improvement. “Unsure” is useful when it names the missing oracle.

Settings are context, not the whole permission model. .pi/settings.json points Pi at Claude skills and the session directory. .claude/settings.json configures a status-line command. Neither file is the verifier’s mutation boundary; that boundary is assembled from persona tools, launcher flags, the tool-call hook, and domain checker.

06 · Operate like Dan

Run the system from the real operator surface

These are the repository’s documented commands. Run them from the codebase root, and keep all interaction in the builder window.

  1. Install through an agent bootloader

    Open Claude Code, Pi, or another agent that can execute the project’s .claude/commands. The command checks critical CLIs, installs TypeScript dependencies, validates personas/scripts, checks a provider key without printing it, and runs TypeScript verification.

    /install

  2. Prime a fresh coding-agent session

    /prime tells the agent which runtime, IPC, persona, and checker files are canonical. The justfile also exposes Claude and Pi priming recipes.

    /prime just prime just primepi

  3. Inspect and clean the launch surface

    Bare just lists the four verifier recipes. Use just clean only for stale verifier tmux sessions, sockets, or breadcrumb files left by a prior crash.

    just just clean

  4. Choose the oracle that matches the task

    Generic is flexible; SQLite and Python have script-only bash policies; image uses vision and a relevance gate. The current code default for just v is the full generic persona, even though stale README text still describes an older SQLite-only build.

    just v # generic just vsql # SQLite just vpy # Python just vimg # image

  5. Prompt the builder with checkable claims

    Prefer “confirm every table has a primary key and each FK targets a real table/column” over “check the database.” The original prompt is forwarded with the stop event and becomes verifier ground truth.

    Inspect tmp/mock_shop.db and confirm every table has a primary key and every foreign key references a real table and column.

  6. Watch proof and recovery—hands off

    Confirm the builder border says verifier connected. After builder completion, watch the verifier atomize, check, Report, and—when needed—prompt the builder back. On Ctrl+D in the builder, the child window, socket, and breadcrumb are cleaned up.

Commander rule: if you want to type into the verifier, stop. Put the missing behavior in agents/*.md, prompts/*.md, scripts/*.py, or the harness. That turns an instance fix into a replaceable, reusable agent capability.

07 · Common agent failures

Most breakage is a contract mismatch, not a weak model

Bundled or vague request

Symptom
Verifier produces coarse PASS or many ambiguous gaps.
Cause
The human did not give atomic, falsifiable intent.
Recovery
Rewrite the builder request as claims with paths, constraints, and observable outcomes.

Wrong specialist

Symptom
PERFECT with zero claims.
Cause
Image/Python relevance gate found no work in its domain.
Recovery
Pick vsql, vpy, vimg, or generic to match the task.

Permission slogan

Symptom
“Read-only” is assumed from persona prose.
Cause
Generic/image bash is prompt-only; Python tests may have side effects; SQLite’s gate is prefix-based.
Recovery
Scope the claim to the persona and inspect all enforcement layers.

No oracle or fixture

Symptom
STATUS: unsure, CONFIDENCE: FAILED.
Cause
The verifier cannot prove an atom with current tools/data.
Recovery
Preserve the gap and template the missing checker, fixture, or rule. Do not guess.

Human becomes the router

Symptom
You copy verifier findings into the builder by hand.
Cause
The correction channel or harness was bypassed.
Recovery
Use verifier_prompt and follow-up delivery; keep the human at launch/escalation boundaries.

Startup stuck on “spawning”

Symptom
No verifier hello within roughly three seconds.
Cause
Often invalid persona model, missing dependency, or tmux/socket trouble.
Recovery
Read surfaced stderr, run the generated wrapper manually if directed, then just clean.

Documentation drift

Symptom
README says SQLite-only/default while the tree ships four personas and generic default.
Cause
Operational source changed after prose.
Recovery
Trust the justfile, persona frontmatter, and current attach() path.

Loop without a stop condition

Symptom
Builder and verifier repeatedly disagree.
Cause
Retries were treated as progress.
Recovery
Keep max_loops bounded; escalate with the latest Report after the threshold.

One giant verifier

Symptom
Broad purpose, broad bash, hard-to-read Reports.
Cause
Specialists were merged for convenience.
Recovery
Clone the two-file persona+script pattern and select it with --verifier-agent.

Duplicate verifier

Symptom
Second connection receives bye: duplicate connection.
Cause
The server intentionally permits one verifier per builder.
Recovery
Use the existing child or clean stale state; fan-out is not implemented here.

08 · Lab · Agent operations

Change the verifier’s durable policy, then watch the loop react

This lab changes the Agent OS, not application logic. You will tighten one persona rule and prove that the new rule controls the next run without a one-off instruction.

Mission · lower the image readability budget

Open .pi/verifier/agents/verify_image.md. Change the literal domain constant from MAX_TEXT_ELEMENTS: 10 to MAX_TEXT_ELEMENTS: 6. Do not alter the generated image by hand and do not type at the verifier.

Run · make the new contract bite

  1. Ensure OPENAI_API_KEY is available as required by the shipped gpt-image-2 builder skill.
  2. Run just vimg.
  3. Prompt the builder to generate a compact architecture diagram with seven or eight distinct text blocks and a specific output path.
  4. Let the image verifier inspect the actual file. The new threshold should fail the readability atom and send a simplification prompt back.
  5. Let the builder regenerate. The next cycle should pass only when the image has six or fewer distinct text blocks and the remaining labels are legible.

Fail deliberately · catch the tempting wrong move

When the seven-label image fails, do not tell the verifier “six is okay this time.” Its input is locked anyway. The correct move is to decide whether six is truly the reusable policy. If it is, keep the persona change; if not, restore ten and improve the rule more carefully.

No image key? Audit the permission boundary instead

In a disposable branch, harden the bash acceptance predicate in apps/verifier/verifier.ts so it accepts the exact expected command or the expected command followed by whitespace—not an arbitrary string sharing the same prefix. Run the repo’s documented type-check:

cd apps/verifier && npx tsc --noEmit && cd ../..

Then verify an off-policy look-alike such as an allowed script path with an extra suffix is blocked with the teaching message. This track changes the harness contract, not product code.

Observable pass criteria

Policy provenanceYou can point to the exact persona or harness line that changed behavior.
Hands-off triggerThe verifier woke on builder stop; you issued no verifier-window instruction.
EvidenceThe failing Report names the violated atom and concrete observed mismatch.
Closed recoveryverifier_prompt is acknowledged and the builder performs the repair turn.
Final proofThe next Report has zero failed atoms and honest confidence.
Compounding moveYou can explain why the edit solves a class of future runs, not one current image.

09 · Teach-back

Explain this Agent OS in six sentences without looking

Close the source. Say one sentence for each numbered prompt. If two prompts collapse into one vague sentence, the system boundary is not yet clear.

Name the human commander’s job and the one behavior they must avoid.

Name the builder and verifier roles, including which one may change state.

Explain what triggers verification, what crosses the socket, and what the verifier reads from disk.

Explain how persona, tool allowlist, bash gate, and domain checker divide responsibility.

Explain how failure becomes a builder follow-up and how the loop terminates.

Finish with Dan’s leverage thesis: replaceability, programmable agents, and spending compute to reclaim human review time.

Reveal a six-sentence reference answer

1. The human commander chooses the goal, verifier domain, authority, and proof, but never types one-off instructions into the verifier.

2. The builder is the state-changing worker, while the sibling verifier is an input-locked observer that decomposes and checks the builder’s claims.

3. Builder completion emits a stop event with intent and line bounds over the Unix socket, while the verifier reads the substantive turn from the builder’s session JSONL.

4. The persona programs purpose and tools, the launcher exposes that tool list, the tool-call hook narrows bash where configured, and the domain checker supplies deterministic evidence.

5. An actionable failure travels through verifier_prompt as a builder follow-up, repeats verification, and escalates to the human after the configured loop bound.

6. Dan’s move is to spend replaceable model tokens on a programmable closed loop so scarce human time shifts from repetitive review to designing better prompts, oracles, and systems.
