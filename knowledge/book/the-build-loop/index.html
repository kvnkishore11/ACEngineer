1

Git is his distribution channel

You cannot learn the loop from the commit history, because the commit history does not contain it.

Nine of ten repositories open with a single commit that dumps a finished project — up to 124 files and 14,000 lines at once. The rest is README churn. The real building happens off-git and gets squashed at publish time.

Anyone who tells you they reverse-engineered this workflow from GitHub is pattern-matching on a press release.

Every history is dead flat on main. The topology never survives publish.
2

One session leaked

Exactly one repository caught him actually building — 94 minutes on 2025‑06‑06. The order is emphatic, and it is the opposite of how most people set up a project.

The machine comes before the work. A slash command and vendor docs land in commit one, before a single line of application code. CLAUDE.md arrives on day four.
THE TELL CLAUDE.md at commit 15 is a retrospective summary — it enumerates files that already existed and even hedges, "prime.md — Additional command (if present)." It is generated documentation of a working system, not a plan for one.

Prime beats memory

Twenty of thirty repos have no memory file at all — including the flagship ones.

The "keep it ~40 lines" advice is real — it traces to a genuine quote, and four course repos are exactly 43 lines, three of them byte-identical.

But the practice is more extreme than the doctrine. His default is not to have one.

The irreducible prime

.claude/commands/prime.md — the whole file
# Prime
Execute the `Run`, `Read` and `Report` sections to understand
the codebase then summarize your understanding.

## Run
git ls-files

## Read
README.md

## Report

Eight lines. This exact file is the ancestor of all twenty-nine.

Add a ## Focus block and tiered read-lists — Core (always), Backend (if working on backend) — only once the repo is big enough to need them.

And write it backwards. Point each READ: line at an artifact after that artifact exists.

2

The plan format that survives

The full skeleton is eleven sections, and they are atomic — every spec that uses any of them uses all of them.

But there is a natural experiment sitting in the corpus: the same plan prompt run through Claude, Gemini and Codex. Weaker models shed sections in a consistent order, and six survive every model. Those six are the irreducible core.

01

Task Description

The task in detail, from the prompt.

02

Objective

What is true when this is done.

03

Relevant Files

Each with a one-line reason. New files under their own heading.

04

Step by Step Tasks

Exact files, exact functions, often exact line numbers.

05

Acceptance Criteria

Measurable, not aspirational.

06

Validation Commands

Command, then what passing looks like. Never optional.

A plan without validation is an open loop.

— the dojo template, stated as a rule

The other governing line: "Explore before you plan — never write a plan against code you have not read."

And validation is never a bare command. The format is always the command and the observable that proves it passed.

how validation commands are actually written
- `just test` — all tests pass
- `cd apps/backend && uv run pytest -v` — backend tests all pass
- `live-bench list` — shows qwen35-vs-gemma4 with 8 charts
CONDITIONAL SECTIONS Add Problem Statement + Solution Approach if the task is a feature or complexity is medium/complex. Add Implementation Phases only for medium/complex. Add Testing Strategy on the same condition as the first pair. The template gates these itself — you do not decide per-project.

The builder, in twenty-five lines

This is the entire build layer.

No priming. No context. Everything the builder needs is inside the plan — which is exactly why the plan had to be good.

Note the two refusals encoded in it: it will not start without a path, and it will not stop before validating.

.claude/commands/build.md
---
description: Build the codebase based on the plan
argument-hint: [path-to-plan]
---

# Build

## Instructions

- IMPORTANT: Implement the plan top to bottom, in order.
  Do not skip any steps. Do not stop in between steps.
  - If you have not run any validation commands, DO NOT
    STOP until you have validated the work.

## Variables

PATH_TO_PLAN: $ARGUMENTS

## Workflow

- If no `PATH_TO_PLAN` is provided, STOP immediately and ask.
- Read the plan. Ultrathink about it and IMPLEMENT it.

## Report

- Summarize the work in a concise bullet list.
- Report files and lines changed with `git diff --stat`

03 — The loop
run this identically for a chore, a bug, or a feature

Two agents. Never one.

This is the whole procedure. Step zero has no agent in it, and skipping it is the most common way the rest fails.

Two touchpoints, not a conversation. You appear once to approve the plan and once to review the diff. The dashed line is the part people skip.
1

The steps

  1. Push the laptop away

    Open raw.md by hand. Write purpose, problem, solution — then the literal output file tree. What will exist when this is done that does not exist now? "We never start by just blasting out prompts."

  2. Fresh agent, /prime

    New terminal, new instance. Check /context — you want roughly 90% free.

  3. Fire /plan with a deliberately vague prompt

    "We're writing a high level prompt, which is a prompt that's void of detail." The detail already lives in the template. Output lands in specs/.

  4. Read the plan. Delete things.

    Touchpoint one. "You always go overboard. By the end of your planning phase, you should be deleting information that isn't relevant." Confirm the Validation Commands section is real.

  5. Commit the spec

    Before any code exists to blur it.

  6. NEW terminal. NEW agent. /build the plan.

    Never continue the planner. This is the rule that survives every contradiction in the corpus.

  7. Watch it close its own loop

    The agent runs every validation command, fixes failures, and reruns all of them from the top — not just the one that failed.

  8. Review the diff, then commit

    Touchpoint two. git diff --stat, then spot-check by hand.

2

Why fresh, every time

It's easy to know what your agent has seen when it's seen nothing.

— the line that makes the whole rule click

He poses the objection himself and answers it flatly:

"Don't we want to keep rolling the important context between planning, building, and really the entire software development lifecycle? No."

REASON 01

Context is freed

"Focus every available token on the task at hand."

REASON 02

Assets become improvable

Prompts and plans are forced to be isolated and reusable with zero dependencies — "a trail of success or a trail of things we can improve."

REASON 03

It prepares for off-device

The same prompts that work in-loop run out-of-loop unchanged.

THE DEBUGGING PAYOFF Because every run starts from committed assets in a clean window, you know exactly what was in context when it failed. You cannot root-cause a failure in a polluted window — which is why /compact is treated as an anti-pattern. If the window fills mid-task, the task was too big. Chop it.
3

Testing is not reviewing

◴ what tests answer
  • Does it run?
  • Deterministic, cheap, repeatable
  • A known command — so it belongs in code, not in an agent
  • Red tests are input, not a crash
◵ what review answers
  • Is what we built what we asked for?
  • Needs judgement, so it needs an agent
  • Graded against the plan, not against taste
  • Requires evidence — a claim is never proof

His later factory deleted its tester agent entirely on exactly this reasoning: "A known command is code, not an agent — if you can write the invocation down (bun test, ruff check), it belongs in a code phase."

04 — When it fails
the engine of the whole method

Never fix the output. Fix what produced it.

Everything else in this guide is setup. This chapter is the part that compounds — and the part almost nobody actually does, because fixing the output by hand is always faster once.

Why didn't you just do that by hand? You're missing the point.

— TAC-6, pre-empting the obvious objection

The rule has a specific shape: you don't fix the issue, you fix the system that caused the issue.

You fix the template. You fix the prompt. You fix the workflow. The broken output is a symptom, and patching it by hand throws away the only information the failure gave you.

1

Blame in this order

Strict order. Skipping to step three is how a broken template survives for months.
2

Attempts > 1 means a missing lever

The target is one shot. Iteration is not a virtue here — it is a diagnostic signal.

"If your attempts are high in the five to ten range, even the three to six range, you need to spend more time figuring out which of the twelve leverage points you're missing."

When you hit that range, stop prompting. The table beside this is the diagnosis.

Counterintuitively, iterating is not good.
SYMPTOM

Agent confused by data shapes

Missing lever — Types. Use them over dicts.

SYMPTOM

Agent can't navigate

Missing lever — Architecture. Verbose names, one responsibility per file.

SYMPTOM

You are reading the errors

Missing lever — Standard Out. Make the code talk to the agent.

SYMPTOM

"Success" but behaviour wrong

Missing lever — Tests.

SYMPTOM

Short iterative prompts

Missing lever — Plans. Sit down and write one.

SYMPTOM

You've done this three times

Missing lever — Templates. Extract the command.

"Are you still manually looking at error messages? Stop. Stop… Give them to your agent. And only when your agent fails do you take your precious time and dig into the error."

— TAC-2
3

Live recovery, in his actual order

  1. Kill the wrong-direction run

    "So I'm going to stop it. Ignore the skill. Just run this directly." Do not let a confused agent keep going out of politeness.

  2. Re-prompt more explicitly, with IMPORTANT

    "I'm going to use the important information dense keyword so that the agent really respects this."

  3. Escape, rewind history, Ctrl-Z

    Roll back to the last good turn rather than arguing forwards from a bad one.

  4. Full clear and restart

    "Never be afraid to just start fresh." Cheaper than it feels.

NEVER Never /compact. "If your agent is running compact, it is losing information." A full window means the task was too large — chop the task, do not compress the context.

05 — Escalation
complexity should be earned, not assumed

Every rung has a gate.

The ladder is real, but almost everyone climbs it too fast — building the multi-agent system before the single agent is reliable. Each rung below has an explicit condition for stepping onto it.

In this chapter 1The rule of three 2The prompt skeleton 3Agent experts 4Going multi-agent
1

Three times marks a pattern

The trigger is stated identically in four separate places, which is how you know it is load-bearing.

"Three time makes a pattern. Three time should trigger your engineering brain. Automate."

But the second half matters more than the first — start ugly. He is explicit that the first version should be almost embarrassing.

"Copy this and literally tell your agent create dot claude slash command slash start and then as a string, just give it exactly what you want in there. Then you can reformat it later. Start with the bare minimum."

— TAC-2
DO IT BY HAND FIRST "There's that saying, do things that don't scale. This is important so that you understand how to actually solve the problem yourself with your agent." Run the risky thing once manually in a throwaway agent, watch what actually works, then encode it. A template written before you've done the job encodes a guess.
2

The skeleton he wrote down

This is not inferred from reading his files. It sits inside meta_prompt.md as a literal Specified Format block — the prompt that writes his other prompts. Sixty of 255 files match it exactly; another 35 match it minus the optional Purpose.

the invariant skeleton
---
allowed-tools: <comma separated>
description: <how we id this prompt>
argument-hint: [<first dynamic var>], [<second>]
model: <or default to 'opus'>
---

# Purpose

## Variables      <- dynamic ($1,$2) FIRST, then static

## Instructions   <- guardrails, NOT the procedure

## Workflow       <- the numbered procedure

## Report         <- a fenced output template

The order Variables → Workflow → Report holds at 100% — zero exceptions across the whole corpus.

Three rules he states outright:

  • "Prefer the $1, $2, … over the $ARGUMENTS notation."
  • "If no variables are requested or mentioned, do not create a Variables section."
  • "Do not create any additional sections or headers that are not in the Specified Format."

Instructions are guardrails; Workflow is procedure. In his words, the bullets "aid the workflow but are not part of the workflow itself."

3

Agent experts — the self-improving rung

Act, learn, reuse. The diff of what the builder just did is the input to the improver.

Build one only where agents keep getting a specific domain wrong. Not for static problems.

Four files per domain: expertise.yaml (the mental model), question.md (read-only Q&A), plan.md (loads expertise, delegates to /plan), and self-improve.md (diffs the model against reality and repairs it).

Four invariants keep it from degenerating: code is truth and the yaml is a lens; memory is bounded by a hard line cap with a repeat-until-under loop; edits are surgical, never work summaries; and the improver is explicitly allowed to do nothing.

Don't directly update this expertise file. Teach your agents how to directly update it.

— if the knowledge comes out wrong, you fix self-improve.md, never the yaml
4

Going multi-agent

THE GATE "Only use sub agents when you need specialization and parallelization. If you don't need to parallelize and you don't need to specialize, just create a reusable prompt." And the readiness test: "If you're losing track of a single agent, you probably aren't yet ready for sub-agents."

His own systems split into two eras that disagree with each other. The later design won, and it is worth knowing which one you are copying.

◴ Mar–Apr 2026
  • An LLM calls delegate() and decides routing
  • Agents message each other
  • Orchestration lives in a prompt
◵ Aug 2026 — the later design
  • A Python script owns sequencing
  • Agents never talk to each other
  • "Agent proposes, code disposes"
01

Tier is the tool list

Leads get delegate and no bash. Workers get bash and no delegate. Topology enforced by capability, not by asking nicely.

02

Tools are not a boundary

bash runs git checkout and write reaches any path. You need a separate writes-allowlist enforced in code.

03

A claim is not proof

The final message is an assertion. A gate is the evidence. Failures return to the same session as a correction, never a cold restart.

04

Never let an agent edit its grader

The gate "lives outside the project and outside your control." This one is not optional.

06 — Out of the loop
the half of the system that isn't in the public repos

The ADW ladder: one file, then seams.

An AI Developer Workflow is a Python script that calls agents through the CLI. Five course codebases show it evolving — and the evolution is not what the marketing says it is.

tac-4 → tac-869 scriptscourse tree only
A CORRECTION I OWE YOU The common framing — "one script that calls one agent, growing into a pipeline" — is wrong. tac-4's origin file already makes seven agent calls in one flat 536-line script. Rung zero is a monolith. What each rung adds is not more agents. It is seams — and every seam is paid for in state.
In this chapter 1The ladder 2PITER 3Isolation 4Where it's broken
1

One file → many → isolated → observable

The organizing law. Every ADW file is either a primitive that calls agents, or a composer that calls other ADWs by subprocess. Nothing else.

The pivot is a seventy-one line file.

tac-4's 536-line monolith becomes adw_plan.py plus adw_build.py, joined by 71 lines of subprocess glue. That file is the invention of the ADW layer — not because it does more, but because it can now be resumed, re-run, and improved one node at a time.

Composers share almost nothing with what they compose. They import a single symbol and otherwise communicate by exit code.

adw_sdlc_iso.py — the composition pattern, ×5
plan_cmd = ["uv", "run",
            os.path.join(script_dir, "adw_plan_iso.py"),
            issue_number, adw_id]
plan = subprocess.run(plan_cmd)
if plan.returncode != 0:
    print("Isolated plan phase failed")
    sys.exit(1)
2

PITER — the four things you need

P

Prompt input

A GitHub issue. The ADW only concatenates: f"{slash_command} {' '.join(args)}". Library grew 13 → 27 commands across tac-4→7.

T

Trigger

Cron poll or webhook. The qualifying condition is literally if comment_body.strip() == "adw".

E

Environment

A git worktree with its own ports. Provisioning is itself a prompt — install_worktree.md.

R

Review

Agentic visual review. Issues carry a screenshot URL and a severity of skippable / tech_debt / blocker.

the state that connects every step

    """Minimal persistent state for ADW workflow.
    Stored in agents/{adw_id}/adw_state.json"""

    issue_number: Optional[str] = None

tac-5's version is the first five fields only. The last five arrive in tac-7 — the schema diff is the isolation feature.

The handoff between scripts is an 8-character id on argv. Everything else rehydrates from disk. The builder refuses to start without it:

"No plan file in state - run adw_plan_iso.py first"

3

Why a worktree, and why deterministic ports

worktree_ops.py — ports derived from the id
def get_ports_for_adw(adw_id: str) -> Tuple[int, int]:
    """Deterministically assign ports based on ADW ID."""
    id_chars = ''.join(c for c in adw_id[:8] if c.isalnum())
    index = int(id_chars, 36) % 15

    backend_port  = 9100 + index
    frontend_port = 9200 + index

Verified against real state files on disk: 41ddb633 → 9109/9209, 5d39a25f → 9112/9212, a8bd4d88 → 9105/9205. The math is real, not aspirational.

Two agents editing one checkout collide on the working tree, the index, and HEAD.

A worktree gives each ADW its own filesystem and its own branch checkout, so N agents commit concurrently without a lock. Ports are the second half — a web app cannot have two agents on :8000.

mod 15 caps concurrency at fifteen. Determinism means a resumed script recomputes the same ports without reading state at all.

◴ adw_sdlc_iso.py — red tests
  • WARNING: Test phase failed but continuing with review
  • Rationale in the comment: "some tests might be flaky"
  • But a documentation error hard-fails the run
◵ adw_sdlc_zte_iso.py — red tests
  • ❌ ZTE Aborted - Test phase failed, then sys.exit(1)
  • Adds a sixth phase: a real git merge --no-ff, not a PR merge
  • But a documentation error only warns

That inversion is real and worth noticing: the safer workflow hard-fails on a docs error while the auto-merging one shrugs it off.

4

Where the course code is broken

These are not nitpicks. Three of them would bite you the first week, and the fourth is the most interesting design accident in the corpus.

BUG 01

The review loop can't reach its own constant

MAX_REVIEW_RETRY_ATTEMPTS = 3, but the break is >= MAX - 1 after resolving. It runs two reviews, never three — so the final blocker fix is never re-verified. tac-6 had it right; the _iso rewrite regressed it.

BUG 02

remove_worktree crashes on its fallback

Calls shutil.rmtree. Never imports shutil. NameError whenever git worktree remove fails — which is exactly when you need the fallback.

BUG 03

all_adws is misnamed

Typed List[str], method is append_adw_id(), and all seven call sites pass a workflow name. It is a breadcrumb wearing an id's name.

BUG 04

A case bug that is also a safety gate

Registry says adw_sdlc_ZTE_iso; the file is lowercase; the launcher does f"{workflow}.py". On a case-sensitive filesystem, ZTE cannot launch.

"DO NOT RUN the adw_sdlc_ZTE_iso workflows unless ZTE is EXPLICITLY uppercased. This is a dangerous workflow."

— classify_adw.md

The uppercase is deliberate. Capitalisation is being used as a human-intent confirmation for an auto-merge workflow — and it collides with os.path.join.

A safety mechanism and a filesystem bug wearing the same clothes. Worth copying the intent; not the implementation.

THE ONE THAT CHANGES THE STORY The orchestrator drops isolation entirely. State moved to a Postgres table and agent invocation moved in-process to the SDK — but worktree_ops.py has no successor. working_dir is a plain path, so two concurrent ADWs share a filesystem. The database isolated observability, not edits. The ladder does not monotonically improve.
ALSO WORTH KNOWING The cron trigger is hardcoded to one workflow and uses blocking subprocess.run — serial, and it cannot launch ZTE at all. Only the webhook path (Popen + start_new_session=True) runs workflows in parallel and can select any of the fourteen. "Ships while you sleep" is the webhook story specifically.
5

What "physically isolated" actually means

The slogan is that the agentic layer never mixes with application code. In the mature codebase you can check it mechanically.

adws/ imports nothing from apps/. It reaches the application through exactly three seams — a Postgres table, a WebSocket client, and subprocess. The app reaches back through none of them.

The entire coupling surface is sixty lines, and its comment says the whole design:

# Only adw_id needed - workflow fetches prompt, working_dir from DB

A workflow's only argument is a UUID. Everything else is a database read.

.claude/ # LAYER 1 — agentic: config, no app code agents/ # subagent templates commands/ # plan build review fix + experts/ hooks/ # 9 lifecycle hooks adws/ # LAYER 2 — deterministic orchestration adw_modules/ # sdk wrapper · ws client · db · logging adw_workflows/ # plan_build · +review · +fix adw_triggers/ # adw_scripts.py — 60 lines, the ONLY seam apps/ # LAYER 3 — the application orchestrator_3_stream/ interactive_file_tree/ # ← built BY the workflows pomodoro_timer/ # ← output, not source specs/ # /plan writes here app_review/ # /review writes here app_fix_reports/ # /fix writes here
TWO CONSTRAINTS DOING MORE WORK THAN THE PROMPT The orchestrator's allowlist contains no Write, no Edit, no Task — delegation is not a policy it follows, it is the only thing it can do. And command agents get full write access but no mcp__mgmt__*, so they cannot manage agents. The hierarchy is exactly two levels deep and structurally cannot recurse.

Specialisation is a config tuple, not a markdown file.

The course tree contains four separate multi-agent designs that disagree with each other. Reading them in order is more useful than picking one, because the disagreements are where the reasoning is.

1

"Building Specialized Agents" has no agent files

Zero. There is no .claude/agents/ directory in that codebase at all.

Its eight "agents" are Python apps on the SDK, and its whole argument is that a specialist is a tuple of configuration — not a prompt file. Anyone arriving from the public hooks repo finds the opposite thesis.

It is not model: almost everything is the same Sonnet build. It is these seven levers.

A subagent, restated. Seven fields, only one of which is prose.
the same model, three roles, one file
# planner — caged to the spec directory
planner_system_prompt = {"type": "preset", "preset": "claude_code",
                         "append": planner_custom_instructions}
ClaudeAgentOptions(..., hooks=hooks, permission_mode="acceptEdits")

# builder — no append, no hooks, wide open
builder_system_prompt = {"type": "preset", "preset": "claude_code"}
ClaudeAgentOptions(..., permission_mode="bypassPermissions")

# reviewer — caged, same as planner
reviewer_system_prompt = {"type": "preset", "preset": "claude_code",
                          "append": reviewer_custom_instructions}
ClaudeAgentOptions(..., hooks=hooks, permission_mode="acceptEdits")

Note the preset + append mode — keeping Claude Code's entire default system prompt and layering a role on top, rather than overriding it.

And note which role is least configured. The builder gets bypassPermissions, no hooks, and no appended instructions. The highest-privilege role in the system receives the least specialisation.

THE ENFORCEMENT MOVE The planner's cage is Python, not prose — a PreToolUse hook returning permissionDecision: "deny" with the reason "Planner can only write to <plan directory>". The comment in-code notes it inherits: hooks=hooks, # Inline hooks for security (works for subagents!)
2

The O-Agent commands processes, not tasks

Not the Task tool. In-process MCP tools handed to the model, plus a session registry. A worker is a database row, not a function call.

command_agent(agent_name, '/compact')

— one agent invoking another agent's context compaction, as a management action

The orchestrator is told to watch its workers' context usage and suggest compacting at 80%. That single line is the AH-4 thesis: if workers are durable, their context becomes a resource somebody has to manage.

{{SUBAGENT_MAP}} is the other half — a placeholder in the system prompt filled at boot by scanning .claude/agents/. A Claude Code subagent definition becomes a reusable class, instantiated into a long-lived named worker.

DISCIPLINE 01

Read-only by capability

Scouts are granted exactly Read, Glob, Grep. Not asked to be read-only — made read-only.

DISCIPLINE 02

Model as a pure price lever

scout-report-suggest and …-fast differ by exactly two lines: the name and opus → haiku. The 118-line body is byte-identical.

DISCIPLINE 03

Agents can wrap commands

planner.md's only work tool is SlashCommand — it exists purely to call /plan, keeping the command the single source of truth.

The swarm is a recall mechanism, not an oracle.

plan_w_scouters.md fans out 3 opus + 5 haiku scouts in parallel, divide-and-conquer. Then step 2.4 tells the orchestrator to manually re-validate the consolidated result.

Its sibling build_in_parallel.md carries the most transferable idea in the repo: parallelism bounded by the file dependency graph. Batch 1 has no dependencies; Batch 2 depends on Batch 1; each batch is barrier-synchronised. Every agent gets a self-contained spec precisely because it shares no context with its siblings.

TOTAL_BASE_SCOUT_SUBAGENTS: 3

   `TOTAL_BASE + TOTAL_FAST` subagents in PARALLEL.
   1. Run 3 @agent-scout-report-suggest in parallel.
      Give each different direction, divide and conquer.
   2. Run 5 @agent-scout-report-suggest-fast in parallel.
   3. Gather the results and consolidate.
   4. Validate the files — MANUALLY validate, double
      check, and look for any missing files.

The step numbering runs 1, 2, 4, 5, 6, 7. There is no step 3.

3

Team pools, and the rubric that isn't one

Phase-stable affinity. Concurrency safety is argued from directory disjointness, not from locking.

Fan-out here is not "spawn N agents." It is N units of work round-robined across a fixed pool of cloned teams.

Twelve agent files instantiate eight teams, because six of them are referenced three times each under different colours. The roster is declared up front in YAML; nothing is created at runtime.

And validators are structurally unable to fix what they find — their frontmatter grants screenshots/ upsert:true but apps/ upsert:false. Path-level ACLs, in the agent definition.

THE FINDING THAT MATTERS MOST There is a rubric — five binary quality gates — but it is a conformance gate, not a comparison. Every variant is judged independently against absolutes; none reference their siblings. The schema proves it: BranchStatus = ['draft','generating','validating','validated','failed']. No score. No rank. No winner. All passing variants ship, and the human is the selector.

Differentiation happens before generation, not after — the lead is instructed to force variants apart on layout, tone, content density and interaction model, with the warning: "Don't just change colors between variants." That is the same conclusion his fusion harness reaches by a different route: machines settle conformance; humans settle taste.

"Write errors are not bugs. They're coordination signals. Re-read, re-apply, retry."

— parallel-mental-model-updates.md

Three clones of one agent share one memory file. There is no lock, no CRDT, no queue — the conflict-resolution algorithm is the model's judgement, taught in prose as read-modify-write with retry.

It even reframes finding a sibling's entry as an asset: "Their context is your context. Ingest their learnings." Optimistic concurrency control, written for a reader that can reason about intent.

4

Where the slogan stops being a slogan

Point it at a different repo with --cwd and it inherits that repo's cast of agents.

A three-line whitelist decides which half of the agentic layer is portable into a product.

agents/, commands/, skills/ get copied into the app. hooks/, output-styles/, status_lines/ and settings.json stay at the root — they are Claude-Code-only. That is a deliberate statement about what a *running product* can consume, not tidiness.

One file is explicitly blacklisted: commands/prime.md, because the app's copy is deliberately app-scoped.

scripts/copy_claude.py

    "commands/",
    "skills/",

THE BEST SINGLE ARTIFACT IN THE CORPUS specs/specialized-agent-templates.md — 570 lines, written in the exact format /plan emits — is a plan, produced by the agent system, specifying the feature that teaches the app to read the agent system's own config files. It shipped: subagent_loader.py exists, and its first line is self.templates_dir = self.working_dir / ".claude" / "agents". That is the slogan implemented, not asserted.
AND TWO META-AGENTS THAT DISAGREE The meta-agent skill says "By default, OMIT the tools field to inherit all parent tools" and defaults to sonnet. The meta-agent agent says "Minimal tool selection" and hardcodes opus. Two generators, two philosophies, both live in the same repo. Pick one before you copy either.
5

Take this one file

If you copy one artifact out of the entire course tree, make it experts/<domain>/self-improve.md.

192 lines of markdown, zero dependencies, and it solves the problem everyone building an agentic layer hits in month two: your docs rot, and rotted context is worse than none — because the agent trusts it.

Three details separate it from "keep a notes file," and everybody omits the second one.

Without #2, a self-improving file grows monotonically until it blows the window.

"Keep in mind, after your thorough search, there may be nothing to be done — this is perfectly acceptable. If there's nothing to be done, report that and stop."

— the instruction most "improve this" prompts lack

An agent handed an improvement task will always find something to improve. That line gives it permission not to. Swap the expertise path and the domain grep patterns, run it on a post-merge hook, and you have a working memory system in an afternoon.

AND THE HONEST PART The expert pattern is beautifully specified and demonstrably under-run. The ADW domain's own expertise.yaml instructs you to "Register in adw_triggers/adw_scripts.py" — and there is no registry in that file; workflows resolve by Path.exists(). The mechanism designed to keep expertise accurate has stale expertise inside it. The advertised autocomplete expert's memory file is three lines with previous_completions: [] — it has learned nothing. And of three expert domains, only two ever got the full file set. The prompts are excellent; they have not been run to convergence, which is the whole point of the pattern.

08 — A worked example
the loop applied to a decision, not a feature

Naming a startup, the same way you'd ship a feature.

The honest test of a framework is whether you can follow it on something it wasn't designed for. This is the loop run on a one-shot, irreversible naming decision — where the product is PiCanvas, and the problem is that it's named after a dependency.

"Pi" is @earendil-works/pi-coding-agent — a third-party SDK.

The product now also runs Claude Code sessions behind the same AgentSession contract, so the name is both borrowed from a vendor and factually stale. Naming yourself after one of two swappable backends invites exactly the question you don't want in a YC interview.

What should be named instead is the thing nothing else has: many agents in one repo, each isolated in a lane, none able to corrupt another's work or the developer's real checkout.

"Lane engine — Scratch tree, lanes as refs/picanvas/lane/*, authored hunks, collisions, pop-out, resolution rounds. Nothing in oh-my-pi has this; it's your differentiator."

— from the product's own design doc
1

The one design decision

Rubric-score only what is checkable; never score taste. Availability is settled by code before any agent gets an opinion. Only survivors reach a body that argues.
WHY THE SPLIT MATTERS A 1–10 aesthetic score across 48 names produces an average — and an average is precisely what a board exists to prevent. His own corpus never rubric-scores creative output. The one verdict mechanism he does ship is a deterministic exit-code gate, and it grades one candidate against a spec, never N against each other.
2

The gate goes first, and must fail

Borrowed directly from his auto-validate harness: the acceptance gate is written before any candidate exists, and it must fail RED against the current state.

A gate that passes before the work is done is a broken gate — either the request is already satisfied or the checks are too weak.

Every FAIL line is written as the generator's next instruction: expected, found, and exactly what to do about it.

the baseline run — as it must be
NAMING ACCEPTANCE GATE — PiCanvas → ?

FAIL: expected at least 8 candidates, found 0 at
  naming/candidates/candidates.txt — run the
  generators before the gate can go green

RESULT: RED (0 passed, 1 failed)
Baseline is RED, as it must be. The loop is live.

Tested against real names, it proved it wasn't vacuous — including on the incumbent:

FAIL: "PiCanvas"    — 'Pi' used as a prefix morpheme (the PiCanvas shape)
FAIL: "Canvas"      — found the category word 'canvas' — cedes the positioning
FAIL: "Conductor"   — competitor collision
FAIL: "Thrmpx"      — no vowel — must survive being said once in a demo video
FAIL: "Loomwright"  — RDAP 200 · github.com/loomwright HTTP 200
THE ARGUMENT FOR GATE-FIRST Loomwright passed every offline check and died on availability. It is a genuinely good name that a board would have happily debated for twenty minutes before anyone checked whether it could be had.
3

Four verdicts, not two

A binary gate lies in two different directions, and both lies are expensive.

If an unautomatable requirement blocks green, green becomes unreachable and the verdict is meaningless. If it is silently omitted, green falsely reads as "ship it."

So the gate reports four states, and the distinction between SKIP and MANUAL is the whole point.

USPTO class 042 is unsearchable from here. So it prints on every run as an outstanding human gate.
naming/ gate.py # written first · baseline RED · PASS/FAIL/SKIP/MANUAL brief/ brief.md # hand-written: Situation · Stakes · Constraints · Key Question candidates/ names-<angle>.md # one per generator — never a shared path gate-results.txt memos/ name-memo.md # ranked, with recorded dissent .claude/commands/ name_generate.md # ONE parameterised generator, not seven files name_board.md

the system's best output was not a name

Six defects. Agents found all six.

The system ran end to end and produced a verdict of HOLD — don't register, don't cut the video. That is the right answer, and how it got there is the most transferable thing in this guide.

1

The defect list

01

"pi" was a substring ban

It killed Spile, Marlinspike, Pivot. The requirement was "don't name the Pi backend," not "ban the letter pair."

02

GitHub 403 read as "taken"

Unauthenticated API caps at 60/hour then answers 403 to everything. Would have false-failed the entire pool.

03

Trademark never checked

The brief required USPTO class 042. Nothing checked it — and it let through a name sitting inside a live mark.

04

Stricter than the brief

The brief allowed acquiring a .com under $5k. The gate hard-failed every registered domain and silently deleted the best tier.

05

It rejected the word "inscribe"

Pronounceability counted consonant letters, not phonemes. This — not the domain rule — is why the pool came out ornate.

06

Two still open

check_npm tests the unscoped package when the brief wants the scope; competitor distance is a two-way substring test where amp kills Example.

The survivors list is a domain-availability report wearing the costume of a naming shortlist.

— the Market Strategist seat, auditing the pool it was asked to rank

Defect five is the instructive one.

English digraphs — ch, th, tch, ck, ng, sh — are one sound written with two or more letters. Counting letters systematically deleted the Anglo-Saxon compound register while waving through Latinate polysyllables.

The result: zero survivors of seven letters or fewer, in a category where Cursor, Warp, Zed and Amp average 6.2.

2

The board, and the tension

Four seats deliberated in parallel, each with a deliberate bias — neutral seats produce mush. Then the Contrarian was shown all four positions verbatim and spoke last. That ordering was implemented, not asserted: the system this was modelled on claims contrarian-last in its prompt while running every seat through Promise.allSettled.

The compromise problem, drawn. Hullkeep won every round by being nobody's enemy — which is tolerance, not conviction, for a word the founder says ten thousand times.
FOUNDER VOICE

Vetoed Separance

One phoneme from Severance — the show about surgically isolated workers, and the word for being fired. "The joke writes itself in every interview."

CUSTOMER ORACLE

Killed Ringfend on findability

Filed under "spelled right, found wrong" — listeners type ringfence. Also disqualified ~20 names on a syllable audit.

MOONSHOT

Reframed the whole decision

"Isolation is the half of this product that commoditizes." The durable asset is the register of holdings — not the wall.

CONTRARIAN

Audited the gate itself

Found the pool was manufactured by a filter, not drifted. Flagged a possible live mark on the front-runner.

3

The transferable lesson

Every defect was found by an agent. None by the person who wrote the gate.

That happened for one structural reason: the seats were given the gate's source, not just its verdicts.

His boards deliberate on options; they never audit the machinery that produced the options. That single change is the highest-leverage thing this build turned up, and it is not in the original design.

CARRY THIS FORWARD When you fan agents out over a filtered set, hand at least one of them the filter. A reviewer that can only see survivors cannot tell you the survivors were selected wrong.
AND VERIFY THE AUDITOR The Contrarian's central evidence — a live company at ringfence.ai with two pending marks — was partly overstated. The domain is registered but has no DNS record; it does not resolve. The trademark serials could not be confirmed (TSDR needs a key, Justia blocks automation). The conclusion survived; the evidence did not fully. Agents propose. Verification disposes — including for the agent that just audited everyone else.
