07 — Teams of agents
four course codebases, four different answers

Specialisation is a config tuple, not a markdown file.

The course tree contains four separate multi-agent designs that disagree with each other. Reading them in order is more useful than picking one, because the disagreements are where the reasoning is.

"Building Specialized Agents" has no agent files

Zero. There is no .claude/agents/ directory in that codebase at all.

Its eight "agents" are Python apps on the SDK, and its whole argument is that a specialist is a tuple of configuration — not a prompt file. Anyone arriving from the public hooks repo finds the opposite thesis.

It is not model: almost everything is the same Sonnet build. It is these seven levers.

A subagent, restated. Seven fields, only one of which is prose.
the same model, three roles, one file
# planner — caged to the spec directory
planner_system_prompt = {"type": "preset", "preset": "claude_code",
                         "append": planner_custom_instructions}
ClaudeAgentOptions(..., hooks=hooks, permission_mode="acceptEdits")

# builder — no append, no hooks, wide open
builder_system_prompt = {"type": "preset", "preset": "claude_code"}
ClaudeAgentOptions(..., permission_mode="bypassPermissions")

# reviewer — caged, same as planner
reviewer_system_prompt = {"type": "preset", "preset": "claude_code",
                          "append": reviewer_custom_instructions}
ClaudeAgentOptions(..., hooks=hooks, permission_mode="acceptEdits")

Note the preset + append mode — keeping Claude Code's entire default system prompt and layering a role on top, rather than overriding it.

And note which role is least configured. The builder gets bypassPermissions, no hooks, and no appended instructions. The highest-privilege role in the system receives the least specialisation.

THE ENFORCEMENT MOVE The planner's cage is Python, not prose — a PreToolUse hook returning permissionDecision: "deny" with the reason "Planner can only write to <plan directory>". The comment in-code notes it inherits: hooks=hooks, # Inline hooks for security (works for subagents!)
2

The O-Agent commands processes, not tasks

Not the Task tool. In-process MCP tools handed to the model, plus a session registry. A worker is a database row, not a function call.

command_agent(agent_name, '/compact')

— one agent invoking another agent's context compaction, as a management action

The orchestrator is told to watch its workers' context usage and suggest compacting at 80%. That single line is the AH-4 thesis: if workers are durable, their context becomes a resource somebody has to manage.

{{SUBAGENT_MAP}} is the other half — a placeholder in the system prompt filled at boot by scanning .claude/agents/. A Claude Code subagent definition becomes a reusable class, instantiated into a long-lived named worker.

DISCIPLINE 01

Read-only by capability

Scouts are granted exactly Read, Glob, Grep. Not asked to be read-only — made read-only.

DISCIPLINE 02

Model as a pure price lever

scout-report-suggest and …-fast differ by exactly two lines: the name and opus → haiku. The 118-line body is byte-identical.

DISCIPLINE 03

Agents can wrap commands

planner.md's only work tool is SlashCommand — it exists purely to call /plan, keeping the command the single source of truth.

The swarm is a recall mechanism, not an oracle.

plan_w_scouters.md fans out 3 opus + 5 haiku scouts in parallel, divide-and-conquer. Then step 2.4 tells the orchestrator to manually re-validate the consolidated result.

Its sibling build_in_parallel.md carries the most transferable idea in the repo: parallelism bounded by the file dependency graph. Batch 1 has no dependencies; Batch 2 depends on Batch 1; each batch is barrier-synchronised. Every agent gets a self-contained spec precisely because it shares no context with its siblings.

TOTAL_BASE_SCOUT_SUBAGENTS: 3

The step numbering runs 1, 2, 4, 5, 6, 7. There is no step 3.

3

Team pools, and the rubric that isn't one

Phase-stable affinity. Concurrency safety is argued from directory disjointness, not from locking.

Fan-out here is not "spawn N agents." It is N units of work round-robined across a fixed pool of cloned teams.

Twelve agent files instantiate eight teams, because six of them are referenced three times each under different colours. The roster is declared up front in YAML; nothing is created at runtime.

And validators are structurally unable to fix what they find — their frontmatter grants screenshots/ upsert:true but apps/ upsert:false. Path-level ACLs, in the agent definition.

THE FINDING THAT MATTERS MOST There is a rubric — five binary quality gates — but it is a conformance gate, not a comparison. Every variant is judged independently against absolutes; none reference their siblings. The schema proves it: BranchStatus = ['draft','generating','validating','validated','failed']. No score. No rank. No winner. All passing variants ship, and the human is the selector.

Differentiation happens before generation, not after — the lead is instructed to force variants apart on layout, tone, content density and interaction model, with the warning: "Don't just change colors between variants." That is the same conclusion his fusion harness reaches by a different route: machines settle conformance; humans settle taste.

"Write errors are not bugs. They're coordination signals. Re-read, re-apply, retry."

— parallel-mental-model-updates.md

Three clones of one agent share one memory file. There is no lock, no CRDT, no queue — the conflict-resolution algorithm is the model's judgement, taught in prose as read-modify-write with retry.

It even reframes finding a sibling's entry as an asset: "Their context is your context. Ingest their learnings." Optimistic concurrency control, written for a reader that can reason about intent.

Where the slogan stops being a slogan

Point it at a different repo with --cwd and it inherits that repo's cast of agents.

A three-line whitelist decides which half of the agentic layer is portable into a product.

agents/, commands/, skills/ get copied into the app. hooks/, output-styles/, status_lines/ and settings.json stay at the root — they are Claude-Code-only. That is a deliberate statement about what a *running product* can consume, not tidiness.

One file is explicitly blacklisted: commands/prime.md, because the app's copy is deliberately app-scoped.

scripts/copy_claude.py
# Whitelist: Only copy these directories from .claude/
COPY_WHITELIST = [
    "agents/",
    "commands/",
    "skills/",
]

# Blacklist: Never copy these specific files
COPY_BLACKLIST = [
    "commands/prime.md",
]
THE BEST SINGLE ARTIFACT IN THE CORPUS specs/specialized-agent-templates.md — 570 lines, written in the exact format /plan emits — is a plan, produced by the agent system, specifying the feature that teaches the app to read the agent system's own config files. It shipped: subagent_loader.py exists, and its first line is self.templates_dir = self.working_dir / ".claude" / "agents". That is the slogan implemented, not asserted.
AND TWO META-AGENTS THAT DISAGREE The meta-agent skill says "By default, OMIT the tools field to inherit all parent tools" and defaults to sonnet. The meta-agent agent says "Minimal tool selection" and hardcodes opus. Two generators, two philosophies, both live in the same repo. Pick one before you copy either.
5

Take this one file

If you copy one artifact out of the entire course tree, make it experts/<domain>/self-improve.md.

192 lines of markdown, zero dependencies, and it solves the problem everyone building an agentic layer hits in month two: your docs rot, and rotted context is worse than none — because the agent trusts it.

Three details separate it from "keep a notes file," and everybody omits the second one.

Without #2, a self-improving file grows monotonically until it blows the window.

"Keep in mind, after your thorough search, there may be nothing to be done — this is perfectly acceptable. If there's nothing to be done, report that and stop."

— the instruction most "improve this" prompts lack

An agent handed an improvement task will always find something to improve. That line gives it permission not to. Swap the expertise path and the domain grep patterns, run it on a post-merge hook, and you have a working memory system in an afternoon.

AND THE HONEST PART The expert pattern is beautifully specified and demonstrably under-run. The ADW domain's own expertise.yaml instructs you to "Register in adw_triggers/adw_scripts.py" — and there is no registry in that file; workflows resolve by Path.exists(). The mechanism designed to keep expertise accurate has stale expertise inside it. The advertised autocomplete expert's memory file is three lines with previous_completions: [] — it has learned nothing. And of three expert domains, only two ever got the full file set. The prompts are excellent; they have not been run to convergence, which is the whole point of the pattern.
