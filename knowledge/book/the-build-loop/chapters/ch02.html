2

The plan format that survives

The full skeleton is eleven sections, and they are atomic — every spec that uses any of them uses all of them.

But there is a natural experiment sitting in the corpus: the same plan prompt run through Claude, Gemini and Codex. Weaker models shed sections in a consistent order, and six survive every model. Those six are the irreducible core.

01

Task Description

The task in detail, from the prompt.

02

Objective

What is true when this is done.

03

Relevant Files

Each with a one-line reason. New files under their own heading.

04

Step by Step Tasks

Exact files, exact functions, often exact line numbers.

05

Acceptance Criteria

Measurable, not aspirational.

06

Validation Commands

Command, then what passing looks like. Never optional.

A plan without validation is an open loop.

— the dojo template, stated as a rule

The other governing line: "Explore before you plan — never write a plan against code you have not read."

And validation is never a bare command. The format is always the command and the observable that proves it passed.

how validation commands are actually written
- `just test` — all tests pass
- `cd apps/backend && uv run pytest -v` — backend tests all pass
- `live-bench list` — shows qwen35-vs-gemma4 with 8 charts
CONDITIONAL SECTIONS Add Problem Statement + Solution Approach if the task is a feature or complexity is medium/complex. Add Implementation Phases only for medium/complex. Add Testing Strategy on the same condition as the first pair. The template gates these itself — you do not decide per-project.

The builder, in twenty-five lines

This is the entire build layer.

No priming. No context. Everything the builder needs is inside the plan — which is exactly why the plan had to be good.

Note the two refusals encoded in it: it will not start without a path, and it will not stop before validating.

.claude/commands/build.md
---
description: Build the codebase based on the plan
argument-hint: [path-to-plan]

# Build

## Instructions

- IMPORTANT: Implement the plan top to bottom, in order.
  Do not skip any steps. Do not stop in between steps.
  - If you have not run any validation commands, DO NOT
    STOP until you have validated the work.

## Variables

PATH_TO_PLAN: $ARGUMENTS

## Workflow

- If no `PATH_TO_PLAN` is provided, STOP immediately and ask.
- Read the plan. Ultrathink about it and IMPLEMENT it.

## Report

- Summarize the work in a concise bullet list.
- Report files and lines changed with `git diff --stat`
