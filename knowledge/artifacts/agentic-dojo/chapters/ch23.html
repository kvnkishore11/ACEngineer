Hooks Inside Prompts: The Self-Validating Agent

yt-28 · "The Claude Code Feature Senior Engineers KEEP MISSING" · 27:29 · jan 19, 2026

Claude Code now runs hooks inside skills, subagents, and slash commands — specialized agents whose validation is deterministic and guaranteed to run. Validation buys trust; trust buys back your time.

  • "If you want your agents to accomplish loads of valuable work on your behalf, they must be able to validate their work."
  • The release everyone missed: hooks in the front matter of prompts, subagents, and skills — PreToolUse, PostToolUse, Stop.
  • The pattern: a PostToolUse hook on Read/Edit/Write runs a validator (a pandas CSV check); on failure it returns "Resolve this CSV error in <path>" plus the errors — the agent self-heals immediately.
  • "A focused agent with one purpose outperforms an unfocused agent with many purposes." A 20-line CSV-edit prompt isn't overkill — it's the point, over tens to millions of runs.
  • Validation must be hyper-focused on the purpose of that prompt — specialized checks, not generic linting.
  • You can prompt "validate your work with X" — but a hook is a guarantee. It always runs: the closed-loop prompt without prompt engineering.
  • Rule of thumb: PostToolUse validates the one file just touched (you get the path); Stop runs global validators over everything at the end.
The closed loop. The failure message re-enters the agent's context automatically — no human, no re-prompt.
REPOdisler/agentic-finance-review — a multi-agent monthly-finance pipeline (/review_finances) where every step — CSV categorize, merge accounts, normalize, generative-UI HTML — carries its own embedded validator hook; plus a parallel one-agent-per-CSV subagent demo.

  • Keep validators in .claude/hooks/validators/; each writes its own log file. "You want proof that these things ran."
  • "Merge slash commands and skills — they're the same thing. It's a prompt." Every abstraction boils down to the Core Four: context, model, prompt, tools.
  • Prompts give the base; subagents add parallelization + context isolation; skills, same idea — the hook pattern extends to all three.
  • Do the agentic layer by hand: "slow down and do it by hand." Reusable prompt formats mean you and your agents never think about structure again.
  • Read the docs yourself: "Don't delegate learning to your agents… that is how you begin the self-deprecation process."
  • Bonus: claude -p --settings <json> passes an entire settings file — hooks included — into a headless primary agent.

Run the drill

  1. Validator first

    Write .claude/hooks/validators/csv_single_validator.py — print "Resolve this CSV error in <path>: <issues>" on failure.

  2. Wire the command

    Create /csv-edit with front-matter tools (Read/Write/Edit/Search) and a PostToolUse hook on Edit|Write|Read calling the validator via uv run.

  3. Prove the pass

    Run on a valid CSV; confirm the log shows a pass.

  4. Break it

    Delete a closing quote, rerun — watch the agent detect and fix it before reporting.

  5. Fan out

    Clone the front matter into a subagent; one agent per CSV file, in parallel.

DONE WHENThe agent autonomously repairs a corrupted CSV with zero extra prompting, and validator logs prove every parallel edit was checked.

The /install Prompt Every Codebase Deserves

yt-29 · "One Prompt Every AGENTIC Codebase Should Have (For Engineering Teams)" · 22:36 · jan 26, 2026

Every codebase should ship a standardized /install (and maintenance) prompt: the new setup hook for deterministic scripts, an agentic prompt for intelligence and interactivity. Because "you can tell how great an engineering team is by the time it takes for a new engineer to run the project locally."

  • The 15-years, 50+ codebases heuristic: great teams onboard with "one link to one doc… and a few commands"; most burn 1–2 days of pair programming and Slack archaeology.
  • "Agents when combined with code beats either alone" — the whole video is one instantiation of this.
  • The new setup hook (claude --init, plus a maintenance matcher) runs before session start — installs, migrations, periodic upkeep you don't want every session. It doesn't appear in the hooks lifecycle diagram.
  • The script alone "is not that novel… raw deterministic code, it's not that valuable." Value appears when a prompt wraps it: run /prime, run the init hook, read its log, write an install-results doc, report — and resolve second- and third-order failures.
  • /install --hil branches into interactive Q&A — database fresh or keep? full or minimal? env-var guided setup? — pair-programming onboarding replaced by an agent, ~4 questions at a time.
  • The justfile as launchpad: "you, your team, and your agents don't need to remember or look up flags more than once." Recipes like just cli and just clmm encode every Claude CLI flag permutation.

The Task System: Teams, Not Todos

yt-30 · "Claude Code Task System: ANTI-HYPE Agentic Coding (Advanced)" · 28:26 · feb 2, 2026

The under-the-radar task system — task_create, task_update, task_list, task_get — lets you reliably build teams of agents. Its real power unlocks inside a template metaprompt, /plan_w_team: self-validation, team orchestration, and templating in one.

  • "More agents, more autonomy, and more compute doesn't always mean better outcomes. What we want is more organized agents that communicate toward a common goal."
  • Three components: self-validation (Stop hooks: validate_new_file — right type, right dir — and validate_file_contains — required sections), orchestration, templating.
  • Template metaprompt = "a prompt that generates another prompt in a very specific, highly vetted, consistent format." Sounds fancy; isn't. It teaches agents to build like you would.
  • Every generated task gets an owner — a named team member — plus dependency blockers, so tasks run in order and parallelize where possible.
  • "Task update is the big one" — how subagents and the primary communicate. Superior to the old to-do list + ad hoc Task calls: tasks block and depend, events ping back, no bash sleep loops.
  • Minimal viable team: builder + validator. "Have an agent build the thing and then have another agent validate the thing." 2× compute per task to buy trust.
  • Layered validation: the builder carries micro-validation (PostToolUse on Write/Edit → ruff + ty on Python); the validator is the macro check.
The minimal viable team. One agent builds, another validates; the task system carries owners, blockers, and status between them.
REPOdisler/claude-code-hooks-mastery — the hooks-education repo, updated live by an agent team (new hooks: session_end, permission_request, setup, post_tool_use_failure + README updates); contains /plan_w_team and the team agents.

  • Teams live in .claude/agents/team/; the plan step says "identify team members from .claude/agents/team or use general-purpose."
  • The orchestration prompt is a second input — a high-level prompt ("one builder and one validator per hook") guiding how the planner composes the team. A HOP-like pattern.
  • Self-critique: "I missed an opportunity — every validator agent could have fired claude -p to validate the log file." Tighter loops are always available.
  • The two constraints of agentic coding are planning and reviewing — this system attacks planning.
  • Anti-hype vs Moltbot/Clawbot/OpenClaw: fine if you know what's underneath; dangerous otherwise. "This entire feature set is just tools and prompts" — portable to any harness.
  • The path, recapped: base agent → better agent → more agents → custom agents → orchestrator agent.

Run the drill

  1. Team dir

    Create .claude/agents/team/builder.md (PostToolUse lint hooks) and validator.md (reports pass/fail only).

  2. Metaprompt

    Write /plan_w_team: inputs = user prompt + orchestration prompt; owned step-by-step tasks; a plan template with embedded per-task prompts.

  3. Gate the plan

    Add Stop hooks validate_new_file (spec .md in specs/) and validate_file_contains (required sections like "Team Orchestration").

  4. Real chore

    Run it on something real ("document + implement missing X"); execute the plan in a fresh agent.

  5. Watch the flow

    Builders parallelize, validators gate, blocked tasks unblock.

Four Layers: Skills, Subagents, Commands, Justfile

yt-32 · "My 4-Layer Claude Code Playwright CLI Skill (Agentic Browser Automation)" · 27:15 · feb 16, 2026

Don't stop at skills. Stack four layers — skills for capability, subagents for scale, commands for orchestration, a justfile for reusability — and automate two whole classes of work: browser automation and agentic UI testing.

  • "You want to be using CLIs, not MCP servers. MCP servers chew up your tokens, and they're very rigid… CLIs give us the massive benefit: we can build on top of them in our own opinionated way." Playwright CLI over Playwright MCP.
  • Two core technologies: claude --chrome reuses your real browser session — great for personal automation, but cannot run in parallel; the Playwright CLI is headless by default with parallel sessions and persistent named profiles for login state — great for scaled UI testing.
  • Agentic UI testing = user stories as tiny files (name, URL, workflow steps); agents execute them like a real user and screenshot every step — "a trail of success and a trail of failure." No "sea of testing configuration for your Jest/Vitest."
  • Swap the URL to staging or prod to re-target the whole suite; have agents write new user stories on the fly. "At the drop of a dime" test creation is the edge over deterministic UI frameworks.
  • /ui-review creates an agent team and teaches the orchestrator how to prompt each subagent ("for each task call, use this prompt") — meta prompt engineering, downward.
  • The HOP pattern — higher-order prompt: /hop_automate takes another prompt file as its argument ("a function that takes a function"), wrapping any stored workflow like amazon_add_to_cart.md in consistent parse → load → execute machinery. Consistent pieces in the HOP, details in the LOP.
  • The Amazon demo: a 20-minute fully autonomous shopping run that "walked right up to the doorstep of the purchase" and stopped as instructed — Opus 4.6 instruction adherence praised, the risk acknowledged.
The 4-layer stack. Capability at the bottom, one-word ergonomics at the top — each layer multiplies the one beneath it.

Pi: The Harness That Is Yours

yt-33 · "The Pi Coding Agent: The ONLY REAL Claude Code COMPETITOR" · 51:36 · feb 23, 2026

Pi, by Mario Zechner, is the open-source, unopinionated, customizable-to-the-core counterattack to Claude Code — for engineers who want to own every layer of their tool and hedge against Claude Code's profit-driven drift.

  • "Every single engineer is limited by the tools they use, because the tools you use shape what you believe is possible. When's the last time you asked yourself: how is my agentic coding tool limiting me?"
  • The hot take: "Claude Code got cancer" — success forces growth toward the masses and profit motives over its original mid/senior-engineer niche.
  • Philosophy, side by side: CC ships great defaults; Pi says "If I don't need it, it won't be built." CC's system prompt is ~10,000 tokens; Pi's is ~200 — "let the model cook." CC has five safety modes; Pi calls security in agentic coding "mostly theater" and runs YOLO by default. CC prioritizes Anthropic models; Pi is any-model (Sonnet, Haiku, GLM, MiniMax, Gemini Flash, Qwen…), any auth.
  • Pi ships just four tools: read, write, edit, bash. No subagents, no task list, no MCP ("you can just call the skill via a script or CLI"). Everything else is a TypeScript extension, and extensions stack: pi -e focus -e footer -e subagents.
  • Demonstrated extensions: pure-focus blank UI, custom footer, component-loader, purpose widget, tool counter, 13 themes with a cycle keybinding, a DIY /sub subagent system, damage-control hooks (rm -rf blocked), and till-done.
  • Till-done: a hook-enforced task list — tools are blocked until the agent registers a task, items must be marked done, and clearing the list needs human approval. "Not to-do — till done."
  • The till-done insight: harness control compensates for model weakness — Haiku completes multi-step work reliably when the harness forces the loop.

There are many coding agents, but this one is mine.

Stripe's Minions: Vibe Coding Is Already Dead

yt-34 · "I Studied Stripe's AI Agents... Vibe Coding Is Already Dead" · 40:31 · mar 2, 2026

Stripe's "minions" — fully unattended Slack-to-production-PR coding agents on a hundreds-of-millions-LOC Ruby codebase — prove that serious-stakes engineering is agentic engineering, not vibe coding. Their agentic layer is a blueprint, literally, you can steal from.

  • The numbers: 1,300 merged PRs a week, zero human-written code, $1.9T total volume, homegrown Ruby libraries LLMs have never seen. "Do you think Stripe can afford to vibe code?"
  • The layer, piece by piece: triggers (CLI + web UI + Slack @devbox), a warm dev-box pool (pre-warmed EC2 sandboxes, ready in 10s, full Stripe code and services preloaded, no human permission checks), a custom harness forked from Block's Goose, the blueprint engine, conditional rules files, the toolshed, CI (3M tests, selectively run), GitHub PR review.
  • Why build their own: "Vibe coding a prototype from scratch is fundamentally different from contributing to Stripe's codebase." Specialization is how you win — "your tooling and your code must also be specialized."
  • Blueprints = workflows designed in code: agent steps interleaved with deterministic nodes (linters, git, config, push). "Agents plus code beats agents alone, and agents plus code beats code alone." TAC members know this as an ADW — an AI Developer Workflow. Blueprint steps also constrain tools and system prompt per step: easy subagent context engineering.
  • Deterministic steps stay deterministic: "Adding an agent to specific steps actually makes the whole system worse, more brittle, and more expensive."
  • Context at scale: no unconditional global rules — cursor-style .rules MDC files with glob front matter, "almost exclusively scoped to specific subdirectories, automatically attached as the agent traverses the file system."
  • The toolshed: a centralized internal MCP server — a meta-tool to discover and select among ~500 MCP tools without token explosion. "A tool that unlocks tools." Net-new, even to Dan.

Agentic engineering is knowing what will happen in your system so well you don't need to look. Vibe coding is not knowing and not looking.

The Library: A Package Manager for Agentics

yt-36 · "The Library Meta-Skill: How I Distribute PRIVATE Skills, Agents and Prompts" · 26:32 · mar 16, 2026

Across 10+ codebases, multiple devices, and multiple agents, your private skills, agents, and prompts rot into out-of-sync duplicates. Manage them with the library: a pure-agentic meta-skill plus one YAML reference catalog — a package manager for agentics, no code required.

  • The audience gate: "If you're an engineer working on one to two repos, this doesn't matter at all. If you install skills or plugins from the public internet without reviewing them, this video is not for you either."
  • The problem: "endless skills everywhere — out of sync, duplicated, hard to coordinate" across repos, teammates, and each teammate's agents.
  • The shape: a meta-skill — "a skill that unlocks other skills, agents, and prompts." Stripe's toolshed idea, broadened from tools to all agentics.
  • The catalog is references, not copies: library.yaml points at private or public GitHub repos or local paths — "think package.json / pyproject… staying synced is super simple because there's one source of truth."
  • The workflow: build → catalog → distribute → use. Build natively in the value-generating repo ("don't interrupt the flow"), then library add a pointer.
  • Cookbook organization: one file per command inside the skill dir — "individual agentic workflows the skill describes when to use."
  • Privacy stance: "Your top-notch skills, agents, and prompts should absolutely be private… we need a way to distribute this privately." Two repos: the library (public template) vs the engineer library (the actual private artifacts).

This is a pure agent application. There is no code associated with this. The application is the skill.
