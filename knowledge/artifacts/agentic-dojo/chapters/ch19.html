multi-agent · ma-4 · the verifier agent

Builder plus verifier: every claim becomes an atomic claim.

Every benchmark tests one model in isolation — but the real capability is combinations. The simplest, highest-value multi-agent system is a two-agent builder + verifier pair: an un-promptable observer that decomposes every builder turn into atomic claims, proves each against actual state, and prompts the builder back. It attacks the review constraint head on.

1

The Idea

"If you're doing things right, you're spending your time planning and reviewing. With the verifier agent, we can improve our review constraint."

The verifier agent is a second Pi agent — auto-spawned, input-locked — that "validates the individual claims the builder agent has made" and "makes sure that what we asked for is what it built." Your normal primary agent is the builder, the verifiable: "the verifier is independent of the verifiable" — it layers on top of whatever your primary agent is. It's a top-down observer: "the builder doesn't know the verifier exists." Only lifecycle ticks (start/stop/error) cross the Unix socket, and the verifier can touch the builder through exactly one tool: verifier_prompt. The loop caps at max_loops: 3, then escalates to the human.

And it holds a special seat in the 2026 theme: "Most agents increase trust or scale, not both. The verifier does both."

The two-agent system. Builder builds; the verifier observes the session JSONL, fires on the stop hook, proves claims, and — when needed — prompts the builder itself.
The art of verification is decomposition. Claims proven one by one; the grade drives a green/orange/red status bar on the verifier's tmux window.

"Everything you prompt into your agents — they're all small axioms… units of information that can be proven true or proven false."

Atomic claims are the unit of trust: evidence beats assertion, and the builder's final message "is a CLAIM, never proof." The verifier proves each claim non-deterministically and deterministically — LLM judgment on top of read-only script ground truth. Its bash is restricted to exactly one read-only script, because "the bash tool is the most dangerous tool you can give your agents… a ticking time bomb." Anything else is "blocked, fully blocked" — "the highest level of control you can give."

And it's un-promptable by design: "I can't prompt this… If something goes wrong, I don't just fire off another prompt. I'm effectively forced to improve one or more of the core four: context, model, prompt, or tools." Every report ends with "What could you not verify?" and "What do you need from me to verify this next time?" — the gap becomes the next thing you template. "This is a compounding system." Finally, run different models on each side: "It's not GPT 5.5 or Opus 4.7. It's GPT 5.5 and Opus 4.7… Stack intelligence. Orchestrate intelligence."

3

What Dan Did

Two side-by-side specialized Pi agents: a builder on Opus 4.7 and a verifier on GPT 5.5 — and the verifier harness "takes no input."

The persona's custom front matter carries the whole design: read-only tools plus the one special verifier_prompt, a pinned model from a different provider, a domain, a loop cap, and a bash policy locked to a single read-only script. The report contract closes the flywheel.

.pi/verifier/agents/verifier.md — front matter
---
tools: read, grep, find, ls, bash, verifier_prompt  # no write, no edit
model: gpt-5.5        # AND, not OR — a different provider than the builder
max_loops: 3          # then escalate to the human
domain: …             # bash policy: exactly one read-only script
---
the report contract
## Report
STATUS · CONFIDENCE (PERFECT | VERIFIED | PARTIAL | FEEDBACK | FAILED)
What did you verify?
Claims: verified / failed / unverified
What could you not verify?
What do you need from me to verify this next time?

  1. Demo 1 — the image verifier

    In the builder: run prime, then a GPT-Image-2 skill to generate arch.jpg describing the verifier system's architecture. On builder completion (stop hook → Unix socket), the verifier fired unprompted, decomposed the work into claims — script ran, file exists, right size, is a JPG, visually depicts the two-agent system — found a violation of the max-10-text-blocks readability contract, and prompted the builder itself. The builder regenerated; second cycle: 7/7 atomic claims verified, clean green status.

  2. Demo 2 — the human in the diagram

    Asked for a human figure added ("we are the ones prompting the verifiable, also known as the builder"). Costs on screen: ~4% Opus vs ~23% GPT 5.5 — "spending 5x tokens" to save review time.

  3. Demo 3 — the SQLite verifier

    j sql boots a builder plus a verify-SQLite persona on GLM 5.1. Prompt: "find all SQLite DBs in this repo, break down tables, columns, and relationships." The verifier re-proved every claim through its single allowed script (any other bash call hard-blocked), spent ~2x the builder's tokens, and reported: all claims verified, nothing unverifiable, no feedback needed.

  4. Released it two ways

    A free public repo — disler/the-verifier-agent — and a souped-up members version with all the domain verifier specialists plus the GPT-Image-2 skill.

4

The Workout

GOALRun and then extend the real two-agent builder + verifier system so every builder turn is automatically decomposed into atomic claims and verified — including writing your own domain verifier.
PREREQUISITESThe public repo (local copy at youtube/_repos/disler__the-verifier-agent), the Pi coding agent installed, tmux, API keys for two different model providers, and just.

  1. Read the contract first

    README.md and the persona at .pi/verifier/agents/verifier.md — note the front matter (tools: read, grep, find, ls, bash, verifier_prompt; model:; max_loops: 3) and the confidence ladder (PERFECT / VERIFIED / PARTIAL / FEEDBACK / FAILED).

  2. Boot it

    Copy .env.sample → .env; run /install in Claude Code (or the manual install), then just v — builder opens in your terminal, verifier auto-spawns in a sibling tmux window with a locked input bar.

  3. Feed it claims

    Give the builder a claim-heavy prompt (e.g. "create a SQLite db with users and orders tables, FK between them, seed 5 rows each, report what you did"). Watch the verifier fire on the stop event, read the session-JSONL slice, and emit a ## Report with per-claim verdicts.

  4. Force the loop

    Prompt the builder to do something that violates a verifiable expectation (or manually break its output between turns); confirm the verifier calls verifier_prompt and the builder receives corrective feedback as a follow-up message — up to 3 loops, then human escalation.

  5. Work the flywheel

    Try to type into the verifier window — you can't. Instead, take one item from its "What could you not verify?" section and template it: edit the persona or verify_on_stop.md so the next run can verify it.

  6. Build your own domain verifier

    Copy verifier.md → verify-<yourdomain>.md (e.g. verify-pytest.md or verify-postgres.md); write one read-only script that is its only allowed bash command; pin a different model than the builder's in front matter — AND, not OR.

  7. Clean up

    just clean tears down stale sockets and tmux sessions.

DONE WHENThe verifier runs unprompted after every builder turn; a deliberately false builder claim produces a FEEDBACK-grade report and an automatic corrective prompt to the builder; a bash call outside the allowed script is blocked; and after templating one gap, the previously unverifiable claim verifies on the next run.
LEVEL UPStack a second verifier persona for a different domain; port the pattern to Claude Code with a Stop hook plus a headless claude -p verifier reading the session transcript; add a rule contract of your own (like the 10-text-block image rule) and watch it get enforced; instrument token spend to see your own tokens-for-time ratio.
