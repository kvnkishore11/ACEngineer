The Idea

Once you have better, more, and custom agents, the bottleneck moves to you — you can't scale one terminal and one prompt at a time.

Dan's answer is the Orchestrator Agent — "the one agent to rule them all... the single interface pattern applied to your fleet of agents." Crucially, it is itself a custom agent: "its system prompt is completely overwritten, its tools are specialized, it's designed to manage other agents."

It sits at the top of the agent scale framework — "base agents, better agents, more agents, custom agents" → orchestrated agents. "At each step, you scale your compute to scale your impact." And it's the R&D framework at scale: the orchestrator's context is reduced, the work is delegated to primary agents.

The single interface pattern, applied to the fleet. One prompt into the O-Agent becomes create / command / status / delete across primary agents — resting on the three pillars.
01

The Orchestrator Agent

Your unified interface. A custom agent whose only job is to CRUD, command, and monitor other agents — never to do the engineering work itself.

02

CRUD for your agents

Agents at scale: read → create → update → delete. "The best code is no code at all. You learn to delete."

03

Observability

Real-time monitoring of performance, costs, and results. "If you can't measure it, you can't improve it. And if you can't measure it, you can't scale it."

You must treat your agents as deleteable temporary resources that serve a single purpose.

Consumed vs produced assets. "Every agent should produce some concrete result. Otherwise, what was the point in the first place?" The orchestrator tracks what each agent read and what it shipped.

Agent templates. Sub-agent definitions in .claude/agents/ get promoted into full primary agents — "we've just pulled it up a level... you can't do all this with a sub-agent. You're locked in, it's too narrow."

PITER · OUT-LOOP The orchestrator UI is "an out-loop PITER system": Prompt input, Trigger (HTTP), Environment, Review (observability) — "remember tactic four, stay out the loop."

What Dan Did

The multi-agent-orchestration codebase — and he pointed the system at itself.

A Vue/Pinia front end, HTTP + WebSocket services, a Claude Agent SDK orchestrator service, and a Postgres/Neon data layer. Every demo below runs the orchestrator against its own repository.

multi-agent-orchestration/ frontend/ # Vue + Pinia observability UI services/ # HTTP + WebSocket services orchestrator/ # Claude Agent SDK service .claude/agents/ scout-report-suggest-fast.md # template → primary agent # data layer: Postgres / Neon

  1. Ping, then fan out

    Command-K prompt bar → ping → the orchestrator replies. Then one prompt spun up 3 agents (front-end, back-end, QA) to write an app-structure summary with mermaid diagrams — 6 tool calls: 3× create_agent, 3× command_agent.

  2. Walk the observability UI

    Per-agent name, status, context window, model, cost; responses, tool calls, hooks, and thinking filters; consumed vs produced assets with one-click diffs into the editor.

  3. "list agents and check status"

    The orchestrator used check-status tools (agent name + tail of response logs) rather than reading raw logs — protecting its own window.

  4. "command all agents..."

    With thinking enabled — it reprompted existing primary agents, not ephemeral sub-agents.

  5. "delete all agents"

    Three delete tool calls. The CRUD loop, complete.

  6. Ecosystem interop

    Created an agent to run the /question slash command ("can our orchestrator and agents use skills?" — yes); ran /prime for the orchestrator, with the caveat that it loads the orchestrator's context.

  7. Template promotion

    Created a primary agent from the scout-report-suggest-fast sub-agent template, commanded a regex-field summary; it produced a report doc.

  8. Scout and build

    The orchestrator thought, created a scout + builder, slept in a 15-second check-status loop, then wrote a detailed builder prompt from the scout's report — shipping gray stat pills to the app header.

  9. The full orchestration prompt

    plan_w_scouters → build → review: three phases plus a final report, shipping a responsive-UI feature (collapse the agent list under 650px). Planner at 21K tokens, then builder, then reviewer — all observable end to end.

Scout and build, orchestrated. The O-Agent creates a scout, polls status on a 15-second loop, turns the scout's report into a detailed builder prompt — and deletes everyone when the job ships.
WHY IT WORKS One agent, one prompt, one purpose (tactic six) — applied to fleets. The orchestrator's context stays reduced; the work is delegated.

The Workout

GOAL Build a minimum viable O-Agent: a custom agent whose only tools are create / command / status / delete over background Claude instances, with a file-based observability trail.
PREREQUISITES AH-3 workout done (you can build a custom agent with custom tools); the Claude Agent SDK; a target repo.

  1. Overwrite the system prompt

    Create apps/orchestrator/: "You are an orchestrator. You never do engineering work yourself. You create, command, monitor, and delete agents. Every agent must produce a concrete file result."

  2. Implement the four tools

    create_agent registers a row in agents/registry.json; command_agent spawns claude -p with that agent's config, streaming output to agents/logs/ and a produced-files list; check_agent_status returns status + log tail; delete_agent.

  3. Disallow everything else

    All stock tools off except your four (plus TodoWrite).

  4. Ping, then a real command

    "Create two agents, one to summarize the backend and one for the frontend, into docs/*.md; check on them until done; report consumed vs produced files."

  5. Add agent templates

    create_agent can read a .claude/agents/<template>.md file as the new agent's system prompt.

  6. Write one orchestration prompt

    Scout → build → review, phases + a final report format — then run a small real feature through it.

  7. End clean

    Finish every session with "delete all agents" and verify the registry is empty.

the O-Agent's only tools
# CRUD over background Claude instances
create_agent(name, model, system_prompt)
    # registers a row in agents/registry.json
command_agent(name, prompt)
    # spawns claude -p with the agent's config
    # streams to agents/logs/<name>.jsonl + produced-files list
check_agent_status(name)
    # returns status + log tail — tail, not full log
delete_agent(name)
    # the loop, closed

Tail, not full log — the orchestrator's context window is the one you protect hardest.

DONE WHEN One high-level prompt yields ≥2 concurrently-working agents, each producing a concrete file; the orchestrator's own context stays small (verify it never reads full logs); agents are deleted after the job.
LEVEL UP Swap the JSON registry for Postgres + a WebSocket UI showing per-agent status, cost, and produced assets — the three pillars in full: orchestrator, CRUD, observability.
