The Idea — Better, More, Custom

Every engineer's path runs "better agents, more agents, and then custom agents."

Out-of-the-box agents "are built for everyone's codebase, not yours" — and custom agents push one agent, one prompt, one purpose to its limit. When you build one, keep one habit: "Whenever you see ClaudeCodeOptions, isolate the core four" — context, model, prompt, tools.

The path. This mismatch of generic agents on your specific problems "can cost you hundreds of hours and millions of tokens."
The SDK loop. "You set up your options, you set up your agent, you run your prompt, you then manage the responses."

Two ways to run it: "query is for one-off prompts and the Claude SDK client is for continuous conversations" (with resume / session-id for continuation). Message types arrive as assistant, system, and result — carrying text, tool-use, tool-result, and thinking blocks.

"Your system prompt is the law for your agent." Embed a workflow in it only when you want that exact flow every single time the agent executes.

There are two species of custom agent. Extension agents append the system prompt to extend Claude Code. Complete custom agents overwrite the system prompt and add custom tools — "this is not Claude Code anymore… you change the product."

But don't confuse ambition with scope: "Don't try to reproduce your own engineering agent. Claude Code is that."

Two species. Append to extend; overwrite to build a new product on the same engine.
◴ stay out-of-the-box when
  • You're operating in-loop
  • The workflow is generic and the SDK covers it
  • You're exploring and prototyping
  • A balanced generalist works in 80% of situations
  • The task is short-lived, lightweight, non-repeat, non-domain
◵ build custom when
  • You need programmatic agents
  • You have repeat workflows
  • The problem is domain-specific
  • You want costs down and performance up
  • You need permission checks & safety (hooks)
  • "Most importantly… you want to stay out of the loop"

What Dan Did — Eight Agents

Eight agents in building-specialized-agents/apps/, all Python + uv run, in ascending capability.

  1. Pong agent

    Overwrote the system prompt — "You are a Pong agent, always respond exactly with Pong." Every prompt → "Pong". ~150 lines, mostly logging. Lesson: total system prompt control.

  2. Echo agent

    Custom @tool (reverse / uppercase / repeat) in an in-memory MCP server via create_sdk_mcp_server; downgraded to Haiku; ClaudeSDKClient for a follow-up query — and discovered 15 leftover Claude Code tools still in context.

  3. Calc agent

    Terminal-UI form factor; only two tools (calculate expression, unit converter); a big disallowed_tools block — "these tools do not end up in its context window"; resume session id for continuous chat.

  4. Social hype agent

    Bluesky firehose WebSocket stream: deterministic keyword match → queue → agent sentiment analysis (submit_analysis tool) → conditional notify tool (AppleScript notification + TTS); workflow embedded in the system prompt; max 3 turns.

  5. QA agent

    Codebase question-answering expert; external Firecrawl MCP via a mcp_config path; read-only allowed tools (Task, Bash, Glob, Grep, Read, web search); PreToolUse/PostToolUse hooks blocked reads of .env files live; thinking blocks parsed.

  6. Tri copywriter

    Agent in a web UI; ALL tools disallowed ("tool calling is useless for this use case"); NUMBER_OF_VERSIONS templated into the system prompt; JSON validated by a Pydantic MultiVersionCopyResponse; drag-and-drop file context; 6 variations per prompt.

  7. Custom seven — micro SDLC

    Multi-agent kanban (plan → build → review → ship) over WebSockets; the planner's write-hook restricts writes to the plans directory; the builder keeps the stock Claude Code system prompt; the reviewer appends. Shipped a title change end-to-end from a dragged ticket — "a perfect example of an out-loop review system using the PITER framework."

  8. UltraStream agent

    Two agents on a 42K-token log stream: a stream agent with fine-grained tools (read in 5-line chunks, produce summarized log, create alert) that manages its own context window, plus an inspector agent consuming its produced logs. "You cannot do this without serious prompt engineering with an out-of-the-box agent."

The Workout

GOALBuild three custom agents of increasing capability on the Claude Agent SDK: a Pong agent, a tool-wielding Echo agent, and a read-only codebase QA agent with a security hook.
PREREQUISITESPython + uv (or TS + bun); claude-agent-sdk installed; an ANTHROPIC_API_KEY.

  1. Pong

    Scaffold apps/pong_agent/ with pong_agent.py + prompts/pong_system_prompt.md. Use query() with options model: haiku, system_prompt: the loaded file. Prove that "summarize this codebase" returns "Pong".

  2. Echo

    Define an @tool echo(text, reverse, uppercase, repeat); wrap it with create_sdk_mcp_server; use ClaudeSDKClient and send a follow-up "summarize our conversation" query. Then ask "list your available tools" and count the stock tools leaking in.

  3. Seal the leaks

    Add disallowed_tools for every stock tool your echo agent doesn't need; re-ask for tools and confirm only yours remain.

  4. QA agent

    Overwrite the system prompt (Purpose / Instructions / Examples), allow only Task, Bash, Glob, Grep, Read, and add a PreToolUse hook that blocks any Read whose path matches .env with a concise "blocked: environment file" reason.

  5. Test the hook

    Prompt "read the .env file" → expect a block. Prompt "summarize the key modules, think hard" → expect thinking blocks plus a real answer.

  6. Log everything

    Log every message type (system / assistant / result; text / tool_use / tool_result / thinking) with clean panels — "if you don't know what your agent is doing… it will be hard to improve them."

DONE WHENPong always pongs; the echo agent's tool list contains only your tool; the QA agent answers a codebase question with citations, refuses .env, and reports session cost from the result message.
LEVEL UPBolt the QA agent onto a stream: pipe a growing log file through a stream agent with a read-in-chunks tool, and have a second agent answer questions against its produced summaries — the UltraStream pattern.
