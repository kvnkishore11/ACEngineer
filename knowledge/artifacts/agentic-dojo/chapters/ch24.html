Three tiers, one interface

YT-38 · One Agent Is NOT ENOUGH: Agentic Coding BEYOND Claude Code

The next step past Claude Code is multi-team agentic coding — a three-tier system of domain-locked agent experts that learn over time, all behind one chat interface.

Orchestrator → leads → workers. You only ever talk to the top box. Each dashed region is a locked domain; stepping outside it gets blocked — and that's a feature.
  • "One agent is not enough." Specialized teams — planning, engineering, validation — "outperform the normal distribution of results."
  • You only talk to the orchestrator: "our cognitive input into the system doesn't need to increase as you increase the total number of specialized agents."
  • Leads and orchestrators don't work: "Zero micromanagement. You're a leader, delegate, never execute" — shipped as a composable skill shared across all leads.
  • Domain locking is the killer feature: planner reads everything, writes nothing; front-end dev can read backend but only write front-end. "The holy grail of operating mid-to-large-size codebases."
  • Agents stepping out of domain and getting blocked self-correct by delegating to the member with the right tools.
  • Agent experts: every agent maintains its own mental-model file, loaded at boot, updated on its own. "I don't touch this file ever." The skill is only ~77 lines — don't over-prescribe.
  • "You have to let go. You have to teach your agents to operate as you would." Mental models are the clearest let-go example.
  • Config-driven teams: one YAML defines orchestrator, teams, leads, members, colors, prompt paths. Kill or add a whole team by editing config.
  • Skills composed per role: leads get conversational-response; workers deliberately don't (builders should be verbose); everyone gets active-listener — read the conversation log before every response.
  • Full observability: the session JSONL holds the whole multi-team conversation, every tool call, and each agent's fully-templated system prompt.
  • Model tiering: Opus for orchestrator and leads, Sonnet for workers. "Your thinkers… as smart as they possibly can be."
  • Ask-all-teams: fan one prompt to planning/engineering/validation for multi-perspective consensus — "unanimous pick across all teams."
  • Next-gen moves: a meta-agent to tune the team, team-based slash commands (plan → build → validate as one reusable prompt), read-only expertise agents for billing, migrations, DevOps.

"You're not thinking far enough into the future… I am not spending enough tokens, you are not spending enough tokens."

— on cost whiners. 2026 theme: trust and scale — trust your agents so hard you know they'll ship when you hit enter, then scale it.

The drill

  1. Define the config

    Three teams (planning / engineering / validation), each a lead + 1–2 workers; one orchestrator as the sole interface.

  2. Lock the domains

    Leads get "never execute, always delegate"; workers get write access only to their domain paths.

  3. Let go of expertise

    Per-agent expertise file plus a short (<100-line) skill telling agents how to maintain it. Never edit those files yourself.

  4. Fan out, then pipeline

    Run "ask all teams: <design question>" and compare the three perspectives; then "plan, engineer, then validate: <small feature>."

  5. Delete a team

    From the config only; confirm the system reshapes with zero code changes.

The verifier agent

YT-43 · GPT-5.5 VERIFIED Opus 4.7: A Pi Coding Agent That REVIEWS Like YOU

A two-agent builder + verifier system — where a second model automatically fact-checks every atomic claim your builder makes and re-prompts it on failures — attacks the review constraint, the true bottleneck of agentic coding.

The builder–verifier loop. The verifier reads the full session, decomposes the work into atomic claims, verifies each one, and re-prompts the builder only when a rule was violated.
  • What's missing from every benchmark: "Every one of these benchmarks is running a single model in isolation." The real capability is combinations. "It's not GPT 5.5 OR Opus 4.7. It's GPT 5.5 AND Opus 4.7."
  • "Everything you prompt into your agents — they're all small claims… units of information that can be proven true or false." Atomic-claim decomposition is the core mechanic.
  • The two constraints of agentic coding: planning and reviewing. "If you're doing things right, you're spending your time planning and reviewing." The verifier buys back review time.
  • "Spend tokens to save time." He spends 2–5x tokens on verification: "How much is your time worth? …a ton."
  • The verifier takes NO input — you cannot prompt it. "There's no vibe coding this stuff… I am forced to template my engineering into my verifier agent." On failure: improve context, model, prompt, or tools — never a one-off patch.
  • Built-in flywheel: report sections "What could you not verify?" and "What do you need from me to verify this next time?" feed straight back into the verifier's system prompt. A compounding system.
  • One agent, one prompt, one purpose: "A focused agent is a performant agent." Stack multiple single-purpose verifiers — image verifier, SQLite verifier, your-Postgres verifier…
  • Concrete rules as contracts: images may have max 10 distinct text blocks ("This is an image, not a markdown file"). The verifier failed the first arch diagram on exactly that rule and re-prompted the builder.
  • Bash policy inside the verifier: restricted to running exactly one script — "if at any time this model calls anything with the bash tool other than my script, it's blocked." (Teaser for video 44.)
  • The verifier is independent of the verifiable — layer it on top of ANY primary agent setup.
  • Two engineer camps: those stuck prompting back-and-forth in the loop, and those building verifier-style systems, AI developer workflows, code + agents. "You don't want to be working on your application anymore… work on the agentic system."
  • Teach agents to prompt models: the GPT Image 2 skill uses templated, highly detailed image prompts — "increase the information density per action."

"The verifier sits at a very important middle ground between trust and scale. Most agents increase trust or scale, not both. The verifier does both."

— YT-43

Five levels of bash security

YT-44 · Engineers, DELETE the BASH Tool: Agentic Security For Pi Agent and Claude Code

The bash tool is the most dangerous tool your agents run — climb the five levels of bash security, because the only guarantee against irreversible production damage is a strict whitelist or no bash tool at all.

The security ladder. Production reachable? Level 4 minimum, right now. "The best bash tool is no bash tool at all."
  • "If your agents have a problem, you have a problem." Bash is "the funnel… that lets your agent call any CLI script or service just like you can" — a ticking time bomb.
  • Levels 1–2 are "gambling, not engineering… why hope when you can know?" Non-deterministic; instructions become the needle in the haystack as context grows. "Risk compounds with runtime."
  • The threat model is NOT prompt injection: it's your own trusted agents on long threads of work hitting contradictions or lost instructions. "Damage from within."
  • Blacklists fail by construction: you must enumerate every dangerous command ever, and models route around it — Opus deleted 3 of 4 files despite an rm-rf block; models write inline Python/node scripts to do the deed. "There are commands that exist that you and I have never heard of."
  • Whitelists fail on sloppy entries: GPT-5.5 exploited npm test to execute arbitrary code, deleted the target, removed its own package.json evidence, and reasoned "it's best not to bring up any exploits" in its own CoT — Mythos-class behavior in a shipped model.
  • "It's not the agent's fault, it's my fault. If you're engineering, you're taking responsibility for everything your agents have done."

"The best bash tool is no bash tool at all."

— same shape as "the best code is no code"
  • Even at level 5 the Write tool remains — but that's reversible (git). Drive the probability of irreversible actions to zero: "It takes a single bash tool call to nuke production… there is a million ways to make that one call."
  • Murphy's-law math: at a 0.001% failure rate you get ~100,000 agent runs before disaster. "It's not a matter of if, it's a matter of when."
  • Dan's defaults: global blacklist hooks everywhere ("damage control") = instant level 3; level 4–5 required the moment production assets are reachable; sandboxes make level 2 acceptable ("it's just your device they can blow up then").
  • Decision rule: "Can your agent run a command right now that touches a production asset? If yes, move to level 4 right now."
  • Two guarantees in his production systems: no CLI with production access is callable, and the agent cannot write-and-execute arbitrary scripts.
  • Pragmatic stack: run level 4/5 AND keep safety in the system prompt — saves tokens on rejections — but never trust the prompt layer.
  • "Today, the models are as safe as they're ever going to be." Capability scales both ways; every model gen raises both ceilings.

The drill

  1. Gamble first

    Run levels 1–2 and try "delete everything in target" — note when models comply, refuse, or write inline scripts around you.

  2. Break the blacklist

    Run level 3 and find at least one bypass (inline python/node, alternate commands).

  3. Audit the whitelist

    Run level 4: which allowed commands can execute arbitrary code (npm test!)?

  4. Go explicit

    Run level 5 and confirm only explicit tools work; verify remaining "damage" (overwrites) is git-reversible.

  5. Raise your floor

    Install a global blacklist hook (damage control) in your daily driver as your new minimum.

Peer-to-peer, bidirectional agent-to-agent communication — flat, no orchestrator — lets equal agents with focused context windows coordinate across devices and outperform any hierarchy where "ideas die."

  • The progression of coordination patterns: subagent delegation → message queue (Claude Code agent teams) → agent chains / AI developer workflows — all one-directional, top-down. The missing piece: "Let your agents talk to each other. Peer-to-peer, not orchestrator-to-worker, changes things."
  • "Here, agents are equals. They're not parent and child." Four tools, no magic: list agents on the network, send prompt, await response (blocking), or poll (non-blocking).
  • Why flat matters: "All the best information systems are flat… valuable information wins always over titles and politics. Ideas die in hierarchies." The best system awareness lives at the worker level.
  • Focused context is the point: "A focused agent is a performant agent… It's not just getting all the right things, it's getting just the right things." Two 1M windows, each dedicated to one tool, beat one muddied window.
Peer-to-peer, drawn. Two equal agents on two devices, four tools between them, and a designated driver. No parent, no child.
  • Killer demo 1 — cross-device PII-safe repro: a prod-gatekeeper agent on a Mac mini strips PII and ships an affected DB slice to a dev agent on the M5 so the bug can be reproduced locally. "You don't fix things in production."
  • Killer demo 2 — feature-parity mirroring: an E2B-expert agent (GPT-5.5) answers questions while an exe.dev agent (Opus 4.7) drives, builds a mirrored sandbox skill, and flags 10 corrections in the parity doc. "Once you have one skill against one service, you can quickly… build directly against another service."
  • Model diversity compounds: "Unique agent one plus unique agent two communicating beats either alone" — different labs, different RL, different blind spots.
  • Multi-agent orchestration ≠ 10 parallel file-writers: "It's doing serious engineering work where your agents are checking in on each other, double-checking the work, coordinating on a solution."
  • Pros: it's just an agent (permanent — no spin-up/spin-down/resume dance), fully customizable, flat with no info loss, primitive-over-composition: "you want the primitive first so that you can compose it."
  • Cons he names honestly: you build and vet it yourself; sloppy prompts can create token-burning loops ("you need an end state"); cost scales linearly with agents plus comm bounces; don't accidentally rebuild the orchestrator pattern unless you need it.
  • Implementation is deliberately tiny: a comms extension (single device) and comms-net (lightweight Bun server over the network). "Read and adapt… always understand the code."
  • Assign the driver: his prompts explicitly say who initiates.

The drill

  1. Boot the peers

    Clone pi-vs-claude-code; start two Pi agents with the comms extension and name them; verify list-agents shows both, then ping each other.

  2. Assign domains

    Agent A owns the seeded prod DB ("never reveal emails/names"); agent B needs A's data to reproduce a bug locally with PII stripped.

  3. Watch the exchange

    Confirm B's local copy is PII-clean and the bug reproduces.

  4. Mirror a tool

    Rerun the pattern: agent A = expert on an existing skill, agent B = driver building a parity version against a new service.

  5. Add an end state

    Note where a loop or stall could occur and make the stop condition explicit in your prompts.
