03

One rail, five routes

You are not changing the method. You are choosing how much machinery each station deserves.

Nothing changes

Use a read-only agent. Mark Plan and Build N/A.
Small

Known edit

DEFINE → PRIME → BUILD → PROVE → SHIP → COMPOUND
Scout/Plan can be N/A only when the shape is truly obvious.
Complex

New or unclear work

ALL 8 STATIONS
Multi-file, behavior, interfaces, data, or anything you had to guess.
Repeated

Same class again

ALL 8 → TEMPLATE / ADW
After a pattern is real, encode it so success can repeat.
High risk

Real downside

ALL 8 + ISOLATION + HUMAN GATE
Money, production, private data, safety, deletion, or reputation.
04

Give work to the right actor

His newest shift is simple: “more agents” is not the goal. The best result comes from humans, agents, and code doing different jobs.

Human

Intent and responsibility

You decide what is worth building and what risk is acceptable.

  • Value and direction
  • Domain judgment
  • Novel trade-offs
  • High-risk approval
Agent

Reading and judgment

Use compute where the work requires understanding or creation.

  • Scout unfamiliar material
  • Create a plan
  • Build the deliverable
  • Review meaning and quality
Code

Known and repeatable

If you can write the exact invocation down, code should own it.

  • Sequence phases
  • Run tests and lint
  • Validate schemas
  • Record traces and retries
Needs taste or accountability? Keep a human decision.
Needs reading or deciding? Give it to a focused agent.
Known command with pass/fail? Make it deterministic code.

07

Build your agentic layer in order

Do not start with a giant swarm. Start with files that preserve your method, then add code and orchestration only after real repetitions.

Tool-agnostic starter shape

├── tests/               ← proof

The folder names can be .claude, .codex, adws, or something else. The responsibilities must exist.

Reusable promptsWhen a class repeats, save prime, plan, build, verify, and learn formats.
Deterministic gatesPut exact commands, schemas, and checks in code. Do not spend agents on known work.
AI Developer WorkflowLet code own the graph; place focused agents inside bounded phases with explicit handoffs.
Factory and orchestratorAdd routing, observability, model stacks, sandboxes, and parallel teams only when the lower levels are trusted.
Level 0 master prompt — use until your rail becomes real files 
Follow my 8-station rail for the request below.

1. DEFINE — rewrite the request as Ask / Where / Done means / Out of scope. Preserve my intent.
2. PRIME — load only the context needed for this task. State what you inspected.
3. SCOUT — report verified facts, relevant artifacts, risks, and open ambiguity. Change nothing.
4. PLAN — create ordered phases. Each phase must name its output and a concrete gate.
5. BUILD — execute the plan. Keep changed artifacts explicit.
6. PROVE — run deterministic checks first, then independently compare the result to the task card.
7. SHIP — package the accepted result and report where it is.
8. COMPOUND — record which station was weakest and propose one reusable prompt, check, or workflow improvement.

Rules:
- Every station leaves an artifact. If unnecessary, write N/A and why.
- Known pass/fail commands are code work. Reading and judgment are agent work. Intent and high-risk approval are human work.
- Never accept an agent's “done” as proof.
- On failure, return exact evidence to the responsible builder, re-run the gate, and stop after three failed correction rounds—or earlier when safety demands it—for human escalation.
- End with a compact station-by-station report and the four KPIs: size, attempts, streak, presence.
