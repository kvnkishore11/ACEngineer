01 — The thesis
read this page and you have 80% of it

Pi ships no sub-agent system. He built five of them anyway.

That sentence is the whole answer. Pi hands you a programmable loop and refuses to decide anything else. He supplies every missing abstraction himself — as markdown and YAML he invents, read by one TypeScript extension he writes.

2

The headline finding

Here is the thing nobody says out loud. Pi's own documentation contains a list of features it deliberately does not have — and "sub-agents" is on that list.

Pi documents no agent-file format at all. A grep across all 24 files in its vendored doc set turns up no agent-definition spec anywhere. The only agents/ path Pi documents is ~/.agents/skills/, which is the Agent Skills standard, not a Pi thing.

And yet: every single harness he built has a .pi/<system>/agents/*.md directory.

So the convention is not a Pi feature. It is his invention. He made up a folder layout and a frontmatter format, and then wrote the code that reads them.

The invention, drawn. Left: what Pi refuses to give you. Right: what he added on top, in plain files. Bottom: the parsers that read them.
ai_docs/pi/README.md:454-464 grep · all 24 ai_docs/pi/docs/*.md verified by V1
CAVEAT Pi does ship an example subagent extension — docs/extensions.md:2529 lists a subagent/ sample. It is not vendored in this archive and its file format is never specified in the docs. So "Pi has no sub-agents" is precise about the documented, shipped, specified surface, not about the existence of any sample code.

Pi gives you a programmable loop and gets out of the way. He supplies the missing abstractions himself, as markdown and YAML he defines, read by one TypeScript extension he writes.

— the archive's summary of the finding, not his words

This is the answer to "how did he build so many harnesses". He is not extending a framework. There is no framework. He is repeating one cheap move: invent a folder, invent six frontmatter keys, write ~100 lines of parser, ship.

Cheap moves scale. Frameworks do not.

3

The parser is 25 lines and it throws things away

Look at what parseAgentFile() actually does in extensions/agent-team.ts:79-105.

It regex-splits the frontmatter. It splits each line on the first colon. Then it consumes exactly three keys and drops everything else on the floor, silently.

The proof is in his own files: bowser.md carries model, color and skills in its frontmatter — and agent-team.ts honours none of them.

That is not sloppiness. That is the point. The convention is deliberately disposable, so a new one costs an afternoon.

◵ consumed — 3 keys
  • name — required; the file is skipped entirely if it is missing
  • description — defaults to an empty string
  • tools — comma string, defaults to read,grep,find,ls
◴ parsed then dropped
  • model — present in bowser.md, ignored here
  • color — present, ignored
  • skills — present, ignored
  • everything else you write

The body of the markdown file below the frontmatter is the agent's system prompt. That is the entire format.

The minimum viable agentic layer

Six directories. That is the floor.

This is the shape he later ports onto Pi almost unchanged. .claude/commands/ becomes prompts in Pi settings. specs/ stays. adws/ becomes the software factory. The layer survived the harness change — which is exactly the point of having a layer.

3

His literal build order

In ah-6 he names the rungs himself, using a Class and Grade scheme. This is not a retrofit — it is the order he tells you to build in.

The ladder. Class 1 is you in the loop. Class 2 takes you out of it. Class 3 puts an agent in your chair.

I would absolutely never build a plan, build, review workflow that cannot be run individually.

— ah-6 transcript, stated twice

This is the cross-cutting rule and it is worth stealing on its own. Every step of every workflow is also a standalone .claude/commands/*.md you can run by hand.

Which means: the automation is a composition of things you can already do manually. When the chain breaks, you drop down a level and run the piece. Nothing is trapped inside the orchestrator.

It is the same instinct that later makes every harness a folder of plain files instead of a framework.

03 — Mastery
the repeatable adoption move

How he mastered Pi: seven moves, numbered 0 to 6.

He did not read the docs and start building. He wrote a comparison table, then three gotcha registries, then one extension per capability — and only then did anything real. The order is the lesson.

0

Compare before you build

The first artifact in the Pi repo is not code. It is a 243-line comparison table.

COMPARISON.md is pinned to a version — "Pi v0.52.10 vs Claude Code (Feb 2026)" — and never wanders into narrative. It is one fixed four-column shape, repeated across 12 sections, including tool-by-tool and hook-by-hook sub-tables.

He then does it a second time. PI_VS_OPEN_CODE.md is 177 lines of the same shape against a different competitor.

The shape is the lesson. One row per capability. A forced verdict. No prose.

COMPARISON.md · 243 lines PI_VS_OPEN_CODE.md · 177 lines
WHY IT WORKS A forced verdict column stops you writing "it depends". You have to commit per capability, which means you have to actually go and test each one. The table is a study protocol disguised as a document.

27 lines

The four built-in tool signatures, written out as one TypeScript block. Now you never guess a parameter name again.

3

Move orchestration into YAML, not code

.pi/agents/teams.yaml · schema, keys only
<team-name>:
  - <agent-name>
  - <agent-name>
.pi/agents/agent-chain.yaml · schema, keys only
<chain-name>:
  description: <text>
  steps:
    - agent: <agent-name>
      prompt: <text with $INPUT / $ORIGINAL>

Shapes, reconstructed from the verified schema — not a byte copy of his files.

A team is a name pointing at a list of agent names. That is the entire file.

A chain adds a description and an ordered list of steps, each step naming an agent and a prompt. Only two substitutions exist: $INPUT is the previous step's output, $ORIGINAL is the user's first prompt.

The same agent may repeat. scout-flow is scout three times. plan-review-plan is planner → plan-reviewer → planner. Once orchestration is data, "run it again with a critic in between" costs one line, not a refactor.

4

Move safety into YAML too

.pi/damage-control-rules.yaml is 278 lines and four keys.

bashToolPatterns holds roughly 90 regex rules. The grammar is minimal and clever: omit the ask field and the pattern is a hard block; write ask: true and it becomes a confirmation. One optional key, two behaviours.

The other three keys are path lists: zeroAccessPaths, readOnlyPaths, noDeletePaths.

Then the same rules file feeds two different consumers. damage-control.ts aborts the turn. damage-control-continue.ts returns actionable feedback so the agent can correct itself and keep going.

Policy as data. Separating the rules from the reaction means you can change how strict you are without editing a single rule.
5

04 — The recipe
identical across ceo · lead · ui · verifier · teams

Every harness he has ever built is the same five moving parts.

Once you see the five, you can read any of his repos in ten minutes — and write your own in an afternoon. There is no sixth part.

the copyable core ceo-agents lead-agents ui-agents the-verifier-agent-system
In this chapter 1The five parts 2The extension surface 3Sub-agents are just pi 4String.replace, not a template engine 5The three gates
1

The five parts

The recipe. Two files you invent, one file you write, one process call, one command to run it.

  1. A config file you invent

    <system>-config.yaml — four top-level keys, every single time, across every harness.

  2. Role files you invent

    agents/*.md — YAML frontmatter for the wiring, the markdown body as the system prompt.

  3. An extension that reads them

    One TypeScript file, export default function (pi: ExtensionAPI). It registers tools, commands, flags and hooks.

  4. Sub-agents that are just Pi again

    spawn("pi", [...]). No agent library, no SDK, no thread pool. A child process with flags.

  5. A justfile recipe

    One word boots the whole thing. If starting the system takes more than one word, nobody uses it — including him.

2

The extension surface he actually uses

extension.ts · the only three imports, anywhere
import type { ExtensionAPI } from "@mariozechner/pi-coding-agent";
import { Text, truncateToWidth, visibleWidth } from "@mariozechner/pi-tui";
import { Type } from "@sinclair/typebox";   // tool parameter schemas

Three packages. Across every harness in the archive. That is the entire dependency footprint of his agentic layer.

The registration surface is small enough to memorise.

pi.registerTool · pi.registerCommand · pi.registerFlag with pi.getFlag · pi.registerMessageRenderer · pi.registerShortcut · pi.sendUserMessage · pi.sendMessage.

That last one carries the interesting options: {customType, content, display} plus {deliverAs, triggerTurn} — which is how you push a message into an agent that nobody typed.

The hooks — and the three that matter most

He uses eight: session_start, before_agent_start, tool_call, tool_result, input, agent_end, message_end, session_shutdown. Three of them are load-bearing for everything that follows.

Four levers on one timeline. Inject the prompt, block the tool, seize the input, re-prompt at the end. Almost every behaviour in every harness is one of these four.
3

Sub-agents are Pi spawning itself

terminal · the child argv, verbatim across two harnesses
pi --mode json -p
   --no-extensions --no-skills --no-prompt-templates --no-themes
   -e <enforcer.ts> -e <lead-delegate.ts> -e <tilldone-lead.ts>   # lead-agents only
   --session <agent.sessionFile>
   [--system-prompt <resolved> --model <model>]   # FIRST CALL ONLY
   <message>

Read the flags. Every one of them is a decision.

--no-extensions --no-skills --no-prompt-templates --no-themes strips the child down to nothing, then -e adds back exactly the extensions this tier is allowed to have. Clean room, then re-arm.

--session is the entire memory design. Pi auto-resumes a session file, so an existsSync(sessionFile) check decides whether this is the first call. On first call you pass --system-prompt and --model. Never again.

Fan-out is Promise.allSettled. Abort is SIGTERM, then SIGKILL after five seconds.

WHY THIS IS GOOD A sub-agent that is a process rather than an object gets you crash isolation, independent context windows, real parallelism, and an abort story — for free, from the operating system. No agent framework gives you all four.
4

Prompt assembly is String.replace. That's it.

There is no template engine anywhere in the corpus. Three passes of plain string replacement, at three different times.

Pass one — the CEO prompt, filled inside before_agent_start. The placeholders are {{SESSION_ID}}, {{BRIEF_CONTENT}}, {{BOARD_MEMBERS}}, {{MEMO_PATH}}, {{MIN_TIME}}, {{MAX_TIME}}, {{MIN_BUDGET}}, {{MAX_BUDGET}}, {{EXPERTISE_BLOCK}}, {{SKILLS_BLOCK}}. The hook's return value { systemPrompt } is the injection mechanism.

Pass two — member prompts, filled at load time in config.ts.

Pass three — runtime paths, filled at first spawn in subprocess.ts: {{DELIBERATION_DIR}}, {{CONVERSATION_LOG}}.

REAL BUG SHAPE lead-agents passes a string as the first argument to .replace() — so only the first occurrence of each placeholder is substituted. Write a placeholder twice in a prompt file and the second one ships raw to the model. Worth knowing before you copy the pattern.
DELIBERATE OMISSION Skill content is never inlined. Only the skill's path goes into the prompt, so "the agent reads the skill file themselves when the time is right." Context is spent on demand, not up front.
5

The three gates

GATE 01 · DOMAIN LOCKING

tool_call → route → first match wins

The hook routes the tool into read / upsert / delete, walks the agent's domain rules, and takes the first matching rule. No match means DENY. Rules reach each subprocess as environment variables: AGENT_DOMAIN_RULES, AGENT_EXPERTISE, AGENT_ALLOWED_TOOLS, AGENT_PROJECT_ROOT.

GATE 02 · SCRIPT-ONLY BASH

a bare startsWith, then a lesson

The verifier's bash gate is literally cmd.startsWith("<runner> <script>"). Anything else returns {block:true, reason} — and the reason is a teaching message with three worked examples, not an error. The block is also a tutorial.

GATE 03 · TILLDONE

a nudge, not a leash

It blocks nothing. On agent_end, if tasks remain, it pushes a hidden system message with {triggerTurn: true}. A nudgedThisCycle flag caps it at once per user turn — so it is a nudge, not an unbounded loop.

And then the trick that makes tiering real: privilege is removed by subtraction.

The parent hands the lead its powers through environment variables — LEAD_MEMBERS_JSON, LEAD_LOG_PATH, TILLDONE_TASKS, TILLDONE_TEAM_NAME, TILLDONE_TEAM_COLOR.

Then the lead extension deletes those variables from the child environment before spawning its own workers. A worker cannot re-register delegate or tilldone because the data those tools need is physically absent from its process.

Not a policy. Not a prompt instruction. An absence.

Privilege by subtraction. Each tier is the tier above it, minus something the process can no longer see.

the single most copyable idea in the corpus

He does not build new systems. He swaps one line in a config.

Two agents independently diffed his config variants. The results are almost comically small: three CEO configurations that differ by a directory prefix and one budget floor; five lead configurations that differ by duplicated team blocks and nine model lines.

1

The CEO harness: three configs, three differences

Three configs, three deltas. A directory prefix, one budget floor, and a header comment. That is the whole surface of "switching the entire board to different models".

Read the diff and you learn his design taste in one sitting.

The only three differences between the three CEO configurations are: (a) the agents-directory prefix, applied to paths.agents and all eight board[].path values; (b) one budget floor; (c) the header comment.

Board names, colours, order, brief_sections, time constraints and editor are byte-identical.

And note where the models are not: they are not in the YAML at all. Each agent's .md carries its own model: line. So "swap the model line-up" means "point at a different agents directory".

The lead harness: five configs, one agent directory

One roster, five line-ups. Scaling a team is duplicating a YAML block and giving the clone a new name and colour — the role files never move.

Here is the part that reframes "he built a huge multi-agent system".

He did not. He wrote ten role files once, and then wrote five small YAML files that select and duplicate them. Adding a second engineering team is a copy-paste of a teams: block with a new name and a new colour, pointing at the same three markdown files.

An honest correction: only two of the five configs reference all ten agents — multi-team and opensource-team. engineering uses four. planning-and-engineering uses seven. plan-and-scale-engineering uses seven distinct files, with the engineering trio referenced three times over.

3

What to actually copy from this

RULE 01

Behaviour lives in files, selection lives in config

A role's prompt, model and permissions go in its .md. Which roles show up, how many times, and under what names go in YAML. Never mix the two.

RULE 02

Variants are files, not flags

Three CEO boards means three YAML files, not one file with an if. You can diff two files. You cannot diff two branches of a conditional.

RULE 03

Give the override an explicit precedence line

He writes the precedence rule as a comment on line 4 of the file that uses it. Cheapest documentation in the corpus, and it lands exactly where confusion happens.

RULE 04

Scale by duplication, then rename the colour too

Clone the block, change name and colour. The colour is not decoration — with several teams streaming at once it is how you read the terminal at a glance.

07 — Tiering
model · tools · domain · skills

The whole org chart is visible in six frontmatter keys.

Ten role files. Same six keys, same order, every time. Read the frontmatter and you know who can delegate, who can run bash, who can delete, and which model is paying for it.

1

Six keys, two tiers

agents/*.md · frontmatter, same six keys and same order in all 10 files
name:       <string>
model:      <model id>
expertise:  [ <paths> ]
skills:     [ <skill names> ]
tools:      [ <tool names> ]
domain:     [ <path rules> ]

Six, not five. The first pass said five; a verifier recounted. The body below the frontmatter is the system prompt.

The tier is not declared anywhere. It emerges from which tools you list.

Leaders get eight tools — write, edit, read, grep, find, ls, delegate, tilldone. No bash. A leader can plan and hand off but cannot run anything.

Workers get seven — read, write, edit, bash, grep, find, ls. No delegate, no tilldone. A worker can run things but cannot create more agents.

Those two lists are complementary on purpose. The power to execute and the power to command never sit in the same process.

Two complementary tool sets. Neither tier is a subset of the other — each is missing something the other has, on purpose.
THE LEAK · DO NOT SMOOTH THIS OVER The tidy story is "workers are scoped to apps/". It is not quite true. backend-dev.md is the only worker whose repo-root . entry is upsert: true — which effectively gives it repo-wide write access. One file undoes the neat diagram above. Found by a verifier that was told to look for exactly this kind of thing, and published rather than trimmed.
2

The skills distribution IS the tier system

Two skills go to everybody. Four are rationed.

mental-model and active-listener are universal — every agent maintains memory and every agent listens properly.

The ladder. Levels 1–2 are persuasion. Level 3 is a blacklist. Level 4 flips the default to deny. Level 5 removes the capability entirely.
◴ blacklist — level 3
  • Eleven regexes in a tool_call hook
  • Returns {block:true, reason}
  • Default is allow. You are enumerating badness — and badness is infinite
◵ whitelist — level 4
  • Ten anchored patterns
  • Shell operators rejected before matching, so ; and && cannot smuggle a second command past an approved first one
  • Default is deny. You are enumerating goodness — and goodness is finite

The jump from 3 to 4 is the one that matters.

A blacklist is a promise that you thought of everything. A whitelist is a promise that you thought of one thing. Only one of those is a promise you can keep.

And the shell-operator pre-reject is the detail most people miss: without it, an anchored whitelist is trivially bypassed by appending a second command.

Level 5 is not a stronger guard. It is the absence of the thing being guarded.

Bash is blocked in the tool_call hook and omitted from pi --tools …. Both. Belt and braces, because a single point of enforcement is a single point of failure.

— The Send-off
where this leaves you

Stop renting the loop. Start owning the ring around it.

You do not need permission, a framework, or a new model. You need a folder name, six frontmatter keys, and about a hundred lines of parser.

RECAP 01

He invented the convention

Pi documents no agent format and ships no sub-agents. Every .pi/<system>/agents/*.md directory is his, parsed by hand-rolled code he wrote.

RECAP 02

Five parts, every time

A config you invent, role files you invent, one extension that reads them, sub-agents that are just spawn("pi", …), and a one-word justfile recipe.

RECAP 03

Variants are diffs, not rewrites

Three CEO boards differ by a directory prefix and a budget floor. Five lead line-ups share one folder of ten role files. Scale by duplication.

There are many coding agents, but this one is mine.
