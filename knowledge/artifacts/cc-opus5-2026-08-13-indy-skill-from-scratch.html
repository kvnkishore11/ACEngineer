04 — The core rule
the single most load-bearing quote in the run

Run it in the loop. Then encode it.

Before he writes any instruction about a mechanism, he makes a throwaway agent do that mechanism raw and watches what actually happens.

"This is a great way to set up for building your skill. Have your agent just run it in the loop, write the prompt, observe the result, and then encode it in a skill."

yt-22 [15:04]
The loop that produces rules you would not have written. The observation step is the whole value.

He applies it twice in Session A. Both times the observation changed the encoding.

APPLICATION 01

Opening a terminal

Before writing a single instruction about launching a terminal, he prompts a fresh agent with the raw mechanism — osascript to open a terminal running ffmpeg --help. It works. Then he encodes it.

APPLICATION 02

The Claude Code cookbook

"Ignore the skill. Just run this directly" [27:23]. He watches the CLI reach for -p (non-interactive), decides he does not want that, and encodes "leave off -p" — a rule he would not have known to write.

THE ANTI-PATTERN, NAMED "the lazy thing to do here is just to default quickly to throwing the agent at the problem"  — yt-22 [15:50]
An open contradiction, closed. Two archive notes that looked like rival orders.

This rule also settles an argument the archive left hanging.

Two distilled notes sit twelve lines apart and appear to disagree: plan on paper first against prototype in the loop first.

They are not competing steps. The notebook fixes the structure of the artifact. The in-loop run verifies each mechanism, immediately before that mechanism gets written down. Different objects entirely.

A rebuild is not a patch. The first four moves are what make the difference.

He already had a working /plan skill. He does not open it and edit it. He opens an empty directory.

V1 becomes a read-only reference — and it ships as one. It sits in the repo as legacy_v1_meta_plan.md, 123 lines, renamed "legacy", never touched again.

That ordering is the whole trick. New shape first, old content second. Reverse it and you get a patch job.

New shape first. The old file is a source to read from, never a file to edit.

The pattern underneath

Recovery has a direction. The fix always travels back up into the artifact.

Four habits repeat across all thirteen.

He diagnoses by watching the agent, not by reading his own file. Stale paths were found by noticing which files got read.

He blames himself first. Twice, explicitly, on camera. The blame order is you → your prompt → the tooling.

The fix goes into the skill. "Wide format always, high quality" became a workflow rule, not a one-off nudge. Three fixes from the live-fire run were written into workflow files.

Some breaks he just ships. The contaminated specs/ reference went into the README as a known edge. Not everything gets fixed.

He never writes a test. He looks at the output — with a fixed list of things to look for.

This is the weakest part of the method and the most honestly documented. Both sessions verify by hand.

Session A — read the artifact that arrived

Verification is manual, end to end. Run it. Look at the window. Run pwd. Read the prompt that was passed through.

ABSENT No test file is ever written or discussed. Not once, in either session.
Proof by inspection. The evidence is a window you can point at.

Session B — six signals, checked in order

He judges the generated document against six things, and he checks them in this order.

SIGNAL 01

Metadata header populated

The cheapest possible check runs first.

SIGNAL 02

Did it honour the one requirement that mattered?

"1 step 1 time configuration."

SIGNAL 03

Is the Problem section about his system?

Not a generic restatement of the brief.

SIGNAL 04

One image per phase present

Structural completeness.

SIGNAL 05

Closed loops present per phase

A phase you cannot exit until its validation passes.

SIGNAL 06 · STRONGEST

Did the free-run Notes section produce something he did not ask for?

It produced an unrequested feature-parity matrix.

The template constrained the shape without constraining the thinking.

— why signal 06 is the one he trusts

That last one is the interesting inversion. Most people verify a template by checking that nothing unexpected came out.

He does the opposite. An unrequested, genuinely useful section is his proof that the template left room to think. A template that only ever returns exactly what you asked for has flattened the model into a form-filler.

Two conventions worth stealing

01 · Loading is encoded in the link syntax

@path means load eagerly. It appears only in commands/prime.md.

A backticked bare path means load on demand. It is the only form used inside SKILL.md.

Zero @ in SKILL.md. Seven in prime.md. The syntax carries the loading strategy, so you can tell from a glance which files enter the context window at boot.

The @ / backtick split. Two characters that decide what costs you tokens at boot.

02 · The cookbook and workflow files are near-identical to each other

That similarity is exactly what proves they are a template and not four independent documents. In fork-terminal, the four cookbooks share the same three headings and four instruction bullets; only the model names and one "bypass approvals" flag differ.

CORRECTION In planf3, 31 of 37 numbered steps match the form N. Title Case Name - imperative clause — not 37 of 37. Five sentence-case names in image-generation.md and one colon-terminated header in build-plan.md:7 break it. The convention is near-total but not absolute, and it breaks in the one file that is a subworkflow rather than a workflow.

10 — The stack
yt-32 · where a skill sits

Four layers, numbered from the bottom up.

Two videos a month apart put the same mechanism in the same four slots. The correspondence is strong — but it is not exact, and the difference matters if you go looking.

Numbered 1–4 from the bottom. Capability at the base; access at the top.

Here is the correspondence, stated precisely.

In Bowser (Feb 16), the justfile labels them Layer 1: Skill (Capability), Layer 2: Subagent (Scale), Layer 3: Command (Orchestration), Layer 4: Just (Reusability).

In The Library (Mar 16), the stack diagram labels them Skills — Capability, Agents — Scale + Parallelism, Prompts — Orchestration, Justfile — Access, numbered 1–4 from the bottom up.

Slots 1 and 2 use the same role words. Slot 3 changes the noun — "Command" becomes "Prompts" — but Bowser itself collapses the distinction: "A custom slash command also just known as a reusable prompt" [12:53].

Slot 4 keeps the same tool and position while shifting the stated purpose from reusability to access. Neither video reconciles the two words, so read it as a change of emphasis rather than a fixed name.

CAVEAT The Library's README lists five rows, adding "The Library — Distribution across devices, teams, and agents" above the four in its own diagram. Do not paper over that.
DO NOT WRITE "The same four layers, identically named." It will not survive a reader checking the sources. Slots 3 and 4 will not hold.

"we can hop into any layer we want to. This is a huge advantage that makes it easier to test and scale up your agents one step at a time."

yt-32 [12:07]

Why bottom-up

The stack is built from the bottom because each layer is independently runnable. You can invoke the skill directly, or the subagent, or the command, or the just target.

That is not an architecture preference. It is a testability property. A stack you can only enter at the top is a stack you can only debug at the top.

It also explains the shape of Session A: build the capability, prove it fires, then wrap it. Never the other way round.

11 — The gate
yt-16 · decide whether before how

His default is not a skill. It is a prompt.

Everything in this guide is downstream of a decision most people skip: whether the thing should be a skill at all.

In this chapter 1Start with a prompt 2The promotion test 3The composition rule 4"Don't build a skill" vs "spend to win"
1

Start with a prompt

"always lead with a custom slash command. When you're starting out, I always recommend you just build a prompt. Don't build a skill. Don't build an sub agent. Don't build out an MCP server. Keep it simple, all right? Build a prompt."

yt-16 [13:08]

He calls converting all your slash commands into skills "a huge mistake" [9:15].

This matters because everything else in this guide is expensive. Thirty minutes with a notebook. Hand-written routing. A cookbook per branch.

None of that is worth spending until the prompt has stopped being enough.

2

The promotion test

The single test. Count the related actions. One is a prompt; a family is a domain.

A single action is a prompt. A problem domain is a skill.

Creating a git worktree is an action — that stays a prompt. Managing worktrees — create, read, merge, remove, list — is a domain. That is a skill.

His phrasing for the moment of promotion: "this is where one prompt is not enough."

3

The composition rule — corrected

Skills sit at the top and can contain MCP servers, sub-agents and slash commands.

Only two edges are illegal:

An MCP server cannot use a skill — "you wouldn't have an MCP server use a skill" [16:59].
A sub-agent cannot use a sub-agent [4:27].

Slash commands are a "super primitive" that can also run skills, MCP servers and sub-agents. So the graph is, in his own word, "circular."

16 — The checklist
what to actually do

Thirteen actions, in order. Most of them are not typing.

The whole method, reduced to things you can do tomorrow. Steps 1 and 2 are the gate — do not skip them just because the rest looks more interesting.

The arc of a build. The last arrow is the one most people never draw.

  1. Don't build a skill yet

    Write the prompt. Run it by hand three times.

  2. Promote it only when one prompt stops being enough

    When it is a problem domain, not a single action.

  3. Close the laptop

    Purpose, problem, solution. Then draw the finished file tree.

  4. Write the raw dump by hand

    Properties before prose. Order them. Expect about 30 minutes.

  5. Scaffold empty files with one short prompt

    Retype your drawn tree as the prompt. Four words of instruction is enough.

  6. Hand-write SKILL.md

    Metadata, trigger phrases, variables, routing. This is behaviour — it is yours.

  7. Before encoding any mechanism, run it raw in a throwaway agent

    Watch what it actually does. Encode what you learned, not what you assumed.

  8. git init and commit before you delegate anything

    "Just get a net."

  9. Build a registration detector

    One line: "List all available skills from your system prompt." Confirm the skill exists before testing whether it works.

  10. Restart the session after editing SKILL.md

    It will not reload live. Metadata loads on boot.

  11. When it doesn't fire, check your description first

    Your fault, then your prompt, then the tool. In that order.

  12. Write one branch by hand, then let the agent mirror it

    One cookbook, one workflow, one route — hand-made. The rest are copies.

  13. Point it at a real task you actually need done

    Not a toy. Then fold what breaks back into the skill, not just into the output.

Nine of these thirteen happen before the agent does anything interesting.

— the shape of the method
THE ONE-LINE VERSION Fix the shape by hand. Run each mechanism raw before you encode it. Hand-write behaviour, delegate replication. Prove registration before behaviour. Fold every failure back into the file.
