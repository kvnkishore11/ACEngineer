Part 1 — The procedure

The Master Loop

Run every unit of work through the same seven stations. Like one method for every physics problem — the inputs change, the loop never does.

1

Stop coding

You · touchpoint 1

Hands off the keyboard — never type implementation code. Write a one-line brief instead: the what, not the how. Coding is not your domain anymore.

→ you produce: a one-line brief  /chore "rename config loader"
2

Prime /prime

Agent

Boot a fresh agent and give it exactly the context it needs: read the README, map the files, report the structure. Your agent is brilliant but blind — prime, don't default. Fresh window every time; old context is pollution.

→ artifact: an onboarded agent with a clean, focused context window
3

Plan /chore · /bug · /feature

Agent

Fire a template meta prompt — a prompt that writes a prompt. The agent explores the codebase and writes a plan to specs/: relevant files, ordered tasks, validation commands. The plan is the prompt; great planning is great prompting.

→ artifact: specs/chore-<slug>.md — the work, compressed into natural language
4

Build /implement specs/<plan>.md

Fresh agent

New terminal, fresh agent, strongest model: read the plan, think hard, execute every task top to bottom. One agent, one prompt, one purpose — never stretch one agent across plan and build.

→ artifact: working code, committed per lifecycle step
5

Validate — close the loop

Agent

The agent runs the plan's validation commands until green: request → validate → resolve. Any failure: stop, fix, re-run every validator. Tests are the rule of law — this is what lets the code write itself.

→ artifact: proof — green tests, screenshots, a report of files changed
6

Review & ship

You · touchpoint 2

Your second and final touchpoint. Testing asked "does it work?" — review asks "is what we built what we asked for?" Read the report and the diff, then merge the PR. Never read error messages yourself; that's agent work.

→ artifact: a merged pull request
7

Upgrade the system

The real job

Every miss is a system bug, not an agent bug. Don't fix the output — fix the template, the plan format, the ADW that caused it. Track your four KPIs; a broken one-shot streak names the missing leverage point.

→ artifact: a better template — the loop gets smarter every run
every failure loops back to step 3 — fix the system, ship the same class better next time
∞ → 2

Part 2 — The governing dials

Tune the dials, not the output

Every agent run is controlled by a small set of levers. When a run fails, don't nudge the agent — find the dial that was set wrong.

The Core Four

— the four levers that define any agent. Every failure is one of these set wrong.

Context

What the agent can see: files, docs, stdout, logs.

rule: minimum needed, nothing more — your agent can only see what you let it see

Model

The brain you rent for the run.

rule: match model to task complexity — throw the most compute at build steps

Prompt

The instructions. The fundamental unit of engineering.

rule: version prompts like code — never ad-hoc strings; one bad prompt compounds failure

Tools

What the agent can do. Prompts that chain tools = agentic prompts.

rule: everything is one tool call away — tools are just functions, functions do anything

The R&D Framework

— Reduce & Delegate: the only two moves that manage any context window.

Reduce

Cut junk out of the window. A focused agent is a performant agent.

  • Prime, don't default — slim CLAUDE.md to universal essentials
  • Drop unused MCP servers & tools (they eat tokens idle)
  • Never /compact — reset (/clear) and re-prime

Delegate

Push work into other agents with their own clean windows.

  • Sub-agents for search, docs scraping, parallel work
  • Fresh agent per lifecycle phase — plan agent ≠ build agent
  • Background agents for anything you'd wait on

The Velocity Scale — In-Loop → Out-Loop → ZTE

— ZTE = Zero-Touch Engineering: the agent ships without you touching the keyboard.

In-loop

You babysit in the terminal

Prompt back and forth, iterate by hand. A great place to start and do deep work — a terrible place to stay.

presence: constant

Out-loop

AFK agents — the PITER frame

Work fires without you: an issue triggers a workflow on a dedicated machine, you review the PR after. Two touchpoints.

Zero-Touch Engineering — the North Star

Drop the R: prompt → production, no review. Only for a problem class that has shipped ~5× in a row with zero fixes from you.

Part 3 — The escalation path

Climb only on evidence

One agent handles most work. Add machinery only when a rule tells you to — always left to right, never right to left. Complexity should be earned, not assumed.

Rung 1 · defaultOne agent, one prompt

A single in-loop agent runs the master loop. Covers ~most of engineering: chores, bugs, small features.

stay here while: work is new, exploratory, or one-off — "do things that don't scale" first
Rung 2 · rule of threeTemplates

Same kind of task a third time? Mint a slash command: /chore, /bug, /feature in .claude/commands/.

climb when: "three time makes a pattern — automate"
Rung 3 · splitPlan → Build agents

Fresh planner writes specs/; fresh builder runs /implement. One agent, one prompt, one purpose — clean windows, reusable plans.

climb when: plans get big enough to pollute one window — free the context, one agent one mission
Rung 4 · automateADW

AI Developer Workflow: code + agentic prompts + a trigger, living in adws/. Code owns sequencing, retries, acceptance; the agent owns one bounded phase. Agent proposes, code disposes.

climb when: a class ships repeatedly — chores first, then bugs, then features
Rung 5 · orchestrateAgent teams

Orchestrator → leads → workers; a CEO agent for decisions, a Verifier agent for proof. 5–10 agents per problem, you still only prompt once.

climb when: one pipeline saturates — "don't compete with a system that kicks off ten agents per problem"
THE GATE FOR EVERY CLIMB: did the simpler level fail a KPI? no → stay. yes → name the missing leverage point, then climb one rung.

Part 5 — Quick start

Do this tomorrow morning

Ninety minutes, one real chore, your first lap of the loop. No new tools required — just three prompt files.

First-lap checklist

The minimum viable agentic layer: .claude/commands/ + specs/. That's it.

  1. Pick one small, real choreLow-risk, easy to verify — a rename, a config change, a styling fix. First ZTE candidates are always "simple, low effort, easy to test."
  2. Write .claude/commands/prime.mdAgent reads the README, runs git ls-files, reports the codebase structure. Never let an agent start cold.
  3. Write .claude/commands/chore.mdInstructions: explore the codebase, then write a plan to specs/ — relevant files, step-by-step tasks, validation commands. End with $ARGUMENTS.
  4. Write .claude/commands/implement.mdRead the plan → think hard → execute tasks in order → run every validation command until all pass → report a table of tasks + files changed.
  5. Fresh agent → /chore "your chore"Read the plan it writes. This is presence #1 — your prompt touchpoint.
  6. New terminal, fresh agent → /implement specs/<plan>.mdWatch it self-validate. Resist touching the keyboard — errors go to the agent, not to you.
  7. Review the diff + report, then mergePresence #2. Ask only: "is what we built what we asked for?"
  8. Log the four KPIs; fix the template, not the outputSize · attempts · streak · presence. Anything the agent missed goes into chore.md — that's the system getting smarter.
Then: third time the same class of work shows up → wrap the two prompts in an adws/ script with a trigger. Chores first, then bugs, then features — and only after a class ships five times clean, drop your review. Stay focused and keep building.
