Workspace onboarding flow

New users land in an empty workspace, see no obvious next move, and leave. This adds a guided three-step onboarding — welcome, connect a repo, generate a first plan — so a new account reaches its first useful artifact in one sitting. "Done" means a fresh signup can go from empty state to a saved plan without reading docs.

01

Objective

Turn the empty-workspace dead end into a guided path. After this work, a brand-new account is met by a three-step onboarding that walks them from welcome → connect a repo → generate a first plan, and the flow only counts as complete once a plan is actually saved to the workspace. The outcome we are buying is activation: a first useful artifact exists before the user has to figure the product out on their own.

02

Scope & non-goals

In scope

  • A three-step onboarding surface shown on first load of an empty workspace.
  • Persisting onboarding progress so a refresh or re-login resumes where the user left off.
  • Completion gated on a real saved plan — not on a "Got it" dismissal.

Non-goals

  • Multi-user / team invite flows — single user activating their own workspace only.
  • A/B testing the copy or step order — ship one path first, instrument later.
  • Re-onboarding existing accounts — this targets fresh signups with zero plans.

03

Approach

Reuse first. The workspace already mounts a route guard at src/workspace/WorkspaceShell.tsx and persists per-user flags through src/state/userPrefs.ts. Onboarding is a new state machine layered on top of those, not a new subsystem: the shell asks "is this workspace activated?" and, when not, renders the onboarding overlay instead of the empty dashboard. The genuinely new delta is one small machine — OnboardingStep = "welcome" | "connect" | "first-plan" | "done" — and the rule that done is reached only when workspace.plans.length > 0.

Hard-to-reverse bet: the completion signal. We make activation a derived fact (a plan exists), persisted as onboarding.completedAt the first time the derivation flips true. Deriving from real data instead of a manual "dismiss" flag means we can never strand a user in a "complete but empty" workspace, and the flag is forward-compatible if step order later changes.

04

Steps

  1. Add the onboarding state machine.

    reuses src/state/userPrefs.ts — add src/state/onboarding.ts exporting OnboardingStep and a selector isActivated(workspace) that derives completion from workspace.plans.length > 0. No new store; it reads existing workspace state.

  2. Gate the shell on activation.

    reuses WorkspaceShell.tsx's existing empty-state branch — when !isActivated, render the new <OnboardingOverlay /> instead of the empty dashboard. One conditional, no route changes.

  3. Build the three-step overlay.

    New src/onboarding/OnboardingOverlay.tsx: welcome → connect-repo (reuses the existing <RepoPicker />) → first-plan (reuses the /local-visual-plan entry). A progress rail shows Step N of 3 and is the user-visible face of persisted onboarding.step: advancing writes the step immediately, so a refresh or re-login resumes on the same screen rather than restarting at welcome.

  4. Persist completion and dismiss the overlay.

    When isActivated first flips true, stamp onboarding.completedAt and unmount the overlay, revealing the real dashboard with the just-saved plan in view. Idempotent — never re-shows for an activated workspace.

05

Risks

  • Overlay traps power users. — Someone who wants to poke around before connecting a repo can feel boxed in. Mitigation: a "Skip for now" ghost link parks onboarding at step without marking it done, so it resumes later rather than blocking.
  • Derived completion could flicker. — If plan creation is optimistic, plans.length may briefly read 0 again on a failed save. Mitigation: stamp completedAt once and treat it as sticky — derivation only ever flips the flag on, never off.

06

Verification

Beyond unit tests on isActivated and the step reducer, run the real user journey end to end.

Smoke test
Create a fresh account → land on the workspace → confirm the welcome step shows → connect a repo → generate one plan → confirm the overlay dismisses and the saved plan is visible. Reload: the overlay does not reappear (completedAt is set). Create a second fresh account and bail at step 2: reload resumes at step 2, not step 1.

07

Open questions

Two decisions would change the build if answered differently. Each has a recommended default so the plan can proceed without blocking.

QuestionRecommended default
Can a user skip connecting a repo and still reach a first plan?No. A plan needs a repo for context — keep the connect step required, offer "Skip for now" only to defer, not bypass.
Where does the connected-repo selection live?Reuse userPrefs.ts under workspace.activeRepo — no new persistence layer.

08

Wireframe

Step 2 of the overlay — "Connect a repo" — shown over the empty workspace. The mock makes the progress rail and the required-vs-defer affordance legible.

  1. Progress rail — "Step 2 of 3" is the persisted onboarding.step; a reload returns the user here, not to welcome.
  2. Repo picker — reuses the existing <RepoPicker />; the selection persists to workspace.activeRepo.
  3. Skip for now — defers without marking onboarding done, so the overlay resumes later (mitigation for the "traps power users" risk).
