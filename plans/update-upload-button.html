01

Objective

The query toolbar in tac/tac-7/app/client currently exposes a secondary button that opens the data-upload modal. Chore #47 wants that button’s label shortened from “Upload Data” to “Upload” for a tighter toolbar, with no change to what it does. After this work the rendered button reads Upload, the modal it opens still reads Upload Data as its header, the README usage section matches the UI, and pytest + the client build pass clean.

Working-tree note
The on-disk button text at app/client/index.html:25 already reads <button id="upload-data-button" …>Upload</button>, and the README click instruction already says “Upload”. The real remaining work is to confirm consistency, settle one wording decision in the README (see Open Questions), and validate with zero regressions — not to re-type a change that is partly present.

02

Scope & non-goals

In scope

  • The visible text of the toolbar button at app/client/index.html:25 reads Upload.
  • The README usage section reflects the shorter label so docs match the UI.
  • Server tests (uv run pytest) and the client build (bun run build) pass after the change.

Non-goals

  • The modal header <h2>Upload Data</h2> (line 53) — it stays; it’s the modal’s context title, not the button.
  • The button’s id="upload-data-button" and class="secondary-button" — unchanged, so the modal-open handler keeps working.
  • Any behaviour, styling, layout, endpoint, or upload logic.
  • The empty-state sentence “No tables loaded. Upload data or use sample data…” (line 45) — generic prose, not the button label.

03

Approach

This reuses the existing markup and wiring entirely — there is no new component, handler, or style. The only edit that matters is the text node inside one button. The trap is the word “Upload Data” appearing in three distinct places that must not move as one:

  • The button (index.html:25) — the one thing that becomes “Upload”.
  • The modal header (index.html:53) — stays “Upload Data”; it labels the dialog the button opens.
  • The README (usage step, ~line 84) — docs the button; the click instruction already says “Upload”, leaving one wording call on the bold step label.

The hard-to-get-wrong part isn’t the rename — it’s the identity that must survive it. app/client/src/main.ts:434 calls getElementById('upload-data-button') to bind the click that opens the modal. So the edit changes only the text between the tags; the id and class are load-bearing and untouched.

05

Risks

  • Renaming the modal header too. — A blind find-replace of “Upload Data” would also hit <h2>Upload Data</h2> at line 53 and strip the dialog’s context. Mitigation: edit only the line-25 text node; the spec Notes explicitly require the header to stay.
  • Touching the button’s id/class. — Changing id="upload-data-button" breaks main.ts:434’s getElementById lookup, so the button stops opening the modal. Mitigation: change only the text between the tags; leave id and class byte-for-byte.
