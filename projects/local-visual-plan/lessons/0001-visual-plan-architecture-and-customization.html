How /visual-plan works — and the four ways to bend it

SECTION 01

The one idea: a prompt bolted onto an engine

Most skills you've authored are self-contained — the SKILL.md does the work, maybe with a helper script. /visual-plan is not that. It splits cleanly into two layers, and almost every "can I customize X?" question is really "which layer owns X?"

The load-bearing insight
The SKILL.md never renders anything. It instructs the agent which remote tool to call and how to shape the payload. The diagrams, canvas, wireframe roughening, HTML export — all of that executes on plan.agent-native.com. So "customize the look" and "customize the behavior" are two completely different jobs in two different places.
SECTION 02

Anatomy of the local layer

Three files, three jobs. This is everything on your disk:

# ~/.claude/skills/visual-plan/
SKILL.md                  # 460 lines — the policy / brain
references/
  wireframe.md            # 261 lines — HTML wireframe quality bar
  canvas.md               # 104 lines — artboard/annotation mechanics
  document-quality.md     # 169 lines — the plan-body quality bar
  exemplar.md             # 62 lines  — good vs. bad worked example
agent-native-skill.json   # 11 lines  — manifest → mcpUrl, contentHash, updateCommand

SKILL.md is pure policy

Read its section headings and you're reading the decision tree the agent walks: When To Use → Plan Discipline → Create A Structured Plan (Never Inline) → Core Workflow → Self-Review Before Handoff → Visual Surface Choice → Tool Guidance → Local-Files Privacy Mode. None of it is rendering code. It's the rules of engagement and a map of remote tools.

The Core Workflow is the spine — and it's literally a sequence of remote calls:

# SKILL.md "Core Workflow", paraphrased to the calls it mandates
1. research the repo (host agent's normal flow, read-only)
2. get-plan-blocks        # authoritative tag list — never memorize
3. create-visual-plan     # or create-ui / -prototype / -design / -questions
4. surface the returned URL, ask user to review
5. get-plan-feedback      # read anchors before editing
6. update-visual-plan     # targeted contentPatches
7. export-visual-plan     # only if a shareable receipt is wanted
Source
Lines 136–191 of SKILL.md. The tool names in monospace are all remote — confirmed by agent-native-skill.json → mcpUrl.

The manifest is the tether

{
  "skillName": "visual-plan",
  "mcpUrl": "https://plan.agent-native.com/_agent-native/mcp",
  "contentHash": "17ed15010f99c2cc",
  "updateCommand": "npx @agent-native/core@latest skills update visual-plan"
}

That contentHash is the catch. Upstream knows what the pristine files should hash to. Run skills update and your hand-edits to tracked files can be reconciled away. Any local customization has to survive that. (More in Path 1.)

SECTION 03

The progressive-disclosure trick

You've built skills, so you'll appreciate this move. SKILL.md never inlines the 261-line wireframe rules. Instead it plants tripwires:

# from SKILL.md — repeated for canvas, document, exemplar
"Before authoring ANY wireframe / <Screen> / WireframeBlock,
 READ references/wireframe.md in this skill directory —
 it is the single source of truth. Do not author from memory."

The heavy quality bar only enters context at the moment it's needed. Three design wins worth stealing for your own skills:

  • Token thrift — the 596 lines of references don't load unless the task actually touches wireframes/canvas/docs.
  • Single source of truth — the references carry <!-- SHARED-CORE:... --> markers and are shared word-for-word with /visual-recap. One file, two skills.
  • Authority framing — "do not author from memory" forces the agent to ground in the file instead of hallucinating tags.
Customizer beware
Those SHARED-CORE blocks are co-owned by /visual-recap and synced from upstream. Edit inside a SHARED-CORE marker and you're fighting the sync. If you must tune the quality bar, prefer adding your own section outside the markers — or fork (Path 2).
SECTION 04

Four customization paths

Ordered by cost and control. Pick the lowest one that reaches your goal.

1Tweak behaviorlow cost

Change how the agent decides and defaults without touching the engine. This is editing prose in files you already understand.

Edit
SKILL.md and the non-SHARED-CORE parts of references/*.md
Good for
Raising/lowering the gate · forcing a default mode · house style in the quality bars · adding repo-specific rules (e.g. "always check actions/ first")
Can't touch
Block types, canvas physics, renderer, export format — those are remote
The catch
skills update reconciles against contentHash → your edits can vanish

Concrete example — make it gate harder and always start UI plans in canvas mode. Find the Plan Discipline → Gate thoughtfully bullet and the Visual Surface Choice section, and tighten the wording:

# SKILL.md, Visual Surface Choice — your edit
- DEFAULT for any plan touching a screen: open with a canvas artboard.
  Only skip the visual surface for pure backend/data/copy plans.
  # (upstream says "usually"; you've made it a hard default)

Surviving updates — three options, strongest last:

  1. Keep a patch file of your diffs; re-apply after each skills update.
  2. Pin the version — don't run skills update unless you choose to, then re-merge.
  3. Add a Stop/SessionStart hook via the update-config skill that re-applies your sed/patch automatically. This is the durable answer for an advanced user.
Rule from the skill itself
SKILL.md line 339: "When the user critiques a plan's look or structure, fix the renderer or this skill — never hand-edit one stored plan. Turn feedback into better guidance." Customization is meant to live in the skill, not in one-off outputs. Path 1 is the sanctioned move.
2Build your own variantmost control

When you want a different renderer — say, self-contained HTML with no plan.agent-native.com call at all — you don't customize visual-plan, you clone its skeleton and swap the engine. You already own great HTML renderers locally (thariq-design, kvnk-html, editorial-report-v11).

Create
A new skill, e.g. ~/.claude/skills/my-plan/
Keep from visual-plan
The structure: frontmatter, gating discipline, progressive-disclosure references, read-only-until-approved rule, single bottom open-questions block
Replace
Every create-* / get-plan-blocks MCP call with "render via <your HTML skill> to plans/<slug>.html"
Win
Zero remote dependency · your design system · no contentHash tether · fully yours

Skeleton to start from — use the write-a-skill skill to scaffold, then:

# ~/.claude/skills/my-plan/SKILL.md
---
name: my-plan
description: Turn a text plan into a self-contained visual HTML plan, locally.
---

# My Visual Plan

## When to use   # (lift visual-plan's gating discipline near-verbatim)
## Core workflow
1. research the repo read-only; name real files/symbols
2. draft the plan as structured sections (objective, scope,
   steps, risks, verification)  # lift document-quality.md
3. render → invoke the thariq-design skill to emit ONE
   self-contained .html to plans/<slug>.html
4. surface the file path; ask user to review & approve
5. edit the .md source on feedback, re-render

## Quality bar — read references/document-quality.md before drafting
   # copy visual-plan's reference, strip the remote-block parts
What you give up
The remote engine's clickable prototype, comment anchors with node-level pins, and multi-user hosted review. If you need collaborative commenting, Path 3 keeps the engine. If you mainly need a beautiful reviewable artifact you fully own, Path 2 wins.
3Self-host / local-filesmedium cost

Keep the real engine — blocks, canvas, wireframe roughening — but run it under your infra, with no DB writes to the hosted app. visual-plan ships this as a first-class mode.

Trigger
Set AGENT_NATIVE_PLANS_MODE=local-files, or just ask for "fully local / private / repo-owned planning"
Output
plans/<slug>/plan.mdx + optional canvas.mdx / prototype.mdx + .plan-state.json
Preview
Local URL via the CLI (below)
Forbidden in this mode
Every hosted tool: no create-visual-plan, update-visual-plan, get-plan-feedback, export-visual-plan
# write the MDX folder yourself (from local context only), then:
npx @agent-native/core@latest plan local preview \
    --dir plans/<slug> --kind plan

# reports a local URL / /local-plans/<slug> route if the
# local Plan app runs with the same PLAN_LOCAL_DIR.
# feedback = edit the .mdx, re-run preview. git-friendly.
Privacy boundary — be precise
Local-files mode keeps plan content off the agent-native database. It does not make your coding model local — for that boundary the host agent/model must also be local. (SKILL.md lines 371–374.) Don't oversell the privacy guarantee.
4Just understand it (the meta-skill)free

Woven through this whole lesson — but worth naming as its own win. The transferable patterns in visual-plan are a masterclass in agent-skill design you can lift into anything you build:

SECTION 05

Choosing your path

If you want to…PathCost
Change gating, default mode, quality wording1 — TweakLow (mind skills update)
A different renderer / your own design system / no remote dep2 — Build variantHigher, most control
Keep the engine but stay private / repo-owned / offline3 — Local-filesMedium
Master the patterns to apply elsewhere4 — UnderstandFree
Decision heuristic
Ask: "Does my change live in the prompt, or in the engine?" Prompt → Path 1. Engine, but I'll keep theirs → Path 3. Engine, and I want my own → Path 2. Your stated mission (own a planning skill you trust) points at 1 first, then 2 — tune the real thing, and when it can't bend far enough, fork it.
SECTION 06

Your next move

One tangible action to convert this from reading into doing — pick the one that matches your itch:

  • Path 1 starter: open SKILL.md, change one gating sentence, run a /visual-plan on a tiny task, watch the behavior shift. Cheapest possible feedback loop.
